# framework：path2 框架能不能「精准表达」标注里的每个特征

本文件中所有项目内路径均相对 repo root。临时验证代码在本目录 `repro/`（只读标注、只读训练段副本）。

## 结论（先读这里）

### 1. 理想的一一对应早就写在命名表里，框架部件基本都有，缺的是「截到哪天」

`GLOSSARY-MAP.md` 命名规则主表已经规定了两边一格对一格。逐格看框架里有没有：

| 标注（用户的实物） | app（框架里的对应物） | 现状 |
|---|---|---|
| pattern + 定义 | dag（`PatternSpec`） | 有 |
| 样本 = 样本日 + 判断 + 成员框 | hit「截到某个买点日为止」 | **没有**：现在的 hit 是一整段生命周期，不是「截到某天」 |
| 样本日 | 买点（`path2/GLOSSARY.md:118`） | 有，但一个 hit 里散着几十个买点 |
| 成员框 | hit 里绑定的 event（`node_index`） | 有，但 event 的跨度不截到买点日 |
| 框（特征的一段） | 这个特征对的 node 的 event | 有；前提是 node 的粒度按特征切，第一版是按阶段切的 |
| 框上的属性（三态） | 这个 node 上按用户的词命名的 where（`path2/GLOSSARY.md:79`），诊断里每条有实测值、阈值、成不成立 | 有（`path2/dag/result.py:27` ClauseWitness）；`tracked`（`path2/GLOSSARY.md:179`）代码里还没有 |
| 框套框 | 复合事件的 child slot（`path2/GLOSSARY.md:62`），或两个 node 之间的包含边 | 有（`W.child`、`Child(node, key)` 端点、child slot 自带 band） |
| 骨架里的先后（A ↓ B） | 时序边 | 有 |
| 负样本 | 那天不该有 hit；`must_not` 落成否定边 | 有 |

**根本的错位是时间参照**，不是部件缺失：

- 样本 =「站在样本日，看得到的证据」，成员框一律在样本日当天或之前结束（`path2/GLOSSARY.md:171`）。
- hit =「从阶跃到企稳状态机结束」的整段：hit 的跨度取所有绑定 event 的最早起点到最晚终点，确认根取最晚终点（`path2/dag/_reify.py:72-76`）；买点是买点 node 那几段企稳段里的每一天。实测第一版 CRNC 一个 hit 带 27 个买入日、INDO 36 个（`repro/hit_causality.py`）。
- 所以一个 hit 对的是一串样本，而不是一个；hit 里的 event 也没有「截到样本日那天是什么样子」的版本。`bracket` 轨上「虚线终点是样本日、实心条终点是最后一个买入日」，特征轨上「框从旧平台画到样本日、event 只是阶跃那一两天」，都是这个错位的表现。这不是参数调得不准，是两边拿出来比的不是同一种东西——用户那句「根本不是一个东西」在框架层面成立。

### 2. 「每条特征轨配一个 detector」在 path2 里的准确含义：每条特征轨配一个 node

node 和 detector 不是一回事：一个 detector 可以同时供几个 node（bo 检测同时产 bo 与 pk 两条流，`path2/GLOSSARY.md:53`），复合事件的 child slot 是没有 detector 的 node（第一版的 `tb_seg`）。用户要的「compare 里看得出哪个特征没认出」，落在框架里是：

- **框 → 一个 node，它的 event 跨度能和框比**。「认出」不用 spec 6.2 的「交叠，且一端落在框外 `TOL` 根以内」：skeptic 实测它在长框上碰巧率中位数 25%，9 个框判出 8 个认出，不说明问题。改按关键位置判，起点不看（见第 3 节末）。
- **框上的属性 → 同一个 node 上的一条 where，clause 名就用用户的词**（「平台交界放量」，不是 `vol_spike`）。不另起 node。
- **一个框装了几段（站上新平台 = 旧平台 → 阶跃 → 新平台）→ 一个复合 detector 产一个复合事件**，三段做它的 child slot。理由：pattern 定义的核心是「阶跃那几根比左右两侧的波动都强」，这是三段之间的关系；where 只能读一个 event，边只能读两个 event（`path2/dag/nodes.py:1-10` 的分工），三段放进同一个 event，这条才能写成一条按用户词命名的 where，并在诊断里看到实测值。若拆成 dag 里三个 node 加边，这条三方关系没地方放。
- **框套框 → 父框那个复合事件的 child slot**（父 detector 本来就看得到子段时）；子特征能独立认出、只关心「在父段里面」时，用两个 node 加包含边。
- 用户没画、app 内部才有的部分（支撑位、阶跃那串突破本身）→ 照样有 band，标「app only」（界面改进第 5 条的方向）。child slot 本来就各自有 band，三段都看得见。

**「一个特征一个 node」不让诊断变粗的前提（回应 skeptic）**：new_step 必有的特征只有「站上新平台」一条，所以它的 node 就是买点本身——这是这个 pattern 只有一个特征的必然结果，不是缺陷。诊断能细到哪，取决于判断写在哪，不取决于 detector 有几个：

- **detector 只切段、不下判断**：只要有阶跃（burst）就产实例，旧平台、新平台、当天这几段一定算得出来、一定挂成 child slot，所以不会出现「某一段没找到、整个复合事件不产、什么都看不见」。
- **所有「够不够格」都写成 where，用用户的词命名**：旧平台平不平、阶跃比左右两侧强多少、放没放量、新平台守没守住、当天的条件，每条在诊断里都有实测值、阈值、成不成立。没买的样本指得出是哪一条、差多少。
- 反过来，若把门槛写进 detector 内部（像第一版企稳状态机那样），哪怕拆成三个 detector，用户在 compare 里照样只看到「有 / 没有」——第一版 CRNC 12-13 没买的原因（支撑被抬到 7.18）就藏在状态机里。

### 3. 因果：在样本日还「正在进行」的特征，要做成「每天一个截到当天的实例」

判定规则只有一条：**一个 hit 里绑定的每个 event，确认根都不能晚于买点日**（`path2/GLOSSARY.md:56`）。确认型、回顾型（`path2/GLOSSARY.md:59`）只是确认根落在区间哪一端，本身不决定能不能用于买点；决定的是「确认根 ≤ 买点日」。

按这条把 new_step 的特征分两类：

| 特征 / 部分 | 和样本日的关系 | 框架里怎么认 |
|---|---|---|
| 底部平稳、触底放量 | 在阶跃之前已经结束 | 回顾型也可以，配一条到买点那部分 `min_gap ≥ 1` 的时序边 |
| 旧平台 | 阶跃那根一出来就知道它结束了 | 复合 detector 在阶跃处往回看 K 线算，确认于阶跃 |
| 阶跃、平台交界放量 | 末根突破当根确认 | 现有 burst 已经是这样（`path2/atoms/breakout.py:88`，每个前缀在它的末根突破确认） |
| 新平台 | **样本日当天还在进行** | 不能用现有平台段：它要价格走出平台才定下终点（`path2/atoms/platform.py:104`）。要做成「每天一个截到当天的实例」：第 t 天产一个跨度 [旧平台起点, t] 的实例，字段全是截到 t 的值 |
| 样本日当天的低风险条件（用户口头说的：没追涨、波动小、守在新平台低点之上、收阳） | 就是 t 当天 | 作为上面那个第 t 天实例上的 where，按用户的词命名。**写什么条件要先问用户**：skeptic 实测 10 个正样本 10 个收阳、9 个当天涨 3% 以上（`notes_skeptic.md` 第三节），字面的「没追涨」和用户自己挑的日子对不上；框架这里只回答「放在哪」，不回答「写什么」 |

「每天一个截到当天的实例」框架里有先例：burst 就是对一串突破的每个可能终点各产一个实例（`path2/atoms/breakout.py:126-150`）。做成这样之后：

- 实例终点 = t = 买点日，框终点（= 样本日时）直接对上；CRNC 那种一个框画到 11-29、却给 12-05、12-13 两个样本共用的，也有一个实例恰好终止在 11-29。**这一条是按构造对上的，不是 app 认得准的证据**（skeptic 指出，同意）：它只保证两边拿来比的是同一种东西；认得准不准，要看旧平台、阶跃落没落在框里该在的位置，以及 app 挑的日子比「阶跃后随便一天」强多少（要有阶跃后的负样本或盲看才数得出来）。
- 一个买点日对一个 hit，hit 跨度 = [旧平台起点, 买点日]，和样本的 `bracket` 虚线是同一种东西；样本 ↔ hit、成员框 ↔ 绑定的 event、属性 ↔ where 的实测值，全部一一对上。
- 没买的样本，「为什么没买」= 截到样本日、各 node 的候选卡在哪条 where（node 诊断，`path2/GLOSSARY.md:98`，`path2/dag/result.py:113`），where 名就是用户的词。

**框的起点对不准，只认终点**：用户框里的「旧平台」振幅 36%～132%，按固定振幅从阶跃往回推，推出来的旧平台长度（1～40 根）和框里的（11～47 根）对不上（`repro/box_geometry.py`）。起点是用户凭整体印象画的，复合事件的起点只能报出来给人看差多少，不宜进「认出」的判定。evidence 的原型（`notes_evidence.md` 第四节）印证：按定义找的旧平台起点和用户差 2～138 根，不可复现；而阶跃位置（5/6）和「样本日那天站没站在新平台上」（7/10）可复现。所以复合事件的「认出」建议按关键位置判，起点不看，分两条：

- **框终点被一个截到当天的实例盖住**（compare-ui 采纳的写法）。这条按构造几乎必然成立，只说明两边比的是同一种东西，是必要条件；
- **用户指的阶跃那几根落在那个实例的阶跃 child 里**。这条才带信息：app 认的台阶是不是用户说的那个（evidence 原型 5/6 可复现）。「用户指的阶跃」只能来自用户画的「阶跃」子框（框套框 ↔ 阶跃 child，用同一条整体判法），不能由对照层从 K 线自己找台阶——那是把走势语义写进 path2_web，越过纯投影层的红线（compare-ui 指出，同意）。没画子框就不核对，父框悬停写「台阶位置未核对」。「app 的阶跃 child 在不在父框里」这种不看 K 线的弱版不采用：父框本来就从旧平台盖到样本日，阶跃几乎必然在里面，不带信息。界面上两条分挂在父框和子框上，不合成一个 tag，免得藏住是哪一条没过。由此给用户的一个建议（不强制）：画「站上新平台」时顺手把阶跃那一两根也框出来，成本很低，换来这条核对。

不按整段跨度重合判，否则起点差会被当成没认出（skeptic 方案 F 同一主张）。这比 spec 6.2「交叠 + 一端在 TOL 内」更具体，属于第二段对照规则的修订。

**同一族实例怎么认（和 compare-ui 定的形状）**：先用「同 node、同起点」，不加任何声明。burst 的前缀族同起点；复合事件的实例同一个阶跃共用一个旧平台起点，也同起点。只有实测发现两个不同阶跃推出同一个起点时，才加声明。到时声明放在事件类上（一个类级属性，写「按哪个 child slot 认族」），不放在 NodeSpec 上：族是 detector 怎么产实例的性质，不是 dag 的声明。后端序列化时把族键带给前端，前端照旧不认类型。

**现有的一个前瞻小毛病（不影响现役 app）**：平台段 `confirm_idx = end_idx`（`path2/atoms/platform.py:104`），但「平台在 end 结束」要等 end+1 那根跳出才知道，单看它自己早了一根；而事件的不变式要求 confirm 落在 [start, end] 内（`path2/core.py:105`），它写不出「end+1 才确认」。现役 app 都没用平台段；接一条 `min_gap ≥ 1` 的时序边时无害，`min_gap = 0` 时会偷看一根。

### 4. 现有 atoms 能覆盖什么、缺什么

| 用户的特征 | 现有 atom | 够不够 |
|---|---|---|
| 平台交界放量（阶跃时放量） | burst 的 `max_bar_vol_ratio` | 够，做成复合事件上的一条 where |
| 阶跃 | burst（一串密集突破） | 能当阶跃那部分；但它只有一两天宽，不是用户那个框 |
| 旧平台 | 平台段（窄幅，默认振幅 ≤ 5%，`path2/atoms/platform.py:49`） | 不够：用户的旧平台振幅 36%～132%，「平」是相对阶跃而言的，要按波动的比来判 |
| 新平台（截到当天） | 无 | 缺。企稳段（`path2/GLOSSARY.md:24`）在近似它，但缺三样（evidence 实测）：支撑取「阶跃前一根收盘」并在每段收口后抬高，不是「新平台最低点」（CRNC 12-13 没买）；量「追涨」的尺子是阶跃前 14 天的真实波幅（绝对价），价格翻倍后同一把尺子相对缩一半，+10% 阳线就算追涨（CRNC、RGTI 的 11-29 没买）；没有「还在新平台上」的上界，一跑 60 根，价格又涨 2～10 倍或一路阴跌都照样开段买（`bracket` 上那一长串 ▼） |
| 底部平稳 | 走势区段（横盘）、平台段 | 部分；「跌了很久之后相对低位、波动比之前小」要新字段 |
| 触底放量 | 无（派发是高位放量收阴，方向相反） | 缺，一个逐根扫描的点事件，`BarwiseDetector` 模板一小段就够（`path2/stdlib/templates.py`） |
| 样本日当天的条件 | 无独立 atom | 放在「截到当天」实例的字段上 |

**要新写的**：一个「站上新平台」复合 detector：吃 burst 流（阶跃），在 detector 内往回看 K 线定旧平台、往后逐天产「截到当天」的实例；字段至少有旧平台波动、阶跃涨幅、阶跃量比、阶跃涨幅相对两侧波动的倍数、新平台截至当天的低点和波动、当天涨幅与 K 线形态；child slot：旧平台、阶跃（直接引用 burst 实例，同 burst 引用 bo 的做法）、新平台、当天。量级和 `path2/atoms/throwback_v4.py`（300 行）相当，加测试。框架引擎不用改，求解器不碰（不触发 INV-C 的 fuzz 要求）。底部平稳、触底放量是加分项，各一个小 detector，可以晚做。

### 5. 要改的框架约定（小）

1. **买点 node 的因果闸**：`path2_web/eval_runner.py:108-118` 只查「买点 node 的 event 起点 ≥ 确认根」。跨度从旧平台起算的复合事件当买点 node 会被拦。两条路：买点 node 写成复合事件里「当天」那个点 child（`<node>.today`，零框架改动，推荐）；或把闸改成查「每个买点日 ≥ 确认根」（更贴本意，要动框架约定）。
2. **hit 级因果检查**：引擎不查「hit 里每个 event 的确认根 ≤ 买点日」，现在靠 app 作者用边保证（第一版实测满足，`repro/hit_causality.py`）。spec 6.12 的因果红线本来就要做，建议做成评估时对每个 hit 的一道检查。
3. **`tracked` 还没有实现**：spec 6.11 要的「算出来、显示、不进求解」的 where 代码里没有。现成的近似：整 node 不进求解用 `NodeSpec(solve=False)`（`path2/dag/nodes.py:60`）；子结构 node 上的 where 本来就只进诊断、不进求解（`path2/dag/spec.py:112-116`）。必过 node 上的一条可选属性还得新加机制。
4. **「每天一个实例」的显示与计数**：同一 band 上会叠几十个同起点的实例、hit 数乘上天数。compare 要把同一阶跃的实例折成一条（按共同的阶跃 child 认族）；评估若按 hit 加权，口径会变（原来一个生命周期一票，改成一天一票）。这两条分别归 compare-ui 和评估。

### 6. mapping「一个特征只对一个 node」要放宽

`path2_web/mapping.py` 现在只许「特征编号 → node」。spec 6.1 本就允许四种落法。建议格式改成每个特征一行、写明落在哪一类：

- 框类特征 → 一个 node，或复合事件的一个 child slot（`node.slot`）；
- 属性 → 某个 node 上的一条 where（按 clause 名，clause 名用用户的词）；
- `must_not` → 否定边；
- 级（`must` / `optional` / `must_not` / `excluded`）一起写。

同时 mapping 只决定「谁和谁对齐」，不决定显示：没对上任何特征的 node 照样画（界面改进第 5 条）。一组 node 合起来对一个框只作退路：它只在 hit 里才有并集，没成 hit 时看不出是哪一段没认出，正是用户要排查的情形。

### 7. 交给用户定的 spec 约束

spec 1.1、第 7 节（V-S1「翻译走不通」那条）、第 12 节都写着「写具体的 detector 不在范围」，V-S1 的前提是「挑一个用现有 detector 就能表达的 pattern」。new_step 证明了这个前提在实际标注里不成立：用户按自己的眼光画框，「新平台」「旧平台按相对波动判」现有 atom 都没有。三条路：

- **A（推荐）把「为认不出的特征写 detector」纳入流程**：6.1 的顺序保留（先试现成的、先排除判定口径、再新写），并把「认不出」写实——node 的 event 认不出框（6.2 的口径），而不是「框里某处有个 event」。代价：每个新 pattern 可能带一到几个 detector，会话工作量上去；用户的工作量不变。
- **B 只为 V-S1 放开一次**：只写「站上新平台」这一个复合 detector 验证格式，通用的「写 detector」以后再定。代价：V-S1 通过后下一个 pattern 还会碰到同一堵墙。
- **C 保持现状**：换一个现有 detector 就能表达的 pattern 重走 V-S1。代价：等于把标注往现有 detector 上凑，正是用户这次否定的做法。

**「改共用的企稳状态机」能不能代替新写（skeptic 问）**：

- 改法：给企稳状态机加可选的做法、默认不变——支撑取「新平台截至当天的最低点」且不抬高、量追涨的尺子换成阶跃后的相对波动、加「还在新平台上」的上界。三样都做成新参数取值，bottom_burst 不设就逐字节不变。
- 碰到的线：只有 spec 6.1「改一个别的 app 也在用的 detector 之前，先给用户看一列小图」（bottom_burst 也用它，`path2_apps/bottom_burst/dag_spec.py`）；默认不变时 bottom_burst 的结果不动，小图照规矩给。不碰 1.1 / 第 7 节 / 第 12 节「不写具体 detector」那条线。
- 能解决的：漏买的 3 个样本。evidence 实测（`notes_evidence.md` 第五节）：只把追涨倍数从 1.5 调到 3.1，就救回 CRNC a、c 和 RGTI a（9/10）；支撑改成新平台低点、收段不上抬，也能救 CRNC c。代价是买得更多：全历史买入日 299→358，CRNC 那台机器 4→39，一直买到 2025-02-21。要砍掉「一长串 ▼」，缺的是「价格还在不在新平台上」这个判断，状态机里没有，是结构问题。所以 6.1「先排除判定口径，再新写」在这里的落法是：口径改法能救回漏买的样本，但会放大多买；新写的必要性来自多买那一半。
- 解决不了的：框和 app 仍然「不是一个东西」——旧平台在 app 里没有任何对应物，hit 仍是一整段生命周期，样本和 hit 仍然一对多；为什么没买仍藏在状态机里，要靠 compare-ui 提的逐根状态旁路才看得见。而且三样改完，它已是另一台状态机，只是挂在旧名字下。
- 所以两条路不互斥：改状态机在现有范围内、能先把买点修好；新写复合 detector 才回答用户「装不下」的那个问题，要用户放开范围。

**顺序（和 skeptic 只剩半步分歧，见文末）**：复合 detector 的 where 分两组，卡点不同：

- **结构那组**（旧平台平不平、阶跃比两侧强多少、阶跃放没放量、新平台守没守住）：来自 pattern 定义和框，不受「没追涨」那道方向题影响。范围一放开就能写。
- **当天那组**（没追涨、收阳之类）：要等用户答「没追涨」指什么，并在阶跃后补几个负样本才有东西可校（skeptic 实测：当天就买 6/10，对阶跃后随便一天 28%，10 个样本分不出来）。在这之前先不写，新平台上的每一天都当候选，和第一版的「企稳段里每天都买」同一个松紧，只是多了「还在新平台上」这个界。

所以：「范围放不放开」现在就问（它决定后面修哪一版）；compare 看得见是第一段范围内的事，可以并行先做；结构那组在放开后写；当天那组排在方向题和补负样本之后。

### 顺手发现：compare 里有没有 hit 取决于视图从哪天开始

GEVO 2024-09-13 的阶跃：传入的 K 线从 2023-06-01 或 2024-01-05 起，burst 越过 2 个峰、有 hit；从 2024-03-01 或 2024-05-01 起，只越过 1 个峰，被「越过的不同峰数 ≥ 2」挡掉，没有 hit（scratchpad 脚本 `gevo_window.py`，已告知 evidence、compare-ui）。原因：越过的峰可以是很久以前登记的，而 new_step 声明的首部缓冲只有 63 根（`path2_apps/new_step/dag_spec.py:65-75`），盖不住峰的回看；`/preview` 按「请求起点 − 缓冲」切窗（`path2_web/api.py:477-482`）。现在的 compare 不受影响：它请求 `/preview` 时起点固定为 `1900-01-01`（`path2_web_ui/src/stores/appLink.ts:24, 68`），每次从第一根 K 线跑到训练段末日（compare-ui 指出，已核对）。受影响的是主视图扫描和按扫描窗口的预览：同一张图在那里和在 compare 里可能给出不同的 hit。evidence 复现：从框起点前 100 天截窗，10 个样本只剩 2 个买；阶跃越过的峰常在 82～332 根以前，首部缓冲只声明了 63 根。这也说明第一版的「越过的不同峰数 ≥ 2」量的是「越过了很久以前的老高点」，和「站上新平台」不是一回事。对框架的含义：凡是读「越过了几个峰」这类字段的 app，首部缓冲按回看窗声明是不够的；compare 改建到主视图上之后，app 那一层必须继续用整段运行的结果。

## 回答 compare-ui 的三个问题

1. **mapping 一对一还是一对多**：框架的结论是每个框类特征对一个 node（或一个 child slot），成对排；属性对那个 node 上的一条 where，排在同一对里；几个特征可以对同一个 node。一个特征对一组 node 只作退路（第 6 节）。所以界面按「一对一成对 + 属性挂在对上」排，再加 app only 的 band。
2. **detector 逐根吐状态的旁路**：框架上可以接受，前提和 on_gate 一样——可选、默认关、不进求解、只用当根及以前的数据、只吐「状态名 + 转换原因类别 + 可选价位线」这类与走势无关的形状（`path2/dag/gate_failure.py` 是先例）。但它是给「判断藏在状态机里」的 detector 打的补丁；按第 2 节「detector 只切段、判断全写成 where」写的复合 detector，每天的实例本身就带着这些信息（每条 where 的实测值、阈值），用不着旁路。建议：只为第一版 / 改过的企稳状态机做，不当通用协议推广。
3. **_rel_rows 按事件存 miss 原因**：不碰 `_solve`，不影响 INV-C；`path2/dag/diagnose.py:126-152` 本来就逐个上游事件算了原因（`_worst_gate`），只是攒成计数加 ≤5 个例子。按事件存的坑只有量：上游事件数 × 入边数，每股几百到几千条，诊断只在单股调用，可以接受。注意一点：它回答的是「这个上游事件在关系上差在哪」，要配合「截到样本日」筛选才对得上某个样本。
