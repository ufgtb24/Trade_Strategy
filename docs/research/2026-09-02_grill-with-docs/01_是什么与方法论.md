# 01 · grill-with-docs 是什么，背后的方法论

> 读完这篇你应该能回答：它到底做什么、为什么这么设计、什么时候该用、什么时候别用。
> 资料来源：`mattpocock/skills` 仓库 main 分支（commit `6654f6b`，2026-08-24）的 SKILL.md 原文与官方 docs 页，外加几篇社区对比文章。引用处标了出处。

---

## 1. 一句话定义

`grill-with-docs` 是 Matt Pocock 的 skill 集合「Skills for Real Engineers」里的一个用户手动触发的 skill。它做两件事，而且只做这两件事：

1. **访谈你**（grilling）：围绕你要做的改动，一轮一轮追问，直到你和 agent 对这件事的理解完全一致；
2. **边聊边写文档**（domain-modeling）：聊到一个术语定下来了，立刻写进仓库根目录的 `CONTEXT.md`；聊到一个「难回头、事后看会奇怪、真权衡过」的决定，写成一条 ADR（架构决策记录）放进 `docs/adr/`。

它的 SKILL.md 本体只有一行字：

```
Call the Skill tool twice, for "grilling" and "domain-modeling".
```

也就是说 grill-with-docs 本身没有任何逻辑，它就是「访谈 skill」+「领域建模 skill」的组合入口。理解这两个底层 skill，就理解了它的全部。

---

## 2. 它想解决什么问题

作者在 README 里列了 agent 辅助开发的四个典型翻车场景，每个配一个解法。grill-with-docs 对应前两个：

| 翻车场景 | 现象 | 解法 |
|---|---|---|
| **#1 agent 做的不是我要的** | 你以为它懂了，结果做出来完全不是那回事。根因是你和 agent 之间的「沟通缺口」 | 开工前先被**访谈**一遍：`/grill-me`、`/grill-with-docs` |
| **#2 agent 太啰嗦** | agent 被扔进项目、边干边猜黑话，于是用 20 个词描述 1 个词能说清的东西 | 建一份**共享语言**（`CONTEXT.md`），让 agent 有词可用 |
| #3 代码跑不起来 | 没有反馈回路，agent 盲飞 | `/tdd`、`/diagnosing-bugs` |
| #4 做成一团泥 | agent 加速了熵增，代码越来越难改 | `/to-spec` 出 spec 前先就**测试接缝**跟你确认（README 里的说法是「先问动哪些模块」）、`/improve-codebase-architecture` 定期体检 |

作者对 #2 的原话值得记住：他自己项目里 BEFORE 是「当课程某一节里的某一课被'落实'（在文件系统里分到位置）时出了问题」，AFTER 是「materialization cascade 出了问题」。术语一旦共享，后面每一轮对话都省字、省 token、省误解，而且变量名、函数名、文件名会自然跟着术语走，代码库对 agent 也更好导航。

## 3. 底层机制一：grilling（访谈）

这是整个体系里其他 skill 都在复用的那块底件（作者叫它 primitive），`grill-me`、`grill-with-docs`、`triage`、`wayfinder`、`improve-codebase-architecture` 底下跑的都是它。SKILL.md 原文不到 30 行，但每句都有讲究。

### 3.1 设计树、前沿、轮次

访谈不是随便问。它把你要做的事想象成一棵**设计树**：每个决定下面挂着一串依赖它的决定。

- **前沿（frontier）**：所有「前置决定都已经定了、现在就能问、不用猜答案」的问题。
- **轮次（round）**：一次把整个前沿全问出来，每题编号、每题附 agent 自己的推荐答案，然后等你回答。
- 你答完一轮，树的形状变了：定下来的决定把前沿往外推，原来被卡住的问题解锁，agent 重新算前沿，再问下一轮。
- 同一轮里的问题彼此不能有依赖；如果 Q3 的答案取决于 Q1，那 Q3 属于下一轮。

官方口径是**数轮次不数题数**：grill-me 文档说 13 个问题通常 3 轮问完而不是 13 轮，46 题 4 轮也算一场普通会话。社区实测（alexrusin）一场 grill-me 问了 37 题，量级吻合。

### 3.2 问题的固定格式

```
❓ **Q1** - **<问题标题>**: <问题正文，可能多段，可含多选项>

➡️ <agent 的推荐答案>

---

❓ **Q2** - ...
```

固定格式是为了让你能**按编号回答**：「1 同意，2 选第二个，3 不，因为……」，不用把问题抄回去。

有个已知的小坑：推荐答案有时是在**反对**问题本身的措辞，这时候「同意推荐」等于对问题说「不」。遇到这种情况直接回答推荐，说一句「按你推荐的」即可。

### 3.3 事实归 agent，决定归你

这是 grilling 与「一般的问问题」最本质的区别，原文两句话：

> Finding _facts_ is your job, never the user's.
> The _decisions_ are the user's: put each to them and wait.

- 凡是能从环境里查到的（文件系统、代码、工具输出），agent 必须自己派子代理去查，**不许问你**。
- 查的时候不阻塞：正在查的东西是「未定的前置条件」，只有依赖它的问题才等，其余前沿照问。
- 凡是需要拍板的，必须交给你，并且**等**。

官方文档明确说：agent 自己替你答了决定，那是 skill 跑坏了，不是「灵活解释」。这也是为什么作者拒绝做「异步模式」（读 issue 后自动出决策备忘录）：没人回答的访谈，产出的是 agent 的观点，不是你的。

### 3.4 什么时候结束

前沿为空（每个分支都走过、没有任何东西被默默假设）时访谈结束。**但结束不等于开工**：还要你明确确认「我们的理解一致了」，它才能动手。弱一点的模型经常在这里翻车，两三个问题加一份提纲就开始写代码。作者给的修法是在你自己的 `CLAUDE.md` 里加一句「未经允许不得实施」。

### 3.5 作者对访谈的几条硬立场

- **不设问题数量上限**（`.out-of-scope/question-limits.md`）。有的计划 3 个问题就够，有的要 50 个；固定上限要么截断难题，要么在简单题上显得武断。要缩短就用自然语言喊停：「收尾吧」「就按现在这样」。问题太多通常说明范围太大，先拆。
- **一次一题是支持的**。默认按轮问，但在全局 `CLAUDE.md` 加一句 `When grilling, ask one question at a time.` 就切回逐题模式。文档说读得慢的人、用第二语言工作的人、需要逐题聚焦的人普遍反映逐题更好，这是「支持的选项」而不是「容忍的偏差」。
- **关掉 plan mode**。plan mode 会把 agent 推向「赶紧出计划」，与「留在提问里」相反。
- **模型要用最好的**。访谈靠模型「知道系统会怎么坏」的直觉，比实现阶段更吃模型能力。
- **有些问题谈不出来**（ungrillable）：「一个长表单还是三页」「这个交互感觉对不对」这种要有东西看了才能答。遇到就停止访谈，用 `/prototype` 做个一次性原型看一眼，回来一句话答掉。硬谈会让会话膨胀。

### 3.6 你这边的责任：别当点头机

`grill-me` 文档里专门有一节叫「这是对话，不是单方面问答」：问题由它出，范围由你把。最常见的失败是**被动**：40 个问题一路「同意、同意、同意」，出来一份 agent 写的、你点了头的计划。它显得很有成效，因为很长；但什么都没真正决定，而且带着一种没挣来的确定感。

主动的意思是：推回去（问题问得比你需要的粗时）、指出跑题、认真说「我不知道」。产出的质量跟着你答案的质量走，不跟着问题数量走。文档的判据：**一次没有任何反驳的会话，是一次你不需要的会话**。

## 4. 底层机制二：domain-modeling（领域建模）

grilling 负责问，domain-modeling 负责在问的过程中把东西写下来。它是「主动」的纪律：不是读一下 `CONTEXT.md` 借个词（那是任何 skill 都能做的一行习惯），而是在你**改动模型**时介入。

### 4.1 会话中的五个动作

1. **对照术语表挑刺**：你用的词和 `CONTEXT.md` 里的定义冲突，它当场指出来：「你的术语表把 cancellation 定义为 X，但你现在的意思是 Y，到底哪个？」
2. **把模糊词磨尖**：你说「account」，它问你指 Customer 还是 User，这是两个东西。
3. **拿具体场景压测**：讨论概念之间的关系时，编几个边界场景逼你把边界说清楚。
4. **和代码对账**：你说系统是这么工作的，它去看代码是不是真这样；不一致就摊开：「代码里取消的是整个 Order，但你刚说可以部分取消，哪个对？」
5. **当场写进 `CONTEXT.md`**：一个术语定下来，立刻写，不攒到最后。

### 4.2 两个产物，两条门槛

| | `CONTEXT.md` | `docs/adr/NNNN-slug.md` |
|---|---|---|
| 装什么 | **术语**：一个东西「是什么」，一两句话，加上 `_Avoid_` 列出弃用的同义词 | **一个决定**：一到三句话，说清背景、选了什么、为什么 |
| 写入门槛 | 一个模糊词变成了正式术语 | **三条同时满足**：难回头、脱离上下文看会奇怪、是真正权衡的结果 |
| 何时写 | 当场，术语一定就写 | **提议**，不是默认；三条缺一条就不写 |
| 绝不装 | 实现细节、spec、草稿、通用编程概念 | 本次会话每个选择的流水账 |

`CONTEXT.md` 的格式（`CONTEXT-FORMAT.md`）：

```md
# {上下文名}

{一两句话：这个上下文是什么、为什么存在}

## Language

**Order**:
{一两句话定义}
_Avoid_: Purchase, transaction

**Invoice**:
A request for payment sent to a customer after delivery.
_Avoid_: Bill, payment request
```

四条规则：**要有立场**（多个词指同一概念时选最好的一个，其余放进 `_Avoid_`）；**定义要紧**（一两句话，说它是什么，不说它做什么）；**只收本项目特有的概念**（timeout、error type 这类通用编程概念不收，哪怕项目大量用）；**自然聚类时分小标题**。

ADR 的格式（`ADR-FORMAT.md`）更简单：

```md
# {决定的短标题}

{1-3 句：背景、决定、原因}
```

作者原话：「一条 ADR 可以就是一段话。价值在于记下**做过**这个决定以及**为什么**，不在于填满各种小节。」可选的 Status / Considered Options / Consequences 只在真有价值时加。

什么样的决定够格：架构形状（单仓、事件溯源）、上下文之间的集成模式、带锁定的技术选型（换掉要一个季度的那种）、边界与范围决定（「客户数据归 Customer 上下文所有，别人只能按 ID 引用」，**明确的「不做」和「做」一样有价值**）、**故意偏离显然路径**（「我们手写 SQL 不用 ORM 因为 X」，防止下一个人把故意的东西「修好」）、代码里看不见的约束（合规、伙伴 API 的 200ms 契约）、否决理由不显然的备选方案（否则六个月后又有人提 GraphQL）。

### 4.3 文件放哪

绝大多数仓库是单上下文：

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-xxx.md
│   └── 0002-xxx.md
└── src/
```

根目录有 `CONTEXT-MAP.md` 才算多上下文（每个上下文各有自己的 `CONTEXT.md` 和 `docs/adr/`）。只有 monorepo 才需要，几乎所有仓库都用不上。

所有文件**懒创建**：没 `CONTEXT.md` 就在第一个术语定下来时建；没 `docs/adr/` 就在第一条 ADR 够格时建。不预先搭架子。

### 4.4 第三种产物：什么都不落盘的那些

这是最容易让人踩坑的地方，官方文档单独列了一张表：

| 会话里定下来的东西 | 落在哪 |
|---|---|
| 一个术语 | `CONTEXT.md`，当场 |
| 一个过三道门槛的决定 | `docs/adr/` |
| **其他所有决定** | **只在对话里，哪都不在** |

`CONTEXT.md` 只是术语表，ADR 门槛很高，所以大部分会话**产出零条 ADR**，这是设计如此。但这意味着你们谈定的大部分内容只存在于当前上下文窗口里。**对策只有一个：别 clear，把同一段对话直接交给 `/to-spec`**。

## 5. 它在整条流水线里的位置

```
grill-with-docs → to-spec → to-tickets → implement → code-review
```

| 步骤 | 干什么 | 关键特征 |
|---|---|---|
| `/grill-with-docs` | 访谈 + 写术语/ADR | 主链的头。产出「共享理解 + 定型术语」 |
| `/to-spec` | 把当前对话综合成 spec，发到 issue tracker | **不再访谈**，只综合。会先和你确认测试的「接缝（seam）」：在哪一层测、越高越好、最好只有一个 |
| `/to-tickets` | 把 spec 切成「示踪弹」ticket | 每张 ticket 是**垂直切片**（穿透 schema/API/UI/测试，单独可演示），**大小以一个新的上下文窗口能装下为准**，每张声明被谁阻塞。切完先问你粒度对不对 |
| `/implement` | 按 ticket 实现 | 内部走 `/tdd`（只在事先商定的接缝上测），常跑类型检查，最后 `/code-review`，提交 |
| `/code-review` | 双轴评审 | **Standards**（守不守仓库规范 + Fowler 的 12 种坏味道基线）和 **Spec**（是否忠实实现了 spec）由两个并行子代理各审各的，**不合并、不重排**，防止一个轴掩盖另一个 |

作者的上下文卫生规则：**1 到 3 步（访谈、spec、切票）保持在同一个上下文窗口里**，别 compact 也别 clear，这样三者建立在同一份思考上。之后**每张 ticket 用一个新会话**跑 `/implement`，票与票之间 `/clear`，因为每张票是自包含的。

前置条件：`/setup-matt-pocock-skills` 每个仓库跑一次，回答三个问题（issue 放哪、triage 标签叫什么、领域文档放哪），写成 `docs/agents/*.md`。skill 本身在所有仓库里一模一样，只是运行时读这几个文件决定行为。这也是作者的口号「Config is death」：不做配置项，偏好写进你的 `CLAUDE.md` 用自然语言表达。

### 5.1 三个访谈入口怎么选

| 你手上是什么 | 用哪个 |
|---|---|
| 没在任何工作目录里（想一个产品方向、一篇文章、一个业务决定） | `/grill-me`：同一套访谈，**无状态**，不写任何文件 |
| 在一个仓库里，一个会话能谈完的改动 | `/grill-with-docs` |
| 一个会话装不下的大工程（greenfield、大功能） | `/wayfinder`：先把工程画成一张「决策 ticket」地图，逐张解决，**只产决定不产交付物**，雾散了再回到 `/to-spec` |
| 仓库一份文档都没有、也没具体功能要做 | `/grill-with-docs`，对着仓库本身谈：「help me scaffold my existing repo with a CONTEXT.md」 |
| 卡在别人脑子里的知识上 | `/to-questionnaire`：写份问卷发给那个人 |

作者给的判据：只要在仓库里，`grill-with-docs` 严格优于 `grill-me`（同样的访谈，多留一条纸面记录）；`grill-with-docs` 和 `wayfinder` 的分界是「一个会话装不装得下」，拿 wayfinder 去做一个范围清楚的功能是常见错误。

### 5.2 阶段边界：五选一

访谈结束、实现结束、QA 结束，这些「阶段边界」是唯一该考虑「上下文怎么办」的地方。作者给了一棵按顺序问的树，**第一个「是」就赢**：

1. **能继续吗？** 下一阶段需要这一阶段的原文（访谈 → 实现就是典型：实现要的是推理原文，不是摘要），或者剩余「聪明区」还够（聪明区指上下文里模型还能保持好状态的那一段，经验值约 150k token）。**继续是唯一保留原始信息的选项，先排除它**。
2. **上下文对下一步完全无用？** `/clear`。最便宜，但一旦判错是单向的：清掉相关上下文就丢了「为什么」，读 diff 也找不回来。
3. **需要带走吗？** `/handoff` 很窄：换 harness、换目录、交给同事、中途分叉一个支线任务。它买的是**可移植性**，没东西要移动就不需要它。
4. **能离开键盘跑吗？** 范围收得够紧、不用你盯着，就派**子代理**。自动评审是标准例子。
5. **否则 `/compact`**。这是**默认项但不是第一反应**，放在最底下是因为上面四个要么更便宜要么更精确。从这里起手的失败模式是：新会话对摘要压扁了的某个决定自信地答错。

## 6. 设计哲学：小、可组合、不接管流程

作者在 README 开头就把立场摆明：

> Approaches like GSD, BMAD, and Spec-Kit try to help by owning the process. But while doing so, they take away your control and make bugs in the process hard to resolve.
> These skills are designed to be small, easy to adapt, and composable.

具体体现：

- **没有 hook、没有自动注入**。每个 skill 要么你手动敲（user-invoked，`disable-model-invocation: true`，agent 永远不会自己触发），要么模型在任务匹配时可以自己拿（model-invoked）。user-invoked 的负责编排，model-invoked 的装可复用纪律；前者可以调后者，**但绝不调另一个 user-invoked 的**。
- **skill 极短**。`grill-me` 一行，`grill-with-docs` 一行，`implement` 五句话。逻辑全在被复用的原语里。
- **agent 不替你拍板**。前面说的「事实归 agent、决定归你」。
- **文档只缓存代码里找不到的东西**（`writing-for-agents` 的「cache」原则）：`package.json` 脚本、目录结构、`--help` 输出这些环境自己就是权威，文档复述它们等于缓存一次查询，只在查询昂贵时才值。该缓存的是**没写下来的约定、选择背后的原因、配置文件里不会坦白的坑**。

社区对比文章（nocoders）把它和 Superpowers 概括成「**framework vs library**」：Superpowers 用 SessionStart hook 注入「哪怕 1% 可能适用也必须调 skill」，由框架接管流程、防止 agent 偷工减料；Pocock 用显式调用，由人掌舵、防止过度自动化。两者优化的是不同的失败模式，不存在谁绝对更好。另一篇（alexrusin）实测：Plan Mode 零问题直接出方案、`grill-me` 问了 37 个问题「每个设计决定都是开发者明确做出的，不是模型默认的」、Superpowers brainstorming 问了 6 个聚焦问题就进结构化规划；结论是「没有普适最佳的规划工具，但前置的上下文抽取产出的代码更好」。

关于「共享语言到底有没有用」，官方文档自己也诚实地收录了反方：有人认为一个术语和它的白话展开对模型效果一样，术语真正压缩的是**人与人**之间的沟通。文档的回应是：这种解读并不否定术语表的价值，只是把价值挪了个地方，从「让 agent 更强」变成「让你和评审者与 agent 保持对齐」。还有一句实在话：一天就能做完的东西，跳过术语表；**未经审阅、agent 自己写的术语表比没有更糟**，它会变成后续会话当真的、听起来很自信的传说。

## 7. 已知的坑（社区反馈汇总，来自官方 docs 页「Common questions」）

按出现频率排，括注是出处的 docs 页：

1. **依赖 skill 没加载**（最常被报告）。`grill-with-docs` 本体一行字，靠加载 `grilling` 和 `domain-modeling` 干活。agent 有时不加载，或只加载了一个。症状：一口气把所有问题倒出来、没有推荐答案、从头到尾不提 `CONTEXT.md`。**修法：直接问它「你加载了哪些 skill」**，通常就能恢复。与模型和 effort 等级相关。（grill-with-docs 页）
2. **`CONTEXT.md` 膨胀成 spec**。模型把「写进 CONTEXT.md」理解成「把我的每个回答都存起来」，文件长到 500、1000、3000 行。修法：`/grill-with-docs make my CONTEXT.md more concise and remove any implementation details from it`。只有文件已经很瘦、还同时覆盖两个读者不想同时拿在手里的领域时，才拆 `CONTEXT-MAP.md`；拆一个臃肿文件只会得到几个臃肿文件。（domain-modeling 页）
3. **其他决定都去哪了**。见 §4.4。精确的答案（顺序保证、否定性需求、数值默认）会在下游被软化成弱一些的散文。对策：同一会话直接 `/to-spec`，然后**拿你自己的答案对照着读 spec**，别假设它都记下了。（grill-with-docs 页）
4. **在别的编排层里跑时，写文件那半静默失效**。有人在 spec-driven 框架、多 agent 框架、或某条 rule 里把它当一步调用，访谈照跑，`CONTEXT.md` 和 ADR 却没出现。已立案、未修复。这种场景下跑完先看工作目录。（grill-with-docs 页）
5. **`/ask-matt` 说一半 skill 没装**。user-invoked 的 skill 因为 `disable-model-invocation: true`，harness 不把它们放进注入给 agent 的 skill 列表，agent 就以为没装。**它们是装了的，直接敲斜杠命令**。（ask-matt 页）
6. **跑完不知道下一步**。收尾消息偏开放。主链答案是同一会话 `/to-spec`；改动小到能立刻做，直接 `/implement`。（grill-with-docs 页）
7. **名字没人满意**。有提议改叫 `grill-domain-model`，没动。`CONTEXT.md` 该不该叫 `GLOSSARY.md` 也是争论最多的命名问题，没有定论；改名要改所有 skill，不建议。（grill-with-docs 页；`CONTEXT.md` 改名之争在 domain-modeling 页）
8. **ADR 格式不能单独换**。术语表和 ADR 在同一个 skill 里，有自己 ADR 规范的团队会撞。目前只能本地复制 skill 改，或在自己的 agent docs 里覆盖。（domain-modeling 页）
9. **不搜 issue tracker**。它只对照代码和已提交的 `CONTEXT.md`/ADR，几个月前在 issue 里争完的命名会被当成新问题再提一遍。修法：把「先查 issue tracker」写进自己的 `docs/agents/domain.md`，skill 本来就会读它。（domain-modeling 页）

## 8. 「它在正常工作」的判据

官方每个 docs 页都有「It's working if」，合并起来是一份自检表：

- `CONTEXT.md` 在会话**过程中**逐条变化，而不是最后一坨出现；
- 术语表读起来是纯词汇（项目自己的词 + 紧凑定义），没有实现细节和 spec 味的散文；
- 代码库能回答的问题，它去读代码，不问你；
- ADR 很少或没有，有的那几条都是「再争一遍你会烦」的决定；
- 它因为你用的词和现有术语表定义不同而挑战你；
- 每轮问题按编号到达、每题推荐答案单独一行、你能按编号答完整轮；
- 同一轮里没有哪题要等另一题先答；
- 后几轮问的是第一轮问不出来的东西；
- 后台的查证不卡轮次，只有依赖它的问题才等；
- 结束时它停下来问你确认理解一致，而不是开始干活；
- **你至少反驳了一次**。

## 9. 一页总结

- grill-with-docs = 访谈（grilling）+ 边聊边写术语表和 ADR（domain-modeling），本体一行代码。
- 访谈按「设计树 / 前沿 / 轮次」推进，每轮问所有能问的、附推荐、等你答；事实 agent 自己查，决定必须你拍。
- 落盘的只有两样：术语进 `CONTEXT.md`（纯术语表，当场写），过三道门槛的决定进 `docs/adr/`（大多数会话零条）。其余决定只在对话里，所以**同一会话接 `/to-spec`**。
- 主链：grill-with-docs → to-spec → to-tickets → implement → code-review；前三步同一窗口，之后每票一个新会话。
- 哲学：小、可组合、不接管流程、agent 不替人拍板、文档只缓存代码里找不到的东西。
- 最大的坑：依赖 skill 没加载（问它加载了什么）、`CONTEXT.md` 变 spec（定期瘦身）、决定留在对话里（别 clear）。
