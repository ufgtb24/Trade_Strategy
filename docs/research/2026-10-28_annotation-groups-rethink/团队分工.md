# 团队分工（lead 开工前定）

## 为什么按这几个维度分

问题有两层：一是**用户到底拿 groups 干什么**（需求侧），二是**现在叫「组」的东西里混了哪些概念**（供给侧）；两层对上之后才谈**界面怎么改**。另有两个容易漏的角度：真实使用时的摩擦只有实际走一遍才看得到；而「优化」最常见的失败是加东西，所以要有人专门守「能不能删、删了会丢什么、用户要记住的东西有没有变少」。

| teammate | 维度 | 回答什么 | 产物 |
|---|---|---|---|
| `flow` | 流程与任务 | 七步流程里，用户在哪些时刻打开这份列表、心里带着什么问题、看完做什么决定、多频繁；每件事最少要看到什么；哪些事其实该在别处做 | `flow.md` |
| `model` | 概念拆分 | 「组」里捆了哪些轴，各自谁给的、何时才有、是每个买点一个值还是一批一个值；拆开后各叫什么（对词表）；边角情形 | `model.md` |
| `sim` | 模拟用户 | 只读白话版、不读代码，按真实任务把现版 mock 走一遍，再走 ui 的各个变体；记下每次看列表想干什么、读错了什么、要记住什么、点了几下 | `sim.md` + 截图 |
| `ui` | 界面方案 | 按 flow / model 的结论做 2～3 个差别很大的变体（复制品，不改 mock_v3），按界面文字规则和色弱配色，数高频任务的操作步数 | `ui.md` + `repro/` 下变体 + 截图 |
| `critic` | 反方与剃刀 | 每个方案（含维持现状、整节删掉）对着 flow 的任务清单挑：哪些可删、删了丢什么（尤其先前定下要靠偏离组暴露的事）、哪里会读错、用户要记的概念数是变多还是变少 | `critic.md` |

心智负担（用户追加的方向）不单设一人，每个人都要按它衡量：flow 数每个任务要用户记住或换算的东西，model 数概念个数，sim 记读错与回想，ui 数步数与屏上的词，critic 把「概念数、要记的规则数」当硬指标。

## 协作顺序

1. 并行开工：flow、model、sim（走现版）；ui 先读现版并起草；critic 先从旧报告整理「groups 不能丢的职责」清单。
2. flow、model 出中间结论就用 SendMessage 发给 ui、critic（也互相发）。
3. ui 出变体后发给 sim 走、critic 挑；最多改两轮。
4. 各自写完 md、给 lead 一段总结后停。lead 汇总成 `final_report.md`，再出白话版。

## 共同约束

只读 `repro/data.js` 的演示数据，不读 `datasets/`；不改 mock_v3、旧报告、票、地图、词表；不提交；playwright MCP 只给 sim 用（端口 8792），ui 用 node 脚本截图（端口 8793）；关进程只按进程号。
