## 一 · 需求

K 线图上要显示阻力位（peak，简称 pk）的三种状态：

| 状态 | 含义 |
|---|---|
| **alive** | 已登记、从未被突破、也没被更高的峰取代，此刻仍压在头顶 |
| **broken** | 被某个 bo 突破过 |
| **eaten** | 被更高的峰 supersede（取代）掉 |

当前图上**只有 broken 态可见**，因为 pk 唯一的现身通道是「作为 `BOEvent.referenced_points` 被渲染成卫星 marker」。实证：bb_v1 上约 28.3% 的峰从未被突破，图上完全不存在。

用户已拍板：三态**全部**要显示，且渲染层改动必须类型无关（不为 pk 开专用路径）。

## 二 · 现有代码事实

### 2.1 `Peak` 不是 `Event`

`path2/atoms/breakout.py` 中 `Peak` 是 `@dataclass`（**可变**），detector 私有，不出 stream：

```python
@dataclass
class Peak:
    index: int              # 峰所在 bar
    price: float            # 峰价(会被 elevation 抬升)
    pk_id: int
    volume_peak: float
    relative_height: float
    original_price: Optional[float] = None   # 首次 elevation 前的原值
```

### 2.2 `BODetector.emit()` 的执行顺序

```python
def emit(self, df, i):
    self._detect_peak_in_window(df, i)   # 1. 峰检测(登记新峰 + peak-peak supersede)
    ...                                   # 2. 突破检测(遍历 self._active_peaks)
```

**峰检测先跑、突破检测后跑**，两者共享同一个 `self._active_peaks`。

### 2.3 峰检测的四道闸（`_detect_peak_in_window`）

1. 窗口热身：`current_idx - total_window >= 0`
2. 窗口 argmax（按 `peak_measure` 口径）
3. 侧翼：峰的局部索引距窗口两端各 ≥ `min_side_bars`
4. 相对高度：`(峰价 - 窗口最低 low) / 窗口最低 low >= min_relative_height`
5. 去重：`peak_already_active` —— 峰的 bar 索引不在 `self._active_peaks` 中

登记成功后，还会做 **peak-peak supersede**：遍历 active，把显著低于新峰的旧峰淘汰。

### 2.4 两处 supersede 的锚定不一致（已核实，无注释解释）

**突破循环里**（`breakout.py:325-327`）—— 锚 `original_price`，有明确注释论证：

```python
supersede_base = peak.original_price if peak.original_price is not None else peak.price
# 注释原文:"supersede 始终锚原始 price:peak.price 在小幅突破后会被 elevation 抬升,
#           若仍以 elevated 价为基会让缓步上行的累计涨幅永远进不到 supersede 分支"
```

**峰检测里的 peak-peak supersede** —— 锚 `price`（即 elevation **之后**的价），无任何注释：

```python
exceed_pct = (max_measure - old_peak.price) / old_peak.price
```

后果：一个峰被小幅突破抬价后，后来的新峰要淘汰它变难了。**突破逻辑反向影响了峰检测。**

### 2.5 elevation 与突破移除

突破循环中，对每个被突破的峰：

- **大幅突破**（超过 `peak_supersede_threshold`）→ 峰从 `_active_peaks` **移除**
- **小幅突破** → `peak.price` 被抬升到当前 bar 的 `peak_measure` 值（elevation），首次抬升时记录 `original_price`，峰**保留**

由「大幅突破后移除」派生一个后果：该 bar 位置不再被去重闸拦截，**同一个峰位可以重新登记并拿到新的 pk_id**。

### 2.6 登记集的纯函数性（已实证）

因为去重闸读的 `_active_peaks` 会被突破逻辑改写，登记集原则上不是 df 的纯函数。

**实证结论**：只要 `breakout_measure` 逐 bar ≤ `peak_measure`，分叉不会发生。864 组参数×数据的对拍中，44 例登记集不一致 **100% 落在 `(peak_measure=close, breakout_measure=high)` 象限**。（与更早一轮独立的 5120 组对拍结论重合。）

四个 measure 存在逐 bar 全序：`low ≤ close ≤ body_top ≤ high`。

### 2.7 `referenced_points` 契约

```python
referenced_points: Tuple[Tuple[int, float, str], ...] = ()
# (bar_idx, price, label);render_grid='price' 时前端按字段存在性渲染卫星 marker
# 字段注释原文:"label 由 detector 填字面字符串,前端不读 label 内容做条件分支"
```

它是渲染层**唯一**使用精确坐标的通道——事件主 marker 一律画在 `bars[start_idx].h * 1.005`（蜡烛高点上方的示意位），只有卫星用真实坐标。

**该约定实际上已被破坏一次**：`path2_web_ui/src/render/chart.ts:187` 硬编码了 `/^pk(\d+)$/`。

## 三 · 引擎协议事实

### 3.1 detector 的调用约定（`path2/dag/engine.py` docstring 原文）

> detector 按真实入参调用：root(`consumes_stream=None`) 只吃 df → `detect(df)`；消费者吃 (上游流, df) → `detect(bos, df)`。

`throwback` / `burst` 已在使用消费者形态。

### 3.2 物化与去重（`engine.py:131-137`）

```python
key = (id(node.detector), node.consumes_stream)   # 两元都必需
if key not in materialized:
    if node.consumes_stream is None:
        materialized[key] = list(run(node.detector, df))
    else:
        materialized[key] = list(run(node.detector, streams[node.consumes_stream], df))
streams[nid] = materialized[key]
annotate_stream(counts, nid, streams[nid], children_of)
```

`NodeSpec.consumes_stream: Optional[str]` 是**单值**。同一 detector 对象被多个 node 引用时只跑一次。

### 3.3 「一个 detector 一条流」的机制来源

- `NodeSpec.event_cls` 反射自 `detector.event_cls` —— 单值
- 物化键 `(id(detector), consumes_stream)` —— 一个 detector + 一个输入流 = 一条输出流
- `annotate_stream` 按 node 给 event 编 `instance_id`
- `on_gate` 是 **detector 级**的回调属性（`detector.on_gate`），产出 `GateFailure` 进诊断侧栏

### 3.4 求解判据（`path2/dag/_solve.py:95-105`）

- **含边 pattern**：孤立 node（不在任何 edge 的连通分量里）**不参与求解**（注释：「孤立即不属 pattern」）
- **零边 pattern**：走「全求解例外」（`all_solve = not edges`），所有 node 都求解

`bo_only` 是零边 pattern。`PatternSpec` **没有** `end_node` 字段（那在 app 层 `eval_meta()` 里）。

### 3.5 Event 契约（`path2/core.py`）

- 不变式：`start_idx ≤ confirm_idx ≤ end_idx`（65 行）
- `is_point: ClassVar[bool]` 是 **`start_idx == end_idx` 的几何承诺**（86 行）
- `render_grid='price'` 要求 `event_cls.is_point=True`（`spec.py:206-222` 反射校验）

### 3.6 渲染分流（`path2_web_ui/src/render/`）

- `renderGridOf(e, topology, bandKey)` 返回 `'price' | 'time'`，缺省 `'time'`
- `render_grid='price'` 的 marker 钉 K 线主图、**不占副图轨道**；`'time'` 占一条副图轨道
- 卫星只从 `priceAnchored` 构造（`chart.ts:186`）——即只有 `render_grid='price'` 的 event 才会画卫星
- 事件按 `node_id` 分 band（`bandKeyOf(e) = e.node_id`）

## 四 · 性能事实（实证）

- 峰检测占 `BODetector` 整趟约 **79%**，突破判定约 20%
- 若峰检测跑两遍，端到端约 **1.80×**（n=1250：45.81ms vs 25.46ms；n=5000：180.83ms vs 103.08ms），阶数不变
- `measure_series(df, 'body_top')` 每根 bar 重算整条序列 → `peak_measure='body_top'` 时整体是 **O(n²)**（n=2500 时比 `'high'` 慢 13.7 倍）。现有 6 个 app 无人使用 body_top，故生产不可达。

## 五 · 三个待评估方案（中立描述）

### 方案 ① `consumes_stream`

新增 `PeakDetector`（吃 df，吐 `PeakEvent`），`BODetector` 改为 `detect(peaks, df)`，通过 `NodeSpec(consumes_stream="pk")` 消费 pk 流。峰只算一遍。

用户提出的疑虑原文：「由于是 pk，bo 的计算过程互不可见，因此无法复刻现有版本中 pk 和 bo 的动态交互。」

（指 §2.4 / §2.5 描述的那些跨域交互：elevation 抬价影响 peak-peak supersede、突破移除影响去重闸。）

### 方案 ② 递归 reference

不引入任何新 event 类型。`Peak` 增加字段记录「我吞掉了谁」（递归累积），构造 `BOEvent` 时把被突破峰的整条吞噬链平铺进 `referenced_points`。

**已知覆盖边界**：能显示的一切必须挂在某个实际出流的 event 上，而 `BOEvent` 只在突破真的发生时诞生。因此覆盖不到两类峰——(a) alive 态（从未被突破也没被吃掉，无任何 event 引用它）；(b) 被吃掉、但吞掉它的整条链从未被突破。

### 方案 ③ 打破「一 detector 一 stream」

扩展引擎，允许一个 detector 产出多条流（如 `BODetector` 同时吐 `BOEvent` 和 `PeakEvent`），峰与突破仍在同一趟扫描内交互，行为可与现状完全一致。

用户的要求原文：「不需要兼容已有 apps，因为这些 apps 并不完善，且重新扫描的成本很低。需要兼容的是其他单一 stream 的 detector，比如 on_gate 指定目标 stream，保证框架的协议统一性。」

## 六 · 已被排除、不要重新提出的选项

- **多 `pk_measure` 并行**：判死（`peak_measure` 视作普通参数）
- **「两个 detector 各自跑同一个峰检测纯函数」（曾称方案 B′）**：用户已否决，理由是两个 detector 必然有两套参数、参数一致性只能靠纪律维持而无结构性保证
- **把「是否被突破」做成 `PeakEvent` 的字段**：未来信息，破坏因果封闭
- **让 `confirm_idx` 延迟到「突破或死亡」**：窗末仍存活的峰将永不出流（实测该比例达 47%）
