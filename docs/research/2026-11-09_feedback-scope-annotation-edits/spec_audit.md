# spec_audit：迭代里改标注——spec、说明书、代码现在怎么规定、怎么支持

> 2026-11-09，agent team 成员 `spec_audit`。本文所有项目内路径相对 repo root。
> spec = `.scratch/annotation-path2/spec.md`，说明书 = `.scratch/annotation-path2/manual.md`；行号是写本文时的行号。
> 复现脚本：`repro/history_visibility.py`（临时目录里造标注、改、读）、`repro/reinfer_members.py`（只读真实标注与训练段副本）。

## 0. 先说人话

**做了什么**：把 spec、说明书、代码里所有和「用户改自己的标注」有关的地方翻了一遍，在一个临时标注目录里实际改了几次再读回来，并用真实标注算了「另建新 pattern 时样本要重放多少、会变成什么样」；又盘点了页面上按状态决定「能不能做」的提示，逐条核了 `method_critic` 的政策与页面引导提案做不做得到、要改哪里。

**说明什么**：
- 现有文字对「迭代中改标注」的态度是**允许、而且当成常规动作**：有十来处明文写着或例子里演示了在循环中补框、改 judgment、挪样本、看着 app 结果标；**没有一处禁止**。唯一定死不让改的是特征的「定义」，理由是改了会让旧框悄悄换意思，意思变了就另起一个特征。
- 界面上框、样本、词名、pattern 定义差不多都能改；不能做的是 pattern 改名 / 删除 / 复制、改样本日期、撤销。
- 每次修改在文件里都留着带时间的整条记录，**但会话唯一被允许的读法只给「现在的样子」，看不出改之前是什么**。所以 spec 里几条依赖「知道你改了什么」的规矩（改判提问、每轮先读变化、「翻了」是谁造成的）现在都没有数据来源。
- 「不满意就另建新 pattern」在检查次数上省不了任何东西（规则写明换名替补仍记在旧 pattern 名下），却要重放或搬走全部样本、丢掉挂在旧 pattern 上的反馈和 app 绑定，并且新旧之间没有任何连线。
- 页面上现有的「能不能做」全是挂在单个控件上的即时提示（按钮变灰、框边拖不过样本日、跨样本日的框收不进）；「整个流程此刻最该做什么」没有任何东西回答——spec 写的 `next` 一格没造，而且照字面也做不全（「有题要问」工具推不出来）。
- 队友提案里「让会话看得见改了什么」的做法可行、代价小，但截止点必须按每台机器各记一个「从 1 起连续到齐的最大批次序号」：按一个时刻或一个批次名记，会把另一台晚同步来的修改永远漏掉；只记最大序号也不行，同步软件默认乱序拉文件，中间缺的那一批会被永远漏掉。

**不说明什么**：哪种政策对「做出好 pattern」更好——那是 `method_critic` 的题；本文只给事实、出处和改动的代价。另外第二段（对照 tag、盲看、版本、检查次数、反馈）大部分还没造，凡写「未实现」的地方，说的是规矩写了、代码还没有。

## 1. 现在能改什么、留下什么记录

存储的共同点（`path2_web/annotation/store.py` 模块说明、spec 5.9）：每次保存新写一个批次文件，只增不改；每条操作带时间、机器名、对象编号、它依据的上一次修改（base）、**改完后的整个值**。所以文件里旧值都在、先后有序。
会话读标注只能经 `read_annotations`（`store.py:176`；spec 5.9「会话只经同一个重放读取函数读取」；项目 CLAUDE.md「不自己解析文件」），它返回当前状态、每个对象最后一次修改的引用（`revs`，含已删对象）、还能拆回的合并（`merges`）、冲突，**不返回旧值**。下表最后一列说的就是这个读法。

| 对象 | 改什么 | 界面上怎么做 | 读结果看得出改前吗 |
|---|---|---|---|
| 框 | 起止 | 点亮 `box` 拖框边；拖右边停在收了它的最早样本日（`annotateGestures.ts:207-212`） | 否 |
| 框 | 特征（换词）、属性三态、`note`、框套框 | `selection` 页（`BoxPanel.vue`） | 否 |
| 框 | 删 | 选中按 Delete 或 `delete`；同一批把它从样本成员里拿掉（`stores/annotation.ts:298`）；**无撤销** | 只看得出「这个编号删过」（`revs` 里有、状态里没有），看不出删的是什么 |
| 样本 | judgment | `selection` 页 `pos` / `neg`（`:393`） | 否 |
| 样本 | 归哪个 pattern | `selection` 页下拉，含 `unsorted` 和 `+ new`（`:413`，逐个）；整行 `move` 只在 unsorted 页（`PatternPanel.vue:62`） | 否 |
| 样本 | 成员框 | 成员链、`others`、框的 `member_of` 手动点进点出，永远算数，记 `members_edited`（`:376`） | 只看得出「手动改过」这个标记 |
| 样本 | `note` | `selection` 页 | 否 |
| 样本 | 日期 | **没有入口**；换日子只能删了重放（成员重新推断） | — |
| 样本 | 删 | `selection` 页 `delete`，框留着（`:441`） | 只看得出删过 |
| 特征 | 名字 | `features` 页 ✎，重名不改（`:471`） | 否 |
| 特征 | 合并 / 拆回 | `features` 页 `merge`（先预览）、`unmerge` | **是**：`merges` 给出那批框改前改后的值（仅限还能拆回的） |
| 特征 | 定义 | 只在空着时能写一次，写下后只读（`DefinitionField.vue`、`:460`）；意思变了另起一个词 | — |
| pattern | 新建 | 顶栏下拉 `+ new`；样本下拉、`move` 里的 `+ new` | — |
| pattern | 定义 | `pattern` 页文本框，**随时改、可清空**（`:430`） | 否 |
| pattern | 改名、删除、复制、归档 | **没有入口** | — |
| ⚑ / 反馈 / 盲看标记 | — | 未实现（反馈按 spec 6.13 将是「点记号改、侧栏删」，同样追加写） | — |

存储层只拦形状和因果（成员框不晚于样本日、成员框在这只股票上），下面三件**存储层放行、只靠界面不提供入口**（`repro/history_visibility.py` 实测）：删 pattern；样本挂到一个不存在的 pattern 名；改已有的特征定义。

真实标注的现状（`read_annotations` 读出）：1 个 pattern `new_step`（有定义）、6 只股票、11 个正样本（含待删的 SMX 2025-11-24）、11 个框、5 个词；171 个批次；历史上建过 51 个框（删了 40 个）、13 个样本（删了 2 个）。也就是说**用户已经在大量改标注**，这些修改的前后值只在文件里。

## 3. 矛盾与空白

### 3.1 现有文字对「迭代中改标注」的表态：明文允许、当成常规，没有禁止

允许或预设了「会改」的地方：
1. spec 1.2「训练段上怎么看都行：看几遍、看着 app 的结果标，都不拦也不记」；1.8 表末行同。
2. 说明书 :437「看着 app 的结果去标是你的自由、工具不记录」。
3. 说明书 ③「循环中看到新东西照样标，挂 `unsorted` 或起新名，不打断当前循环」；「发现混进了别的东西……整排 `move` 走」。
4. 说明书 ④「需要你在图上动手的（补画、收进、改 judgment），会话只提醒，由你在工具里改」。
5. spec 6.10 / 说明书 ④ 第 1 步：每轮先读「新样本、新框、改过的 judgment」——循环本身预设标注每轮会变。
6. spec 6.1 改判提问——预设用户会改 judgment，只问「理由那天看不看得见」。
7. spec 1.11 / 6.13：「你觉得不该砍的那天，用 point 放正样本」——反馈环节里明文要求补正样本。
8. 说明书第八节例子：第 4 步会话出题后用户把 TVRD 正样本「挪回 `unsorted`」（:675）；第 5 步看到对照结果后在负样本的回踩框上补一条属性（:682）；第 6 步盲看时在图上画框（:686）。
9. spec 5.9、6.12：「必须照常放行的操作：用户自己改框的起止、删样本、给特征改名、合并」。
10. spec 第 7 节：V-S1 没过、格式要改时，首批标注「只当试用」。

禁止的只有一处：**特征定义**定下不改（spec 1.3、说明书设计 3），而且它的出路正是「意思变了另起一个特征」——和用户提的「不满意只能另建新 pattern」是同一种做法，只是作用在特征一级。

所以「标注第一轮定下、之后只能另建 pattern」**与现行 spec 第 1 节（1.2、1.11）和说明书多处直接冲突**，采纳要改拍板层（spec 页首：改第 1 节先问用户）。

### 3.2 空白：改了什么，会话看不见

- 文件里有完整历史，但会话只许经 `read_annotations` 读，而它不给旧值（`repro/history_visibility.py`：改判 pos→neg、挪到新 pattern、改 pattern 定义之后，读结果里只有新值和一个文件引用）。
- 受影响的规矩：6.1 改判提问、6.10「读上次以来的变化」、6.3「是哪条改动造成的由会话在对话里说」。三条都需要「上一轮时标注长什么样」，现在没有出处可取；spec 也没写会话该自己存一份快照。
- 补法（只供核对代价，不是推荐）：
  - (a) `store.py` 的 `read_annotations` 加一个参数，只重放截止点以内的批次：重放本来就是确定的，过滤一下再重放即可；不改文件格式，不违反「会话不写标注、不自己解析文件」。估计几十行加测试。截止点要记成**每台机器从 1 起连续到齐的最大批次序号**，不能记成一个时刻或一个批次名：两台机器时，另一台时间戳更早的批次可能在会话读完之后才同步到，按时刻截会把它算成「上次已有」，它里面的改动从此永远比不出来（详见 5.2 P2）。
  - (b) 会话在每版 app 时把 `read_annotations()["state"]` 存一份（scratchpad 或随 app 进 git），下轮比对。零代码，但靠会话自律，丢了就比不出。

### 3.3 空白：pattern 定义随时可改，但它直接决定定级

- 特征定义改不了，pattern 定义却能随时改、清空（`stores/annotation.ts:430`），历史对会话不可见。
- spec 6.1 定级表第一行：「pattern 定义里已经说清——照定义定，不问。只认 pattern 定义」。改一句 pattern 定义就可能改掉某个特征的级，而会话看不出它改过（3.2）。
- spec 和说明书都没说：改 pattern 定义算不算「改意思」、要不要像特征那样另起，或者至少要告诉会话。这是对本题最直接的一处空白。

### 3.4 空白：「翻了哪几张」分不清是 app 改的还是标注改的

spec 6.3 按 app 版本存每个样本的 match，比上一版。两版之间用户若改了 judgment、成员框或框的起止，结论也会翻，却会被列成「这一版 app 翻了」。spec 没写怎么区分；有 3.2 的历史读法才区分得了。

### 3.5 空白：检查次数的「替补」认定没有记录

- 规则（spec 6.7 第 4 条）：替补上场算旧 pattern 的新版本；「标注时另外看出来的规律」才单独起算。谁判、记在哪没写；账本字段没有「替补自谁」。
- pattern 在存储里以名字为身份，没有改名功能；一个新名字在数据上和一个独立的新 pattern 无法区分。
- 如果政策是「不满意就另建 pattern」，每次另建都要做一次这种认定，这条空白就从偶发变成每轮都碰到。账本还没造，加一个字段零迁移。

### 3.6 范围比字面窄：成员冻结只防自动推断

故事 15 说「旧样本的成员冻结，以便后来补画的框不会悄悄改掉旧判断」。实际冻住的只是「自动往里加框」；成员框本身改起点、改特征名、改属性、手动点掉成员，都照样改到旧样本的依据（`member_of` 只负责让人看见会波及谁，拖右边只防越过样本日）。所以「把标注当标准锁住」不能靠冻结机制顺带实现——要锁就得另做（锁框、或改框时复制一份），工作量大。

### 3.7 文档和代码对不上（与本题相关的）

- 说明书 ③「点开某个特征的计数……整排 `move` 走」「和某个已有 pattern 对得上的行，直接多一个 `move <pattern 名>` 按钮」：都没做。pattern 页上要把样本挪走只能逐个改。
- `v-s1-notes.md:43`：删框没有撤销。物理上没丢（文件里有），但用户和会话都取不回来。

### 3.8 小空白

- 样本日期不能改，要换天只能删了重放，手动挑过的成员会丢。
- 反馈（6.13）按 pattern 名挂；审查报告 R27 只写了「以后做改名时样本和反馈一起搬」，没写「样本挪到别的 pattern 时它附近的反馈怎么办」。
- 存储层放行删 pattern、挂到不存在的 pattern、改特征定义（第 1 节）。按「只拦撤不回的」取向，这些都撤得回（只增不改），不必补拦；但若政策改成「标注锁定」，就得在存储层补。

## 4. 「另建一个新 pattern」现在要做的事、会丢的东西

以 `new_step` 为例：6 只股票、11 个样本（10 个有效）。

| 东西 | 另建时怎样 | 要做的事 / 代价 |
|---|---|---|
| pattern 名 | 新建 | 顶栏 `+ new` 起名，一下 |
| pattern 定义 | 不带过来 | 重写；没有复制功能 |
| 框、词、属性、特征定义 | 框不属于任何 pattern，词表跨 pattern 共用，**自动保留** | 无。但如果不满意的正是框：改框会连带改旧 pattern 样本的依据（`member_of` 看得到）；想保住旧的就另画一个框，新样本推断时会把新旧两个同名框都收进来（挂 `dup`），要手动点掉旧的 |
| 样本（路线 A：挪） | 每个样本只属于一个 pattern | `selection` 页逐个改归属，10 次（pattern 页没有整排挪）；**旧 pattern 被掏空**，等于没留下「标准」 |
| 样本（路线 B：复制） | 切到新 pattern，逐图在同一天再点 `point` | 6 张图、10 次点；新样本 judgment 默认 `pos`、`note` 不带过来（`RGTI 2024-12-04` 的「稳定了」要重写）；成员按默认重新推断——**实测 11 个里 3 个和现存成员不同**（QBTS 2024-12-03、RGTI 2024-12-04、SMX 2025-12-02：用户手动点掉的框又被收回来，`repro/reinfer_members.py`），要逐个再点掉 |
| 反馈（未实现） | 记录里存的是 pattern 名 | 不跟过来；会话不写标注文件，不能代搬。按反馈审查的模拟（约 15 条、约 60 下点击）就得再点一遍，否则新 pattern 少了这批回归核对 |
| ⚑、盲看标记、上一版 match、量特征结论（都未实现） | 挂在 pattern 或 app 版本上 | 不跟过来 |
| mapping 与 app | `path2_apps/<app>/mapping.yaml` 的 `pattern:` 按名字绑定，一个 app 只对一个 pattern，两个 app 写同一个 pattern 都不能用（`path2_web/mapping.py` 说明） | 会话改一行（旧 pattern 随即没有 compare），或复制 app 目录另建一个（新模块要重启后端） |

### 7.3 缺的（照用户三分法对照）

- **「此刻最该做什么」只有 `next` 一格，而且照字面做不全**：`run_session` 的第一个条件「有题要问」工具推不出来——题和回答只在对话里，工具不记（spec 6.1「工具不显示题干、不记回答」）。要做全，就得让会话往工具读得到的地方写一个状态。现成通道是 `mapping.yaml`：后端每次请求重读，审查 R8 已打算往里加账本段；`mapping.py` 现在只带出固定几个键，要加几行把新段带出（小）。
- **`next` 漏了一个推得出的信号：「app 写完之后标注又改过」**。这正是迭代里改标注时用户最需要的提示（改了要叫会话再跑一轮）。有 5.2 P2 的截止点就能算（小）。
- **`you` 一个值装了三件性质完全不同的事**：说明书写「继续标、调参，或送最后检查」——前两件随时可做、撤得回，第三件消耗撤不回的数据。三分法里它们分属「随时可以做」和「此刻该不该做要看清单」，现在没分开。
- **「随时可以做」没有任何地方明说**：哪些动作在任何阶段都可以做（画框、放样本、改 judgment、挪样本、看 compare）只散在说明书各节，页面上没有。
- **「此刻不能做」只覆盖控件级**（变灰的按钮、拖不过去的框边）；流程级的「不能」——例如盲看这一版没做完不该调参、进门清单没过不该送检——spec 都写成「建议」而非拦截（6.7「清单没过，用户坚持送也可以」），页面上也还没有任何呈现。
