# Write User Doc Skill

只做一件事：**产出给人读的白话版**，目标是让用户用最小的心智负担把事情看懂。

**输入是什么都行**——一份已有的报告、一段没有任何文档沉淀的代码、一次对话里讨论定的结论。没有可翻译的底稿时就自己把机制讲清楚，不要因为"没有机器版"而拒绝。

**不负责给 AI 读的文档**：研究报告（`docs/research/` 下的 `final_report.md` 等）、实施计划（`docs/tmp/` 的 plan）读者是下一轮没有本次对话上下文的 session，谁做研究 / 谁定方案谁写，不走本 skill。用户要的是"给我看懂"，才是本 skill。

## 与 AI 上下文的边界

本 skill **绝不**写入根目录的 `CLAUDE.md` 或任何 `CONTEXT.md`。如果用户请求的是"维护 AI 上下文"/"刷新代码地图"/"提炼模块意图"，应使用 `update-ai-context` skill；如果是"术语该怎么定义"，应使用 `/grill-with-docs`。

## 白话版的硬要求

- **自包含**：读这一份就能做决定，不必打开底稿。底稿可能是临时的（`docs/research/` 实施完就删），指过去的引用会失效，所以关键事实要抄进来。
- **头部标注来源**：从哪份文件、哪个版本（日期）翻过来的；没有底稿就说明是从代码还是从对话来的。
- **先结论后推导**：开篇给一句话版本，然后才是为什么。数字压进文末附表，正文只留读得懂的话；指标名要么翻成大白话，要么进附表。
- **能出图优先出图**：流程用 Mermaid（`flowchart`，节点文字用 `["..."]` 包住、换行用 `<br/>`）；数据分段、时间轴这类用 ASCII 框图，终端和编辑器里都能看。
- **组织**：概览 → 流程图 → 宏观逻辑 → 细节 → 局限 / 下一步。

## 术语与出处

判据在根目录 `CLAUDE.md`「用户指令映射」节（词的来源决定待遇），这里只讲做法。读者是项目主人，但**不是词表的日常使用者**——`CONTEXT.md` 的词是谈定当场写进去的，几周不用就记不起来。

- **开头列一张词表**：正文要反复出现的词一次列全，每行「词 → 一句话意思 → 出处」；出处写 `path2/CONTEXT.md:82` 这种形式。文档正文里引用时用 Markdown 链接指到文件或大节即可（词条是 `**词**：` 格式、不是标题，锚点到不了具体词条）。
- **词表只收真会反复出现的词**，一般 5～8 个；只出现一次的概念就地讲清楚，不进表。
- **涉及某个 skill 管的领域时，先查它有没有人话译法表**（`.claude/skills/tune-gates/SKILL.md` 第三节是范本）。表上左列的词一个都不要出现在文档里——**在词表里给它加注解不算数**，正文每出现一次读者就得回头查一次。
- **项目外引进来的概念**（统计方法、文献术语）不出现名字，只讲它在这件事里起什么作用；只有这一类可以打比方。

## 放哪、叫什么

- **有底稿**：和底稿同目录并排，`<底稿名>_白话版.md`（如 `final_report_白话版.md`）。两者同生共死——研究目录删掉时白话版一起删。
- **没有底稿**（解释代码、对话结论、临时方案）：`docs/explain/<主题>_通俗解释.md`。这类是长期的。

## 允许的内容

- ✅ 历史演进、"曾经尝试过 X 但失败"
- ✅ 未来规划、待解决问题、多个备选方案
- ✅ 推导过程、思考脉络、权衡分析
- ✅ 非当前代码状态（讲的是某个时间点的快照）

## 流程

1. 认出底稿是什么（一份文件、一批代码、还是本次对话），读完再动笔——不要只读摘要就翻译。
2. 按「术语与出处」把要用的词过一遍：grep 词表拿行号，查相关 skill 有没有人话译法表。
3. 写：开篇一句话版本 → 词表 → 正文（概览 → 图 → 机制 → 细节）→ 局限 → 附表。
4. 写完告诉用户路径，并用三五句话说清这份文档回答了什么。
