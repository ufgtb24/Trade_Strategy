# 多流引用翻译机制设计

> 2026-09-01 · 承接 `docs/research/2026-09-01_multistream-tendency/final_report.md`（倾向方案③）
> 解决的问题：方案③（同一 detector 同趟产多流）下，同源流之间的事件引用（如 BO 引用它突破的 PK、PK 引用它吃掉的 PK）如何获得精确的 `instance_id`。
> 所有行号基于 commit `50dbc16`。

---

## 一 · 核心洞察

**同源多流引用与现有跨 detector 引用，本质差别只有一个：被引用流是否已完整物化。**

- instance_id 在整条流 `run` 结束、`annotate_stream` 之后才分配（`engine.py:138`）。
- 跨 detector（不同 run、逐次产生）→ 上游已物化 → 下游 detect 期读得到。既有先例：`tb_v1.anchor_bo_id = last_bo.instance_id`（`throwback_v1.py:274`）。
- 同 detector 多流（同 run、同时产生）→ 谁都没物化 → detect 期谁都读不到谁的。

**翻译机制 = 把「引用解析」从 detect 时刻推迟到标注时刻。** 让同一趟产出的多流在全部物化后获得精确引用。

---

## 二 · 核心机制：对象引用 + 标注后翻译

detect 内部用**事件对象引用**作临时索引，引擎在标注阶段翻译成 `instance_id` 字符串。

```
detect 内部：
  peak = PeakEvent(index=..., ...)                    # 峰事件对象
  yield ("pk", peak)                                   # 进 pk 流
  bo = BOEvent(referenced_events=(peak, ...), ...)     # 直接引用对象
  yield ("bo", bo)

标注阶段：
  所有流标注完 → 每个对象已有 instance_id
  bo.referenced_event_ids = (peak.instance_id, ...)    # 对象 → 字符串
```

**为什么对象引用是最自然的临时索引**：detect 内部本来就有这些对象；对象即身份；标注后查 `{obj: instance_id}` 即得。不需要人为造序号，也不需要知道编号规则（`instance_id` 的 idx 依赖事件的 start/end、非产生顺序，人造序号会错）。

**职责分离**：`referenced_events`（对象，中间形态）只存在于 detect 内部与翻译前；序列化只走翻译后的 `referenced_event_ids`（instance_id 字符串），发布形态与现状渲染层兼容。

---

## 三 · 判断依据：字段类型驱动，非构造函数声明

**引用关系是「代码里发生了什么」的事实，不是「作者想声明什么」的意图。** 主机制用类型驱动：

- 事件约定一个引用字段（如 `referenced_events: Tuple[Event, ...]`）
- detect 填了对象引用 → 引擎必然翻译；不填 → 空、无操作
- **零声明、零漂移、零遗漏**。若靠构造函数声明「bo↔pk 有引用」，「声明了但没引用」「引用了但没声明」都会成静默 bug——后者尤其危险（翻译漏掉，前端退回归一解析）。

**用户建议的构造函数声明，改作可选防御性校验**（不承担功能开关）：

- detector 在 `produces` 里注明引用方向（如 `referenced_flows = {("bo" → "pk")}`）
- 引擎翻译后核对：声明有引用但实际空、或有引用但未声明 → 报错
- 这样声明只做诊断，翻译不依赖它，避免「声明 vs 实现」漂移成为新故障源。

**多流之间没有引用时**：引用字段为空，翻译无操作，零成本——不需要任何开关或判断。

## 四 · 翻译时机：统一标注 + 统一翻译（两阶段）

**推荐「全部标注完成后统一翻译」。不选「标注过程中翻译」，也不用「逐流分别标注再翻译」。**

| 候选 | 问题 |
|---|---|
| 标注过程中翻译（边标边翻） | 同次 run 产出所有流，run 结束前一条都没标注，不存在「边标边翻」的可行起点；且隐含「被引用对象先标」的顺序约定，双向/同流引用无解 |
| 逐流分别标注再翻译 | 单向引用可行（先标 PK 再标 BO），但**同流引用**（PK 吃 PK，都在 PK 流里）与**双向引用**有先手问题——标 PK 流时部分对象同时被 BO 流引用，翻译归属混乱 |
| **统一两阶段（推荐）** | 先给所有流所有事件编 instance_id，再统一扫描翻译。此刻任何引用方向（跨流/同流/双向）都安全，被引用对象必然已标注。逻辑最简单、最健壮 |

```
阶段1（标注）：对 {流名: [events]} 逐流 annotate_stream（现状逻辑，不翻译）
阶段2（翻译）：跨所有流扫描引用字段，obj → obj.instance_id；写入 referenced_event_ids
```

---

## 五 · 健壮性边界

- **引用到事件池外的对象**（detect bug，如引用一个被丢弃的峰）→ 翻译阶段 `ref.instance_id is None` → **报错**，不当静默忽略（静默会污染渲染）
- 空引用 → 无操作
- 同流引用、双向引用 → 统一翻译覆盖

## 六 · 与现有机制的全景关系

| 引用场景 | 机制 | 例子 |
|---|---|---|
| 跨 detector（不同 run，逐次产生） | **逐流交错标注**（现状） | `tb_v1.anchor_bo_id = last_bo.instance_id` |
| 同 detector 多流（同 run，同时产生） | **统一标注 + 翻译**（本设计） | BO→PK 跨流、PK→PK 同流 |

instance_id 的可得性统一成一条规律：**流完整物化之后引用才可解析**。翻译机制只是把「同源未物化」的引用解析推迟到物化完成。

## 七 · 与「缺失 X」的关系

本机制天然是「缺失 X」（一对多跨流引用的一等化，见三方案评估 `final_report.md` §8.3）在「同源多流」场景的实现：

## 九 · 协议形态定稿：`ref_slots()`，与 `child_slots()` 同构，零 dag_spec 声明

> 2026-09-01 补记。§二/§四 的 `referenced_events: Tuple[Event, ...]` 单字段是概念原型；**本节约定最终协议形态**，比原型更完整。

**先核实一个前提**（决定协议形态的关键）：`segments` 不是「协议挂靠的变量」，而是**事件类的事实**。`engine.py:54-63` 的 `_annotate_children` 从 `e.child_slots()` 取槽名，`child_slots()` 是 `Event` 基类方法（`core.py:115`），dag_spec 的 `children={"segments": "tb_seg"}` 只是**给已存在的槽配一个子 node_id**（决定子事件 instance_id 前缀归属）。**唯一事实源在事件类，声明只是归属。**

⟹ 协议的载体在**事件类基类**上，不在 dag_spec。多流引用协议 = 与 `child_slots()` 同构的第二个方法 `ref_slots()`：

```python
# core.py —— Event 基类
def child_slots(self) -> Mapping[str, Event | Tuple[Event, ...]]:
    """子事件槽位（标注归属）。默认空。"""
    return {}

def ref_slots(self) -> Mapping[str, Tuple[Event, ...]]:
    """引用槽位（翻译身份）。默认空。"""
    return {}

# 具体事件类
class BOEvent(Event):
    broken_refs: Tuple[Event, ...] = ()
    def ref_slots(self):
        return {"broken": self.broken_refs} if self.broken_refs else {}

class PeakEvent(Event):
    eaten_refs: Tuple[Event, ...] = ()
    def ref_slots(self):
        return {"eaten": self.eaten_refs} if self.eaten_refs else {}
```

引擎标注后统一扫描 `ref_slots()`：每个槽的引用对象若已标注 → 直接用；未标注（同源）→ 翻译成 instance_id，填 `{槽名}_ref_ids`。语义（broken/eaten）由槽名承载，与 `segments` 的「槽名语义化」同款。

**为什么零 dag_spec 声明——比 children 更纯粹**：

| | children（子事件） | ref_slots（引用） |
|---|---|---|
| 载体 | `Event.child_slots()` | `Event.ref_slots()` |
| 被引用物已有身份？ | **没有**——子事件不在独立流里，须挂父 node 名下才有 instance_id | **有**——被引用事件自己就是流里的独立事件，已有 node 归属 |
| dag_spec 需声明 | `children={槽名: 子node}`——配归属 | **无**——引用不改变被引用事件的归属 |
| 事实源 | 事件类 `child_slots()` | 事件类 `ref_slots()` |

`children` 要 dag_spec 声明，是因为子事件需要自己的身份前缀、必须有人告诉引擎「segments 槽归 tb_seg 名下」；多流引用的被引用事件**身份已经存在**（自己在 bo/pk 流里独立），引用只是「A 指回 B」。所以**纯事件类事实驱动，零声明**——「唯一事实源」哲学的彻底版。

## 十 · anchor_bo_id 的定位：另一类引用协议，不迁移到 ref_slots()

**使用链核实**（commit `50dbc16`）：
- 赋值侧（detector 内部，4 个 tb 版本同款）：`throwback_v1.py:274` / `throwback_v4.py:288-297` / `throwback.py:338` 都是 `src_id = last_bo.instance_id` → `anchor_bo_id=src_id`
- 字段声明：每个 tb 版本事件类各写 `anchor_bo_id: str = ""`（如 `throwback_v1.py:211`）
- **消费侧是引擎协议**：`TemporalEdge.anchor_field`（`edges.py:46-101`）——「dst 端 anchor_field 等于 src 端身份的复核约束」；`_solve.py:12,78,91-92` 把 anchor_field 非空边的 src 节点加入求解（B4）

**结论：anchor_bo_id 已经是「半协议」，且走的是另一类引用协议——不应迁移到 `ref_slots()`。**

两类引用协议的本质区分：

| | anchor_field 边协议（现状） | ref_slots 事件协议（本设计） |
|---|---|---|
| 层级 | **边级**（TemporalEdge 声明 + `_solve` B4 消费） | **事件级**（事件类声明 + 引擎翻译） |
| 被引用物物化状态 | **已解析**——跨 detector，交错标注在 detect 期已给 instance_id，直接 `last_bo.instance_id` | **待解析**——同源未标注，须存对象、标注后翻译 |
| 语义职责 | **校验边的两端身份一致**（这条边是否真如声明连接） | **表达引用并解析身份**（A 指回 B） |
| 例子 | `tb.anchor_bo_id` | `bo.broken_refs` / `pk.eaten_refs` |

**为什么不该迁移**：
1. **ref_slots 的核心价值对 anchor_bo_id 无用**——它的价值是「同源未标注场景的翻译」，而 anchor_bo_id 交错标注已给，detect 期直接读 instance_id 是**更短**的路径（存对象 → 引擎翻译 → 边再读，是绕路）。
2. **消费侧不同**——anchor_bo_id 被 TemporalEdge.anchor_field 边校验消费，那是「边的身份复核」语义；ref_slots 是「事件的引用表达」语义。强行统一会模糊两者的分工。
3. **迁移成本不对称**——要改 4 个 tb 版本的事件类 + detect 侧 + TemporalEdge 消费侧（字段名从 `anchor_bo_id` → 翻译后字段），收益只是「统一性」。

**真正值得记下的标准化机会（可选，不阻塞）**：4 个 tb 版本各写一行 `anchor_bo_id: str = ""` 是重复声明，若想消除可提「已解析单值引用」的公共基类字段。但它是「已解析引用」的公共字段，**不是**待翻译的对象引用——与 ref_slots 是两码事，且重复度低（一行），优先级不高。

**全景定论**：path2 有两类引用协议，各有适用场景——
- **跨 detector 已解析引用** → anchor_field 边协议（现状，够用，不迁移）
- **同源待解析引用** → ref_slots 事件协议（本设计，补多流缺口）

两者互补，共同覆盖「instance_id 可得性 = 流完整物化之后引用才可解析」这条规律的两侧。
