## #1 · solve 取候选：预排序 + 二分定位窗口（2026-06-08）

**位置**：`path2/dag/_solve.py` → `_lef_dfs` 候选生成 `:221-222`（`_any_dfs` 对称 `:351-352`）。

**现状**：每次填角色 v，候选 = 从 `ptr[v]` 到流尾**线性扫整个后缀** → 过滤 `start ∈ [lo,hi]` → 再 `sort((start,end,原始下标))`。即每个 DFS 节点都 `O(后缀长度)` + 一次 sort。

**优化想法**：流的 event 提前按 `start` 排好，则取窗口候选可**二分定位**（`O(log n + 窗口内数)`），并**省掉每次的 sort**。

**技术要点 / 陷阱（实施时必须处理）**：
1. **按 `start_idx` 排，不是笼统"时间"**——event 有 start/end 两个端点，候选过滤看的是 `start`（`:221`）。
2. **现状流是 `end` 排序**（`run()` 只保证 `end_idx` 升序、`start_idx` 可非单调，见 `kleene_bind` 注释 `:131-134`）。`end` 序被 `ptr` / `reify` / `kleene_bind` 的坐标系依赖——**别动流本身**，而是额外预建一份 `(start, end, 原始下标)` 的 start-sorted 索引。
3. **不能纯二分一刀切**：取候选有**两个**过滤条件——`start∈[lo,hi]`（窗口）+ `原始下标 ≥ ptr[v]`（非重叠消费前沿）。`ptr` 按原始下标（= end 序）定义，在 start 序里"已消费"的 event 是**散布**在窗口内的；二分定位窗口后**仍要在窗口内逐个过滤 `ptr`**。所以收益是"遍历范围从整个后缀缩到窗口内"，**不是**"完全不遍历"。
4. **窗口 `[lo,hi]` 是动态的**（每次填 v 由已填前驱决定，`:191-194`）——预排序只能加速"每次怎么取候选"，**不能**把候选集合预算出来。

**最小侵入方案**：每个流预建 start-sorted 索引（一次性）→ 候选生成改为「二分窗口 → 窗口内过滤 `ptr` + `where` + `C1`」→ **不动流的 end 序 / 不动 `ptr` 语义 / 不动 Kleene 路径**。可用现有匹配做回归（结果须逐 match 不变）。

**暂缓理由**：
- 收益只在「窗口 ≪ 后缀」时显著；`max_gap` 大（窗口宽）则窗口内候选接近整个后缀，省不了多少。
- **真瓶颈未确认**——流不长 / DFS 不深时，`O(后缀)` 线性扫未必是热点，开销更可能在 `satisfies` 充要复核（`:234`）/ `reify` / 上游 detector。
- 改动牵涉 `Kleene / where / C1 / ptr` 交互，有引入**漏匹配**风险。

**状态 / 下一步**：**暂不优化**。先用真实全集扫描 profile「取候选 / satisfies / reify / detector」各自耗时占比，确认取候选确为热点后，再按最小方案实施。
