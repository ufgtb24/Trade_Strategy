# simplicity：v3 的复杂度与可用性红队 + 防过度设计守门

日期：2026-10-05。所有项目内路径相对 repo root。读者：AI（lead 与队友）。
证据档：**已验证**（读代码 / 跑复现 / 查 git 与数据）、**推理**（由已验证事实推出，未实测）、**推测**（合理但缺证据）。
复现：`docs/research/2026-10-05_tune-gates-v3-design-review/repro/simplicity_repro.py`（合成数据、临时账本；4 个测试全部通过：`uv run python -m pytest -q -p no:cacheprovider <该文件>`）。v3 自带的 143 项测试也全部通过（已验证）。

## 0. 一句话结论

v3 把旧版里**服务于旧架构**的复杂度大量删掉了：长表、一致性验证、筛选族、稳健区、四种指纹。这部分删得对。代码从约 1.08 万行降到约 1600 行，用户需要拍板的次数从 3~4 次降到 0~1 次。

但 v3 新增或保留的**治理机制**有几处在主线 app 上会直接把流程卡死：

- 复核的结论事先已定死；
- 代码指纹几乎必然阻断验证；
- 行情没更新就跑验证，会把这段数据作废；
- 阶段之间还有一段约 3 个月的空档（可选修，见 S6）。

此外，自然说法的触发词仍指向旧版，4/5 的 ADR 和 3 份白话说明已经过期。

**这些修法以「删 / 改一两行 / 改文档」为主，没有一条需要新增机制。**

队友建议去重后共 11 条，裁决结果（§6）：9 条保留，其中 1 条只报告；1 条部分降级；1 条不加。全队的改动合起来是「净删除」：

- 删掉统计折扣、「确认」状态、两道绝对下限和两道绝对数量下限；
- 复核沿用最后验证的规则；
- 新增只有两样：一个只报告的分辨力数字，和几句文档。

我自己的 S6（取消阶段空档）经 selection 挑错后，降为可选项。

## 1. 结论（按严重程度排序）

### S1. 「暂用→到期复核」在实现里退化成「暂用→到期必然恢复原参数」——已验证

- **证据**：
  - `comparison()` 恒给 `evidence_sufficient=False`、`improvement_lower/upper=None`（`.claude/skills/tune-gates-v3/scripts/scoring.py:434-436`）。
  - `adoption()` 在 `stage="review"` 时：确认分支要求 `evidence_sufficient`，永远到不了；暂用分支要求 `stage == "final"`，复核阶段也进不去。剩下只有 `rollback`（`scripts/governance.py:381-396`）。
  - 复现 R1：复核段新参数方向分 1.0（全部先上），原参数 0.0，要求全过，结论仍是 `rollback`。R1b 把复核阶段所有可能的 metrics 组合枚举了一遍，输出全是 `rollback`。v3 自带测试同样断言复核结论为 rollback（`tests/test_run.py:105-106`）。
- **失败情形**：
  - 一个真改善的候选通过最后验证、暂用、写进正式参数。几个月后跑复核，不论新数据多好都被恢复。
  - 为此付出的代价：预留一段新数据并把它永久消耗；等待一个完整的未来期限（bb 上约 6~10 个月，见 §4）；正式参数写两次。整套复核机制都不承担任何决策作用：复核预留、复核计算、撤回落地流程（`references/runbook.md:39-50`）。
- **与用户方向的冲突**：ADR 0004 要求「暂用前固定后续复核的数据、时机、**确认与撤回规则**」（`docs/adr/0004-tune-v3-provisional-adoption.md:12`）。白话说明的流程图写「暂用到期：新数据支持则确认」（`docs/explain/tune-gates_v3纲要_通俗解释.md:32`），伪代码写「if 规则支持确认改善: 确认采用」（`docs/explain/tune-gates_v3伪代码_通俗解释.md:86-87`）。而用户被告知的说法是「预定复核仍不足确认则恢复原参数」（`docs/research/2026-10-02_v3-bb-training-calibration/final_report_白话版.md:65`），这句话本身没错，但没有点明「当前不可能不足以外的结果」。**推测**：用户以为复核能转正。
- **取舍（需用户拍板，因为它决定参数何时变成永久）**：

| 选项 | 改动 | 真实效应为零的候选被永久留下的概率（推理，按噪声对称、两段独立） | 真改善被留下的概率 | 复杂度 |
|---|---|---|---|---|
| 现状 | 0 | 0% | 0% | 整套复核机制都在，但不起作用 |
| A：复核沿用最后验证的同一条规则（要求全过且观察到改善 → 继续用；状态名用「继续使用」，说明写「两次独立观察均改善，非统计确认」） | `governance.py` 复核分支约 3~5 行，改 3 条测试的期望值，文档改几句 | 约 25% | Φ(δ/σ)² | 不增加任何机制 |
| B：删掉复核，暂用即采用，下一轮调参时自然重评 | 删 review 预留、复核阶段、撤回流程，约 −40 行代码、−2 段文档 | 约 50% | Φ(δ/σ) | 最省，但违背 ADR 0004 |

  **量级**（selection 的推算，正态近似，忽略下限与平局；`selection.md` 第 11 节）。零效应被留下的概率**不会**因为样本变大而下降：只看「是否改善」的检查，对零效应永远是抛硬币，两关都过约 25%。256 股时的模拟值是 16%，比 25% 低，只是因为机会下限和平局多拦了一些。样本变大改善的是对非零效应能否判对方向：

| 每段的配对噪声 | 变差 0.03 被留下 | 零效应被留下 | 改善 0.03 被留下 |
|---|---:|---:|---:|
| 0.083（256 股） | 13% | 25% | 41% |
| 0.04（全池，缩放只兑现一半） | 5% | 25% | 60% |
| 0.018（全池，按出买点的股票数推算，属下限） | 0.2% | 25% | 91% |

  推荐 A。它是让代码兑现 ADR 0004 的最小改动；与 B 相比，零效应候选被永久留下的概率减半，代价只是多一段等待。为什么更简单的做法不够：B 违背用户已拍板的方向；现状则让一整套机制空转，白白消耗新数据。对用户的说法用 selection 的版本：「扩大股票池后，变差的改动几乎不会被留下，真有约 0.03 改善的改动大多能留下；零效应的改动仍有约四分之一被留下，但按定义它没有坏处。」

### S2. 代码指纹几乎必然阻断最后验证与复核，而且没有回退把手——已验证（阻断机制）+ 已验证（git 节奏）+ 推理（外推）

- **证据**：
  - `source_hash` 对 `path2/`、`path2_apps/`（全部 app，含历史与实验残留）以及 skill 脚本里所有 `.py` 求哈希（`scripts/run.py:59-68`）。
  - `run_check` 发现哈希不一致即拒绝，最后验证和复核都受这条限制（`run.py:386-387`）。
  - 冻结记录只有 `config / config_hash / run_id / source_hash`，没有 git 提交号（`run.py:300`，复现 R3 已断言）。
  - 过去 4 个月，path2 与 path2_apps 的 `.py` 改动日期是 06-26、07-03、07-19、08-03、09-03、09-06、09-15，相邻两次最长间隔 31 天（`git log --all`）。
- **失败情形**：bb 系的最后验证最早要到 2027-02（§4）。在这段时间里，只要改过任何一个 app 或 path2 的一行代码，甚至只是未提交的本地改动，验证就被拒。想恢复，只能找一个文件内容哈希恰好等于记录值的提交；如果搜索时有未提交改动，这个提交根本不存在。好在拒绝发生在使用记录写入之前（`run.py:386` 早于 `:397`），数据不会被作废，但这一轮走不下去了，预留的区间要一直占到 `abandon` 为止。
- **最小修法**：冻结时多记 `git rev-parse HEAD` 和一个「工作区是否干净」标记（约 3 行）；runbook 补一句「哈希不一致时，在该提交的 worktree 里跑 validate，`TUNE_LEDGER_DIR` 指向主目录」。
  - (b) 代价：约 3 行代码、2 句文档，用户不需要多付出注意力。
  - (c) 为什么更简单的不够：直接删掉这道守卫，会让「搜索时的检测代码」和「验证时的检测代码」悄悄不一致，验证的就不是当初冻结的那个候选；把哈希收窄到该 app 实际 import 的模块，需要做依赖分析，反而更复杂。

### S3. 行情文件没更新就跑最后验证，这段数据被永久作废，而实际上没看到任何结果——已验证

- **证据**：`run_check` 先写使用记录（`run.py:397`），再建评价器读数据（`:398-400`）；行情不齐在 `daily.py:216-221` 报错。之后再跑，`claim` 拒绝「这轮的该检查已经消耗」（`governance.py:314-315`）。复现 R2 已走通这条路径。文档把它写成有意为之：「文件滞后时失败并保留使用记录」（`SKILL.md:43`）。
- **失败情形**：系统日期已经过了验证段的标签截止日，用户却还没下载新行情（这个项目的数据靠手动从 Yahoo 拉）。agent 照「到期了」去跑 validate，结果整段等了数月的新数据作废，这一轮也作废。这种情况很可能发生：判断「到期」的依据是日期，而数据是否到齐是另一件事。
- **修法**：把「每只股票的行情是否到齐」这一检查挪到写使用记录**之前**。只读每个文件的最后日期，不看涨跌，不构成数据暴露。净增约 5 行，主要是挪位置。
  - (c) 为什么更简单的不够：只在文档里写「先更新行情」，仍然依赖 agent 自觉；而违反一次的代价是数月的数据。

### S4. 自然说法触发的是旧版，v3 实际上只能靠点名进入——已验证

- **证据**：
  - 旧版 description 含「调一下 XX 的参数」「继续调 XX」「新数据来了…还成立吗」，并自称「唯一编排入口」（`.claude/skills/tune-gates/SKILL.md:3,8`）。
  - v3 的触发词是「用 v3 调参」「Optuna 调参数」「启用统计折扣」「结合新旧方法调参」「复核 v3 暂用参数」（`.claude/skills/tune-gates-v3/SKILL.md:3`）。
  - `authoring-path2-app` 把纯调参转给 `tune-gates`（`.claude/skills/authoring-path2-app/SKILL.md:36`）。
  - 另外两处问题：「结合新旧方法调参」对应的能力在 v3 里并不存在，v3 明令新旧两版不能在同一 app 上同时跑（`SKILL.md:27`），属于误导性触发；「统计折扣」是设计讨论里造出来的词。
- **失败情形**：用户说「调一下 bottom_burst 的参数」，进入的是旧版：8 阶段、3 个停点、稳健区。用户以为自己在用 v3。
- **取舍（需用户拍板默认版本）**：若以 v3 为默认，把自然说法的触发词移到 v3，旧版 description 收窄到「旧版 / 稳健区域 / 这道闸该不该删」，并把 authoring-path2-app 的转发目标改成 v3。代价是改 3 处 description，0 行代码。注意：旧版**目录不能整体删除**，因为 feature-study 按路径加载旧版的 `inference.py` / `budget.py`（`.claude/skills/feature-study/SKILL.md:26`）。

### S6.（经 selection 挑错后降为可选）阶段之间强制空出「首部缓冲」，代价约 3 个月，泄漏风险只在一种路径上——推理（泄漏分析）+ 已验证（日期计算）

- **证据**：
  - `normalize_config` 要求「训练的 label_end < 最后验证的 history_start」「最后验证的 label_end < 复核的 history_start」（`run.py:229-231`）。
  - 使用记录登记的暴露区间从 `history_start` 开始（`run.py:266-270`），新鲜度检查也按这个区间算（`governance.py:235-239`）。
  - bb 的首部缓冲是 63 个交易日（`path2_apps/bottom_burst/dag_spec.py:95`，实测 `eval_meta` 输出 63）。
- **推理（selection 已复核同意）**：同一轮内部，阶段按「训练 → 最后验证 → 复核」前向排列。最后验证段的预热历史只用来算买点**之前**的特征，所以就算它和**本轮训练段**的标签尾部重叠，选参也不会因此看到最后验证段的结果。
- **selection 指出的修正**（`selection.md` 第 11 节，均接受）：
  1. 预热段仍**不能**读进**其他轮次或同谱系旧账本中尚未消费的预留区间**：预热读到的价格，可能正是别人最后检查买点的后续表现。所以只能放宽「对已消费数据」和「对本轮自己训练」的冲突判断；对他人未消费预留的判断，仍要覆盖完整的 `[history_start, label_end]`。
  2. 改动不止 6 行：账本要同时记两个起点，记录格式要升级，`run.py:266-270`、`governance.py:325-327`、`governance.py:235-240` 三处判断都要分别改。粗估 15~25 行，另加测试。
  3. 默认回看要取**整个搜索范围内**的最大首部缓冲，不能固定为 63，否则加长回看的候选开头会少买点（`daily.py:269` 是按每组参数各自取的）。这一条不是泄漏问题，是公平性问题。
  4. 去掉空档也就去掉了一条隔离带，相邻时段的动量相关可能让检查略偏乐观（推测，量级小）。
- **代价与收益实算**（NYSE 日历，H=40，最后验证段买点窗 21 个交易日）：

| 规则 | 最后验证最早出结果 | 复核最早出结果 |
|---|---|---|
| 现规则 | 2027-02-16 | 2027-08-13 |
| 放宽，但把 bb_v1 的向前确认窗（2026-03-03..08-17）当作「未消费预留」继续保护（selection 的口径） | 2027-02-12（几乎不省） | 2027-05-12（省约 3 个月） |
| 放宽，且承认该确认窗已被 bb_v1 自己的 discover 记录烧掉（2022-09-01..2026-06-19，标签到约 2026-08-18），不再需要保护（我的口径） | 2026-11-12 | 2027-02-11 |

- **裁决**：从「推荐」降为「可选」。
  - 收益：确定能省的是「最后验证 → 复核」之间约 3 个月。最后验证端能不能也省 3 个月，取决于一个口径问题：一段已被旧版自己烧掉的预留，还需不需要保护（见 §7 分歧 3）。
  - 代价：15~25 行代码加一次账本格式升级。
  - 结论：在用户拍板 S1（复核是否有决策作用）之前不值得做。S1 维持现状的话，复核本来就注定撤回，提前 3 个月也没有意义。
- **与 S8.1 拆开**：「history_start 默认取 start 往前推『搜索范围内最大首部缓冲』个交易日」这一条**独立保留**（约 5 行，删掉一个人工决定）。在现规则下，如果默认值与上一阶段冲突，配置检查会在任何数据被读取之前就报错（`run.py:229-231` 在 `normalize_config` 里），所以是安全的。

### S7. 「统计折扣」应整体移出正式 skill——已验证

- **证据**：
  - 用户在校准任务里定下的规则是「**折扣确实有帮助才加入；证据不足就先采用基础分**」（`docs/research/2026-10-02_v3-bb-training-calibration/原始问题.md`）。
  - 真实比较的结论是「未展示统计折扣改善选参」：fold1 两种评分选了同一组，fold2 没有可行候选（同目录 `final_report.md` §1、§3）。
  - 但它仍以「默认关闭的实验开关」形式进了正式 skill：`scoring.py:36-59, 62-103` 约 66 行，`tests/test_shrinkage.py` 145 行，`method.md:54-75`、`configuration.md:74-90` 约 40 行文档，`SKILL.md:20,61,70`，外加一个触发词「启用统计折扣」。
- **删掉会在什么情形出错**：说不出来。它默认关闭，默认流程完全不受影响；需要时 git 历史和研究目录里都有完整实现。
- **代价对比**：删除可减约 210 行代码和测试、约 45 行文档，少一组概念（τ、相关跨度、保留比例、工作误差、三种退化状态），少一个误导性触发词；报告字段也会变少。保留的代价是：每次读 SKILL 都要多消化一段不会生效的规则，用户也可能被触发词引去打开一个未经验证的选项。

### S8. 几个「一失手就烧数据」的配置坑——已验证（代码路径）+ 推理（发生概率）

1. **省略 history_start → 最后验证段整段落在预热期**：
   - 省略时 `history_start = start`（`run.py:223`），评价器从 start 起裁数据（`daily.py:204-206`），前 63 个交易日的买点被排除（`daily.py:300`）。

   - 配置检查只核对交易日数是否不少于 21（`run.py:243-246`），不核对缓冲。
   - 修法：history_start 默认取「start 往前推『搜索范围内最大首部缓冲』个交易日」，约 5 行，独立于 S6 保留（见 S6 末条）。
2. **最后验证段买点数不足 30**：最后验证沿用训练的全部硬要求，包括 `min_buy_days=30`（`scoring.py:367-381` 经 `comparison→assess`）。段太短或股票池太小，就会被确定地拒掉。文档没有提示（`configuration.md:45` 只说至少一个评分窗口）。修法：若采纳 objective D3 / selection D3（全局删掉「≥30」，只保留「≥原参数一半」），这个坑随之消失，不必另写文档。
3. **在 worktree 里跑**：

   - 各 worktree 的账本副本互相看不见对方的使用记录，要等合并才同步（推理）。
   - 修法：SKILL 加一句「只在主目录跑，或把 `TUNE_LEDGER_DIR` 和运行目录指到主目录的绝对路径」。0 行代码。

## 7. 分歧与已解决的争点

1. **删统计折扣的代价**（selection 提出）：会失去训练里唯一一个针对「挑最大值偏向噪声大候选」的手段。
   - **处理**：我接受这个代价，不改裁决。理由是它在真实对照里没改变过任何一次选择；病根是「噪声相对效应太大」，A1 与 N1 直接对着病根。
   - 状态：已记录，无进一步分歧。
2. **D3 的范围**：selection 原提「只在最后验证和复核里不查」，我主张全局删。
   - selection 已同意，并补充了一点：「≥30」在训练里唯一多出来的作用，是原参数买点稀疏时把候选全部卡死，这和 M2 是同一类毛病（用现役参数自己也不满足的条件去拒绝候选）。
   - 状态：已解决。
3. **S6 的口径（未解决，影响小）**：一段已经被旧版自己的 discover 记录烧掉的预留（bb_v1 的向前确认窗 2026-03-03..08-17），还需不需要当作「未消费预留」保护起来，不让别的 app 拿去做预热？
   - selection 的口径（保护）：bb 第一次最后验证不省时间，2027-02-12 出结果。
   - 我的口径（不保护：预留的目的是让数据保持没被看过，已经被看过就没有可保护的东西）：2026-11-12 出结果。
   - 建议：S6 本身是可选项，在用户就 S1 拍板前不做，这个分歧不必现在定。如果要做，按保守口径（selection）先实现，省下的复核端 3 个月不受这个分歧影响。
4. **零效应被留下的概率**（已纠正）：我原先暗示扩大股票池会降低这个概率。selection 纠正：只看「是否改善」的检查，对零效应永远约 25%；扩大样本只改善对非零效应的判断。我接受纠正，S1 节已改用 selection 的表和对用户的说法。
5. **N1 的措辞**（objective 自己修正）：原参数自身的波动约为相近候选配对差的两倍。所以报告不把 X 说成「两套参数能分辨的差」，只说「偶然波动约 ±X，相近参数之间的差别一般是它的一半左右」，避免夸大分辨难度、误发提醒。我同意。
6. **N1 与 selection「不建议开跑前分辨力闸」**：两者不冲突。N1 只报告，不阻断、不进采用规则；selection 反对的是门槛。已一致。
