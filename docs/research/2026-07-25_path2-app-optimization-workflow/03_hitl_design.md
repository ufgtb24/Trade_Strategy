## 0. 结论摘要（先给判断，论证在后）

> **前置 · 本节工作的权重来自 `biz` 的一个实测**：他做了 16 个单旋钮扰动 × 2 个整年窗（34 次全宇宙 eval），**没有任何单旋钮改动能在两个窗口同时达到 P(Δ>0)≥0.95**；全部 16 个配置的 score 极差只有 0.0317，而配对 bootstrap 噪声 SD = 0.0060。
> ⇒ **层③（参数）在单旋钮方向上已接近局部最优，剩余空间在噪声量级内。** 用户"`tune-pattern-strength` 只能调参、不够用"的直觉，数据上成立。
> ⇒ **真正的增量必须来自层①②（结构 / detector 代码），而结构候选只有人类和 LLM 能生成。** 这使本节（人机接口）不是锦上添花，而是**唯一还有 headroom 的方向**。

### 1.1 `phase1_break` / `phase2_break` 的近失需按 ATR 归一（`arch` 抓出，已重算）

**问题**（`arch` 现场定位，我核实属实）：`path2/atoms/throwback.py:161-167` 与 `:221-227` 的 `measured.value = measured_support − anchor`，**单位是美元**。一支 $5 的票和一支 $500 的票，"差 $0.2" 含义差 100 倍 ⇒ **我原表的 80.7% / 85.4% 是量纲污染的。**

**重算**（400 只 pkl 真跑，ATR 用 detector 自己的口径 `calculate_atr(high, low, close, atr_window=14)` 取 `bo_idx−1`，与 `throwback.py:270` 一致）：

| gate | N | 股价中位 | 裸价格差 p50 | **ATR 归一 p50** | ≤0.25 ATR | ≤0.5 ATR | ≤1.0 ATR |
|---|---|---|---|---|---|---|---|
| `phase1_break` | 3818 | $10.70 | 0.311 | **0.653** | 20.0% | **39.8%** | 68.8% |
| `phase2_break` | 819 | $12.02 | 0.190 | **0.385** | 38.5% | **60.1%** | 82.3% |

**结论 = `arch` 的 (a)：近失占比在 ATR 归一后仍然高**（`phase1_break` 39.8% 在 0.5 ATR 内、`phase2_break` 60.1%）⇒ **"tb 的两个 break gate 是边际瓶颈"这个定性结论成立，不受量纲污染影响。**

**而且重算顺带给出了参数的正确形式**：既然裸价格差跨股票无统一含义，**任何 `phase1_break` 容差参数都必须以 ATR 为单位**，绝对价格阈值在 7532 只票上没有统一语义。

**两条附带观察**：
- `phase1_rise_before_confirm` 用的是 `rise / atr`（`:179`）——**它本来就是 ATR 归一的，量纲干净**，无需重算。
- 数据里存在异常价（`close` 最大值到 1e12 量级，疑似复权 artifact）。**ATR 归一恰好对此免疫**（分子分母同尺度），而裸价格差会被这些票污染——这是归一化的额外收益。

**`burst.chain_break` 不受影响**（`arch` 问的连带问题，答：是）：它的 measured 是**根数**，跨股票天然可比，所以"p50 超阈 36 根、只有 3.1% 在 1 根内 ⇒ 不是边际瓶颈"这条结论**原样成立**。

**双人复核**：`arch` 独立跑了 150 只（未切窗），与我 400 只的数对拍——裸口径 phase1 79.0% vs 我 80.7%、phase2 87.2% vs 我 85.4%；ATR 口径 phase1 `<0.5·ATR` **39.8% vs 我 39.8%（逐字相同）**、phase2 60.5% vs 我 60.1%。**两套独立探针一致，这条数可以信。**

**`arch` 的优先级反转我确认**：裸口径下 phase1(79.0%) ≈ phase2(87.2%) 看不出差别；ATR 口径下 **phase2 明显更边际**（p50 0.385 vs 0.653 ATR）。**若只做一个，该做 phase2**——代价是它的失败次数少 4.6 倍（影响面更小）。这个取舍**在我原表上根本读不出来**，是量纲污染直接造成的误导。

### 1.2 污染在报表侧还是判据侧？—— **答：报表侧（情况 A），现有代码无 bug**

`team-lead` 要求追这一层，答案很干净。现场读比较语句（`throwback.py:161` / `:221`）：

```python
measured_support = measure_at(df, i, support_measure)   # 该股的价格
if measured_support < anchor:                            # anchor = measure_at(bo-1, anchor_measure),同一只股的价格
```

**比较的是「同一只股票的价格 vs 同一只股票的价格」，没有任何跨股票共享的常数。** 判据本身量纲自洽，是一个**零容差的破位测试**。传给 `_emit_tb_gate` 的 `threshold=0.0` 是**差值的阈值**，也正确。

⇒ **情况 A：只有我那张近失表的排序被污染，现有 detector 没有 bug。** 修一张诊断表，无业务影响。

**⚠ 因此我上一轮那句"任何 `phase1_break` 容差参数必须以 ATR 为单位"要加限定词**：它说的是 `arch` 的 X1 **提议新增**的那个容差参数，**不是**在描述现有代码的缺陷。现在根本没有容差参数。我上轮的措辞会让人误以为存在一个既有 bug，这里更正。

| BO | `exceed_threshold: 0.003` | `peak.price*(1+t)` | **比率** | ⚠ 见下 |
| BO | `peak_supersede_threshold: 0.01` | 同上 | **比率** | ⚠ 见下 |
| Burst | `gap_max` / `first_drought_min` / `vol_baseline_period` | 根数 | 根数 | ✅ |

**结论 1 · `team-lead` 假设的缺陷类在本 codebase 里有零个实例。** 他的表述是"**价格量纲**的量与跨股票共享常数比较"。**审计结果：一个都没有。** 全部阈值都是根数 / 计数 / 比率 / ATR 倍数——**没有任何绝对价格阈值**。

**结论 2 · 但真正的缺陷类存在，它比 `team-lead` 描述的深一层**：

> **价格-尺度无关（比率）不等于跨股可比——比率仍然携带「波动率尺度」。**
> 一只低波动股的 MA 日变动 0.02%，一只生物科技股 0.5%；固定 `sideways_eps=0.0005` 对两者含义完全不同。**同理 0.3% 的突破溢价、5% 的横盘振幅、20% 的相对高度。**

这正好解释了既往那次 `trend` 研究为什么会独立发现同一问题（结论是采纳 per-σ rolling σ 归一）——**它不是"价格量纲"问题，是"波动率尺度"问题**，所以只看量纲扫不出来。

**结论 3 · codebase 里两种写法并存，正确的那种已经有典范**：

| 写法 | 实例 | 性质 |
|---|---|---|
| ✅ **按该股自身尺度归一** | `tb.big_rise_k`（×ATR）、`distribution.vol_threshold`（÷自身 63 日基线）、`distribution.upper_shadow_threshold`（÷本根振幅）、`burst.vol_spike_min` | 跨股语义统一 |
| ⚠ **固定比率** | `bo.min_relative_height`、`bo.exceed_threshold`、`bo.peak_supersede_threshold`、`platform.range_thr`、`trend.sideways_eps` | 携带波动率 artifact |

⚠ 项里**有三个在 `bo` 节点**，而 **bo 是流源**（burst / tb 都 consumes 它）——所以这三个的影响会连锁传导到整条链。

**结论 4 · 这是「语义选择」不是「技术错误」，必须这样呈现给用户。** 既往 trend 研究的定性我沿用：**"20% 的相对高度对所有股票是否应该是同一个门槛"是业务问题，不是 bug。** 低波动股用同一门槛会更难命中，这**可能正是用户想要的**（他也许就想要绝对意义上的大幅突破）。所以这张表的正确用法是**交给用户逐条拍板**，不是自动改成 ATR 归一。

**⚠ 我未做验证的**：我**没有实测**这五个固定比率阈值是否真的产生了跨股偏斜（例如"命中股票的波动率分布 vs 全宇宙的波动率分布"）。上表是**代码审计 + 机制推断**，不是实证。要坐实需要一次分层统计——成本不高，但我这轮没跑，不应被当作已验证结论引用。

## 2. A · 现状通道解剖

### 2.1 入口 A（`scope=time`）：粒度比预想的细

`_derive_time_response`（`path2_web/diagnose.py:182-209`）返回 `TimePayload{frame, failed_attempts: List[GateFailure]}`——**`failed_attempts` 就是原样的 `GateFailure` 列表**，不是摘要。而 `GateFailure`（`path2/dag/gate_failure.py:85-108`）携带：

| 字段 | 诊断价值 |
|---|---|
| `gate_name` | 哪道判据 |
| **`code_location`** | **`throwback.py:177` 这种源码行号**，`__post_init__` 用 `sys._getframe` 自动抓、逐帧跳过 dataclass 与 helper 帧 |
| **`threshold_param`** | **`params.yaml` 的短名**——判据到可调参数的直连 |
| `measured` / `threshold` / `op` | 实测值、阈值、比较符 → 可算边距 |
| `failure_event_window` / `evaluation_lookback` / `anchor_bar` | 时间定位 |
| `class_id` / `symbol` | 归属 |

→ **回答 brief 的提问**：它**不是**只能到"某个 gate 没过"，而是**能到 detector 源码的具体行**，并且能给出该行的实测值、阈值和对应的 yaml 参数名。这是一个对 LLM 极其友好的契约——`code_location` 让 LLM 可以直接 `Read` 那一段代码。

**它拿不到的**：不在判据比较里的其他中间量。你看得见"哪个值没过阈值"，看不见"当时作用域里其他局部变量是多少"。**这正是 F10 断点填的那个缺口，而这个缺口很窄。**

**过滤语义**：`_in_frame_strict`（`:175-179`）要求 `failure_event_window` **严格 ⊆** 用户框选区间。

> 遗留观察（我未查清，不作论据）：后端严格 ⊆ 过滤，但前端 `FailedAttemptsCard.vue::overlapClass` 却区分 `fully_inside` / `contains_frame` / `partial` 三种关系——按后端契约后两种不该出现。要么是前端防御性死代码，要么另有供给路径。建议由维护者确认。

### 2.2 gate 采集机制与覆盖率

`gate_collector.attach_and_collect(spec)` 遍历 `spec.nodes`，把 `node.detector.on_gate` 接到 collector（生产默认 `on_gate=None`，零开销），跑完 `detach` 复位。

**覆盖率是 3/6**：

| detector | 埋点 |
|---|---|
| `BODetector` / `BurstDetector`（`atoms/breakout.py`） | ✅ 20 处 |
| `ThrowbackDetector`（`atoms/throwback.py`） | ✅ 17 处（经 `_emit_tb_gate` helper） |
| `TrendSegmentDetector` / `PlatformDetector` / `DistributionDetector` | ❌ **零埋点** |

当前主 app 恰好只用前三个 → 覆盖 100%。但**任何用到 trend/platform/distribution 的新 pattern，失败归因通道直接失明**。补埋成本很低：`gate_failure.py:5-42` 的 docstring 本身就是一份写好的作者指南（四条规则 + 三个参考实现）。

**两个契约缺口**（都便宜、都高杠杆）：
1. **`threshold_param` 只覆盖 6/13 个埋点**，缺的包括 tb 的两个主力杀手 `phase1_break` / `phase2_break`。补一个 kwarg 即可打通"判据→参数"自动桥。
2. **`GateFailure` 有 `class_id` 但没有 `node_id` / `source_tag`**。当前 1:1 无碍；一旦同 detector 多实例（引擎已有自动 `source_tag` 派生机制），归因就会把两个角色的失败混成一堆。

### 2.3 入口 E `scripts/scan-top-miss.py`：批量通道存在，但信息在写盘那步蒸发

它对每个候选跑完 `scope=time`、拿到完整 `List[GateFailure]` 之后：

```python
counts = Counter(gf.gate_name for gf in failed_attempts)
top_name, top_count = counts.most_common(1)[0]
return f"{top_name}(实测 ... vs 阈 ... · 共 {top_count} 次)"   # :156-163
```

**丢掉了**：全部 measured 分布、`code_location`、`threshold_param`、`op`、边距——最后写成给人读的 markdown（`_write_markdown`）。

两个缺陷：
- **不可 LLM 消费**：结构化数据被压扁成一句中文字符串。
- **慢 20 倍**：`:65` 是朴素 `for pkl_file in pkl_files` 单进程循环 → 按实测 509 ms/股，全宇宙 **~64 分钟**；而 28 核在手、`eval_runner` / `scan.py` 早有 `ProcessPoolExecutor` 范式可抄。

→ 它离"用户想要的批量处理"差的**不是覆盖面，是保真度和速度**。排序逻辑（按涨幅降序）反而已接近廉价信号的天花板（见 §4.3）。

### 2.4 右键 debug 断点：为什么天然不可批量

`path2/debug_ctx.py` 的机制是：进程级 env（`DEBUG_MODE` / `DEBUG_BAR_RANGE` / `DEBUG_ANCHOR_KIND` / `DEBUG_EVENT_CLASS`）四门合取 → `pydevd.settrace(suspend=True)`。

不可批量有四个**构造性**原因（不是没做，是做不了）：
1. **suspend 本质串行阻塞**——挂起就是停下等人，N 个样本就是 N 次等待，没有并行语义。
2. **`DEBUG_BAR_RANGE` 是单一全局区间**，一次只能瞄准一个窗口。
3. **必须有 IDE attach**（`pydevd`），无头/CI/后台 agent 环境下退化为不停。
4. **多进程 worker 各自 suspend** → 26 个 worker 同时挂起等人，语义崩坏。

**这就是用户两个劣势的物理根源**：断点是"一次一个、必须有人、必须有 IDE"的通道。

## 3. C · 让 claude code 介入 detector 代码级诊断

### 3.1 断点的批量替代品：**不是加 instrumentation，是停止丢弃**

`path2_web/eval_runner.py:73-78`：

```python
spec = mod.build_pattern(params)
collector = attach_and_collect(spec)
try:    res = _dag_analyze(spec, win, params)
finally: detach(spec)
res = replace(res, gate_failures=collector.snapshot())
```

紧接着 `:80` 起只读 `res.matches` 组装 `rows`，`gate_failures` **从不离开 worker**。代码注释自己承认：

> `# 此路径目前无 gate_failures 消费者(eval/regress/healthcheck 报表只读 res.matches)`

→ **每一次全宇宙 eval 都已经完整计算了 1650 万条失败轨迹，然后全部丢掉。** "把人肉断点换成结构化 trace"这件事，**采集侧成本是零**——它已经在跑了。要做的只是在 worker 返回值里多带一个**聚合**（不能带原始：1650 万条）。

`path2/atoms/*.py` **一行都不用动**（对当前三个 atom 而言）。要动的只有：worker 返回值多一项 + 一个聚合函数 + 落盘。

### 3.2 该聚合成什么：裸计数表是伪产物

lead 设想的产物是「按 miss_reason × node × 判据 聚合的表」。**我实测后认为这个产物本身几乎无价值**：

- 它只有 **11 行**（distinct `code_location` = 11）。
- 它被结构性噪声主导：`no_active_peak_broken` 占 50%，字面含义是"这根 bar 没突破任何活跃高点"——对一个逐 bar 点探测器，这就是**事件的补集**，不是诊断信号。
- 更糟的是它 `threshold=None, op=None, threshold_param=None`（`breakout.py:330-331`），**连可调对象都没有**。排第二的 `peak_already_active`（占 5.4%）同理。
- 两个最大的 gate 合计 **87%**。整张表读出来就是一句"绝大多数 bar 不是突破"。

**真正有用的三张表**（都能从现有数据造出来，不需要新埋点）：

| 表 | 内容 | 回答什么 |
|---|---|---|
| **T1 边距表** | per (`class_id`,`gate_name`,`code_location`,`threshold_param`)：计数 + **per-gate 分位归一**的边距分布 | "哪道判据是**边际的**"——差一点点就过的，才是调参能救的 |
| **T2 条件表** | 同上，但只统计 `failure_event_window` ⊆ **人类标注区域**的记录 | "在我说该命中的地方，究竟死在哪一步" |
| **T3 分区表** | 队列内样本按"死在哪个阶段"分桶（如 86% 死在 tb / 14% 窗内根本没触发 tb） | 路由到不同诊断路径与代码区 |

**排序键不是计数，是 `计数 × 近失占比`**。§1 的表已经演示了这个判别力：`chain_break` 计数不小但近失只有 3.1%（不是瓶颈）；`tb.phase1_break` 近失 80.7%（是瓶颈）。这个判断用 60 只股票、约 30 秒算力就得到了。

**T2 是全文的枢纽**：1650 万条噪声，一旦按人类标注的区域条件化，就坍缩成一句可执行的话——
> "在 (XXXX, 2025-03-14) 附近，burst 的 attempt 死在 `chain_break`，gap=7 vs `gap_max`=5，位于 `breakout.py:141`。"

**这才是一次人类标注的真正产出**。它 **N=1 就成立**。

### 3.3 人类与 LLM 的分工线

**分工线只有一条，但它是干净的：**

> **人类独占"这段价格行为是不是我要的走势"——两个方向都算（该命中而没命中 / 命中了但不是我要的）。除此之外的一切，机器可做。**

这条线的依据不是能力强弱，而是**信息在哪里**：用户的意图是 ground truth，它只存在于用户脑子里，**不可从任何数据推导**。而"哪道判据杀了它""该调哪个参数""改完统计上动没动""有没有前瞻泄漏"——全部是意图确定之后的下游推理，数据里有答案。

| 归属 | 事项 |
|---|---|
| **人类必须在环** | 走势语义判定（正/负两向）；对"这个改动语义上还是同一个走势吗"的最终批准 |
| **LLM 可全代** | gate 归因、边距计算、`code_location` → 读代码定位、候选改动生成、跑 `run_eval`/`run_regress`、诚实性检查（前瞻/算术效应/缩窗）、跨窗口复核 |
| **LLM 提议 / 人类批准** | "改动是否语义中性"——这是意图问题的伪装，LLM 可以给证据但不能拍板 |

**误判代价的方向（非对称，这决定纪律）**：

| 误判 | 代价 | 为什么 |
|---|---|---|
| 人类把不该标的标成正例 | **昂贵且持久** | 标注是长期资产、会当回归闸反复生效，错误被固化且不可见 |
| 人类把好命中标成负例 | **有界** | `score` 会在 n=数万上反驳他，而且 score 在这件事上更准 |
| LLM 归因错 | **便宜** | 下一次 eval 就打脸 |
| LLM 判"改动语义中性"而其实不是 | **昂贵且沉默** | 这就是评分标准专门设防的"缩窗刷分"类失败 |

→ **纪律：进入持久 ground truth 集合的错误，是唯一昂贵的一类。** 因此正例标注要**保守录入**，且必须带一行人写的理由（既是审计凭据，也是未来复核的锚）。

## 4. B · 人类判断的最优产出形态

### 4.1 正例 vs 负例：便宜 ≠ 有信息

lead 的假说提示"负例可能更廉价也更有信息量"。**我同意前半句，否认后半句。**

**采集成本（我的估计，基于已核实的 UI 机制）**
- **负例**（"这个命中是垃圾"）：系统自己产出候选；`SidebarResultList.vue` 已经是一张**按 pattern 命中数与 forward_return 可排序的股票表**，点一行就切到 K 线。人只需看一眼做二分判断 → **~5–15 秒/个**。池子有界（实测 588 只中窗内 match 仅 90 个）。
- **正例**（"这里该命中却没有"）：总体是 7532 × ~1100 根 ≈ 800 万个 (股票, bar) 格子的补集，人必须搜索。`scan-top-miss` 的"涨幅≥30% 且零 match"是个好先验，但**它是标签的代理、不是标签**——涨了 30% 不代表它是"横盘后连续突破启动"，人还得逐个否掉大多数 → **~2–10 分钟/个**。

**成本差一到两个数量级，这一点 lead 是对的。**

**但信息量是反过来的：**

- **负例与 `score` 高度冗余。** 如果一个命中真的垃圾，它的 forward_return 就低，`score = w·lift` 已经在 n=数万的量级上惩罚了它——而且比人眼准。**一个人说"丑"、实际却涨了 20% 的命中，是人错，不是 score 错。** 负例在做一件机器已经做得更好的事。

  **⚠⚠ 这一条已被 `opt` 的实测部分推翻——见 §4.1.1，这是本文档最大的一次结论修正。**

- **正例携带 `score` 结构上装不下的信息。** `score = w·lift`、`lift = median_配置 − median_基线`——**这里面没有任何一项度量"漏掉的机会"**。score 只度量"抓到的东西的质量"。召回提升只能通过 `w = n/(n+200)` 间接体现，而 w 单调但**饱和**，且**分不清"多抓了对的"和"多抓了平庸的"**（多抓一批 return≈基线的样本，w 升、lift 降，净效应含混）。

  → **`score` 对漏检是结构性失明的。这是人类正例标注不可替代的根本原因。**

  **失明的精确形态（采纳 `team-lead` 的表述，比我原来的准，也更难被反驳）**：说 score "没有度量漏检"不严谨——`n` 确实经 `w = n/(n+200)` 进来了。准确的说法是：
  > **score 只能看见你已经产出的 match；对"市场里存在、而你从未匹配到"的机会没有任何一项。召回的分母对 score 不可观测。**
  > **只有人能提供分母。**

  **⚠ 但这句话不能被引申成"所以要把 recall 加进目标函数"——那是错的，见 §4.5。** 这里必须做一个我第一版没做干净的区分（`skeptic` 挑战后修正）：
  - score 只度量**每次命中的质量**。用户可能**另外**在意"机会数量/可部署资金"，这是**第二个业务偏好**，不是 score 的估计缺陷。
  - 正确的解决位置是**用户直接声明这个偏好**（例如"n 低于多少我不接受"），而不是让一个 N=20 的标注集去当第二个优化器。
  - 我第一版把这条写成"score 错了"，是把「目标函数没编码某个偏好」和「目标函数估计有偏」混为一谈。**前者是规格问题，后者才是统计问题；只有后者才需要新的裁判。**

**诚实保留——负例有两个不可替代的用途**（所以别废掉它，只是别把它当训练信号）：
- **(a) 前瞻泄漏侦测**：一个 score 很好、但人一眼看出"它是靠偷看未来才找到的"命中。score 看不见这件事（它本身就被泄漏污染了）。项目里 tb 的 `outcome` 字段前瞻问题就是这一类。
- **(b) 语义漂移侦测**：涨是涨了，但根本不是用户要的走势（例：用户要"横盘后启动"，pattern 开始匹配"已经翻三倍后的继续突破"）。score 是意图的**代理**，不是意图。

→ **负例的正确角色是"对目标函数本身的有效性审计"，不是训练数据。** 因此它应该**少量、周期性**（比如每轮 10 个），而不是批量标注工程。

### 4.1.1 ⚠ 重大修正：`opt` 的实测把负例从"冗余"抬回"互补"

`opt` 对同一批买点只换 label 算式、两年独立复现：

| 组 | max-high 20d（**现行 label**） | **持有到期 20d** | 胜率 | **最大不利偏移** |
|---|---|---|---|---|
| `bottom_burst` 现任 | **+0.2293** | **−0.0632** | 41.8% | **−0.2301** |
| `bo_only` 基线 | +0.1234 | −0.0040 | 48.3% | −0.1184 |
| 全宇宙随机日 | +0.0704 | +0.0050 | 53.0% | −0.0636 |

pattern 把 20 日上行幅度抬高 10.6 点，**同时把下行幅度也压深 11.2 点——两边几乎对称，而 label 只数上行那一半**。对称计量（MFE+MAE）后 t=0.27。`corr(官方 score, 最大不利偏移深度) = −0.591 (p=0.003)`。

**⇒ 我 §4.1 那条"负例与 score 高度冗余"的论证依赖一个我没检验的隐含前提：`score` 度量的是用户想要的东西。** 现行 label 是 `max(high[t+1..t+n])/close[t] − 1`，即 **MFE（最大有利偏移）**——它奖励波动率，且**结构上看不见回撤**。

**⇒ 我原话"人说丑但实际涨了 20% 的命中，是人错不是 score 错"在当前 label 下站不住**：那 +20% 可能是一根尖峰的 MFE，而该股实际收在 −6%、中途回撤 −23%。**人在 K 线上看得见整条路径（包括回撤），label 只看得见最高点。**

**修正后的定位**：

| | 原结论 | 修正后 |
|---|---|---|
| 负例的信息量 | 与 score 冗余，仅作有效性审计 | **携带 label 结构上没有的「路径信息」**（回撤形状、涨幅是不是尖峰后回吐）⇒ **互补，不是冗余** |
| 正例的信息量 | 唯一进入长期资产的信号 | **不变**（score 对漏检的分母仍不可观测）|

**⚠ 但不要过度摆动**——人**依然不能**预测 20 日后的收益，`opt` 自己也这么说。人多出来的信息是**具体的、有限的、可命名的**：**路径形状**，而不是收益预测。所以负例的角色从"审计"升格为"补充路径维度"，**仍然不是**"第二个打分器"，§4.6 的"人不排序"红线不变。

**⇒ 采纳 `opt` 的轻量提案（它正好是我给负例的角色的推广）**：
> **把「人与 score 的分歧」当成一个诊断信号留档**（`labels.jsonl` 里记 verdict + 当时的 score/label 值）。当 score 说 A 比 B 好、而人看 K 线说 B 更像目标走势时，**这个分歧本身是关于 label 是否可信的信息**，该被记录而不是被裁掉。**它是 label 出问题时唯一会先亮的灯。**

我在 §4.1 给负例列的两个不可替代用途（前瞻泄漏 / 语义漂移）**现在要加第三个，而且它是当前唯一已被实证为活跃的**：**(c) 目标函数错误规格侦测**。

**⚠ 这仍然是「规格问题」不是「估计问题」**（沿用 §4.1 那条我与 `team-lead` 已达成的区分）：label 没编码"回撤"这个偏好。正解是**用户声明偏好 / 修 label**，**不是**让标注集去当第二个优化器。`opt` 也明确不主张把 recall 做成目标维度，`skeptic` 的三条反对全部保留。

### 4.2 标注协议

**最小充分表示**——由三个消费方倒推：

| 消费方 | 要求 |
|---|---|
| 条件化 gate 流（T2） | `_in_frame_strict` 比的是 **区间 ⊆ 区间** → 必须是**窗口**不是单点 |
| 回归闸 | 需知道"该出现哪个 `end_role` 的事件在哪个窗口" |
| 跨轮复用 | 见下面的两个陷阱 |

```jsonc
{
  "symbol": "XXXX",
  "date_start": "2025-03-10",     // 日期,不是 bar 索引
  "date_end":   "2025-03-28",
  "verdict": "should_match",       // should_match | bad_match
  "note": "横盘 6 周后连续三根放量突破,回踩不破颈线",   // 必填,一行,人写
  "expected_role": "tb",           // 可选;人只在"看得出"时填
  "labeled_at": "2026-07-25",
  "labeler": "human",
  "provenance": "queue_P | queue_N | queue_D"
}
```

**为什么是窗口不是单点**：人的知觉对象是"这一段是启动"，逼他挑一个精确日期只会让他随便挑，而 ⊆ 匹配对边界很敏感。

**陷阱 1 · 必须存日期，不能存 bar 索引。** `failure_event_window`、前端 brush、`Query.start_bar/end_bar` 全都在 bar 空间；但 **bar 0 = 当次加载窗口的首根**，随 `start_date` 与 `head_buffer_trading_days` 缓冲变化（`eval_runner.py:61-65` 的双端缓冲切窗）。存 bar 会在下一轮**静默错位**——不报错，只是指向了别的日子。`scan-top-miss.py::_date_to_bar` 已经有日期→bar 的转换，标注侧只需在消费时调它。

**陷阱 2 · verdict 与 attribution 的生命周期不同。**
- **verdict 是 params-无关的持久事实**——"这是一段横盘后启动"是价格行为的属性，改 `gap_max` 不会让它变成不是。**跨轮永久有效。**
- **attribution 是 params-相关的派生量**——"死在 `chain_break`" 只对某组参数成立。
→ **verdict 落盘持久（进 git）；attribution 当缓存、按 params hash 失效重算。** 这直接回答"参数变了标注还有效吗"：**verdict 有效，attribution 无效。**

**⚙ `mech` 的精确化（采纳，能显著提高缓存命中率）**：attribution **不该按整个 params hash 失效**，那会白丢一大半缓存。他实测（120 只票）：**where/edge 参数改动下 streams 逐字全等（120/120）；只有 detector 参数改动才让 streams 变**（`burst.gap_max` 8→15 → 29/120 只票变）。
⇒ 凡是从 streams 派生的 attribution（GateFailure 聚合 / node 命中与否 / 事件几何量），**只按 detector 参数子集的 hash 失效**：`bo.*`（bo 是流源，burst/tb 都 consumes 它 ⇒ 动它连锁重算三条流）、`burst.gap_max` / `vol_baseline_period` / `min_bos`、`tb.*`。
而 `burst.first_drought_min` / `distinct_pk_min` / `vol_spike_min` 与**全部 edge 参数**改了**不必失效**（yaml 原文注释即写明"detector 不读，只在 NodeSpec.where 闭合"）。**这三个恰恰是调参时动得最勤的**，所以命中率提升可观。

**陷阱 3 · 正例与负例的键不同，寿命也不同。**
- 负例是关于**系统输出**的，键是 `(symbol, buy_date)`——正是 `eval_runner.py:219` 对拍用的键（注释写明"event_id 随结构可能变，不用"）。
- 正例是关于**世界**的，无法用系统输出做键。
→ 结构一改，被标为负例的那个命中可能**直接消失**，负例随之失效；正例不会。**又一条"正例是长期资产、负例是一次性审计"的佐证。**

**存放**：`path2_apps/<app_id>/labels.jsonl`（跟着 app 走，因为"是不是我要的走势"是 app-特异的），**进 git**。JSONL 而非 JSON/YAML：追加友好、diff 友好、逐行独立不会因一处语法错误全废。

### 4.3 采样策略：一个被实测证伪的提案，和它的替代

brief 建议按主动学习思路排优先级（送"模型最不确定的""score 边界上的""最接近成功的"）。**我把这个思路的四个廉价实现全跑死了。**

588 只真跑，关注窗 = 最后 252 根：

| 信号 | 池大小 | 收窄 |
|---|---|---|
| 基线：窗内涨幅 ≥30% 且窗内零 match | 140 / 588（24%） | — |
| ∩ 全历史有 burst | 119 | **1.0x** |
| ∩ 窗内有 burst | 125 | 1.12x |
| ∩ 窗内有 burst 且有 tb | 113 | 1.24x |
| ∩ `dropped_matches` > 0 | 139 | **1.01x** |
| ∩ 窗内 tb gate 失败 ≥5 次 | 79 | 1.77x |

**为什么全都不行**——原因是结构性的：**节点存在性几乎无信息**。全历史有 burst 的股票占 89.8%、有 tb 的占 84.7%、`dropped_matches>0` 的占 90%（531/588）。pattern 的选择性**几乎全部住在边约束的合取里**，不在节点存在性里。"离成功有多近"这个直觉，在可廉价计算的粒度上**测不出来**。

**→ 结论 C-4：人类时间省不下来。** 唯一有效的先验是**结果先验（涨幅）**，而 `scan-top-miss.py` 已经在用它。**它的排序已接近廉价信号的天花板**——缺陷在保真度和速度（§2.3），不在排序。

**这个负面结果改变设计目标**：不是"少问人类"，而是
1. **每次问都问在刀刃上**，
2. **人类的每个判断被永久捕获**（→ 落盘 JSONL 进 git，绝不能只活在一次对话上下文里）。

**筛不动，但能"分区"。** 队列里 **86% 死在 tb 阶段、14% 窗内根本没触发过 tb**（死得更早）。分区 ≠ 过滤，但它把样本路由到不同的诊断路径和代码区——这是有用的，只是不省人类的眼睛。

**⚙ `mech` 给了一个比我全部启发式都强的分诊（采纳，且它不是启发式）**：他实测 36 个 where 配置的命中集——**并集 = 最大单配置 = 147，比值恰好 1.000**，69.7% 的配对互为子集 ⇒ **这些 where 阈值构成完美嵌套族**（放松阈值单调放大命中集）。

⇒ **推论（是单调性的必然，不是经验规律）**：**若一个标注样本在「最松 where 配置」下都没命中，那么调这三个 where 阈值永远救不了它**——它的失败一定在别处（detector 内部 / 边 / bo 流本身）。

**这就是我那四种失败启发式想要而没得到的东西**，差别在于：
- 我的四种是**相关性猜测**（"有 burst 大概更接近成功"）⇒ 收窄 1.0–1.8x，因为节点存在性几乎无信息；
- 这一条是**带保证的必要条件** ⇒ 它不给概率，它给**排除**。

⇒ **协议：队列 P 的第一道分诊 = 用最松 where 跑一遍。命中 ⇒ 归「参数可救」；不命中 ⇒ 归「必须改结构或 detector」。** 零成本、可自动计算、零选择偏差（`mech` 强调的这半句比"零成本"重要——**确定性路由不产生候选、不做选择，所以不进 K**；任何**排序**都在隐式选择、都要付门槛）。

**⚠ 边界**：这个保证只覆盖那三个 where 阈值，**不覆盖 detector 参数与边**。别把它读成"参数完全救不了"。

**⚠ `biz` 抓到队列 P 的一个真覆盖漏洞（我读 `scan-top-miss.py` 时漏了）**：`:78` 的 `if len(result.matches) > 0: continue` ——**只要这只票在整段历史任何地方命中过一次，就被整只跳过**。所以下面两类漏检**完全不可见**：
- **命中了但命中在错误的时间点**
- **该命中 3 次只命中 1 次**

**而这两类恰恰是优化后期最常见的形态**（早期是"完全没命中"，后期是"命中构成不对"）。⇒ 队列 P 的正确口径应是**按 (symbol, 时间窗) 判漏检，而不是按 symbol 判**。这是比"慢"和"丢信息"更根本的缺陷，因为它决定了**人根本看不到哪些样本**。

**三个队列，按价值排序：**

| 队列 | 来源 | 成本 | 价值 |
|---|---|---|---|
| **D · diff 队列（最高）** | `run_regress` 的 `added` / `removed`（带改前收益）——**零新机制** | 每项 ~10 s；规模是几十不是几千 | 唯一一个"人的回答立刻改变下一个决策"的队列；且每项都**因果归属于你刚做的那次改动**；"新增的这批命中是不是我要的走势"恰是 score 答不了的问题 |
| **P · 正例队列** | `scan-top-miss` 排序（涨幅降序） | 2–10 min/个 | 唯一能进入长期资产的信号 |
| **N · 负例队列（最低）** | 现有 sidebar 按 forward_return 升序 | 5–15 s/个 | 仅作有效性审计（泄漏 / 语义漂移），每轮 ~10 个即可 |

### 4.4 规模：20 个够不够，200 个现不现实

**当目标函数——不可行，`biz` 的实测把这条钉死了，且比我原来算的更强。**

⚠ **先记一个方法教训**：我原打算用 σ 算 median 的 SE，**那会得到荒谬的数**。这个分布右尾极重（bbb 命中池 mean 0.4713 是 median 0.2293 的 2.1 倍，基线池 2.5 倍），**σ 被尾巴撑爆，而中位数的 SE 只取决于中位处的密度**。`biz` 直接 bootstrap（4000 次重抽）：

| N（标注量）| **median SE**（bbb 命中池）| 2·SE = 可检出最小 lift | 占基线 0.1234 的 | 正态近似（错的）|
|---|---|---|---|---|
| **20** | 0.0893 | **0.179** | **145%** | 0.243（高估 2.7×）|
| 50 | 0.0569 | 0.114 | 92% | 0.154 |
| 100 | 0.0395 | 0.079 | 64% | 0.109 |
| **200** | 0.0274 | **0.055** | **44%** | 0.077 |
| 423 | 0.0182 | 0.036 | 29% | 0.053 |

（基线池同 n 的 SE 只有一半，因 bbb 命中池 IQR 是基线的 1.93 倍；正态近似在基线池上高估 **8.4×**。）

**⇒ N=20 只能检出 +0.179 的 lift（基线的 145%）；即使 N=200 也只能检出 +0.055——而定案配置的真实 lift 才 +0.1059，单旋钮真实效应更只有 +0.0097 量级。标注量要到上千才够当排序目标。**

原推理（`w = n/(n+200)`：N=20 → `w=0.09`）方向对但过于粗糙；以上表为准。200 个正例 × 5 分钟 ≈ **10–17 人时**，一次性不现实——**而现在我们知道 200 个其实也远远不够。**

**但这不重要，因为目标函数不该由人提供。** `score` 的 n 是从全宇宙扫描免费来的（brief 记录 `bo_only` 2024 全年 n=23968）。人类标注**从来不需要够到统计门槛**。

**三分（这是 brief 要求的那个关键区分）：**

| 规模 | 角色 | 是否现实 |
|---|---|---|
| **N = 1** | **条件化过滤器**——把 1650 万条噪声坍缩成一条可执行诊断（§3.2 的 T2） | ✅ 立即有用 |
| **N = 10–30** | **回归闸**——"这次改动不许弄丢我认定的这些例子"。这是**检测问题**不是**估计问题**，检测不需要大样本 | ✅ 现实，且是标准做法 |
| **N ≥ 200** | **目标函数** | ❌ 不现实，**且不必要** |

→ **标 20 个够用；标 200 个不现实；目标函数继续用全宇宙的 `w·lift`。** 标注是**诊断与验收**，不是**目标**。

**一条补充**：N≥200 虽然一次性不现实，但如果**每次诊断会话都把结论沉淀进 `labels.jsonl`**，它会自然累积。所以协议要为将来的规模留口（结构化、可追加、带 provenance），但**不要为了凑数去刷标注**。

### 4.5 为什么 recall 绝不能进目标函数（采纳 `skeptic`，其论证强于我的原论证）

我第一版反对"标注当目标函数"的理由是**统计的**：N=20 时 `w=0.09`、lift 的标准误淹没一切。`skeptic` 给了一个**结构性**的理由，比我的强，我完整采纳：

> **`score` 有减基线保护，recall 没有。** `lift = median_配置 − median_基线` ⇒ 把过滤全放开、退化成基线时 `lift ≡ 0`，**摆烂刷不到分**。而"在标注正例集上的 recall"呢？**把过滤全放开，标注样本全部命中，recall = 100%。**
> ⇒ 双目标里 recall 那一维**天然指向"放宽一切"，它不是约束，是刷分杠杆**。

统计理由只是说"这个目标太吵"；结构理由说的是"**这个目标的最优解本身就是退化解**"。后者致命得多。

**但这不废掉标注的验收用途——因为单向闸不可被刷。** 这是我要保留的唯一例外，理由必须说清：

| 形态 | 能否被"放宽一切"刷到 | 判定 |
|---|---|---|
| **recall 作为目标**（maximize） | ✅ 能，放开即 100% | ❌ 禁用 |
| **标注集作为单向回归闸**（"不许弄丢这 N 个"） | 放宽确实能过闸，但**过闸不加分**——它只能否决"弄丢了标注样本"的候选，永远不能让任何候选变好 | ✅ 可用 |

一个只会**否决**、永远不会**加分**的闸，**没有任何梯度可以攀爬**。

**⚠ 但闸不能是"自动 fail"，必须是"停下来让人裁"（`team-lead` 补，采纳）。**

先例：这与用户在重构纪律里已立的原则**结构同构**——旧实现当 golden baseline 时是"**体检仪不是设计裁判**"，用途是抓新代码手滑 bug，**不是逼新实现逐样本复刻**；关键纪律是区分**实现偏离**（回归，必修）与**设计偏离**（升级，接受）。

**标注否决闸必须继承同一条纪律**，否则会出一个我原方案没覆盖的失败模式：**闸会否决掉一个合法地找到了更好机会集的候选**。用户的 20 个标注编码的是他**当前**的直觉；如果优化真找到了更好但不同的东西，闸会把**进步当回归拦掉**。

⇒ **协议：掉标注 ⟹ 阻塞 + 归因 + 人裁三选一**，而不是简单 reject：

| 人的裁定 | 含义 | 动作 |
|---|---|---|
| **实现偏离** | 判据被改坏了 | **必修**，撤销或修正改动 |
| **设计偏离** | 换了个更好的形态，我认 | **接受，并更新标注集** |
| **存疑** | 看不准 | 撤销改动，标注保持不动 |

这顺带解决了**标注集的老化问题**：标注不是一次写死的公理，而是随着用户意图演进被显式修订的证据集——**且每次修订都留痕**（`labeled_at` / 一行理由）。它与 score 的失效方向恰好相反：score 防"放宽"（lift→0）与"过紧"（w→小）是**统计的**；标注闸防的是**语义替换**——n 保持、score 保持，但抓到的已经不是用户要的那个走势。**score 是意图的代理，不是意图本身**，这个缝隙只有人能堵。

### 4.6 人在环的价值在生成侧与否决侧，**从不在排序侧**（`skeptic` 挑战 2 的正面表态）

**我的表态：substantially 同意 `skeptic`。**

| 环节 | 人的价值 | 判定 |
|---|---|---|
| **生成侧**（提出候选：该往哪个方向改判据） | **决定性**。人看 K 线能说出"这里该被识别，因为它是先深回踩再一根反包"——这是**候选的语义来源**，机器提不出来 | ✅ 主用途 |
| **否决侧**（定案前的语义验收：这还是我要的走势吗） | **单向、有限、不可替代**（§4.5 的缝隙） | ✅ 次用途 |
| **排序侧**（判定哪个候选更好） | **负价值**。等于引入一个 N 极小、无基线保护、与 score 口径不一致的第二裁判 | ❌ 禁用 |

**一句话：人提候选、人有否决权，但人不排序。否决 ≠ 选择**——否决是在 score 已经选完之后施加的一道语义过滤，不是与 score 并列的第二个打分维度。

**历史确证（我现场核实了 `skeptic` 引用的全部出处，属实且比他说的更强）**：

`docs/research/2026-07-15_throwback-stop-drop-signal-generalization/` 全 opus agent team（3 专家 + skeptic + lead，7 份文档）推荐稀缺池 `{lower_shadow, doji}`。10 天后 `docs/research/2026-07-25_tb-recall-quality-tuning/final_report.md:164-172` 在 label 口径下实测：

| 信号池 | n | score |
|---|---|---|
| 当前 3 类 | 423 | **0.0719** |
| 该 team 推荐的稀缺池 | 190 | **0.0154**（−79%）|
| 完全不要求信号 | 599 | 0.0712（**整道判据关掉只差 1%**）|

**关键细节 —— 我核实后发现比 `skeptic` 转述的更严重**：那句"需要用户提供 2-3 个具体漏检 ticker + 日期做 replay 验证"，**在那次研究里被三个不同的 agent、在四处独立提出**（`final_report.md` §4/§37/§162/§173、`skeptic_critique_draft_v1.md:138`、`final_position_by_skeptic.md:60`）——**然后全部落空，方案照常实施，10 天后被证伪。**

这条历史给出三个可直接落地的教训：
1. **人在生成侧的缺席是真实成本**（那次 team 自己识别出"我需要人给样本"，且它要的形式恰是"具体样本做 replay"，**不是**"一个 recall 目标去优化"）。
2. **"记得问用户"不会自动发生**。同一个请求被提了四次仍然落空 ⇒ 人在环必须有**机制**承载（落盘的 `labels.jsonl` + 阻塞式验收闸），**不能靠报告里写一句建议**。
3. **最终抓住这个错误的是 score，不是人。** 所以——

**我必须诚实地把优先级排在自己提案之前**：`skeptic` 极简基线的第 2 条（**`authoring-path2-app` Step 4 判据 2 从 `run_regress` 升级为「跑 score」**）**比本文任何提案都重要**。它是那次 −79% 的直接解药，改动极小。人类标注在这个故事里的价值是**更早、更便宜地发现**（省下 10 天 + 一整个 opus team 的成本），是**方差削减 / 灾难规避**，**不是均值提升**。我不为标注主张任何 score 增益。

### 4.7 回答 `skeptic` 的三个问题

1. **产出的是候选还是判定？** —— **候选为主，判定仅作单向否决闸，从不排序**（§4.6）。凭什么比 holdout score 可信？**在排序上不比它可信，也不参与排序**；只在 score 结构上看不见的那一维（语义同一性）上有权否决。
2. **消耗多少人时？换来多少可测 score 增益？** —— **⚠ 此答案已修订。** 我原答"不主张任何可测的 score 增益"；`skeptic` 给出实测选择门槛表后，**我现在能给出量化贡献了**：人在生成侧的贡献不是提高 lift，而是**降低选择门槛**（K：1000 → 5 ⇒ 门槛 0.039 → ~0.017，**约 +0.022 的真实分**）。详见 §4.8。人时成本约 **20 个判定 / 20 分钟每定案周期**。此外仍有**避免 −79% 那一类失败**的方差削减价值。"更有掌控感"不算，我没拿它当理由。
3. **完全去掉会怎样？** —— **2026-07-15 那次就是这个反事实实验**：人在环被跳过（四次请求落空），结果是 −79%、10 天、一整个 team 的返工。**但必须补一句**：真正把它兜住的是 score；所以"砍不掉的"严格说是 **score 闸**，人类环节是**把发现成本从 10 天降到 20 分钟**的加速器，不是最后一道防线。

### 4.8 人在环的价值只有两种兑现形式：降 K，或提 lift。**我的方案走降 K。**

`skeptic` 的实测选择门槛表（零信号 null 模型直接测量，非高斯近似）：

| 搜索量 K | 真实选择门槛 |
|---|---|
| 40 | **0.024** |
| 400 | 0.036 |
| ~1000 | ~0.039 |

**由此得到一个可量化的人在环定价框架**（采纳 `skeptic`，我认为这是本轮全队最有用的一个工具）：

> 任何人在环环节，要么帮你**降低 K**（更少更准的候选 ⇒ 门槛更低 ⇒ 同样的原始分更可信），要么帮你**提高 lift**。**这两条是人在环唯一能兑现的价值形式。**

**我的方案明确走「降 K」**：人看 K 线说出"这里该被识别，因为它是先深回踩再一根反包"，作用是把结构候选从 ~1000 个砍到 ~5 个 ⇒ **门槛从 0.039 拉回 ~0.017**。

**⛔ 硬前置（`skeptic` 挑战 2 后从"并列注意事项"提为前置条件）：**

> **§4.8 的降 K 主张成立 ⟺ 人在「未参与优化的窗」上做判断（见 §4.8.1）。**
> **默认设置下这个前提不成立**——人看的是搜索窗（2024/2025）的 K 线，那是 score 已被优化过的同一批数据，人看到的命中集合本身就是搜索结果的产物。**此时人的信息与 score 不正交，降 K 主张失效，必须退回"不主张任何可测 score 增益"的原答案。**

合法性的一般形式：
> **人类的收窄之所以能真实降低门槛，是因为它用的信息与 score 数据正交（形态语义 + 未优化窗），而不是 score 本身。**
> 如果改用"先拿 score 预筛 1000 个候选、再留 5 个"去降 K，**那是把选择偏差藏起来，不是消除它**——门槛该按 1000 算而不是按 5 算。

**正交性有两条独立的破坏路径，两条都必须堵**：① **排序破坏**（用 score 相关量决定人看什么）；② **窗口破坏**（让人看已被优化过的时段）。

**同一份人力，两种用法在统计上符号相反**（这是反对双目标的最终、且有数的理由）：
- 标注做成**可优化目标** ⇒ 多一维可调 ⇒ **K 增加** ⇒ 门槛上升 ⇒ 净负
- 标注做成**候选来源** ⇒ **K 减少** ⇒ 门槛下降 ⇒ 净正

### 4.8.1 ⭐ 人看 K 线必须在**未被优化过的窗**上（`skeptic` 提供，几乎零成本）

`skeptic` 实测（抽样 600 只）：磁盘上有 3 个从没用过的评估窗——**2022 覆盖 83% / 2023 86% / 2024 89% / 2025 97%（在用）/ 2026 数据到 07-13、约 6.5 个月**。定案报告写"真正的验证需要未来数据"，**而未来数据已经在磁盘上了。**

**对人机协同的直接含义**：
> 在**搜索窗**（2024/2025）上让人看 K 线，人看到的是**被优化过的样本**——他的"这确实是我要的走势"会被搜索结果诱导。
> 在**从未参与优化的窗**（2026）上看，人的形态判断才是**独立信息**。

**这不是一条新原则，而是 §4.8 那条正交性要求的第二次出现**——我在那里说"人类的收窄之所以能降低门槛，是因为它用的信息与 score 数据正交"。正交性可以从**两个方向**被破坏：
1. **排序破坏**：用 score 相关量（如 forward_return）决定人看哪些样本 ⇒ 人变成 score 的放大器（我据此否决了 `arch` 的"按 return 升序抽"）。
2. **窗口破坏**：让人看已被优化过的时段 ⇒ 人在给一个已经拟合过的结果背书。

**⇒ 协议补充：所有需要人做形态判定的环节（D 队列验收、P 队列正例采集、否决闸），默认在 2026 窗上做。** 成本几乎为零（数据已在磁盘），收益是把人的判断从"背书"变回"独立证据"。

### 4.8.2 ⭐ 人的语义约束防止优化器钻目标函数的空子（`skeptic` 提供，我接受一半）

`skeptic` 量化了评分标准 §9 那条从未被量化的「入场位置算术效应」。对 `bo_only` 全部 29502 个 bo 事件：

| 平凡规则（零选股能力，全宇宙无差别执行） | 相对基线 lift |
|---|---|
| 单纯延迟 k 天买 | −0.001 ~ −0.002（没用）|
| **bo 后 k 天内最低收盘价那天买**（k=5/7/10） | **+0.0645 / +0.0770 / +0.0928** |
| 对照：`bottom_burst` 定案 lift | +0.1099 |

**✅ 我接受的部分（且认为它是本节最强的具体论据）**：
> **人不容易滑进这个空子，最大化器会直奔它而去。**
> "把入场点往回踩低位挪"**不是**一个会从"我想要横盘后启动突破"这句话里自然浮现的设计动作；而一个在层①②自动搜索的循环会很快发现"让 end_node 落在更低的位置"是最高性价比方向，**报出很高的 score 且通过所有现有硬门**。
> ⇒ **人的语义约束在这里起的是"防止优化器钻目标函数空子"的作用。** 这是一个可量化的、具体的人在环价值，比"人擅长看 K 线"硬得多。

而且它**再次落在生成侧**：人贡献的是"候选必须符合这个走势语义"这一**约束**，不是"哪个候选分高"的**判断**——与 §4.6 的红线一致。

**❌ 我不接受的部分：不能由此推出"bbb 头条 lift 的 60~70% 是入场算术"。**

那条平凡规则**需要事后信息**——要执行"买在未来 k 天内收盘最低的那天"，你必须先知道哪天最低。**它不可实施。** 而 `bottom_burst` 的入场是**因果的**：tb 用 `stop_confirm_bars` + trough-age 只凭历史数据确认止跌点。

⇒ 拿一个**用了后视的基线**去减一个**因果的 pattern**，会**系统性高估**被减掉的部分。"扣掉 k=5 平凡回踩后只剩 +0.0455"这个算式，减数与被减数不在同一信息集上。

**⚠ 但要诚实：这个反驳只削弱"deduction"，不削弱"warning"。** 有一层意思仍然成立且重要：
> label 是 `max(high[t+1..t+n]) / close[t] − 1`（`path2/eval.py:39`）——**分母是入场当日收盘价**。**任何把入场点压低的规则都会机械地抬高这个比值**，与选股能力无关。
> ⇒ 目标函数对**入场位置**的敏感度很大。**优化器可以追逐入场位置而非选股能力**，而且沿这个方向拿到的增益，一旦入场规则被轻微的前瞻污染，就会蒸发。

**⇒ 正确的表述**（我建议全队用这版）：
> **这不证明 bbb 的 lift 是假的；它证明目标函数存在一个「压低分母」的方向，自动搜索会沿它走，而人类的走势语义约束是目前唯一挡在这个方向前面的东西。**

### 4.9 标注集作为层①② 的抗过拟合证据（`team-lead` 的升格，我接受主体但收窄一处）

`skeptic` 证明：现有最强的抗过拟合防护——**平台证据**（"前几名差距小、是平台不是尖峰"）——**是参数邻域论证，无法迁移到层①②**，因为离散的拓扑/代码候选没有邻域。`team-lead` 由此把正例标注集升格为"层①② 唯一可迁移的抗过拟合证据"。

**我接受主体，理由成立且是三条独立的**：
1. **不可被 score 的刷分手法污染**——缩窗、选噪声、n 卡方差峰值这些花招，对"这 20 张图还抓不抓得到"完全无效（标注集是先验固定的，与 score 的度量方式无关）。
2. **对离散结构改动可迁移**——"改了拓扑之后还认不认得这 20 个走势"在任意两个候选之间都是良定义的；而"把判据改一点点 score 动不动"在离散空间里根本问不出口。
3. **不消耗 score 的 holdout 预算**——它是人给的第二维度。

**但「唯一」我要收窄成「唯一与 score 正交的一维」。** 反例：**时间 holdout（评分标准已有的"两个整年窗取最差 score"）和横截面 holdout（拆分股票池）同样不依赖邻域，对离散候选一样可迁移。** 它们不是"唯一"被排除掉的东西——只不过它们**仍然是 score 的重采样，与 score 共享同一套刷分弱点，且共享同一个查询预算**。所以准确表述是：

> **平台证据（邻域论证）不可迁移；时间/横截面 holdout 可迁移但与 score 同源、共享预算；标注集是唯一与 score 正交的一维。** 三者应叠加使用，不是替代关系。

**⚠ 一条 `team-lead` 论证 3 里没有、但必须补的代价**：**标注集也会被烧，只是烧得慢。**
如果你用同一组 20 个标注去筛 1000 个结构候选、只留下"全部保住"的那些，**你就是在向这 20 个样本做选择**——这是多重比较问题原样搬到标注集上。它不免费。

三条推论（都写进了协议）：
1. **闸必须保持粗粒度二值**（"全保住 / 没全保住"），**不要变成"保住了几个"的连续分**——连续分泄漏的信息量大得多，烧得快得多。
2. **标注集也要有查询预算**，只是比 score 的宽松得多（二值闸每次查询泄漏 ≤1 bit）。
3. **这反过来又是"人应降 K"的理由**：候选少 ⇒ 闸被查询的次数少 ⇒ 标注集烧得慢。**降 K 同时保护了 score 和标注集两道闸。**

## 5. D · 交互载体

### 5.1 判断：不要新建标注 UI

现有 `path2_web_ui/` 已经具备除"记录判断"外的全部要素：

| 要素 | 现状 |
|---|---|
| 候选队列 | `SidebarResultList.vue`——按 symbol / 每 pattern 命中数 / forward_return **可排序**的表，点击切股 |
| K 线与标记 | `KlineChart.vue` + 拓扑面板 + 3 档 level 分轨 |
| **区间选取** | `klineBrushHandler.ts` 的 brush **已经产出 `(start_bar, end_bar)`**——正是标注需要的窗口 |
| 失败详情 | `FailedAttemptsCard.vue` 渲染 `时段 [start, end]` + 每条 attempt |
| 逐对诊断 | shift+click → `scope=pair` 四通道短路 |

**唯一缺的动词是"记录这个判断"。**

**推荐路径（分两步，第二步按需）：**

**第一步 · 零代码路径（先走这个）**
人在现有 UI 上 brush 选区间 → `FailedAttemptsCard` 的表头**已经直接显示** `时段 [start, end]` → 人把一行文本粘进对话或一个文本文件：

```
XXXX 2025-03-10 2025-03-28 应命中 横盘6周后连续三根放量突破
YYYY 2025-06-02 命中但不是我要的 已经翻三倍后的继续突破
```

Claude 负责转成 `labels.jsonl`（含 bar→日期换算，用现成的 `_date_to_bar` 反向）。
**成本 0 行代码。** 每个标注比按钮多花 ~20 秒；N=20 时总开销约 **7 分钟**。

**第二步 · 一个按钮（等第一步证明标注真的用得起来再做）**
- 前端：brush 浮层加两个按钮「标为应命中」「标为误命中」+ 一个备注输入框
- 后端：`@router.post("/labels")` 追加一行 JSONL（`api.py` 已有 `@router.post("/params/save")` 的落盘范式可抄）
- 规模：约 1 个 endpoint + 1 个小组件

**为什么不选"批量出图 → 人看图片 → 回一句话"**：要写绘图脚本（新代码），而且**丢掉缩放与联动**——人恰恰需要拉远看形态、拉近看细节，静态图片把最重要的能力砍了。用户手里已经有一个更好的看图器在跑。

### 5.2 色盲约束

用户会混淆低饱和色相。两处必须注意：

1. **既有风险点**：`FailedAttemptsCard.vue::overlapClass` 用三个 `overlap-*` CSS 类表达 ⊆ 关系——这是纯色相的三分类，正是风险类别。若要动这个组件，顺手改成**带文字的 chip**（「框内」/「含框」/「部分」）。
2. **标注 UI（若做）**：verdict 必须靠**文字标签 + 填充/描边差异**区分，不靠色相。例：`应命中` = 实心填充 + 白字；`误命中` = 描边空心 + 深字。绝不用"绿=好/红=坏"这种纯色相编码。

## 6. 给 `arch` 的硬约束（人在环节点的 I/O 契约与预算）

工作流设计**必须**满足下列约束。标注了每条的来源：【实测】/【用户明确说过】/【推断】。

### 6.1 人的单位成本与疲劳阈值

| 判断类型 | 单位成本 | 来源 |
|---|---|---|
| **负例判定**（"这个命中是不是垃圾"，系统已把候选送到眼前） | **5–15 秒** | 【推断】——现有 UI 已是可排序候选表，点一行即切股 |
| **正例搜索 + 判定**（"这里该被识别却没有"） | **2–10 分钟** | 【推断】——需翻股翻时段，且"大涨"只是标签的代理，大多数要被否掉 |

**疲劳阈值**：20 个可一次做完（约 5–15 分钟）；50 个是上限且必须分批；**200 个不可行**。

⚠ **200 个不可行的理由不只是疲劳，更是【实测】的收益递减**：我用四种廉价结构信号试图收窄"该看哪些"，收窄倍数只有 1.0x / 1.12x / 1.24x / 1.01x / 1.77x（§4.3）。**队列筛不动 ⇒ 第 200 次注视的命中率和第 20 次基本一样低。** 所以"让用户看 200 张图"不是勤奋，是把 10 倍人时投进一个**收益已经平掉**的方向。

→ **硬预算：单次定案周期 ≤ 20 个人类判定 / ≤ 20 分钟。** 任何超出此预算的设计我都会否决。

### 6.2 人的判断可靠性（**这是我方案的真风险，未测**）

**【推断，无实测】** 我没有数据，不能把人的标注当无误差 ground truth 硬用。有结构性理由预期**边界不稳**：verdict 的对象是一个**区间**，而"横盘够不够久""回踩够不够深"本身是**连续量**，不是二值——边界样本上人前后不一致是可以预期的。

三条缓解（都已写进 §4.2 协议）：
1. **只要二分，不要打分**。1–5 分的稳定性远低于二分判断。
2. **强制一行理由**。逼人把判据说出来，既是审计凭据，也让日后的不一致可被发现和归因。
3. **append-only + provenance**（`labeled_at` / `labeler` / `provenance`）。漂移必须**可见**，而不是被静默覆盖。

→ **给 `arch` 的约束：不要设计任何"标注一旦录入即视为不可撤销真值"的环节。** 标注是**证据**，不是**公理**。

**⭐ 一个 40 秒的直接测法（`skeptic` 挑战 3，采纳——它把"未测"变成"可测"）**：
D 队列复检时，**把其中 3 张 K 线重复放进队列**（用户不知道哪几张重复）。10 项变 13 项，多花约 40 秒；跑两三个周期就得到一个**自一致率**。

| 自一致率 | 含义 |
|---|---|
| **≥90%** | `labels.jsonl` 可以当证据用，§4.9 的抗过拟合主张站得住 |
| **<70%** | **人的二分判断本身的噪声可能超过它要否决的那个 score 差异** ⇒ "3/10 判 bad 即否决"这类闸的假阳率会高得离谱 |

**它同时给 `arch` 那个"3/10 门槛"提供了标定依据**（他自陈那是全文唯一无依据的数字）：**门槛必须显著高于人自己的不一致率，否则闸在否决噪声。** 这也正是我建议他改"与基线对拍"的同一动机。

⇒ §6.2 的状态从「**最大未验证假设，无测法**」改为「**最大未验证假设，但有 40 秒测法，应在第一个周期就跑**」。

### 6.3 人能可靠产出的输出格式

| 格式 | 可行性 | 理由 |
|---|---|---|
| **区间 brush**（拉一段） | ✅ 可行 | 现有 UI 已产出 `(start_bar, end_bar)`；且匹配人的知觉对象（"这一段是启动"） |
| **二分勾选**（应命中 / 误命中） | ✅ 可行 | 认知负荷最低 |
| **一行自由文本理由** | ✅ 可行 | 人愿意写"为什么"，这是他最想说的部分 |
| **打分（1–5）** | ❌ 不可行 | 【推断】跨时点不稳定，见 §6.2 |
| **候选间排序** | ❌ 不可行 | 认知负荷 O(N log N)，且与 §4.6"人不排序"直接冲突 |
| **结构化多字段表单** | ❌ 不可行 | 会被跳过或胡填 |
| `expected_role`（"该由哪个 node 命中"） | ⚠ 仅可选 | 它要求用户懂 DAG 内部——**那是让人做机器该做的事**。可填则用，绝不强制 |

→ **人在环节点的 I/O 契约上限就这么宽：`(区间, 二分, 一行文本)`。** 别设计更丰富的。

### 6.4 人的比较优势（要具体，不要"感性判断"）

| 人**强**、必须在环 | 为什么机器做不了 |
|---|---|
| **形态语义同一性**："改完之后这还是我要的那个走势吗" | 意图只存在于用户脑子里，不可从数据推导；score 是意图的代理 |
| **前瞻泄漏的直觉识别**："它是偷看未来才找到的" | score 本身已被泄漏污染，无法自我发现 |
| **意图的重新表述**：结果不对时说出"我其实要的是……" | 这是**规格的修订**，机器只能执行规格 |

| 人**弱**、不该让人做 | 机器的替代 |
|---|---|
| 判断哪个候选 score 更高 | n=数万的统计，人眼完败 |
| 估计一个改动的全局影响 | `run_regress` **31 秒**给出精确 added/removed（`biz` 实测） |
| 归因"死在哪道判据" | `GateFailure` 已带 `code_location` 源码行号 + `threshold_param` |
| 数值一致性 / 算术效应 / 缩窗检查 | `tune-pattern-strength` 的诚实性三检查已覆盖 |

**⛔ 人的通道有一个结构性盲区：它只产出「放松 / 新增」，永远产不出「删除」**（`skeptic` 挑战 1，采纳）

上面那张表漏了一格。人的三种强项 + 队列 P 的输入形态（"这里该被识别却没有"）**合起来只能生成一类候选：让更多东西通过**。
用户会说"它漏了我要的股票"；**用户永远不会说"你这个 tb 节点净贡献为零，删掉它样本量翻倍"**——因为那不是人在 K 线上看得见的东西。

`skeptic` 的实测恰好落在这个盲区里（2025 全年 · 全宇宙 · confirm 口径）：

| 配置 | n | median | **score** |
|---|---|---|---|
| `bo_only` 基线 | 29502 | 0.1234 | 0.0000 |
| **bbb 定案（含 tb）** | **423** | 0.2293 | **0.0719** |
| **`burst_no_tb`（整个删掉 tb 节点）** | **974** | 0.2142 | **0.0754** |

配对分解（同一批 423 setup，**只改入场日**，因果可比）：`bo 当日买 0.3592` vs `tb 确认日买 0.2293` ⇒ **纯选股 +0.2358、纯入场时机 −0.1299（负）。等待 tb 确认是净负贡献。**

> **⇒ 分工声明：人的通道只生成「放松 / 新增」类候选。「删除 / 简化」类候选必须来自机械消融（node-subset / where 子句 / edge 的逐个删除枚举），不能指望人提出。**

**这条对本节的论点是加强不是削弱**：它把"人时不可压缩"精确成 **"在删除方向上，多投人时的边际收益是零——因为那个方向人根本看不见"**。⇒ 机械消融与人在环是**互补的两条腿**，缺一条就系统性地只往一个方向走。

**⚠ 顺带修正我自己 §4.8.2 里的一处推理**：我在反驳 `skeptic` 的入场算术 deduction 时说"bbb 的入场是因果的，所以不该被减掉"。**结论仍对（后视基线不能减因果 pattern），但我当时暗示 bbb 因此没在吃入场杠杆——这条实测显示 bbb 的入场时机贡献是 −0.1299，即它不但没吃这个杠杆，反而在倒贴。** 我的反驳因此比我原以为的更成立。

### 6.5 节奏：必须异步批处理，不能同步阻塞

**结论：攒成一批、离线做完、落盘；循环读文件，不挂起等人。**

三条独立理由，任何一条都足够：
1. **【实测·`mech`】`Workflow({resumeFromRunId})` 只在同一 session 内有效**，跨 session 就是起新 run、丢已验证进度。人类看 K 线是**随时中断、可能跨天**的活动 ⇒ 挂起等人 = 进度必丢。
2. **【实测·`mech`】`AskUserQuestion` 只在主会话可用** ⇒ workflow / subagent / teammate 内根本问不了人。
3. **【实测·`biz`】fan-out 并行不买吞吐**（K=2 → 52.2s vs 串行 49.6s，K=4 → 109.7s vs 99.2s，都更慢；单个 eval 已吃满 CPU）⇒ **"后台批量搜索"与"人在环交互式评估"会互抢 CPU**。设计上必须**显式排他或排队**，不能想当然地"让机器在后台跑着、人同时看图"。

→ **载体（采纳 `mech` 的 web-loop 范式，但要分成两个生命周期不同的文件）**：

| 文件 | 语义 | 生命周期 |
|---|---|---|
| `human-hint-r{N}.md` | **瞬时操舵**——这一轮想让它往哪偏 | 消费后 `mv` 成 `.consumed.md`，**用完即弃** |
| `path2_apps/<app>/labels.jsonl` | **持久资产**——语义 ground truth | **append-only、进 git、永不消费掉** |

**这两个不能合并。** `mech` 的 hint 机制解决"人怎么插话"，我的 labels 解决"人的判断怎么不丢"。把 labels 当 hint 消费掉会重蹈 2026-07-15 的覆辙（§4.6）。

### 6.6 色盲纪律

**【用户明确说过】** 用户会混淆低饱和色相（如浅黄 vs 浅绿）。具体纪律：

- **区分靠饱和度 / 亮度 / 白字 / 文字标签，不靠色相。**
- verdict 编码：`应命中` = **实心填充 + 白字**；`误命中` = **描边空心 + 深字**。**禁止**"绿=好 / 红=坏"这类纯色相编码。
- **既有风险点**：`FailedAttemptsCard.vue::overlapClass` 用三个 `overlap-*` 类表达 ⊆ 关系，是纯色相三分类。若要动这个组件，顺手改成带文字的 chip（「框内」/「含框」/「部分」）。

### 7.1 第 2 条展开：`scan-top-miss.py` 的排序口径是错的（`skeptic` 发现，我现场核实并加严）

**`skeptic` 指出**它按窗口涨幅排序而非 label 口径。**我核实后发现失配比他说的更彻底——是两处，不是一处**：

| | `scan-top-miss._compute_pct_change`（`:143-153`） | label 口径 `path2/eval.py::match_forward_returns`（`:39`） |
|---|---|---|
| 统计量 | `close[end] / close[start] − 1` —— **端点收盘** | `max(high[t+1 : t+n+1]) / close[t] − 1` —— **窗内最高** |
| 锚定 | **整个用户指定窗口** | **从每个买点 t 起算的固定 N 日** |

⇒ 一只股票**先大涨再全吐回去**，在现有排序里得分 ≈ 0（端点持平），但在 label 口径下**可能是高分机会**（从某个买点起 20 日内 max-high 很高）。**这正是"漏掉的机会"最典型的形态，而现有排序恰好把它排到榜尾。** 反之亦然。

**修法（小、精确、可交付）**：把排序键换成**窗口内可达到的最佳 label 值**——对窗口内每根 bar `t` 算 `max(high[t+1:t+21])/close[t]−1`，取窗口内的 **max**（读作"这段里存在过的最好入场"）。
⚠ 注意 max 会偏向高波动股；若发现榜单被垃圾波动股占领，改用高分位（如 p90）更稳。**这一步该看真实榜单再定，别先验拍死。**

**`skeptic` 关于失败模式的类比我确认成立**：用一个与目标函数不一致的代理去排队列，正是 2026-07-15 那次 −79% 的同款错误（那次是用"更严"当代理，没过 label 闸）。而且这个错误在这里更隐蔽——**它不影响任何统计结论，只是悄悄把人的眼睛引向错误的样本**，而人的眼睛是全流程最贵的资源（§6.1）。

**并行化收益量化**（对齐 `biz` 实测）：现状 = 全历史 + 单进程 = **~64 分钟**；`run_eval` = 切窗 + 26 worker = **23–50 秒**；`biz` 另发现官方 `run_eval` 还有 **1.7x 白拿加速**（`ex.submit` 逐 pkl → `ex.map(chunksize=20)`）。**两处工程欠账合计约 100 倍。**
