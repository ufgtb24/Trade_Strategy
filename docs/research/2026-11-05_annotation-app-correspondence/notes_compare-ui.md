# compare-ui：怎样让 compare 看得出 app 错在哪

本文件中所有项目内路径均相对 repo root。只分析、没改任何正式代码。事实引用同目录 `repro/` 里 evidence / skeptic 已跑出的产物（`daily_*.txt`、`tb_trace.py`、`skeptic_chance_overlap.py`）；自己只加了一个只读脚本 `repro/compareui_endcover.py`（两种「认出」判法的对比，见 2.8）。

## 结论（先读这段）

1. **「不知道错在哪」这一半，毛病在 compare 把 app 只露出一角**（「装不下」那一半是 app 的 node 粒度问题，归 framework）。 现在的 compare 是「在标注图上贴 app 的碎片」：只画 mapping 写到的那一个 node（这一版只有 burst），tb、tb_seg 这些真正决定哪天买的 band 一条都不画；主视图已有的档位按钮、拓扑面板、hit 聚焦、诊断侧栏在 compare 里全藏了；悬停连 node 名都不给。所以用户看到的只有结果（hit 条和 ▼），过程全被挡在外面。
2. **改法：compare 改成「主视图原样 + 标注叠上去」，mapping 只决定谁挨着谁，不决定画不画。** 两边成三对对上：用户的框 ↔ app 的事件（band 上），样本日 ▲ ↔ 买点 ▼，样本跨度 ↔ hit 的 bracket。每个特征的框轨插在它 map 到的 band 正上方；app 独有的 band 照拓扑顺序留在原位、表头标 `app_only`；用户独有的特征轨排在最后、标 `unmapped`。
3. **「怎么来的」分两条路回答，都只给类别、不给数字。**
   - 点一次 hit：亮出它由哪几个事件组成、每条 where 和边都过了（复用主视图的 hit 聚焦和逐次命中留痕）。
   - 点一个样本：在 `selection` 页按 node 列出「这个样本的时段里，每个 node 走到了哪一档、断在哪」——没检测到（附 detector 短路的闸名）、检测到但哪条 where 没过（where 名）、够格但边没连上（哪条边）、买点 node 在样本日当天是什么状态。断在的第一个 node 就是「错在哪」。
4. **现有设施能复用大半。** CRNC 12-13、RGTI 11-29 为什么没买，用现在的 new_step、不写新 detector 就答得出类别：图上一眼看出断在哪条 band（tb_seg 在 ▲ 底下断开、tb 在 ▲ 前一天结束），点一下样本读出原因（前一段 `outcome: rise` 即追涨收段；`machine_outcome: break` 即跌破支撑、机器结束）。答不出的只有「支撑放在哪一价」这一层，它藏在企稳状态机内部；framework 同意为企稳状态机单独加一条逐根状态旁路（只吐状态、原因类别和价位线），但不推广成通用协议——照 framework 的做法新写的复合 detector 把判断全写成 where，诊断里本来就看得到。
5. **spec 6.2 的 tag 本来就是为「错在哪一层」设计的**（说明书原话：「哪一层断了，就知道是 node、边还是整体的问题」），但它只透过 mapping 看：看不到 app 独有的部分，mapping 自己错了也看不出，「认出」又只要一端靠近——skeptic 实测这条判法把 9 个「站上新平台」框里的 8 个判成认出了阶跃，而阶跃只有 1～8 根宽、框有 18～53 根，同宽框随便挪个地方也有中位数 25% 的机会被判认出。处理：
   - 提前到第一段：compare 对等显示、hit 聚焦、样本诊断块、`tier tag`（含 `missing`，配改过的认出判法）、`match tag`；
   - 留在第二段：`diff tag`、`link tag`、pattern 页按 mapping 分层、`chance_high`、⚑；
   - 设计要改：「认出」改成「事件盖住框的终点」（起点是用户凭印象画的，不看），并且只用于同粒度的配对——第一版把三段的框对到只有阶跃的 node，任何重叠判法都救不回来（新判法只是不再说「认出了」，剩下判认出的 3 个也是碰巧）；框里的关键位置（如阶跃在哪）要用户画子框、mapping 对到复合事件的 child slot 才判，界面不从 K 线替用户猜；`chance_high` 按 tag 报的那一档算；mapping 允许一个特征对一个 node 或一个 child slot、属性对一条 where；「不给数字」明确成「给类别、不给数字」。
6. **和全仓改名的先后：改名 02 → 03 先跑完，期间只改 spec、不动前端；03 之后再做 compare 重排**，顺带吸收界面改进第 10 条（档位按钮）和第 6 条（拖动）；第 9 条（左侧列表）独立，随时可插。
7. **和用户「每条特征轨配一个 detector」的想法不冲突，但界面改动两种情况下都要做**：就算特征和 node 一一对上，app 仍有用户没标的内部机制（bo、阶跃那串突破），mapping 也可能写错，买点仍由 detector 内部决定——这三样只能靠「对等显示 + 样本诊断」看出来。一一对上之后，成对排列会更整齐，`tier tag` / `missing` 的含义也更干净。framework 主张的「每天一个截到当天的实例」会让一条 band 上叠几十个同起点的实例、hit 数乘上天数；界面按「同一族」折成一条、每天一格上色（2.9），bracket 轨上的样子和现在的「一条 hit 带一串 ▼」几乎一样，读法不变。

## 一、现在为什么看不出原因（事实）

| 现象 | 出处 |

| compare 只画进了 mapping 的 node，「没进 mapping 的 node……都不画」 | `path2_web_ui/src/render/compareOverlay.ts:8` |
| mapping 一个特征只许对一个 node；new_step 的 mapping 只有 `站上新平台 → burst` 一行 | `path2_web/mapping.py:21`、`path2_apps/new_step/mapping.yaml` |
| annotate、compare 下不显示档位按钮、pattern、参数、拓扑、诊断侧栏 | `path2_web_ui/src/components/ChartArea.vue:6`（`v-if="!annotating"`）、`:49-50`；`annotating` 含 compare（`stores/view.ts:260`） |
| compare 悬停只给档位和起止，「不给 node（那等于露出 mapping）」 | `path2_web_ui/src/render/annotateLanes.ts:22` |

| compare 其实已经在后台取了诊断数据（qualified 档就靠它），只是没往外显示 | `stores/view.ts:1040-1055`（`appId` 在 compare 下取现算的 app） |

V-S1 的 new_step 一共四个 node：bo（主图三角）、burst、tb（企稳状态机容器）、tb_seg（企稳段，买点就是段里的每一天）。compare 只露出 burst，于是：

- 图 11 的两条 hit 里密密麻麻的 ▼，全是 tb_seg 的日子——tb_seg 那条 band 在 compare 里根本不存在，用户无从知道 ▼ 为什么落在这些天；
- 图 12、13 的「站上新平台」框里只有两小块 burst，用户看到的是「app 认出的东西比我的框小一大截」，却看不到紧跟在 burst 后面、真正填满那段时间的 tb。

**没买的样本，原因在哪一层**（取自 `repro/daily_*.txt` 的企稳状态机逐根回放，回放已与 detector 逐段核对一致）：

| 样本 | app 那天的状态 | 用户该在界面上看到的原因（类别） |
|---|---|---|
| RGTI 2024-11-29 | 当天大涨，企稳段因「涨出波动且过前峰」收口，状态机转为上涨段 | tb_seg 在样本日前一天收口，收口方式 `rise`（追涨） |
| CRNC 2024-11-29 | 同上 | 同上 |
| CRNC 2024-12-13 | 前一天收盘跌破被抬高的支撑，这台状态机已结束 | tb 在样本日前一天结束，`machine_outcome: break`（跌破支撑） |
| SMX 2025-12-02 | 样本日附近没有哪次 hit 的状态机在跑（回放只覆盖进了 hit 的状态机，没进 hit 的没回放） | 要往上游看：burst 有没有、够不够格、边连没连上，或状态机跑了却没进 hit |

这几条原因，现有界面一条都给不出：tb 和 tb_seg 不画；收口方式和机器结束方式虽然就挂在事件上（`tb_seg.outcome`、`tb.machine_outcome`），悬停不显示；「被抬高的支撑」这种状态机内部量，连事件上都没有。

## 二、界面方案

### 2.1 三种模式是同一张图上的图层组合

照 v-s1-notes 第 8 条的原则「标注只往主视图上加东西」：

| 模式 | 标注层（框、样本、样本跨度） | app 层（全部 band、hit、▼、档位按钮、拓扑显隐） | 带数字的诊断（诊断侧栏、框选查闸、两事件查边） |
|---|---|---|---|
| `annotate` | 开 | 关 | 关 |
| `compare` | 开 | 开 | 关（只给类别，见 2.6） |
| `app` | 关 | 开 | 开（就是今天的主视图） |

三种模式共用一套图、一套拖拽缩放；切模式只开关图层，不换画法。今天 compare 那套独立的标注轨画法（`compareOverlay.ts` 的「把 event 塞进特征轨」）整体退役。

### 2.2 compare 的布局

```
主图   K 线 + 成交量 + 用户样本 ▲/△；app 的主图标记（bo 三角、pk 线）照拓扑面板开关，默认关
──────────────────────────────────────────────────────────────────────────────────
level  [detected] [qualified] [in_hit]          topology  burst ● tb ● tb_seg ● bo ○ pk ○
──────────────────────────────────────────────────────────────────────────────────
bracket  user  ┆- - - - - - - - - - - - - -▲a     - - - - - - ▲b - - - - - - - - - - -▲c
               ┆                            matched           matched                unmatched
         app        ①[▼  ▼▼▼]                     ②[ ▼▼▼▼ ▼▼▼▼▼▼▼▼▼▼▼▼▼▼ ]
──────────────────────────────────────────────────────────────────────────────────
┌ 站上新平台   ┆- - - - - - - - - - - - - - - - - - - - - - - - - - - - -┆        ← 用户的框（虚线）
└ burst                       ▇                    ▇                              ← 和它成对的 band
  tb        app_only            ████████████        ███████████████████
  tb_seg    app_only               ██ ███             ██ ███████ ███████            ← ▼ 的来源一目了然
──────────────────────────────────────────────────────────────────────────────────
  底部平稳   unmapped  ┆- - - - - - - - - - - - ┆
  unnamed
```

排法的规则（全部只用拓扑、mapping 和标注，不认任何具体事件类型）：

1. **band 一律照主视图的顺序**（拓扑先后），每个 node 一条，档位、着色、lane 分行、`tier tag` 都和 `app` 模式一样。上下读下来就是 app 的因果链，「断在哪」往下找第一处断口就行。
2. **每个特征的框轨插在它 map 到的第一个 band 正上方**，左侧一道竖线把「框轨 + 它对的所有 band」框成一组。一个特征对几个 node（如「站上新平台」将来对 burst → tb → tb_seg 一整串）就把这几条 band 都框进来；几个特征对同一个 node，就几条框轨叠在它上方。
3. **app 独有的 band 留在原位**，表头挂 `app_only`；不进求解、只显示的 node（如 pk）照主视图默认收起。
4. **用户独有的特征轨（没 map 的）排在最后**，表头挂会话蓝的 `unmapped`；`unnamed` 轨永远最后一条。
5. **bracket 轨**：上面几行是用户的样本跨度（虚线，右端 ▲），下面几行是 app 的 hit（琥珀实心条，条里 ▼ 是买入日，第一段已做）。样本跨度和 hit 跨度本来就不是同一种东西（前者到样本日为止，后者包括买点之后的收尾），真正该成对比的是 ▲ 和 ▼；所以 ▲ 下方挂 `match tag`，让「这个样本 app 买没买」不用数 ▼ 也看得出。

为什么选「band 原位、框轨插进去」而不是「标注一块、app 一块上下分开」：分开排最省事，也做到了对等，但一个框和它对的 band 可能隔着七八条轨，用户要上下来回对时间，正是「看不出哪个特征没被认出」的老问题；插在一起则每一对都上下贴着，一眼看出大小、位置差在哪。分开排可以当实现上的第一步，不建议停在那里。

### 2.3 「这次 hit 是怎么来的」：点 hit

- 点 bracket 轨上的一条 hit，或它里面的一个 ▼：这次 hit 用到的事件在各条 band 上照常亮，其余变淡——这是主视图现成的 hit 聚焦（`stores/view.ts` 的 `focusedMatchId` / `highlightedEventIds` / `markedMatchIds`，`render/chart.ts` 的 `makeRenderBracket`）。
- 点的是 ▼ 时，再把这一天所在的那段买点事件（这一版是那段 tb_seg）单独加粗：「这天能买，是因为它落在这段企稳段里」。
- `selection` 页列这次 hit 的组成：node → 事件起止（日期）、每条 where 和每条边过没过（取 `predicate_trace` 里的 `satisfied`，不取实测值和门槛）。

### 2.4 「这次为什么没 hit」：点样本，看 `diagnose`

选中一个样本时，`selection` 页在样本信息下面多一块 `diagnose`（沿用词表里「node 诊断」的叫法，`path2/GLOSSARY.md:98`）。它是主视图诊断侧栏「node 漏斗」的一个缩小版：只看这个样本的时段，只给类别。

```
selection
  sample   c · pos · 2024-12-13            match  unmatched
  diagnose   2024-09-17 … 2024-12-13
    node     reached   on_sample_date   reason
    burst    in_hit    —
    tb       in_hit    ended            machine_outcome: break      ← 状态机前一天已结束（跌破支撑）
    tb_seg   in_hit    none             outcome: break
```

每一行的算法（纯投影，前端用已有接口就能拼出来）：

- **时段**：从这个样本最早的成员框起点到样本日（`path2/GLOSSARY.md:171`）；没有成员框时取样本日往前 `NEAR` 根（默认 40，待验证）。
- **`reached`**：这个 node 在时段内的事件走到的最深一档：`in_hit` / `qualified` / `detected` / `none`。
- **`on_sample_date`**：只对买点 node（app 的 `eval_meta()` 声明的那个）及其容器填：样本日当天有没有它的事件、容器在样本日前是不是已经结束。
- **`reason`**，按档位分：
  - `none`：时段内这个 node 的 detector 短路过哪些闸（闸名，取 `/diagnose?scope=time`，框 = 时段）；一道都没有就写「时段内没有上游输入」。
  - `detected`：最接近的那个事件没过哪几条 where（where 名，取诊断数据的 attr 行；compare 已经在取这份数据）。where 照 spec 6.1 用用户的词命名，用户读得懂。
  - `qualified` 但没进 hit：它在哪条边上找不到伙伴（取诊断数据 rel 行的 `ok_src_ids`；现成数据只能说「有没有」，要说「差在哪一类」需要后端按事件存原因，见第三节）。
  - 事件上的类别字段（如 `outcome`、`machine_outcome`）原样列出；数值字段不列。
- **第一处断口加粗**：从上往下第一个 `reached` 比上一行浅、或 `on_sample_date` 为 `none` 的那一行。这就是「错在哪」。
- **悬停注明这是局部检查**：每个 node 单独查，单个 node 都过不代表能凑成一次 hit（`path2/dag/diagnose.py` 开头的说明：逐事件的失败归因受求解路径影响，本来就只能按 node 局部查）。

**一眼与一点（回答 skeptic 的问题）**：用现在的 new_step、不写任何新 detector——

- 一眼（图上，不点）：CRNC 12-13 的 ▲ 正上方，tb 那条 band 在前一天结束；RGTI 11-29 的 ▲ 正上方，tb_seg 那条 band 在前一天断开。「断在哪条 band」不用点就看得出。
- 一点（点 ▲，读 `diagnose`）：CRNC 12-13 →「状态机前一天因跌破支撑结束」；RGTI 11-29 →「前一段企稳段因涨出波动且过前峰收口（追涨）」。这两条类别都是事件上现成的字段（`tb.machine_outcome`、`tb_seg.outcome`，`path2_web/serialize.py` 的 `_event_to_dict` 已把它们平铺进 JSON），不需要新数据。
- 答不出的一层：「支撑被抬到了哪个价、用户心目中的支撑在哪」、「追涨的尺子为什么这么短」。前者要 2.5 的价位线；后者是数字（尺子的长度），按 2.6 不进 compare，属于会话和调参的事。

对 V-S1 那几个没买的样本，这块会这样说：RGTI / CRNC 11-29 → `tb_seg` 行 `on_sample_date: none`，前一段 `outcome: rise`；CRNC 12-13 → `tb` 行 `ended`、`machine_outcome: break`；SMX 12-02 → 断口在 burst 或 tb 那几行（具体哪一行，现有回放没覆盖，要实跑才知道）。用户读到这里就能对会话说「追涨的界线不对」「支撑取法不对」，这正是结构层面的修法，不需要看任何数字。

### 2.5 企稳状态机的逐根状态（只为它做，不推广）

2.4 能说出「段在前一天因追涨收口」「机器因跌破支撑结束」，但说不出「哪条支撑」——支撑价、峰、谷是状态机的内部变量，事件上没有。`repro/tb_trace.py` 证明：把状态机逐根回放一遍，每一天「为什么买 / 不买」都能写成一句类别化的话（不再创新低 → 开段 / 涨出波动且过前峰 → 收段（追涨）/ 跌破支撑 → 机器结束）。

framework 的结论（`notes_framework.md`「回答 compare-ui 的三个问题」第 2 条）：这条旁路框架上可以接受（和 `on_gate` 一样可选、默认关、不进求解、只用当根及以前的数据），但它是给「判断藏在状态机里」的 detector 打的补丁；照「detector 只切段、判断全写成 where」写的复合 detector，每天的实例自带每条 where 的结果，`diagnose` 块直接列出没过的 where 名就够了。所以只为企稳状态机（第一版或改过的）做，不当通用协议。界面上：

- 买点 node 的 band 下方多一条细的状态条：每根 K 线一格，按状态分深浅，转换的那根挂一个小记号，悬停写原因类别；
- 价位线（如支撑）画在主图上，深灰细线，跟参照层的峰线同一种画法（spec 5.7），选中某台状态机时才画；
- 只给类别和线，不给数字，符合 2.6。

这条不做，2.4 仍然成立，只是用户要多推一步（「收口方式 `break` → 一定有条支撑被跌破了」）。

### 2.6 「不给数字」的边界

spec 1.4 与说明书第七节第 9 条的理由（看到实测值和门槛，人会一张张放宽，app 变成拟合那几张图）照旧成立，本方案不碰。要明确的是这条线划在哪：

- **compare 里给**：档位、node 名、where 名、边是哪条、闸名、事件上的类别字段（收口方式之类）、价位线的位置（图形，不写价格）。
- **compare 里不给**：实测值、门槛、间隔根数、价格数字。
- **要看数字切 `app`**：主视图的诊断侧栏、框选查闸、两事件查边（`PairDetailCard`）照旧都在那里，一键可达。

现在的 compare 比这条线还严（连 node 名都藏），那是为了第一段「不显示 mapping」；对等显示以后 band 表头本来就写着 node 名，这条限制随之取消。

### 2.7 配色与文字

- 用户的框、样本跨度：虚线黑；app 的 band：实心，`in_hit` 画 node 本色、`qualified` 深灰 `#9ca3af`、`detected` 浅灰 `#d1d5db`（spec 4.4 不变）；hit 琥珀实心；`unmapped` 会话蓝；`unmatched` 正样本朱红。
- **要改的一处**：主视图里有两样东西用了虚线——候选 bracket 的琥珀虚线描边（`render/chart.ts:1226`）、被吃掉的峰（`render/chart.ts:1260`）。合进 compare 后会和「虚线只表示用户画的」（spec 4.4）撞；compare 下这两样换成实线加深浅区分。
- 新出现的界面固定文字：`app_only`、`diagnose`（沿用词表）、`reached`、`on_sample_date`、`none`、`ended`。照 `GLOSSARY-MAP.md`「命名规则」起，交付前列给用户过目。

### 2.8 「认出」的判法要改

spec 6.2 的认出：事件和框交叠，并且事件「一端就够」落在框外 2 根以内（`.scratch/annotation-path2/spec.md:540`）。这条判法当初防的是反方向的错——框画得松、事件稍出界就被判 `missing`（spec V-01-2）。但它对图 12 这种「框长两个月、事件只有几根」的情形会判成认出：事件完全在框里，两端都满足「不超出框外 2 根」。用户的原话是「根本不是一个东西，连判断准不准都不配」，tag 却会说「认出了」，这是在替 app 打掩护。

skeptic 的实测（`repro/skeptic_chance_overlap.py`）：9 个「站上新平台」框里 8 个被判成认出了阶跃，而认出的那一块只有 1～8 根宽、框有 18～53 根；同宽的框随机挪 40 次，被判认出的比例中位数 25%、最高 57%，4 个框会挂 `chance_high`。

怎么改，要同时照顾三件事：

- 图 12 这种「框里某处有一小块」不能算认出（用户的判断）；
- 框的起点是用户凭整体印象画的，同一张图重画很稳、跨图差很多，按任何规则从阶跃往回推都推不准（`notes_framework.md` 第 3 节末「框的起点对不准，只认终点」）——判法不能看起点；
- 还在进行中的东西（回踩、企稳段）事件会越过框的终点继续走，不能因此判成没认出（spec V-01-2 当初防的就是这个）。

**建议的判法：事件盖住框的终点才算认出**——事件和框交叠，并且事件的跨度包含框的终点（前后各放宽 `TOL` 根，默认 2，待验证）。起点一律不看。框的终点有意义：成员框一律在样本日当天或之前结束，终点就是「用户站在那天看到的样子」。

同一批框上两种判法的对比（`repro/compareui_endcover.py`，只读；碰巧率的种子与 skeptic 脚本相同）：

| | 现行（一端就够） | 建议（盖住终点） |
|---|---|---|
| 9 个框里判成认出（全部检测到的阶跃） | 8 | 3（RGTI 两个、SMX 一个） |
| 同宽框随机挪 40 次的认出比例，中位数（最高） | 25%（57%） | 8%（18%） |
| 只算过了 where 的阶跃，碰巧率中位数（最高） | 8%（18%，skeptic） | 0%（8%） |

**这张表不能读成「新判法认对了 3 个」**（skeptic 指出，同意）：9 个框里 8 个的终点就是样本日，框对的又只是阶跃，所以「盖住终点」在这里量的是「样本放得离阶跃有多近」。剩下的 3 个（RGTI 两框、SMX）只是样本离阶跃近，CRNC 阶跃后 5 根放样本就判没认出。新判法在第一版上的作用只有一个：大多数框不再被说成「认出了」，不再替 app 打掩护；它挑出来的那 3 个同样是碰巧。

根子在粒度：一个装了旧平台 → 阶跃 → 新平台三段的框，对到只有阶跃那一段的 node，任何一条按时间重叠的判法都救不回来。所以：

- **整体判法只管「框 ↔ 同粒度的 node」**：一段的框（如「底部平稳」）对一段的 node；三段的框对 framework 的复合事件（实例跨度到当天）。这时「盖住终点」就是「样本日那天 app 认为这个特征在场」。框对的就是买点所在的复合事件时，它和这个样本的 `match tag` 说的是同一件事——两者按构造一致，不算额外证据，`diagnose` 里合成一行，不重复挂。
- **框里的关键位置，要用户画出来才判**：skeptic 提议对三段框按段判（阶跃那段看 app 的阶跃落没落在框里、和框内涨得最猛的那几根对不对得上；新平台那段就是 match；旧平台起点只报不判）。方向同意，落法不同：「框内涨得最猛的那几根」要在对照层从 K 线现算，是把走势语义写进 path2_web，越过「后端纯投影、前端类型无关」的红线；而且用户并没有标出阶跃在哪，界面替用户猜是哪几根，又回到「拿现有的应付」。标注格式本来就支持框套框：用户在「站上新平台」里再画一个「阶跃」子框，mapping 把它对到复合事件的阶跃 child slot（`node.slot`，framework 第 6 节），这一对就用同一条整体判法，阶跃位置对不对是用户自己标的、app 自己认的，两边都有出处。用户没画子框时，阶跃 child 的 band 照样挨着画（2.2），由眼睛看，不挂 tag。（skeptic 已接受：阶跃只有 1～8 根、边界最清楚，是整张图上唯一值得对边界的地方；子框可选、不强制。）
- **framework 的「两条合起来才算认出」怎么在界面上表达**：framework 提议复合事件的认出分两条——①框终点被一个截到当天的实例盖住（按构造几乎必成立，只说明两边比的是同一种东西）；②用户说的阶跃落在那个实例的阶跃 child 里（evidence 原型 5/6 可复现，这条才带信息）。界面上拆在两个框上各挂各的，不合成一个 tag：父框（「站上新平台」）的 tag 只说①，即「样本日那天 app 认为这个特征在场，到了哪一档」；②挂在用户画的「阶跃」子框上，由子框和阶跃 child 那一对用同一条整体判法给出。合成一个 tag 会藏住是哪一条没过，正违背「看得出错在哪」。②里的「用户说的阶跃」只能来自子框：没画子框时，界面不从 K 线去找「框里的阶跃那几根」（同上，红线），父框 tag 的悬停写明「台阶位置未核对，在框里画阶跃子框可核对」，不替 app 说位置对。
  - 不采用的弱版：不画子框时核对「实例的阶跃 child 落在父框里」。父框从旧平台盖到样本日，阶跃几乎必然在里面，核对它不带信息（framework 同意不采用）。framework 会在汇报里给用户一条不强制的建议：画「站上新平台」时顺手把阶跃那一两根框出来。
- **旧平台起点只报不判**，和 framework、skeptic 一致；这里的「报」就是成对排列里两条的左端摆在一起，不写差几根（2.6）。
- **整体判法对一段的框是否也该看起点**：现有标注里只有「站上新平台」配了 node，「底部平稳」还没有，判不了。默认先只看终点，等一段的框有了配对的 node，再照 V-01-1 的做法逐个列出「看起点 / 不看起点」会让哪些框换结论，请用户只看方向。

另外两点：

- **状态只用现有的词**：认出就照档位写 `in_hit` / `qualified` / `detected`，否则 `missing`。悬停区分「有交叠的事件，但没有一个到框的终点」和「这段时间里根本没有这个 node 的事件」，不另起新词。
- **`chance_high` 按 tag 报的那一档算**。spec 6.2 没写按哪一档算，这本身是个缺口（skeptic 指出）；只算全部检测到的会严重高估。若采用 framework 的「每天一个截到当天的实例」，只要阶跃还在，框终点那天就一定有一个实例在场，按检测档算的碰巧率会接近 100%——这正是「按构造对上、不算认得准」的意思，所以更要按 `qualified` 那一档看。

这改的是 spec 6.2 的判法，不动拍板层 1.4 的字面（输出仍只给状态，不给差几根），但它会改变用户看到的结论，交付时要讲给用户（见第五节 C2）。

### 2.9 「每天一个截到当天的实例」怎么画（回应 framework）

framework 主张把样本日当天还在进行的特征（新平台）做成每天一个实例：第 t 天的实例跨度是 [旧平台起点, t]，一个买点日对一个 hit（`notes_framework.md` 第 3 节、第 5 节第 4 条）。直接画会出两个问题：一条 band 上叠几十个同起点、越来越长的条；bracket 轨上的 hit 数乘以天数。

折叠办法：

- **认族**（和 framework 定的形状）：先用「同 node、同起点」，不加任何声明——burst 的前缀族同起点，复合事件同一个阶跃的实例共用一个旧平台起点，也同起点。只有实测发现两个不同阶跃撞上同一个起点时才加声明，声明放在事件类上（类级属性「按哪个 child slot 认族」），不放 NodeSpec：族是 detector 怎么产实例的性质，不是 dag 的声明。后端序列化时把族键带给前端，前端照旧不认类型。
- **band 上一族一条**：画成从族的起点到最后一个实例终点的一条，条里每一天一格，按那天那个实例的档位上色（`in_hit` 本色 / `qualified` 深灰 / `detected` 浅灰）。一眼看出「这一族在哪些天够格、哪些天不够」——这正是用户要的「这天能不能买」。档位色之间靠深浅拉开，符合色盲配色规则。
- **bracket 轨上一族一条**：和现在一样，一条琥珀条带一串 ▼，只是每个 ▼ 现在是一次 hit。点一个 ▼ 就聚焦那一天的 hit。
- **选中样本**：`diagnose` 直接取终点等于样本日的那个实例，列出它没过的 where 名（framework：「截到样本日、各 node 的候选卡在哪条 where」）。
- **计数**：样本表、`match tag` 都按样本找最近的那一天的 hit，不受 hit 数乘天数影响；要显示「这只股票有几次 hit」时按族数，不按天数。评估口径（一天一票还是一族一票）不归界面，见 framework 第 5 节第 4 条。

这套折叠和现在 bracket 轨上「一条 hit 带一串 ▼」看上去几乎一样，用户的读法不变；变的是每一格、每个 ▼ 背后都有一个能单独点开的实例。

### 2.10 compare 读数要稳：沿用整段跑

framework 发现 new_step 有没有 hit 取决于 K 线从哪天开始传入（越过的峰可能登记得很早，首部缓冲盖不住；GEVO 2024-09-13 窗口从 2024-01-05 起有 hit、从 2024-03-01 起没有）。对 compare 的影响：**现在的 compare 不受这个影响**——它跑 app 时从这只股票的第一根 K 线跑到训练段末日（`stores/appLink.ts` 的 `WHOLE_HISTORY_START = '1900-01-01'`），和视图拖到哪无关；诊断数据也按同一窗口取（`stores/view.ts` 的 `appWindowOf` 取这次运行的窗口）。受影响的是主视图的扫描和单股预览（从扫描的起点往前减缓冲）。所以 compare 改建在主视图上时，**app 层必须继续用这份整段运行的结果，不能换成主视图按扫描窗口算的那份**，否则拖一下视图，compare 里的 hit 就可能变。

## 四、spec 6.2 逐项：本来回答什么，现在怎么办

说明书第五节「⑤ 对照」写明这些 tag 的设计意图：「`tier tag` 管一元 where（这一段认没认出），`link tag` 管边（两段连没连上），`match tag` 管整次 hit……哪一层断了，就知道是 node、边还是整体的问题」（`.scratch/annotation-path2/manual.md:431`）。所以 6.2 本来就是为「错在哪」设计的。它的盲区是只透过 mapping 看：每个 tag 都挂在用户的框或样本上，问的是「map 到的那部分怎么样」。于是：

- app 独有的部分（这一版的 tb、tb_seg，以及任何 app 都会有的内部机制）没有任何 tag 能说到；
- mapping 本身写错了（如「站上新平台」只对到阶跃那一小段），tag 会照着错的 mapping 给出看似正常的结论；
- 买点为什么落在这些天，是 detector 内部的事，不在任何一层 tag 里。

| 项 | 原本回答 | 能不能回答「错在哪」 | 处理 |
|---|---|---|---|
| compare 照主视图原样画、档位画到 detected | app 输出全貌 | 能，前提是真画全部 band（6.2 第一行本意如此，但说明书写成「画在你的框所在的同一条轨上」，第一段也照这个做了） | **提前到第一段**，改成 2.2 的对等显示 |
| `tier tag`（图上灰条 `qualified_only` / `detected_only`；`selection` 页 `in_hit` / `qualified` / `detected` / `missing`） | 这个框对应的 node 认到哪一档 | 能，回答「哪个特征没认出」 | **提前**。图上那套和档位按钮重复，照主视图现有画法保留；`selection` 页那套取值不变，判法换成 2.8 的「盖住终点」 |
| `missing`（琥珀，不受档位管） | app 该认没认出 | 能，最直接的「哪个特征没检测到」 | **提前**，配 2.8 的判法。第一段 mapping 没有级，暂按「map 了就算该认」 |
| `match tag` | 这个样本 app 买没买 | 只说结果，但它是找原因的入口 | **提前**（▲ 下方），成本很低 |
| `link tag`（相邻两段连没连上） | 边那一层 | 部分；它按「相邻两个特征」问，依赖 mapping 的先后 | **留第二段**。node 层面的边断口已由 2.4 覆盖；按特征汇总的 `link tag` 等 mapping 有级、有先后再做 |
| `diff tag`（成员框 vs mapping） | 标注和 mapping 哪里不一致 | 不回答「app 错在哪」，回答「翻译和标注哪里对不上」，是会话出题的依据 | **留第二段**，设计不改 |
| 框上属性 vs app where 逐条核对 | 属性层的对不上 | 能，但依赖 where 和属性的 mapping | **留第二段**；2.4 先给「哪条 where 没过」 |
| `chance_high` | 随手一框也认得出的底 | 防误读，不定位错误 | **留第二段**，但要补上「按 tag 报的那一档算」（spec 没写，skeptic 指出）。它防的是「事件铺满时间轴」，不是「事件比框小一截」，后者要靠 2.8 |
| pattern 页按 mapping 分层（各段计数、段间 `↓` 连接计数） | 跨样本看哪一段是瓶颈 | 能，是「错在哪」的汇总版 | **留第二段**；等单样本的 2.4 用顺了，再考虑一个不依赖 mapping 级的简版：按 node 数「几个正样本的时段里这个 node 走到了哪一档」 |
| ⚑、定级、出题 | 会话流程 | 不是界面诊断 | 留第二段 |

## 五、和 spec 的冲突点

标「拍板层」的牵动第 1 节，改之前要问用户；其余属于第 2 节以后，按 spec 抬头的规矩就地改、在交付说明里写明。

- **C2** 6.2「一端就够」的认出判法（`spec.md:540`）→ 改成 2.8 的「事件盖住框的终点」，起点不看；`chance_high` 写明按 tag 报的那一档算。不动拍板层 1.4 的字面（`spec.md:71`，输出仍只给状态），但用户看到的结论会变（第一版同一批框 8 个认出 → 3 个，剩下 3 个也是碰巧），交付时要讲给用户；V-01-2 的检查口径跟着改。配套两条：整体判法只用于同粒度的配对；框里的关键位置靠用户画子框、mapping 对到 child slot 才判（2.8），对照层不从 K 线现算任何东西。
- **C3** mapping 一个特征只对一个 node（`path2_web/mapping.py:21`）与 spec 6.1「一个 node、某个 node 上的一条 where、一组子事件，还是一条否定边」→ 照 framework 的结论放开：框类特征对一个 node 或一个 child slot（`node.slot`），属性对某个 node 上的一条 where，`must_not` 对否定边；一个特征对一组 node 只作退路（`notes_framework.md` 第 6 节）。mapping 只决定对齐，不决定显示。
- **C4** spec 4.4「虚线全界面只表示用户画的」与主视图候选 bracket、被吃掉的峰的虚线 → compare 下这两样换线型（2.7）。
