# 整族反馈按基准 node 认「同一次形状」

Type: grilling (HITL)
Class: direction —— 认错了只会以「显示成改好了」的方式出现：错误买点只是挪了位置，页面却显示 `unmatched`，正常使用中看不出
Status: resolved
Claimed: 2026-11-16 annotation-path2 分支，会话 session_01XubwzNUzXnr5hZEGqZ1yoe

## Question

### Purpose

用户靠反馈核对判断每一版 app 有没有把他指出的毛病改掉；这张票让整族反馈在 app 改了切法或拓扑之后，仍能认出「同一次形状上还在买」。

### 起因（2026-11-16，new_step 第 2 轮标注改版）

- 现行规则见 spec 1.11「核对」与 1.13 的反馈状态 `lost`：整族反馈除了看那段日期里还买不买，还看「起于同一起点的那一族」还买不买；新版里连这个起点都没有任何事件时记 `lost`（改版报告写「起点认不出」），页面并进 `unmatched`，由会话在报告里逐条交代是改好了还是认法变了。
- 第 2 轮把 new_step 的阶跃认法换了，阶跃起点普遍往前挪一两天；旧平台固定取阶跃前 15 根，开头跟着挪；族起点就是旧平台第一天，于是旧反馈记下的起点对不上。10 条反馈里 2 条落进「起点认不出」：
  - IXHL 2025-08～09（f-pc-90）：真改好了。
  - QBTS 2025-03（f-pc-92）：你标的那几天不买了，但同一次阶跃在 05-08、05-09 还买，正是错误买点平移。页面显示 `unmatched`，是会话手查才发现的。
- 毛病出在「同一族」的认法：要求起点日期完全相同，只在第一段切法不动的小改下成立。改了切法或拓扑后两头都坏：认不出（`lost`，交给会话兜底）；或新版恰好有个无关的事件同一天开头，被当成同一族、显示假朱红（目前没有任何检查管这种情况）。
- 这不是 new_step 特有的：任何 pattern 改版动到第一段的切法都会发生。new_step 多发，是因为它的起点由阶跃倒推。

### 拟定方向（2026-11-16 用户提出、会话完善，用户要求记下；以 Answer 为准）

1. **每个接了标注的 app 声明一个基准 node**：这个 pattern 的「这一次」以哪一段为准。判据是依赖关系：它挪了，其余各段都得跟着挪；其余各段挪不动它。new_step 的基准 node 是 `step`。防的是：族起点由别的段倒推，一改切法就对不上。
2. **判据不是检测顺序。** 用户最初提「最先检测的那个 node」，讨论后改为依赖关系。防的是：基准随写法或引擎的求解顺序变动，在最需要它稳定的拓扑改动时跟着换。三条理由：
   - 用了几个 detector 的 pattern，各 detector 各扫全段，没有先后；拼成 hit 的顺序由引擎安排。
   - 单个 detector 里也有歧义：new_step 的识别器先看阶跃前 15 根的波动当尺子，照字面算最先看的是旧平台那一段。
   - 检测顺序是写法上的选择：同一个形状可以先扫平台、再找大涨。
3. **按共用 K 线认同一次形状**：新版里某一族的基准 node 的 event，和反馈当时那一族的基准 node 的 event 共用至少一根 K 线，就是同一次形状；其中任一族还在买，这条反馈就是 `matched`。防的是：基准本身的边界挪一两天就对不上（第 2 轮这两条的阶跃起止都挪了，要求起点相同照样会丢）。共用 K 线不需要另设门槛。
4. **只要求接了标注的 app 声明，不改 path2，也不像 `eval_meta` 那样强制所有 app。** 防的是：框架里多出一个框架自己不用的概念（基准是哪一段属于走势语义）；从不接标注的 app 被迫补声明、漏写就从页面消失。
5. **不悄悄降级**：有整族反馈、却没声明基准 node 的 app，在 annotation-round 开头的检查里报成问题，修好才往下走，不退回按起点日期去对。防的是：静默降级把这个毛病藏回去。
6. **自动结论有不管的两处，由会话判断**：
   - 基准 node 本身被换掉或改了意思时，自动结论两头都不信，由会话按反馈理由逐条判断。
   - 反馈理由只针对那几天的具体情形时，挪到同一次形状别处的买点算不算同一个错，也由会话读原话判断。

### 会话默认（待验证）

- 声明写在 app 的 `mapping.yaml` 里：这份文件本来就是标注与 app 的对照，由会话维护，开头检查读得到。名字由会话按 pattern 定义提，拿不准时问用户。
- 基准 node 可以是不参与求解的子 node（new_step 的 `step` 就是 `plateau` 的子段）。
- 用户写整族反馈时，页面把当时那一族基准 node 的 event 起止存进反馈记录：页面现算状态时手里只有当前版 app，旧版跑不出来。已有的整族反馈一次性补存：用写反馈时那一版 app 的代码，在 git 里找得到。
- 要跟着改写的现行文字：spec 1.11「核对」、1.13 里反馈状态 `lost` 那一条；项目 CLAUDE.md 后端边界红线里的「反馈状态只做 app 买点日与日期范围的比对」，改成同时比基准 node 的 event 有没有共用 K 线（声明来自 app，后端仍不含走势语义）；annotation-round 的报告与账本里关于「起点认不出」的说法。
- 时机：赶在 new_step 第 3 轮之前做。第 3 轮多半还要动阶跃起点（「往前找起点要不要加限定」那道题），不做的话整族反馈会再次大批落进「起点认不出」。

### 倾向（2026-11-16 用户确认）

自动认法拿不准是不是同一次形状时，交给会话逐条判断，不让页面自动显示成改好了。会话每轮会多查几条，换来的是错误买点平移不会被当成改好了。本票 Question 里「拟定方向」第 1～4、6 条照原样采纳；第 5 条按下面结论第 1 条收紧（凡接了标注的 app 都要声明）；第三态 `lost` 保留，含义改为「基准 node 对不上」（结论第 3 条）。下面各条补上落地时要定死的几处。

### 结论（每条后面写它防的是什么）

1. **每个接了标注的 app 在自己的 `mapping.yaml` 里声明基准 node（`reference` 键，值是 node_id；new_step 写 `step`）。缺了它、或它指向不存在的 node，就算 mapping 有问题，后果照现有的 mapping 问题处理**：页面上这个 app 的 `compare` 叠加和反馈状态整个停用，顶栏提示这个 mapping 不能用；annotation-round 第 0 步把它报出来，改 app 那一步和 app 一起修好，修好之前出不了改版报告。可以声明不参与求解的子 node。
   - 防的是：页面在你写下第一条整族反馈时就得知道基准是哪一段。如果「有整族反馈才要求声明」，第一条就会在没声明时写进去，之后只能悄悄退回按起点日期对。这比 Question 第 5 条的说法更严一点：凡是接了标注的 app 一律要声明，不等有了整族反馈才查；声明由会话写，多一行字。
2. **新建整族反馈时，页面把这一族各个 hit 的基准 node 的 event 起止（去重）连同基准 node 的名字一起存进这条反馈。之后改这条反馈的 note、点出的 node、所属的 issue，存下的起止原样保留，不按当前版 app 重算。**
   - 防的是：页面判状态时手里只有当前版 app，旧版跑不出来；不存下来，就没有东西可比。改一次 note 就重算，等于悄悄换成新版的阶跃，平移就再也认不出来了。
3. **整族反馈的状态按下面的次序判**（在原有的「范围里还有买点 → 朱红」之后）：
   - 当前 app 里有 hit 的基准 node 的 event 与存下的某一段共用至少一根 K 线，而且这个 hit 还在买（买点日在哪都算）→ `matched`（朱红）。
     防的是：错误买点只是挪了位置，却显示成改好了。
   - 存下的起止里至少有一段，当前 app 有和它共用 K 线的基准 event，但这些 hit 都不买了 → `unmatched`（改好了）。
   - 当前 app 的全部基准 node 的 event（不论档位、不论在不在 hit 里）和存下的每一段都不共用 K 线；或 `mapping.yaml` 现在声明的基准 node 和存下的名字不同；或这条反馈根本没有存下起止（如票 18 补存之前的那 4 条）→ 第三态 `lost`，不报错，也不退回按起点日期去对。页面照常色显示（同现行 1.13），改版报告里列为「基准 node 对不上」，会话逐条交代是改好了还是认法变了；判为认法变了、毛病还在的，照旧挂原因标签。
     防的是：一根都不共用时，自动结论可能是真改好了，也可能是同一次阶跃挪远了还在买。按倾向，这种情况交给会话判断。只有一根的阶跃（QBTS 03-14、CRNC 01-03）挪开一根就会这样；反馈存的是写它那一版的起止，连改几轮后的漂移也会走到这一步。
4. **每个 hit 单独判，不按族判**：新版里不再要求「同一族」，只看每个 hit 自己的基准 event 有没有和存下的共用 K 线。
   - 防的是：new_step 的阶跃停一下又续上时会换成更长的一版，同一族里会有几个起点相同、终点不同的阶跃。按族合并起止会把不相干的段连起来。
5. **基准 node 换了意思（名字没变，指的东西变了），由会话在当轮改版报告里写明，并把这个 app 的全部整族反馈当作 `lost` 逐条交代。**
   - 防的是：换意思时机器看不出来，自动结论会两头都错。会话改基准 node 的认法（如第 2 轮换了阶跃认法）不算换意思；换成指另一段形状才算。
6. **已有的 4 条整族反馈（CRNC f-pc-74、IXHL f-pc-90、LUMN f-pc-95、QBTS f-pc-92）补存当时那一族的基准 event 起止**（2026-11-16 用户同意）。用写反馈那一版 new_step 的代码（`app_ver` 1afa716bc5248d4b）在临时 git worktree 里跑出来，再经 `append_batch` 新写一个批次文件写入。note、点出的 node、日期范围、`family_start` 一律不动，已有文件一个不改。真写之前列出 4 条各要加什么，你点头再写；写的时候你别在页面上同时改这 4 条。
   - 防的是：这 4 条没有存下的起止，新判法判不了。不补，它们就永远落在 `lost`。
   - 这是项目 CLAUDE.md「`annotations/` 会话只读不写」之外的一次性例外，只限这一次补存。你的同意写进票 18 的 Inherited Direction，不写进 CLAUDE.md：一次性的事不进常驻规则。
7. **后端仍然不含走势语义**：基准是哪一段由 app 的 `mapping.yaml` 声明，后端只比两段日期有没有共用 K 线。项目 CLAUDE.md 的边界红线照此改写（见「批准后同步改的东西」）。
   - 防的是：框架或后端里多出一个只属于某种走势的概念。path2 本身不改，也不像 `eval_meta` 那样强制所有 app 声明（Question 第 4 条）。
