# critic：对抗审查（标注流程与界面打磨）

本文中所有项目内路径均相对 repo root。审查对象：当前设计（`docs/research/2026-10-26_annotation-topology-grouping/final_report.md`，下称「上轮报告」）、`背景.md` 第 3 节 lead 的候选方案（下称「候选」），以及本轮 flow / ux 的改版。用词照 `path2/GLOSSARY.md`、`path2_web/GLOSSARY.md`。

## 0. 停止线

- **防谁**：防用户被流程或界面带错、做错、看不懂、要记太多。**不防**用户在训练段上看着 app 去标、去改（用户已定这是他的自由，背景 §2 末条）。
- **追什么**：只追撤不回的、或会让用户做错方向决定的。撤得回的小别扭记一笔、标「低」，不缠斗。
- **补一条（用户 2026-10-27 追加，`原始问题.md` 末段）**：单张撤得回、但会随标注量累积，到归组 / 写 app / 盲看时一次性爆出大清理的，也算要管的。判法是看**补救的代价随什么涨**：
  - 补救一次就能覆盖全部旧标注（随名字个数或组数涨，如词的合并、整组挪 pattern、会话问一句）→ 可以随用户去，事后再管不会更贵；
  - 补救要逐张回图（随图数涨，如逐个把框排出成员、改写成属性）→ 在攒后患，要在标的当下引导，或者换一种不需要逐张补救的设计；
  - 事后连「哪些要补」都分不出来（数据存下来时就丢了信息，如默认带上的属性和用户确认过的存成一样）→ 只能在当下管，必须在设计里堵住。
  反过来，补救一次就能覆盖的事却在标注当下加引导或限制，算过度设计。
- **严重度**：高 = 会让用户做错方向决定、丢掉补不回的证据，或规则自相矛盾、写不进实现；中 = 会让用户在某一步看错、多绕一轮；低 = 撤得回的小别扭。
- **来回**：每条质疑最多来回两次；对方回复后我给结论（接受 / 不接受 / 交用户定），不再追。
- 上一轮 critic 已判已解决的 30 条（`docs/research/2026-10-26_annotation-topology-grouping/critic.md`）不重提，除非本轮候选让它重新出问题。

## 1. 核实过的硬事实（质疑的地基）

1. **顶层「有时有有时没有」在 path2 里写不出**：一次 match 要求每个参与求解的 node 都绑一个事件（`path2/GLOSSARY.md:95`）。否定边的 dst 不进 match（`path2/dag/edges.py` 的 `NegationEdge` 说明：dst 是约束、不是结构成员）——所以顶层能写「要求没有」，写不出「可有可无」。lead 这条对。
2. **次级的「可有可无」能写，但写法约定还挂在票 06**：子事件槽允许为空（`path2/dag/engine.py` 的 `_check_children_declarations` 对空槽直接跳过），where 用 `W.children` 加自定义判断能读空组；但单个取子事件的 `child` 在槽空时抛 KeyError（`path2/core.py:137-139`），票 06（`.scratch/annotation-path2/issues/06-k-of-n-and-composite.md`）把「可有可无的子事件怎么写」列为未定。
3. **「属于」判定没有容差**：mock 里子框必须完全落在父框起止之内（`docs/research/2026-10-26_annotation-topology-grouping/repro/mock.html:219`），子框右边多出一天就不算属于；只交叠的按「紧接着」读成先后（上轮报告 2.8 节表格「起点包含、交叠」一行）。
4. **「app 建好了、顶层名却不在 app 里」在现设计里是合法取值**：上轮报告 2.5 节的 resolver 有一种写法是「会话选来认、但没接进 app 的事件类名」，mock 里横盘就是 `TrendSegment:sideways`（`mock.html:104`），缩量不在对应表里 → `unmapped`。所以用户看到的现象不全是演示数据的毛病，有一半是设计本身允许的状态。
5. **mock 的 TVRD**（截图 `sim_r1_00_initial.png`）：2024-12 那个 buy 的成员 = 放量突破 → 回踩；2025-04 那个 buy = 横盘（⊃ 缩量）→ 放量突破 → 回踩；2025-05-08 的 no_buy 与后者同串。按 buy 数多数算，横盘不在骨架里。
6. **方向文档第 8 节**（`docs/research/2026-10-23_annotation-path2-direction/方向讨论.md:165`）把骨架定义为「pattern 由哪几个 node 组成」；但更晚的票 01 Comments（`.scratch/annotation-path2/issues/01-structured-annotation.md:38`，2026-10-25）定了「用户标注时不区分 node 和 where，由会话决定」，并收回过「名字 → node」那一层，原话举例「横盘可单独框，也可写在突破框上『前面横盘』，两样都对」。

## 2. 第一轮质疑清单（独立做，未看 sim / flow / ux 稿）

### Q1【高】「顶层」被偷换成「node」，把 node / where 的决定搬回用户手上

- **针对**：候选「同一个 pattern 只允许一种顶层骨架」「顶层没有 unmapped」「可有可无只在次级」。
- **失败场景**：硬事实 6 里「横盘单独框、写成突破框的属性，两样都对」。候选下这两种画法后果不同：单独框 = 顶层 = 进骨架、缺了就偏离标红；写成属性 = 次级 = 可有可无。用户在 TVRD 2025-04 那张顺手把横盘框出来，就等于声明了「这个 pattern 必须有横盘」，而他画的时候并不知道这层意思；回头 2024-12 那张没横盘的 buy 被判偏离，他要么回去把横盘框改写成突破框的属性，要么拆 pattern——这是在用画法替 app 做 node / where 的决定，正是 2026-10-25 收回的那一层。
- **建议方向**：把规则说成用户能直接判断的意思：「顶层成员 = 这个 pattern 的 buy 都得有」。必须有的东西在 app 里写成 node 还是写成相邻 node 的 where，仍归会话（bb_v1 的「突破前沉寂够久」就是把「前面一段平静」写成 burst 的 where）。用户只回答「必须有吗」，不回答「是不是 node」。框出来、但不是必须有的，挪进外框或写成属性。
- **结论**：这条改变了「单独框一个东西」的含义（从中性的记录变成「必须有」的声明），**交用户定**。

### Q2【高】像但不买被规则误伤，丢掉最有用的反例

- **针对**：候选「顶层名称恒为 in N/N」「有 app 的 pattern 里第二种骨架的组标红」「不符骨架显示违背预期」。
- **失败场景**：最有信息的 no_buy 正是顶层差一样的：①「没横盘就突破，不买」——成员少一个横盘；②「突破后冒出派发，不买」——成员多一个派发框（上轮报告 2.8 节：否定靠跨图证据「像但不买上常为 true」）。按候选，这两个 no_buy 在 groups 里自成一组并标红；用户为了消红把它挪出 P，P 恰好丢掉「横盘是必须的」「派发是不买条件」的证据；或者横盘显示 `in 3/4`，用户反而以为它可有可无。②里的派发在 app 里落成否定边，根本不进 match，「顶层恒 in N/N」对它天然不成立。
- **建议方向**：「顶层一致」只管 buy；`in` 的分母只数 buy，no_buy 另报。no_buy 和 buy 在顶层上的差别是给会话的证据，不是偏离，不标任何警示。

### Q3【高】「这个 pattern 的骨架」以什么为准，候选没说

- **针对**：候选「写 app 时定成一个骨架」「出现第二种骨架的组标红」。
- **失败场景**：上轮报告 2.1 节定骨架和 groups 都是界面现算、不存。要判「第二种」就得有一个参照。若拿 buy 多数现算：mock 的 TVRD（硬事实 5）多数说横盘不在骨架，被标偏离的是用户认为对的那组；之后再标两张带横盘的，多数翻转，偏离标记跳到另一组，用户什么都没改。
- **建议方向**：参照骨架由会话写 app 时连同对应表一起记下（落点已定：随 app 进 git，上轮报告 2.1 节末条），偏离按它算；没有 app 时不判偏离。这是对上轮报告「骨架界面现算」的一处修订，要写明。

### Q4【高】循环会改骨架，阶段表却是直线的；「没画还是没有」不能缩到次级

- **针对**：候选阶段表、「顶层的模糊只允许在写 app 之前」「翻成可有可无前先问没画还是没有，缩到次级」。
- **失败场景**：方向文档第 3 节第 5 步：盲看「不是」的理由翻成要加的 node，回到第 3 步。例：盲看三张都写「前面没跌够」，会话给 P 加一个必须有的「下跌」。这时 P 里所有旧 buy 都没画下跌——按候选全部变成「第二种骨架」、一片红；哪些该补、哪些本来就没有，正是「没画还是没有」要问的，而候选恰好把这一问从顶层撤掉了。首次归组同理：一组 buy 缺横盘，是没画（补框）还是没有（拆开，或横盘不是必须的），也是顶层的问题。
- **建议方向**：「顶层一致」写成循环每一轮开头的检查（会话发现不一致 → 列出缺的那几个 buy、配缩略图、问没画还是没有），不当阶段门槛；「没画还是没有」顶层、次级都问。阶段表写明阶段按 pattern 算：P 进了循环，别的买点照样自由标、挂未归类（方向文档 `:162`「先定目标的阶段里看到新东西照样标」）。

### Q5【中高】朱红一色两义；默认成员往多收会造出假红

- **针对**：候选「第二种骨架的组标红」「顶层出现 unmapped 就标红」。
- **失败场景**：已定朱红 = 违背预期，现有用法全是「app 和你对不上」（漏买、误买、没认出、没连上、fail），该会话去修 app。骨架偏离是「你这几张和 pattern 的定义对不上」，该用户挪组 / 补框，或会话改定义——动手的人相反，同一个红，用户第一反应是「app 又错了」。再叠加默认成员（相邻两段隔 20 根以内就收、往多收偏，上轮报告 2.3 节）：循环阶段用户在突破前顺手框了个新词「缺口」只想记一笔，它挨着就被并进 buy 的成员 → 顶层多一个 unmapped → 组和名称两处红，都出自一个探索框；要在 edit 栏把它点出成员才消，用户不知道要做这件事。
- **建议方向**：偏离不用朱红。P 下有偏离时 groups 出现本身就是信号（已定「≥2 种骨架才出现」）；把偏离组排在符合骨架的组前面（现在按个数从多到少，偏离的小组恰好沉底）。顶层新词就是普通的 `unmapped`，和次级一样，等会话下一轮处理。

### Q6【中】顶层还是次级，由边界画得准不准决定（建议已由 critic 撤回，见 6.3）

- **针对**：候选把「次级」当作可有可无的唯一落点。
- **失败场景**：硬事实 3。用户把缩量框右边多拉一天，它就不在横盘里，按「交叠读作紧接着」成了横盘后面的顶层成员 → 新骨架。候选之前，这只多出一个小组；候选之后它让组被判偏离、挡住会话写 app。唯一的提示是框角 `⊂` 没了，用户看到偏离时想不到去看框角。
- **建议方向**：「属于」判定带和对照一样的容差（暂取票 01 的框外容差 2 天，待验证）；偏离组的缩略图里，子框露出父框的那一截要看得见。

### Q7【中】顶层不显示 `in`

- **针对**：候选「顶层名称不再显示 in」。
- **失败场景**：(a) 按 Q2、Q4，有 app 后顶层 k<N 仍会正当出现（no_buy、新加了必须项还没补框），藏掉 `in` 就藏掉了唯一的计数；(b) P 下有偏离组时，elements 由全部买点的成员汇成，偏离组独有的名字也会列进 elements，没有 `in` 就看不出它只在 1 个买点里，会被读成骨架的一员；(c) 同一行有没有 app 长得不一样，又多一条要记的规则。
- **建议方向**：`in` 照旧常显，分母按 Q2 只数 buy。「顶层就该 N/N」靠参照骨架（Q3）加偏离组呈现，不靠藏数字。用户这次困惑的根子是演示数据（顶层横盘 `in 2/4` 配一个没有横盘的 bb_v1）；数据换掉后，正常 P 的顶层自然全是 N/N，不需要藏。

### Q8【中】`unmapped` 改名「还没放进 app」

- **针对**：候选「unmapped 改成『还没放进 app』并悬停说原因」。
- **失败场景**：(a) 界面文字规则要求状态用短标识符，中文短句当状态违规；(b)「还没」暗示会放，但票 05 批准过「看得出没多大用 → 默认不并」（`.scratch/annotation-path2/issues/05-measure-in-context.md:106`），量过决定不放的词会永远挂着「还没放进」，用户每次看都以为会话忘了；(c) 现设计里「不在 app 里」已有两种写法：`unmapped`（会话没处理）和 `TrendSegment:sideways` 这种（会话选了 detector 但没接进 app，硬事实 4），再加一种就是三种，用户分不清差在哪——这正是用户问「app 建好为啥还有 unmapped」的另一半来源。
- **建议方向**：只留两个枚举：「会话还没处理过」（如 `unmapped`，下一轮会处理）和「处理过、决定不放」（如 `excluded`，悬停写原因：量过没多大用 / 先留着等量）；「选了 detector 没接进 app」这一态在有 app 时取消——会话要么接进去，要么判不放。取名待定，方向是「两态、标识符、不用中文句」。

### Q9【中】「写 app 前先查骨架唯一」做成拦截

- **针对**：候选阶段 3 门槛。
- **失败场景**：用户的护栏原则是只拦撤不回的。app 写错骨架撤得回（重写一版，训练段随便看）。做成「不唯一就不写」，会话会卡在等用户整理完所有组（近义词合并、补框、拆组；上轮报告 V4 预期 groups 会碎），用户想先看看第一版 app 跑出来什么样都不行。
- **建议方向**：会话写之前把偏离摆出来、按 Q1 的意思问「这个必须有吗」，用户可以说「先按多数写，剩下的以后再说」；剩下的照常留在 P 里显示为偏离组。

### Q10【中】「新买点须符合骨架」暗含新 / 老区分

- **针对**：候选阶段 4「新买点须符合骨架」。
- **失败场景**：用户 2026-10-26 定过认出数不按新老拆、不设「接触过 app」记号。「新买点」要判就得记哪些是 app 之后标的；即便只是措辞，实现者照字面会做出一个新老标记。
- **建议方向**：写成「P 的所有 buy」，不出现「新」。

### Q11【中】挂现成 app 算不算一条路，要说死

- **针对**：候选「mock 里的情况主要是演示数据的毛病」。
- **失败场景**：如果会话可以说「bb_v1 已经就是你这个 pattern」并把它挂成 P 的 app（票 01 Answer「现成的先试」说的是 detector，没说整个 app），那「app 建好、顶层名不在 app 里」就是这条路的常态，用户会再问一遍同样的问题。
- **建议方向**：写明 P 的 app 一律由会话照 P 的标注写（可复用 detector 与 node 写法，不整个挂现成 app）；或允许挂，但挂之前会话按参照骨架补齐 node。二选一说死；lead 拿不准再交用户。

### Q12【低】次级「可有可无」依赖票 06 未定的写法

- 硬事实 2。候选说「次级可以可有可无」时注明依赖票 06（「复合事件不论有没有某组子事件都产出、子事件只经 where 起作用」是落点），别写成框架现成能力。

### Q13【低】mock 顶栏 pattern 下拉仍列 `bb_v1`

- 上轮报告 2.1 节已定 pattern 显示用户起的名、app 编号作旁注；mock 没跟上（`sim_r1_00_initial.png` 顶栏 `pattern bb_v1`）。sim 走流程时会把 pattern 读成 app，产生不属于设计的摩擦。换演示数据时一起改。

### Q14【低】虚线在主图和侧栏的意思相反

- 主图：虚线 = 用户的框（成员是粗虚线）。侧栏 edit：members 实线边、others 虚线边，`unmapped`、`null n` 也是虚线签（= 空着 / 不在）。撤得回，只记不追。

## 3. 候选有没有消掉用户问的那几种模糊

| 用户的问题 | 候选的回答 | 消掉了吗 |
|---|---|---|
| 同一个 pattern 要不要同一拓扑 | buy 顶层骨架唯一 | app 一侧 path2 本来就强制唯一（硬事实 1）；用户一侧没给参照（Q3）、误伤 no_buy（Q2）、把画法变成 node 决定（Q1）。改后可消 |
| app 建好了，顶层还要不要「可选」 | 不要；顶层不显示 `in` | 意思答对了，但靠藏 `in` 实现（Q7），等于连真实的偏离一起藏了 |
| 模糊是否只在建 app 前 | 阶段表：顶层模糊只在写 app 前 | 循环会改骨架（Q4），应改成「每轮开头清掉顶层不一致」 |
| app 建好了为啥还有 unmapped | 演示数据的毛病；以后只许次级出现 | 只答了一半：设计本身允许「选了 detector 没接进 app」（硬事实 4、Q8）；app 之后新标的词是正当的 `unmapped`，顶层出现就标红和「看到新东西照样标」冲突（Q5） |

## 4. 我认为够用的最小改动集

1. 规则一句话：P 的 buy 的顶层成员一致，意思是「这些都得有」；必须有的落成 node 还是 where 归会话；会话写 app 时记下参照骨架（Q1、Q3）。
2. 偏离 = groups 里不符合参照骨架的 buy 组，排在前面，不用朱红；会话每轮开头处理，问「没画还是没有」，顶层、次级都问（Q4、Q5）。
3. `in` 常显、分母只数 buy；no_buy 在顶层上的差别不算偏离（Q2、Q7）。
4. 「不在 app 里」只留两态：还没处理 / 决定不放（Q8）。
5. 「属于」判定带容差（Q6）。
6. 演示数据换成照标注写的假 app，顶栏显示 pattern 名（Q11、Q13）。

候选里其余几项（藏 `in`、顶层 unmapped 标红、骨架偏离标红、写 app 前拦截、「没画还是没有」缩到次级）建议不做。

### 5.2 Q1 / F1 两条出路的比较（我的判断，供 flow 和 lead 用）

问题是同一个：可有可无的东西（典型是排在突破前面、套不进突破框的横盘）在哪里表达。

- **出路 U（我第一轮的建议）**：规则落在用户的画法上——顶层成员 = 这个 pattern 的 buy 都得有；可有可无的就画进外框或写成属性。好处：pattern 页的层级就是框的层级，所见即所得，不用再对一张表。代价：前置段套不进后面那段的框，只能删框改属性或画一个包住两段的大框，用户要回头改图；界面也没有「把名字降成属性」的操作（sim F1）；本质上还是用户在画的时候替会话定了一部分 node / where。
- **出路 S（sim 的建议）**：用户照常画；归组时允许一个 pattern 里有几种顶层串；会话写 app 时逐个问「这个必须有吗」（先问没画还是没有），必须有的写成 node，可有可无的写成某个 node 的 where 或子事件；写完后 pattern 页的层级按会话的对应表显示——横盘挂到它依附的那一段下面。好处：标注时不分 node / where（守住票 01 已定）；用户原话「可选只发生在次级」在 app 一侧自动成立，界面上也正是这样显示；参照骨架不用另存，就是对应表里「本身就是 node」的那些名字按 app 的先后排（Q3 自动解决）。代价：写 app 后，pattern 页的层级和图上框的套法可以不一样（横盘在图上是独立的框，页上挂在放量突破下面），pattern 页里表示「挂在下面」的记号要和图上框套框的 `⊂` 分开，否则又是一个记号两种意思。

**我的倾向改为 S**：U 的唯一好处（所见即所得）换来的是回头改图和违背已定决定，S 的代价是界面上一个记号要分清，撤得回。「必须有吗」这个方向问题在 S 下照样交给用户，只是在写 app 时由会话在对话里问，而不是靠画法表达。交用户定的方向题因此写成：「可有可无的东西，是画的时候就要表达出来（画进外框或写成属性），还是照常画、写 app 时会话问你『这个必须有吗』，然后在 pattern 页把可有可无的挂到它依附的那一段下面？」推荐后者。

补一条论据（用户 2026-10-27 追加问「灵活性与规范性的分界点、哪些原则要规定用户不这么做」，见 `原始问题.md` 末段）：U 把一条规矩压在用户的画法上，而违反它的后果看得见、撤得回（偏离组）；按用户「只拦撤不回的」原则，这类事不该是用户要守的规矩，该是会话写 app 时的活。S 的代价随名字个数涨（每个名字问一次），U 的代价随图数涨（每张框了横盘的图都要排出成员、改写成属性）。

### 5.3 灵活与规范的分界：critic 独立推的清单（未看 flow 的分界一节前写下）

按第 0 节补的判法（补救代价随什么涨）把标注里常见的「用户怎么想、怎么做」分成五类：

**A. 必须规定用户不这么做**（事后分不出、会致错，界面和会话都补不了）
- A1 正例按「这一天有这个样子、当时会买」标，不按「后来涨了」挑（方向文档第 3 节第 2 步）。事后分不出哪个是按结果挑的；致错的方式是 pattern 抓到涨了的那批图的偶然共性，训练段上越看越好，直到最后检查（用掉没碰过的数据，撤不回）才暴露。
- A2 像但不买的理由、写成 false 的属性，必须在买点那天以前看得到；买点之后才看出来的想法不写进标注，在对话里当新想法提（方向文档第 3 节允许当新想法验证，但标注里分不出哪条是事后的）。
- A3 一个词的意思变了就另建一个词，不在原词上改定义（票 01 已定）。在原词上改，所有旧框悄悄换了意思，事后分不出哪些是按旧意思标的。界面能帮一把：改一个已经用过的词的定义时，旁边显示用了几次。
- （数据墙不算用户规矩：读数据只经截到 2025-12-31 的副本，系统强制。）

**B. 必须在设计里当下堵住**（用户怎么做都不该能造成；事后分不出）
- B1 点名字时属性默认带成 true（sim F3，R4 / X5）：带上没改的和确认过的存成一样。堵法：带过来的默认 null。
- B2 买点之后才开始的框当成员：现设计 `others` 只列买点之前开始的框，已堵住，保持。

**C. 当下给看得见的提示**（单张撤得回，但补救要逐张回图）
- C1 默认成员没核对：放下买点即选中、members / others 一眼看得见（已定），保留。
- C2 误造的一天框（sim F10）：ux U7 合并工具后堵住。
- C3 像但不买不挂它像的 pattern（X8）：事后要逐张回忆。不拦，pattern 一格显示成空着待选即可。
- C4 若选出路 U：可有可无的前置段画成顶层成员，补救是逐张排出成员、改写属性，必须在标的当下就按规矩画——这是 U 把一条规矩压给用户的根源；出路 S 下这一条不存在。

**D. 随用户去**（补救一次覆盖全部旧标注）
- D1 近义词：框只记词的编号，事后在词表合并一次就覆盖全部旧框；所以合并功能可以晚做，晚做也不会让清理变贵，标的当下不必提示。
- D2 定义空着：写 app 时每个名字问一次。
- D3 未归类攒着、归组拖着：按组挪。
- D4 背景框画不画、画了收不收：出路 S 下会话问一次判 `excluded`；出路 U 下变成 C4。
- D5 子级没画：`null` 本来就是「没看过」。
- D6 看着 app 去标、去改：用户已定的自由。
- D7 忘切 pattern：骨架不同时自成一组，整组挪；相同时看不出，已接受。
- D8 属性 `null`：会话到要用、看过的太少时才请补点（已定）。

**E. 过度设计**（补救一次就能覆盖，却在标注当下加引导或限制）
- E1 写 app 前「骨架唯一」门槛（Q9）。
- E2 偏离标红（Q5）。
- E3 近义词在输入时拦或强提示（D1）。
- E4 名字第一次出现时强制写定义（D2）。
- E5 放买点那一刻显示骨架差（flow P4）：只在出路 U 下有必要（防 C4 攒后患）；出路 S 下它会诱导用户为消签去补画不在意的框（flow 自己的 V3），属过度。默认成员切短的早发现，已有 C1 的当下展示。

### 6.2 已解决（按主题归并）

- **用户原问的几件事**：app 一侧只有一种拓扑，是 path2 决定的（硬事实 1）；用户一侧照常画，写 app 时会话给每个名字定级（必须有 / 可有可无 / 必须没有 / 不放），写完后 pattern 页按级分层，顶层只剩必须有、每个正例都有，可有可无挂在它依附的那一段下面（Q1、R1、X9）。所以「模糊只在写 app 之前」成立；app 建好后的 `unmapped` 只会是上一轮之后新出现的名字，会话决定不放的另显示为 `excluded` 并写原因（Q8、X15 前半）。
- **像但不买**：规矩只管正例，分母只数正例；像但不买按与必须有 / 必须没有的差分组，当证据不当偏离（Q2、R5）。
- **偏离**：只在写过 app 后才有，以对应表的必须有 / 必须没有为准，不按多数现算（Q3、R2）；不标朱红，排在最前，组头差签 `−X` / `+Y` / `order`（Q5、X6、X9）；偏离组照常显示 `app:buy`（X1）。
- **「没画还是没有」**：保留，并进每轮开头的一张单子，只对必须有的名字逐张核对；「画了没收」对所有名字机械查、算进是否过半，缩略图那一行有 ◂ 一下收进（Q4、R3、R11、X4）。
- **单子本身**：放进界面；机械能算的条目（缺必须有、画了没收）界面现算、改好即消、不用答；要判断的条目（定级、那天看得见吗）在单子里给选项、回答由界面记下，不在对话里（sim L2，flow 确认）；定级与核对一遍答完；出现在全部正例里、没写定义的顶层名字不预填（R15～R17）。
- **写 app 不设门槛**：三选一可只答一部分说「先写」；唯一一道真拦是送最后检查（Q9）。
- **灵活与规范的分界**：按「补救的代价随什么涨」分五档；用户自己要记的规矩只剩两条——一个词不装两种意思（意思变了另建词）；label、像但不买理由、属性有没有都按当天看得见的判。其余都改成界面默认或会话的活：近义词有 vocab 合并（选了先在词块里预览「n 个框：A → B」，点 `merge` 才改、`cancel` 放弃；改完存成记录，目标词下 `unmerge` 能拆回，sim L3、ux U13）、起名时相近词冒出来；套框画歪了在子框 edit 栏点上 `⊂`；脱离图的说法由会话反问；`let_go` 改名 `not_sample`（R10、R14、X13、X14）。
- **回头翻 label**：会话每轮机械列出无结构原因翻过 label 的买点、以及盲看揭开前后同一处判断相反的，问「那天看得见吗」（R9、R13 窄版）。
- **成员与框的操作**：「属于」按严格包含判，首尾交叠一律按先后读；想表达属于而边画出去了，在子框 edit 栏手动点上 `⊂`；名称级从属（轨标题 `⊂`、轨序）要这个 pattern 多数正例同意才成立（sim L1，lead 裁定）；拖选中框的边改起止（X11）；自动并进跟着「当前买点」走，bracket 内已有框改动不并（R12、X12）。
- **界面杂项**：`in k/N` 只数正例、不足全数才显示（Q7）；页头 `next` + `ask n`，用户待办只数会话问了没答的（R7、X10）；对照换图不自动关（X7）；未归类下放的 no_buy 显示 `pattern?` 待选（X8）；mock 顶栏用 pattern 名、app 编号作旁注（Q13）；挂现成 app 没有捷径，都要过每轮自查（Q11、R6）；可有可无的子事件写法依赖票 06，`W.child` 遇缺子事件会让整只股票中断（Q12）。

### 6.4 交用户定（白话方向题）

**D1　可有可无的东西，在哪里表达？**（Q1、R1；flow D1、ux 同）

这决定画框那一刻你要不要想「这个是不是必须的」。比如横盘有时出现在放量突破前面、有时没有，你觉得有更好但不必须。

- **照常画，写 app 时会话问你（推荐）**：看到什么画什么。写 app 时，会话对每个名字问一次「是买的理由（每个都得有）、有更好、还是只是背景」；写完后 pattern 页按这个分层，顶层只剩每个正例都有的，横盘挂在放量突破下面。代价：pattern 页的层级和图上框的套法可以不一样（横盘在图上是单独的框，在页上挂在别人下面），界面要用两种不同的记号分开；写 app 时多答一张单子，但每个名字只问一次。
- **画的时候就表达**：单独框出来的就等于「每个正例都得有」；有时有的要改写成后一个框的属性，或套进一个大框。好处是 pattern 页和图上一模一样。代价：画框那一刻就要定它是不是必须的；定错了要逐张回头改图，图越多越费事；这也和已定的「标注时不分 node 和 where」相冲突。

推荐第一种：「是不是必须」要看过好几张图才说得准，放在写 app 时问一次，比每画一张图定一次更省、也更准。

**D2　给框选了名字后，以前和这个名字一起用过的属性，默认算「有」还是「没看过」？**（R4、X5；flow D2、ux 方向题 1 同）

现在已定的是默认算「有」，你按图勾掉没有的。问题在于：没勾掉的「有」和你确认过的「有」存下来一模一样，事后谁也分不出；会话会照着这些「有」去写 app 的条件。界面已经把候选缩到「当前 pattern 里用过的」，跨 pattern 带过来的那一半已经没了，剩下的是同一个 pattern 里没看过却被算成「有」。

- **默认没看过，点一下才算有（推荐）**：属性照样列出来省得你找，只是都先算没看过。代价：每个新框多点几下。
- **维持默认有**：标得最快。代价：漏勾的就成了你没判断过的证据，你和会话都看不出来。

**另交 lead 一并问的词表题**（不是方向题）：「骨架」「主组」「偏离组」「必须有 / 可有可无 / 必须没有 / 不放」「当前买点」「画了没收」和界面标识符 `elements`、`groups`、`members`、`others`、`next`、`ask`、`not_sample` 都不在两份词表里，按项目规矩问一句要不要收。

### 6.5 残余风险（接受，交实施阶段盯）

1. **第一次定 label 时看着后续走势**：机械上查不了，只能由最后检查兜，而最后检查撤不回（R13）。用户自己要记的两条规矩里这条最常见、最晚爆；界面能做的只有选中买点时买点之后暗一档（X14）。
2. **默认成员仍是地基**：少收的有「画了没收」机械标记兜住；但夹在成员中间的多收框不改变 bracket 长度，只在选中买点时看得见（上一轮残余风险 3 不变）。
3. **定级预填与一半门槛**：用户可能不看就接受预填的级；最危险的一类（全部正例都有、没写定义）已不预填，其余错了在分层上看得见、能 ⚑。顶层名字不到一半默认不放，只在 `excluded` 区写原因，用户不看那一区就不知道（flow V2 验证）。
4. **pattern 页层级与图上框套法不一致**（D1 选推荐项时）：分层页用级标签 `optional` / `must_not` 和落法 `where` / `child` / `negation`，不用 `⊂`；是否一眼分得开要用户亲眼看。
5. **两条用户规矩靠记忆**：只在点名字（显示定义）和选买点（之后暗一档）两个时刻提醒。
6. **当前买点的自动并进**：顺手画的探索框会并进当前买点（bracket 当面伸长、看得见）；量在 flow V4 / ux U20 验证。
7. **严格包含的代价**：子框边画出去一点就按先后读，直到用户在 edit 栏点上 `⊂`；提示只有框角没出现 `⊂` 这一处。代价只在那一个框，不外传。
8. **近义词只靠同字冒出来**：「横盘 / 平台」这类没有同字的近义词起名时冒不出来，只能靠定义里的同字或事后在 vocab 合并（可拆回）兜住（sim L6）。
9. **几个显示数要用户亲眼判**：买点之后暗一档（黑 7%）与非成员框透明度约 0.3 分不分得开；浅琥珀与浅灰（上一轮 V5）；拖框边热区 5px 在短框上挤不挤。
10. **`ask` 单子依赖票 09** 把会话的问题存成随 app 的文件；票 09 没做之前，单子只能在对话里列。
11. **小别扭只记不改**：虚线在主图（= 你的框）和侧栏（= 空着 / 缺）意思不同（Q14）；`mapped` 状态没有悬停解释、悬停里漏出内部编号「critic X1」、买点之后变暗盖住后面的买点三角（sim L4、L5、L7，已告诉 ux）。
