## 1. 第一段：必要性

原问题里的「resume 状态」是 §3.2 定义的广义状态：**跨中断保持、使后续行为正确**。具体指「这批数据已经被搜过哪些格」。下面逐条回答四个硬问题。

### 1.1 Q1 谁消费 —— 没有消费者（决定性否定）

现状的 optimism 是（`region_core.py:490-505`）：

```
optimism = mean_b [ s_nb^(b)(ĉ_b) − s_nb^(0)(ĉ_b) ],   ĉ_b = argmax_{c ∈ G_now} s_nb^(b)(c)
```

跨轮信息只有一个进入口：把 `G_now` 换成 `G_all = ∪_r G_r`。公式本身好写。问题在于它要求对 **G_all 里的每一个格**，都能在**当前这份数据**上取到 `s_nb^(b)(c)` —— 而那需要该格的四态计数（`fp_up/down/both/none`，按 symbol、按 fold），不是一个名字。于是二分，两边都落空：

- **旧格的行还在当前长表里**（典型：上一轮网格更宽，这一轮删了一维）。此时公式确实能算——但这时候更简单的做法是**直接把 `region_find` 的 `COMBO_LEVELS` 设成并集再跑一遍**。它是识别端常量，`reference.md` §4.0 表最后一行明确「只改 `region_find` 侧常量（功效线、`REF_POINT`、邻域轴）不需要重做对拍」，而 `region_find` 本身是分钟级（§8 坑 10）。**跨轮状态在这里是多余的：需要的东西本来就在手上。**

  ⚠️ **这条论证依赖那份旧长表继续存在，而它现在只靠「没人删」撑着**：2026-08-25 那份 38MB 长表不但不在 git 里（该目录自带的 `.gitignore:2` 排掉了 `longtable/`），而且**当前代码已经再生不出来**——`study.py:5` 的 `BASE_YAML = "p2.yaml"` 指向的文件已被 `41fd193` 删除（实测 `path2_apps/bb_v1/` 下只剩 `params.yaml`），跑 `multivar_scan` 会直接 `FileNotFoundError`；即使把 yaml 恢复也不行，`throwback_v1.py` 已换代重写。所以「删维时材料本来就在手上」成立的前提是**别把旧长表当垃圾清掉**（critic 已就此纠正 app-lifecycle 的删除清单初稿）。

- **旧格的行不在**（换了档位数值、换了 detector 源码）。此时元数据能提供的只有格的**名字**，bootstrap 要的是格的**计数**，名字补不出计数。存下来给谁？没有人。

**唯一能纯靠元数据写出来的公式**是模型化惩罚——不重算旧格，而是按候选数放大 optimism，例如 `optimism × √(ln m_all / ln m_now)`。这条路我实测后否掉：`repro/optimism_vs_gridsize.py` 的 null 场景里，`optimism / √(2 ln m)` 从 m=16 的 0.0015 单调涨到 m=1024 的 0.0050，**根本不是常数**，这个缩放律在本工具的打分口径（fold 最小 → r=1 邻域最小 → 排序）下不成立。硬套等于拿一个编出来的数字换掉一个有 bootstrap 实测支撑的数字，与 skill「三口径并报、不折中」的取向相反。

**这一条是否定性的、也是最硬的一条。** 前序报告 §4.2 说「缺四件事：状态怎么表示、存在哪、谁更新、谁消费；最后一条是真空缺」——查下来它不是「暂时空缺」，是**结构性地不存在**。

### 1.2 Q2 人的判断能不能被捕获 —— 一半不能，另一半现在正在丢

拆成三类：

| 决策 | 能否自动捕获 | 现状 |
|---|---|---|
| 网格本身改了什么 | **能** | `apps/<app>/study.py` 进 git，每次改动是一个 commit；`classification.json` 还存了 study 指纹 |
| 在同一份数据上「又看了一遍」（换功效线 / 换 `REF_POINT` / 换邻域轴重跑 `region_find`） | **能，但现在全丢** | 见下 |
| 删维的**理由**（「我看到这维全负」） | **不能** | 只能靠人写 |

中间那一行是真缺口，而且它比原问题设想的更具体：

`region_find.py` 末尾是 `(out / "region_report.md").write_text(...)`，`out` 默认 = 长表目录的父目录 = `outputs/tune_gates/<APP>/`，而 `outputs` 在 `.gitignore` 第 3 行。**每次运行无条件全量覆盖，前一次的报告不留痕。** 而那份报告里其实已经含有一次「选择」的全部要素：study 指纹、长表、`HEAD_BUFFER`、fold、功效线、邻域轴、网格形状与格数、参照格、ĉ、naive / optimism ± SE / split-half、bootstrap 稳定性、三档判词。

对照扫描端：`multivar_scan.py` 里 `run_stats.jsonl` 的注释写得很清楚，它就是为了修**同一个覆盖病**才加的（「`ledger.md` 此前每轮无条件 `write_text` 整体覆盖……改为 append-only 历史」，修复轮 1 Important 1）。**扫描端修了，识别端没修——而识别端才是「选择」真正发生的地方。**

这不是假想的：`apps/bb_v1/notes.md` §6 明确记录了本例跑过敏感性口径（可评估面 81.7% 买点日口径 vs 56.1%），也就是同一份数据换判据看了第二遍；换功效线会改变可评估面 → 改变候选集 → 是货真价实的第二次搜索。那次运行的报告现在已经不存在了，数字之所以还在，是因为**人手抄进了 notes.md**。

**与自由文本 `ledger.md` 的实质区别**（这是原问题特别要求回答的）：
- `ledger.md` **不是**人写的自由文本——它是 `multivar_scan.py:268` 的机器产物，每轮全量覆写（这一点前序报告初稿说反了，主会话已在 §4.2 加了事实修正）；
- 它**只覆盖扫描端**，识别端一行不写；
- 它现在**没有任何读者**（历史上有过一个：`region_find` 旧版的 `_check_head_buffer()` 用正则从 ledger 文本里抠 `HEAD_BUFFER`，该函数已被删除、职责交给了 `run_meta.json`）；
- 它在 gitignore 目录里，**且改网格恰恰会把它清零**：`study_io.py` 的 `RUN_CALIBER` 含 `study_fingerprint`，改了 `study.py` 就撞 `write_run_meta` 的 `raise SystemExit(...换口径请换 OUT_DIR...)`，历史从新目录零开始。**产生跨轮暴露的动作清零计数器，不产生暴露的续跑反而累加**——方向正好反了。

所以答案是：**「看了几次、每次用什么判据、选出了什么」完全可以自动捕获且零成本，「为什么这么删」不能。** 前者值得做，后者不值得为它设计机制。

### 1.3 Q3 不做的代价 —— 实测与 0 不可区分

这一条我做了两个模拟（`repro/`，纯 null 合成数据 + 真实的 `region_core` 打分与 bootstrap）。

**(a) 候选数本身的效应**（`optimism_vs_gridsize.py`，R=8 次数据重复，B=200）：

| 格数 m | 16 | 64 | 256 | 1024 |
|---|---|---|---|---|
| optimism 均值 | +0.0035 | +0.0094 | +0.0121 | +0.0185 |

量级与 `SKILL.md` 红线里「4096 格选 1 抬高 +1～2.5pt」一致。注意它**不**按 √(2 ln m) 走（见 §1.1）。

**(b) 直接模拟「删维」这个场景**（`two_stage_optimism.py`，R=5，B=200）——这才是前序报告 §3.2 点名的「最隐蔽的一种」。做法：全网格跑 → 按「逐档均值极差最小」挑出那条换档不改变分数的轴 → 锁死重跑；然后把**删维本身当成流程的一部分**，每个 bootstrap 副本都重跑整套两段流程，得到正确的估计量 `opt_2stage`，与现状实际报告的 `opt_sub`（只在子网格上重采样）比较：

| 锁死档位的规则 | 现状报告 `opt_sub` | 正确值 `opt_2stage` | 低估量 = 正确 − 现状 |
|---|---|---|---|
| 锁在该维当前最好的档 | +0.0188 | +0.0167 | **−0.0021 ± 0.0024** |
| 锁在底座档 | +0.0165 | +0.0160 | **−0.0006 ± 0.0011** |

两种规则下低估量都与 0 不可区分，**而且符号是负的**——现状报告的 optimism 反而略微**偏大**（偏保守）。对照量级：
- 单次 bootstrap 自身对 optimism 的蒙特卡洛 SE ≈ 0.0023（同一批模拟）；
- bb_v1 真实运行：optimism = 0.1263 ± 0.0062，naive 0.0705 ↔ split-half −0.1319，跨度 **20.2 pt**（`apps/bb_v1/notes.md` §5）。

也就是说：**跨轮删维带来的偏差，比 bootstrap 自己的估计噪声还小，比决策实际依赖的证据跨度小两个数量级。** 在精度上它是噪声。

**(c) 真实长表上的独立验证**（critic 做的，`repro/critic_optimism_vs_gridsize.py` + 同名 `.log` / `.json`；下面每个数字我都用 `.json` 程序重算过，不靠肉眼读日志）：用 2026-08-25 那份真实长表（`docs/research/2026-08-25_multivar-bb_v1/longtable/`，43 分片 / 38MB / 7,831,477 行 / 3985 股），先逐字复现基线 `naive=0.0705 / opt=0.1263±0.0062 / sh=-0.1319`，再做 14 个塌缩条件。

**第一组：单轴塌缩 11 条**（= 这一轮没搜这一维）：

| 塌缩掉的轴 | 格数 | optimism | split-half |
|---|---:|---:|---:|
| （全网格） | 442,368 | **0.1263** | −0.1319 |
| `burst.peak_age_max`（pred） | 221,184 | **0.1379** | −0.0757 |
| `tb.day_drop`（pred） | 221,184 | 0.1186 | −0.1319 |
| `burst.first_drought`（pred） | 147,456 | 0.1014 | −0.0690 |
| `burst.distinct_pk`（pred） | 147,456 | 0.1162 | −0.1859 |
| `burst.max_bar_vol_ratio`（pred） | 147,456 | 0.0886 | −0.1319 |
| `bo.min_relative_height` | 110,592 | 0.1008 | −0.1127 |

**第二组：同时塌缩多根 combo 轴 3 条**（把候选集压到三个数量级之外）：

| 条件 | 格数 | optimism | naive |
|---|---:|---:|---:|
| 塌缩前 2 根 | 27,648 | 0.0818 | +0.0196 |
| 塌缩前 4 根 | 1,728 | 0.0909 | −0.0184 |
| 塌缩前 6 根 | **432**（= 全网格的 1/1024） | 0.0885 | −0.0350 |

三条读数：
1. **单轴塌缩 11 条**：optimism 落在 [0.0886, 0.1379]，相对全网格 0.1263 的最大偏移 **0.0376**，**11 次里 3 次反而变大**。在有真实结构的数据上，「候选集大小 → optimism」这条关系弱到连方向都不稳定。
2. **跨三个数量级也一样**：候选集从 442,368 一路压到 432 格（**1024×**），optimism 只从 0.1263 走到 0.0885。**全部 15 个条件的 optimism 都落在宽 0.0561 的同一条带子里。**
3. 与噪声地板对照（见 (d)）：**候选集变动三个数量级带来的 optimism 全部变动范围（0.0561），小于 split-half 单是换随机种子的噪声（sd 0.0762）。**

两条诚实标注：
- 塌缩一根轴同时改变了候选数、邻域结构（`neighbor_min` 少一根轴）和可评估面，**不是干净的「只改候选数」操作**。但它恰好**就是**「第二轮删了一维」的真实形态，对本节要回答的问题反而比干净操纵更贴切。
- **第二组那 3 个多轴条件已经离开原问题的语境**：`naive` 在后两条上翻负（−0.0184 / −0.0350），是与全网格不同的 regime。它们支撑的是「optimism 对候选数不敏感」这个更一般的观察，**不**直接是「删一维的代价」——后者由第一组 11 行和 (b) 的两段式估计（−0.0021±0.0024）承担。别让这 3 行替删维结论背书。

**(d) 噪声地板：拿什么当分母**（同一份真实长表，critic 后续补测）。上面 (c) 的散布混了「换条件」和「换随机性」两件事。干净的测法是**全网格不动、只把 `split_half()` 的 seed 从 0 换到 19**：

```
split_half over 18 seeds: mean=-0.1659  sd=0.0762  min=-0.3083  max=-0.0346  range=0.2737
（20 个种子里 2 个返回 NaN——两个方向的选中格都不可评估）
```

于是量级阶梯是（同一份真实长表、同口径）：

| 量 | 大小 |
|---|---:|
| **split-half 自身的种子间 sd** | **0.0762** |
| 候选集变动 1024× 时 optimism 的全部变动带宽（(c) 15 条） | 0.0561 |
| 单轴塌缩对 optimism 的最大偏移（(c) 第一组 11 条） | 0.0376 |
| optimism 自身的 bootstrap MC SE（B=300） | 0.0062 |
| **本节 (b) 直接测的两段式删维偏差** | **0.0021 ± 0.0024** |

**要校正的那个量，比同一份报告里 split-half 自身的种子噪声小 36 倍**（0.0762 / 0.0021）。所以「在精度上是噪声」这句可以说得更实一点：它比三口径中另一个口径**自身的随机抖动**小一个半数量级。

> 数字口径的更正过程如实记（三方各错过一次，最终以 `.json` 程序重算为准）：critic 最初给的是一张跑到一半的日志快照（8 条），我据日志重算成 9 条、把它的「最大偏移 0.038」改成 0.026 并提出质疑；实际完整跑完是 **15 条**（11 单轴 + 3 多轴），单轴最大偏移 = **0.0376**——**critic 原来的 0.038 是对的，我的 0.026 才是错的**（源自不完整的日志）。上表已全部换成我从 `.json` 独立重算的值。
>
> 另注：`split_half()` 只做一次对半分、`SEED` 硬编码 0、报告里以四位小数无不确定度上报「下界」，而它的种子间抖动比 optimism 的 MC 噪声大一个数量级——**这本身是一个独立的统计缺陷**，由 critic 单独报给 lead 作后续项。本文只把 0.0762 当量级对照的分母用，**不把修它写成本方案的落点**（本方案已判定为「服务于人的审计日志、不进公式」，把一个真的统计缺陷绑上来会让两件事互相拖累）。

**这一条的诚实边界（请按这个强度读，不要读强）：**
1. (a)(b) 的合成数据是纯 null 且**格间独立**；真实长表里同一个 match 会落进很多格、格间强相关。这一格由 (c) 补上，方向一致。
2. **(a)(b) 测的是这个机制最弱的一档**：null 下每档均值都是 0 + 噪声，「删哪根轴」这个第一段决策基本由噪声决定——在 null 下「随数据变化」与「随机」观测不可分。这不使实验失效（噪声驱动的选择**正是** winner's curse 的机制本身，所以测的东西是真的、不 vacuous），但真实数据里删维决策会被真实结构强烈驱动，那种情形合成设计够不着。**这才是限制的真正来源，R=5 只是次要**（均值的 SE 与均值同量级，所以结论只能是「未观测到可区分于 0 的低估」，不能是「一定为 0」）。这一格同样由 (c) 补上。
3. 第一版删维规则我写错过：每条轴取「该轴上 s_nb 的最大值」，结果对所有轴都等于同一个全局最大值，`argmin` 恒返回 0 号轴，两段式退化成固定子网格，低估量恒等于 0——那是算术恒等式不是实证结论。已修正为按逐档均值极差挑轴（修正后 5 次重复删的轴分别是 d0/d1/d4/d2/d3，确认决策随数据变化），脚本里留了注释记这个坑。

### 1.4 Q4 有没有更简单的替代 —— 对样本内有，对外推窗没有

现行防线两条：「唯一无偏数字是同 `HEAD_BUFFER` 的外推窗」+ 红线「holdout 不碰」。

**对样本内暴露：确实已经兜住了。** 样本内的 naive / optimism / split-half 三个数字，skill 本来就声明它们不是无偏数字，只当方向证据用；跨轮泄漏是在一个已经声明不可信的数字上再动零点几个百分点（§1.3）。为它加一套机制，属于给已经打了折的数字再精确打一次折。

**对外推窗：完全没兜住，而且这是唯一真正无防线的泄漏。** 外推窗的无偏性只对**第一个**被拿去验证的候选成立。第一轮把候选 A 拿到 2026 窗、不行；第二轮改网格、拿候选 B 去同一个窗——从第二次起这个窗自己就变成了一个搜索空间，而且**没有任何校正**（bootstrap 只作用于样本内长表，够不着外推窗）。红线里「别借缓冲差异挑子窗」防的是同一轮内选择性使用外推数据，跨轮重复使用不在其射程内。

`SKILL.md` 第 7 步已经写了「记录尝试次数（防隐性超支）」。我 grep 了 `apps/bb_v1/notes.md`、`docs/research/2026-08-28_tune-bb_v1-tb-v2/`、`.claude/skills/tune-gates/`：**没有任何文件承载这个计数**。这条要求目前是悬空的。

### 1.5 第一段小结（哪个论点是真论点）

- **真论点**：Q1 无消费者（可查代码，二分穷尽）；Q2 识别端覆盖病（可查代码，且扫描端已为同一个病打过补丁）；Q4 外推窗跨轮重复使用无防线（可查红线文本射程）。
- **中等强度**：Q3 的量级（实测，但 null + 独立格 + R=5，只支持「未观测到可区分于 0 的低估」）。
- **弱论点，我不拿它当论据**：「ledger.md 是自由文本所以不够好」——事实上它是机器产物，问题在覆盖和作用域，不在「自由文本」。
- **一条我明确**不**用的论证**：critic 的独立核查确认「现有系统里跨轮暴露的记录量 = 0」（`ledger.md` 里唯一带「轮」字的 `n_runs` 数的是同一长表目录被续跑几次，与选择偏差正交）。这条事实是双向的——它堵死了「已有半成品、补齐即可」这条省力论证，但**不**自动推出「所以必须新建机制」。我下面的推荐不建立在它上面，只建立在 §1.2 那条具体的覆盖病上。
- **我逆着自己的动机审的一处**：我被派来研究一个机制，天然有动机论证它必要。§1.1 那条足以否掉原问题设想的整个机制，我没有绕过它去谈实现；下面第二段推荐的两件事都**不声称**能被 optimism 公式消费，消费者明写是人。

## 2. 第二段：实现方案（只覆盖判定为「要做」的部分）

### 2.1 【推荐做】识别端 append-only 运行历史

**先做一处切割，防止标签替论证干活**：**这不是 §3.2 所说的那个 resume 状态。** §3.2 给那个状态的授权理由是「丢了它 optimism 就低估、报告就是错的」，而这条理由已经被 §1.1 与 §1.3 拆掉了——`exposure.jsonl` 丢了，算出来的数字一个都不会变，变的只是人解读时手上有没有背景。按 §3.2 的定义（跨中断保持、使后续行为**正确**），它兑现的是「使后续判断更**知情**」。所以它是一个更小的东西：**识别端的运行审计日志**，不是 resume 状态。

**它解决什么**：`region_find` 每次运行都覆盖 `region_report.md`，同一份数据上「又看了一遍」这件事不留任何痕迹（§1.2）。补上之后，报告可以引用「这个 app 在这份数据上已经识别过 N 次、涉及 M 个不同网格」，供人在解读三口径时纳入判断。

**数据表示**：`.claude/skills/tune-gates/apps/<app>/exposure.jsonl`，append-only，一行一次运行。

```json
{"ts":"2026-08-29T14:02:11","tool":"region_find","git_head":"13cc12e",
 "study_fingerprint":"a1b2c3d4e5f6","longtable":"outputs/tune_gates/bb_v1/longtable",
 "window":["2024-01-01","2026-01-01"],"head_buffer":250,"folds":["2024","2025"],
 "grid_shape":[4,4,4,4,4,4,3,3,3,2,2],"n_cells":442368,"n_evaluable":361629,
 "min_count_per_fold":100,"neighbor_axes":"all","ref_point":{"bo.min_relative_height":0.2},
 "c_hat":{"bo.min_relative_height":0.3},"verdict":"corrected_negative",
 "naive":0.0705,"optimism":0.1263,"optimism_se":0.0062,"split_half":-0.1319,"stability":0.07,
 "note":"敏感性口径复跑;指纹不一致但用户裁定复用"}
```

**存在哪 / 为什么**：必须是 `apps/<app>/`，不能是 `outputs/tune_gates/<APP>/`——
1. `outputs` 在 `.gitignore` 第 3 行，不进 git（长表历来如此——2026-08-25 那轮把长表放在研究目录下，也专门加了一行本地 `.gitignore` 把 `longtable/` 排除掉）。旧长表现在还在盘上（38MB / 43 分片）靠的是没人清理，不是制度保证；
2. `study_io.RUN_CALIBER` 含 `study_fingerprint`，改 `study.py` 就强制换 OUT_DIR（`write_run_meta` 直接 `SystemExit`），历史会碎在多个目录里，而**改网格恰恰是最需要被记住的那次跨轮动作**。

⚠️ 它因此是一个**新的 app 耦合物**（已同步 `app-lifecycle`）：`apps/<app>/` 下的文件从 3 个（`study.py` / `classification.json` / `notes.md`）变成 4 个，且第 4 个是机器 append 的、不是人写的。

**删除某个 app 时它的性质与另外三个不同**（`app-lifecycle` 问到，这里给判断与两面理由）：`study.py` / `classification.json` / `notes.md` 是**这个 app 的配置与记录**，app 没了它们就没有意义，删得干净；`exposure.jsonl` 记的是**对这批数据的暴露史**，即便同名 app 被删掉重建、底层 pkl 数据还是同一批，「已经在这批数据上看过多少次」这件事在方法论上仍然成立。两面：
- 支持随整夹删：它的唯一读者是这个 app 后续的 `region_find` 运行；app 都退出了就没有后续轮要保护。留着还有反效果——删掉再用 `cp -r apps/_template apps/X` 重新接入时，旧历史会被静默继承，而那时网格与窗口都已经换过了。
- 支持不自动删：它是唯一持久的「看过几次」证据，删了就真没了，而 §1.4 那条泄漏正是靠它兜。

**我的建议**：默认随整夹删，但**删除动作必须显式点名它、报出条数**（「这里有 N 条识别运行记录，删除后不可恢复；要留请先复制到 `docs/research/`」），而不是静默 `rm -rf`。这是 `app-lifecycle` 分级表里的一个拍板项，不是我能单方面定的。

**谁写**：`region_find.main()` 末尾，紧挨 `region_report.md` 的 `write_text` 之后追加一行。**落点不需要新增任何常量**——`region_find.py:44` 已经从 `run_meta.json` 拿到 `APP`（`meta["app"]`），路径直接是 `study_io.APPS_DIR / APP / "exposure.jsonl"`。写法**直接照抄 `multivar_scan.py` 的 `run_stats.jsonl`**，那两处防御是实战修出来的、不要重新发明：
- 追加前若文件末字节不是 `\n` 先补一个（修复轮 3·3：上轮被 kill 截断的半行会把本轮拼成烂行）；
- 读侧逐行 `try/json.loads/except JSONDecodeError: continue`（修复轮 2·2：半行容错）；
- 字段取值一律 `.get(k, 默认)`（修复轮 3·2：兼容日后字段增删）。

**谁读、怎么用**：
1. `region_find` 自己在 `region_report.md` 头部多写一行：`本 app 历史：识别运行 N 次，涉及 M 个不同 (study 指纹 × 网格形状) 组合，最近一次 <ts>；本次判词 <verdict>`；
2. 人。**明写在报告与 `reference.md` 里：这个计数不进 optimism 公式**（理由见 §1.1 与 §1.3），它是解读时的背景，不是校正项。

**与 `ledger.md` / `run_stats.jsonl` 的关系**：**并存，分工不同，不取代任何一个**。

| | 端 | 粒度 | 写法 | 位置 |
|---|---|---|---|---|
| `ledger.md` | 扫描 | 本轮快照 | 覆盖 | outputs（gitignore） |
| `run_stats.jsonl` | 扫描 | 跨轮，**同一长表目录内** | 追加 | outputs（gitignore） |
| **`exposure.jsonl`** | **识别** | **跨轮、跨长表目录、跨网格** | **追加** | **`apps/<app>/`（进 git）** |

不与 `run_stats.jsonl` 合并：后者按长表目录分裂，前者必须跨长表目录才有意义。

**已知副作用（拍板项，见 §3）**：每跑一次 `region_find` 就会让 git 工作区变脏一行。我认为这是**特性不是 bug**——「我又在同一份数据上看了一遍」这件事出现在 diff 里，正是它该有的可见性；但它确实与「skill 目录应当安静」的直觉冲突。

**顺带修掉的一个真实缺陷**：`SKILL.md:32` / `reference.md:41` 要求「把『指纹不一致、用户裁定复用』写进本次 ledger」——而 `ledger.md` 是机器每轮覆写的，人写进去的话下次运行就被抹掉。这句指示当前是空转的。`exposure.jsonl` 的 `note` 字段可以承载它（由 Claude 在该次运行时填），或者把那句指示改指 `docs/research/<日期>_<任务>/` 的本轮记录。**两种改法都要动 skill 文本，本轮不实施，仅报告。**

**APP 从哪来（与问题二的接口）**：**不引入第四个 APP 来源**。`region_find.py:44` 已经从 `run_meta.json` 拿到 `APP = meta["app"]`，写盘路径就用它。若问题二最终选了 `study_io.CURRENT_APP` 这类单源，`exposure.jsonl` 仍应按 **`meta["app"]`**（长表实际归属的那个 app）归档而不是按 `CURRENT_APP`——两者本来由 `check_run_matches_classification` 绑住，但真出现分歧时，按长表归属存才不会把记录归错档。

**验收**：连跑两次 `region_find`（第二次改 `MIN_COUNT_PER_FOLD`）→ `exposure.jsonl` 两行、`region_report.md` 头部显示「识别运行 2 次」；手工把文件末行截断一半再跑第三次 → 不崩、烂行被跳过、新行另起一行。
⚠️ **验收基线当前不是绿的**：critic 实测 skill 自测 13 failed / 47 passed / 8 errors，两个根因都来自 tb 换代（详见 `critic_facts.md` §5）。其中 **8 个 error 与本文 §1.1 那条「旧长表不可再生」是同一个根因**：`41fd193` 删掉了 `p2.yaml`，而 `study.py:5` 至今指着它（critic 跨全部分支遍历该文件的每个历史版本，两个版本逐字都是 `p2.yaml`——所以 provenance 报告 §一 说这处修正「已做」是不成立的，从来没改过）。**改那一行同时解开三处**：skill 自测 8 个 error、长表不可再生、provenance「下一步」第 4 步跑不起来（另 10 个 failed 还需重做 `fixtures/bb_v1_p2_wide.json`）。实施时不要把「pytest 全绿」当门槛，只能比对**改动前后失败集合不变**。本方案只在 `region_find.py` 末尾追加写盘、不碰 `region_core` / `study_io` 的既有函数，而写死 bb_v1 三个数字的 `test_region_core.py:278-279,315-316` 测的是 `region_core` 的数值，不受影响。

### 2.2 【建议做，但请按记录纪律读，不要当机制】外推窗使用计数

**它解决什么**：§1.4 那条唯一无防线的泄漏。

**为什么它不能自动化**：tune-gates **不执行**外推步骤（`reference.md` §7：「本工具不做这一步」）。没有脚本跑外推，就没有脚本能自动写这个计数。**因此它只能是人填的**——也就是说它落在了我在 §1.2 批评过的那一类里。我不为它辩护，我只主张两点：
1. 它从一开始就不声称有公式消费者，所以不构成自相矛盾——我批评的是「用人填的自由文本冒充能被 bootstrap 消费的状态」；
2. **原设计指定的落点结构上承不住这个量**。`SKILL.md` 第 7 步原文是「整轮落 `docs/research/<日期>_tune-<内容>/`，记录尝试次数（防隐性超支）」——落点是**指定了的**（研究目录），所以我此前说「补的是落点」不准确（critic 指出，已改）。真正的问题是：研究目录**按轮切分**，把一个**跨轮**计数器放进按轮切分的目录里必然碎片化——这与我反对把 `exposure.jsonl` 放 `outputs/`（改 study 强制换 OUT_DIR → 历史碎在多个目录）**是同一条论证**。所以这不是「执行没跟上」，是原指定落点的结构缺陷，建议改指 `notes.md`（每 app 一份、跨轮累积）。

**最小做法**：`apps/<app>/notes.md` §7「外推」加一张固定的表，人每次做完外推追一行——日期 / 外推窗 / 被验证的候选格 / 该候选来自哪次识别运行（`exposure.jsonl` 的 ts）/ 结果 / 这是这个窗的第几次使用。配一句读数纪律：**第 k 次使用同一个外推窗时，那个窗对这次结论已不是无偏的**，报告要显式说明 k。

**明确不做**：不为它建新文件、不建计数器脚本、不试图把 k 折进任何数字（做 Bonferroni 之类的调整需要先定清楚「一次使用」的边界，那是另一个研究问题）。

### 2.3 【要做，不急】`compare_longtable` 断点续跑（字面意义的 resume）

**必要性**：低但为正。`compare_longtable.py` 确认没有 done 集（`grep` 过：`n_done` 只是循环里的进度计数器，只写 log，不落盘），崩了从头再来。代价按 `reference.md` §3.1 的全量外推是二十几分钟——**且注意这个数字本身是外推、不是全量实测**（前序报告 §4.1 已标注，`WORKERS` 从 8 提到 16 后的实际值同样未实测）。另外对拍的作用域绑定「app × spec 拓扑 × 维度分类」（§4.0），不是每轮都要跑，所以期望损失还要再乘一个小于 1 的频率。

**方案**：与 `multivar_scan` 同款按股 done 集——
- 新增 `compare_done.csv`（或 jsonl），每完成一只股票追加一行 `symbol, n_cmp, n_mism`；
- 启动时读它构造 done 集，从任务表里剔除；
- **异常不计入 done**（与扫描端一致，避免暂时性失败被永久跳过）；
- 落在长表目录的父目录（与 `compare_longtable.log` 同处），随 outputs 一起被 gitignore——这个是**纯效率状态**，不需要进 git。

**注意一处不能照抄**：扫描端的 done 集靠「已有 parquet 分片 ∪ baseline ∪ filtered」三源推导，对拍端没有对应产物，必须显式落一个 done 文件。别为了「对称」去推导，会推出错的东西。

## 3. 需要用户拍板的三项

1. **`exposure.jsonl` 放 `apps/<app>/`（进 git、每次运行弄脏工作区）还是 `outputs/`（安静、但跨轮不持久、改网格即清零）？** 我推荐前者，理由见 §2.1；后者等于把这个机制的唯一价值（跨轮）扔掉，我不推荐但列出来。
2. **外推窗计数要不要做？** 它是人填的纪律项，价值取决于用户是否愿意每次外推后动手填一行。不愿意的话直接不做——半途而废的计数比没有更糟（会造成「已经在管」的错觉）。
3. **`SKILL.md:32` / `reference.md:41` 那句「写进本次 ledger」怎么修**：改指 `exposure.jsonl` 的 `note` 字段，还是改指研究目录的本轮记录？两者都行，需要选一个。

## 4. 明确不做的清单（连同理由，防止日后重新捡起来）

| 不做 | 理由 |
|---|---|
| 把跨轮候选集并进 `bootstrap()` 的 argmax 空间 | 需要旧格在当前数据上的四态计数；有的话直接改 `COMBO_LEVELS` 就够，没有的话元数据也补不出（§1.1） |
| 按 ln m 缩放 optimism 的模型化惩罚 | 实测缩放律不成立（`opt/√(2 ln m)` 从 0.0015 到 0.0050），等于编数字（§1.1） |
