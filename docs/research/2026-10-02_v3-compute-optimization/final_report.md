# v3 计算优化研究结论

日期：2026-10-02。项目内路径均相对 repo root。状态：研究完成的原型建议，尚未实施到正式 skill。原问题为“启动 agent team 研究计算优化”，逐字记录见 [原始问题](原始问题.md)。

## 1. 结论

5000 只股票、约两年的股票日表现可以批量计算，并不需要因为记录达到约 252 万条就缩小普通买入对照。实验表明，滚动数值运算本身相当便宜，逐买点切表、构表和每轮扫描固定全池才是更值得先删除的重复工作。

推荐组合是：**内置滚动统计＋批量构表；close 首次穿越默认编译早停；普通对照预先按日期与波动档汇总、每候选重新配比；随机窗口用每日累计数量查询；共享不可变股票日结果。**不默认上区间树、巨型三维矩阵或复杂按需初始化。

必须分清：现有代码已经一次生成未来表现，再给不同候选复用。本轮不是发现“每轮重复算全部标签”，而是找到这次准备怎样更快，以及标签已经缓存后，每轮仍有哪些全表工作可以消除。

三名研究 agent 分别负责滚动准备、close 穿越、对照汇总，互相核对端点、状态接口及等价条件。全部实验使用合成完好数据，没有读取真实行情、训练/验证集，没有修改正式代码。结果只支持计算优化，不判断策略是否赚钱或评价公式是否正确。

## 3. 哪些优化优先做

### 3.1 启动准备：减少逐条 Python 和 pandas 操作

`path2/calc/atr.py:rolling_atr_pct_nanmedian` 当前通过 `rolling.apply(np.nanmedian)` 逐窗调用。可先做最小替换，使用内置 `rolling.median`；再把三列表拼接求 TR 改为数组运算。内置滚动接口默认有已编译实现，但本报告的秒数来自本地实验，不能由接口文档直接推定。[pandas 官方文档](https://pandas.pydata.org/pandas-docs/version/2.3.3/reference/api/pandas.core.window.rolling.Rolling.median.html)

必须保持 M 包含买点当日、头部完整窗口要求、偶数中位数规则。这里不能照搬项目另一个排除当日的波动函数。

`.claude/skills/tune-gates-v3/scripts/daily.py:_prepare` 对每条记录截取未来 DataFrame、求最高价、格式化日期，再追加元组。可改为按股批量滚动最大值、整列构表与复用日期字符串。新原型保留旧输出 schema，前 100 股所有列、检测输入帧与数据 hash 均逐位一致。详见 [滚动与准备实验](rolling.md)。

这部分足以先做；0.22 秒的滚动最大值再优化到 0.03 秒，优先级低于清除数秒乃至更长的构表工作。

### 3.2 收盘首次穿越：简单编译早停优先

每个起点的上下线先固定，向后检查 close，第一次碰到任一条线就结束；需要的是最先方向，而非两条线以后各自何时都会碰到。相比展开整个未来窗口，它省掉首次碰线之后的无用比较。编译数值循环有首次启动成本，必须与后续运行分开计时。[Numba 官方指南](https://numba.readthedocs.io/en/0.61.2/user/5minguide.html)

比较五种精确实现：逐股索引矩阵、32 股一批滑动视图、编译早停、最高/最低值区间树、滚动极值筛选后早停。H=20/60/120，快、中、几乎不触线三种合成情景全部核对最早位置和方向。

- 编译早停在快、中情景最好，本机暖运行全池 0.014–0.041 秒；几乎不触线、H=120 时约 0.186 秒。
- 滚动 close 最高/最低价可先排除整段都不可能碰线的起点，再检查剩余起点的先后。在几乎不触线的 H=60/120 情景更快，含筛选分别约 0.044/0.047 秒；快、中情景反而多做工作。
- 区间树在长窗几乎不触线时优于单纯早停，但这次仍不如滚动筛选，并额外占约 164 MB。以后若反复查许多不同 H 或任意区间，才值得重新考虑它。
- 不希望依赖编译库时，分批滑动视图矩阵仍是可用备选。视图减少复制，却不消除每个窗口内部的比较；这与 NumPy 对滑动窗口一般计算量的说明一致。[NumPy 官方文档](https://numpy.org/doc/2.2/reference/generated/numpy.lib.stride_tricks.sliding_window_view.html)

当前环境已经安装 Numba；若未来正式代码直接依赖，应明确依赖声明与分发，不靠当前机器偶然已有。未安装任何新依赖。详见 [首次穿越实验](passage.md)。

### 3.3 每轮评分：普通对照不再逐行展开权重

将当日全池按固定波动档分组，一次保存每组的上穿、下穿、未触线数量。每候选仍根据自己在各日期、各档的买点数量重新配比，普通对照不会固定成一个不随候选变化的平均数。

等价条件是：日期与波动档固定、组内普通股票权重相同。对一个组，“每行权重×每行状态再求和”等于“组权重×组状态数量”。先合计数量再求比例；不能直接平均每组的方向比例。本轮比例采用上穿数除以上穿加下穿数，同时保留未触线数量，**不借优化决定最终如何对未触线评分**。

计算复杂度从每轮遍历全池 N 行，降为候选 C 行＋日期×档位数量＋窗口数量。候选与普通对照的方向计数核对通过；浮点相加顺序改变，最大比例差约 `8.72e-15`，属于舍入范围而非逐位相同。

固定 BO 用自己的买点、同样的窗口，方向计数可以一次缓存。本轮仅用了合成 BO 选择集合，**未测真实 BO 检测时间**。如果后续要求 BO 也逐候选匹配日期/波动，则它同样要每轮重配，且可能存在无对应 BO 的组。详见 [对照汇总实验](baselines.md)。

### 3.4 随机时段：每日累计数量，窗口两端相减

保持随机起点、连续约一个月、有放回、同一批 200 窗口供所有候选使用。每次先形成按日上/下/未触线数量，再建立累计数量；任何窗口的数量由末端累计数减去起点累计数得到。窗口交叉或重复都无需重新扫描原始股票日。

这是窗口内方向计数的计算优化。每个窗口仍独立产生结果，交由确定后的外层评分规则处理；不能把 200 窗全合并、只算一个总体比例，也不能把 200 当作独立历史样本数。

## 4. 缓存如何组织

1. **股票日结果共用一份。**固定评价定义后，一次计算 M、方向状态和前瞻收益；候选主要保存选中的整数行号。固定 BO 也引用同一结果，避免相同买入日重复计算未来表现。
2. **冻结数据以后只完整校验一次。**现有评分每轮重新复制、校验、散列固定基线。不可变快照、版本与整数身份先建立好，之后只检查候选身份。若数据仍允许随时修改，就不能直接删掉这些校验。
3. **缓存键不能漏掉评价定义。**至少包括数据版本、股票与日期范围、复权/日历、买入价格、M 定义、H、上下线、close/high-low 模式、实现版本。BO 定义与检测参数另外版本化。
4. **缓存结果设容量上限。**Optuna 连续参数未必重复；每组都保存完整标签表会持续占内存。共享数组＋候选行号、按总字节限制，比依靠参数取整提高命中率更可靠；不得为了复用任意取整参数。
5. **先全量一次，再讨论按需。**本次规模的核心计算便宜，多轮候选可能逐步覆盖全池。先用简单全量准备和缓存，只有实测读盘/内存/覆盖范围说明有必要时，再引入按需或分批加载。

方向状态＋两个 float64 数值在 252 万行下约 40.86 MiB，仅指紧凑数组有效载荷；不包含行情、身份索引、日期、临时数组和 Python 对象。当前字符串表的 pandas 深度估算约 320 MiB，可能重复计算共享字符串，也不等于进程峰值内存。不能拿这两个不同口径直接报告实际内存节省倍数。详见 [缓存与代码审查](cache_architecture.md) 与 [载荷推算](cache_payload_sizes.json)。

## 5. 不能借优化改变的事情

| 边界 | 约束 |
|---|---|
| high/low 改 close | 这是评价定义变更，不是性能等价替换；两种分别验证 |
| 前瞻窗口 | 包含 t+1 至 t+H；不足 H 不记成未触线；不跨允许训练标签边界 |
| 波动计算 | 包含买入当天的既定历史窗口，不擅自平移 |
| 统计单位 | 候选先按同股票同日去重；组汇总不把日期变成窗口内等权单位 |
| 原股票重抽 | 日期×波动档统计不能重建逐股票权重；新窗口设计与旧重抽不是等价替换 |
| 空窗口 | 没有买点、BO 没有买点或全部未触线都是完好数据的自然结果；如实返回数量与未定义标记 |
| 空间中位数 | 不能以“组中位数的中位数”替代原始股票日的精确中位数 |
| 可靠性计算 | 分组计数能保存中心比例，未必足以保存股票/日期相关性；原始身份和明细仍需保留 |

如果前瞻收益或其普通对照仍参与每轮评分/合格判断，就必须在每轮准确计算；不能移到最终候选报告，声称搜索决策没有变化。本次未优化这类随候选加权的精确中位数，也未确定可信度校正公式。

## 6. 实验质量与限制

环境为 i7-14700KF、约 31 GiB 内存、Python 3.12.12、NumPy 2.2.6、pandas 2.3.3、Numba 0.61.2；版本及源文件哈希见 [environment.json](environment.json)。团队计时经同一文件锁串行，数学库单线程，避免多个 agent 同时跑基准互相干扰。未固定到同一 CPU 核；短计时有调度扰动，不用小幅差异作确定排名。

三组实验输入互相独立：穿越组固定外传 M，专门测内核；滚动组使用合成 OHLC，保留旧 high/low 的准备语义；对照组直接生成状态，不重新算价格。真实数据读取、实际 BO/pattern 检测、完整 Optuna、最终组合评分、磁盘缓存保存与重载均未测。本次不能回答完整搜索最终是几秒或几分钟。

完整规模含 504 个目标买入日；为了让每个目标日有完整前瞻，合成行情另补必要历史/未来段。**这不表示实际只有两年价格也一定有 504 个可评价买入日**。真实数据必须按原允许范围截断，不得借准备缓存读取预留验证数据。

一致性证据：

- M/未来最高价有独立标量参考、热身/尾窗/偶数中位数/重复价格例子；兼容准备前 100 股所有列、检测输入与 hash 相等。
- close 穿越有 14 组小随机例、6 个手工边界、九组全规模交叉比较；最早位置与方向零差异。
- 对照有 36 候选、重复窗口、边界窗口、空候选/未触线、相同波动切点与空档位检查；整数计数一致，加权计数报告真实浮点误差。

原始重复次数、种子、输入生成、独立计时范围和误差均保存在 [rolling_results.json](rolling_results.json)、[passage_results.json](passage_results.json)、[baselines_results.json](baselines_results.json)，重建步骤见对应报告。临时实验脚本交付前删除；正式代码和 skill 未改。

## 7. 后续实施建议

先完成批量准备与不可变缓存，再完成每候选的小型方向汇总；close 首次穿越采用简单早停。暂不把滚动预筛、区间树、GPU、复杂按需缓存加入默认方案。

实施验收时先在同口径下逐值核对，再分开记录实际数据读入、标签准备、一次 BO 检测、每候选 pattern 检测、评分和结果保存。只有这条完整调用链跑过，才能给出完整优化收益；如果检测仍占主要耗时，再针对检测研究，不能用本次数值核的提速替代它。
