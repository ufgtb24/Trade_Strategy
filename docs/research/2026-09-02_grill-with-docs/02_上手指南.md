## 第 1 步 · 安装

两种装法，两种哲学，**只选一种**（都装会每个 skill 出现两份）：

| 装法 | 命令 | 性质 | 适合谁 |
|---|---|---|---|
| **Claude Code 插件**（推荐） | 终端 `claude plugins install mattpocock-skills`，或会话内 `/plugin install mattpocock-skills` | 只读订阅，作者发版自动更新 | 你已经用插件方式装了 superpowers，习惯一致 |
| skills.sh 复制 | `npx skills@latest add mattpocock/skills` | 把 SKILL.md 复制进你的仓库，可以改，但不会自动更新（`npx skills update` 手动拉） | 想大改 skill 正文的人。勾选式安装务必把 `grilling`、`domain-modeling`、`setup-matt-pocock-skills` 一起勾上：`grill-with-docs` 只有一行，没这几个底件装了也不工作 |

推荐插件方式。理由：作者自己的 docs 页明确说「改 SKILL.md 的建议常常正确但不持久」（更新会覆盖），**标准做法是把你的偏好写进 `CLAUDE.md`**，skill 本身不要动。本项目 `CLAUDE.md` 已经是这么用的。

**验证**：

```
claude plugin details mattpocock-skills
```

应看到版本号和 skill 列表。或者在会话里敲 `/ask-matt`，让它介绍一遍自己。

**一个已知的假警报**：`/ask-matt` 或 agent 可能告诉你「grill-with-docs / to-spec / to-tickets 没装」。这是因为这些 user-invoked skill 带 `disable-model-invocation: true`，harness 不把它们放进注入给模型的 skill 列表，模型就以为没装。**它们装了，直接敲斜杠命令就行**。权威清单是插件的 `.claude-plugin/plugin.json`。

装完后你能用的（本项目会用到的加粗）：

- 用户手动触发：**`/grill-with-docs`**、`/grill-me`、**`/setup-matt-pocock-skills`**、**`/to-spec`**、**`/to-tickets`**、**`/implement`**、`/wayfinder`、`/triage`、`/improve-codebase-architecture`、`/ask-matt`、`/handoff`、`/wait-what`、`/teach`、`/to-questionnaire`
- 模型可自动拿：`grilling`、`domain-modeling`、**`tdd`**、**`code-review`**、`diagnosing-bugs`、`prototype`、`research`、`codebase-design`、`resolving-merge-conflicts`、`wizard`、`writing-for-agents`

## 第 2 步 · 每仓库一次的配置：`/setup-matt-pocock-skills`

在本项目仓库根目录开一个会话，敲：

```
/setup-matt-pocock-skills
```

它是「提示驱动」的，不是脚本：先探索仓库（`git remote`、`CLAUDE.md`、有没有 `CONTEXT.md`、有没有 monorepo 迹象、有没有装 `triage`），把发现摆给你，然后**一节一个问题**，每节先给推荐答案，你一个字就能接受。

### 2.1 三个问题与本项目的建议答案

**A · Issue tracker（工作项放哪）**

选项：GitHub Issues（用 `gh`）/ GitLab / **本地 markdown**（`.scratch/<feature>/`）/ 其他（你用一段话描述）。

本项目建议 **本地 markdown**。理由：
- 你的工作纪律是「禁止开 PR、合并一律手动」，不走 GitHub Issues 流程；
- 现在的 spec / plan 本来就是仓库内 markdown（`docs/superpowers/specs/`、`plans/`），本地 tracker 只是换了个目录和粒度；
- solo 项目，本地 tracker 是「一等选项不是兜底」（官方原话）。

注意它会**先推荐 GitHub Issues**：skill 的默认姿态是按 `git remote` 提议，而本仓库 origin 在 GitHub，本地 markdown 要你主动改选。官方还提醒一句：两者是替代关系不是叠加，用 GitHub Issues 就别再用本地文件。本项目不在 GitHub Issues 里跟踪工作项，所以选本地是干净的。

选完它写 `docs/agents/issue-tracker.md`，约定如下（来自 skill 自带模板 `issue-tracker-local.md`）：

```
.scratch/<feature-slug>/spec.md              ← /to-spec 的输出
.scratch/<feature-slug>/issues/01-<slug>.md  ← /to-tickets 的输出，一票一文件，从 01 编号
.scratch/<feature-slug>/issues/02-<slug>.md
```

每张票顶部有 `Status:` 行（`ready-for-agent` 等）和 `Blocked by:` 行，评论追加在文件底部 `## Comments` 下。

> `.scratch/` 要不要进 git？作者的模板说 issues「live as files in this repo」，默认是提交的。本项目现在的 spec/plan 都提交，建议 `.scratch/` 也提交，和 `docs/superpowers/` 同等对待。如果你更想沿用 `docs/` 前缀，可以在这一节选「其他」，用一句话说明「issues 放 `docs/tickets/<feature>/`，其余同本地 markdown 约定」，skill 会原样记下来、下游照做。两种都行，前者零摩擦。若选「其他」，把本地模板里的 **Wayfinding operations** 一节（`map.md`、`issues/NN-*.md`、`Blocked by`、`Status: claimed/resolved`）一并抄进你的描述：`/wayfinder` 就读这一节，没有它就没有约定可用。

**B · Triage 标签**

只有装了 `triage` skill 才会问。插件是整套装的，`triage` 在里面，所以会问一句「保留默认标签吗」，答 **是**。本项目不处理外部 bug 报告，`triage` 基本用不上，这一步只是让 `to-spec` / `to-tickets` 知道 `ready-for-agent` 这个字符串。

**C · 领域文档布局**

默认**单上下文**（根目录一个 `CONTEXT.md` + `docs/adr/`），不问直接写。本项目没有 monorepo 迹象，就是单上下文。

### 2.2 它会写什么

- `docs/agents/issue-tracker.md`：上面那套约定
- `docs/agents/domain.md`：告诉所有 skill「探索前先读 `CONTEXT.md` 和相关 ADR；没有就静默跳过、不要提议创建；输出时用术语表的词、别漂到 `_Avoid_` 里的同义词；和 ADR 冲突时显式标出来而不是静默覆盖」
- `docs/agents/triage-labels.md`：五个角色到标签字符串的映射表（恒等）
- `CLAUDE.md` 末尾追加一个 `## Agent skills` 块，三行各指向上面三个文件

写之前它会把草稿给你看，让你改。**它不会碰任何 SKILL.md**，如果碰了就是跑错了。

### 2.3 验证

```
ls docs/agents/         # 三个文件
tail -15 CLAUDE.md      # 看到 ## Agent skills 块
```

之后要改 tracker 约定，直接编辑 `docs/agents/*.md`，不用重跑。skill 升级后要不要重跑：作者被直接问过，答案是重跑（seed 模板会随版本变）；skill 自己的收尾话术更松，只说换 tracker 或推倒重来时才需要。下游 skill 的行为和 `docs/agents/*.md` 对不上时，重跑是最便宜的修法。

### 2.4 先给 superpowers 让路（本机必做）

superpowers 的 SessionStart hook 每次会话注入「哪怕 1% 可能适用也必须调 skill」，并且规定「做任何创造性工作前必须先 brainstorming」。你一敲 `/grill-with-docs`，它就可能先要跑 brainstorming，两个访谈叠在一起是浪费。所以第一次访谈之前，先在项目 `CLAUDE.md` 加一句（`using-superpowers` 自己写明「用户指令优先于 skill」，这句话就够）：

```
当我显式调用 mattpocock 的 skill（/grill-with-docs、/to-spec、/to-tickets、/implement、/wayfinder）时，
不要触发 superpowers 的 brainstorming / writing-plans / executing-plans，主链以 mattpocock 为准。
```

superpowers 要不要禁用、什么时候禁用，见 `03` 文档 §5。

## 第 3 步 · 第一次 `/grill-with-docs`

### 3.1 开场怎么说

先确认这件事值得访谈：只改数不改结构走本项目的 `tune-gates`，验证某个特征与 label 的关系走 `feature-study`，一个会话装不下的大活走 `/wayfinder`（第 10 步）。判据表在第 9 步。

新开一个会话（**别开 plan mode**），一句话说清你要做什么，然后敲 skill：

```
/grill-with-docs 我想给 bottom_burst 加一个「tb confirm 后破位」的过滤闸，
把超涨派发类的假阳性挡掉。研究结论在 docs/research/2026-08-11_超涨派发过滤/final_report.md。
```

给它一个入口（研究报告路径、spec 路径、或者一段描述）就够了，剩下的事实它自己去查。

### 3.2 第一轮长什么样（示意）

下面是按 grilling 格式、用本项目语境写的**示意**，真实会话的问题由模型现场生成：

```
我读了 final_report.md 和 path2_apps/bottom_burst/dag_spec.py，派了子代理在查
throwback.py 里 confirm 之后的 outcome 字段现在有哪些取值。先问不依赖那个结果的部分：

❓ **Q1** - **「破位」的定义**：报告里 W 组 21/21 的判据是「tb confirm 后收盘跌破
某个价位」。这个价位你指的是 (a) tb 段的最低价 (b) 回踩起点 (c) confirm 那根 bar
的低点？三者在 BRNS 那种双段 tb 上会给出不同答案。

➡️ 推荐 (a)。报告的 W 组统计用的是 tb 段最低价，换口径会让 21/21 这个数字失效。

---

❓ **Q2** - **闸放在 where 还是边**：这是 tb 自身的一元资格（tb 事件上带一个
「confirm 后是否破位」标量，where 直读），还是 tb 与后续 bar 之间的二元关系？

➡️ 推荐 where。按 glossary「用语纪律」，破位只看 tb 自己和它之后的价格，不涉及
另一个 node，属于一元条件。具体挂在哪个字段上，等子代理把 outcome 的取值报回来
再问。

---

❓ **Q3** - **滞后几根**：破位要在 confirm 后几根 bar 内发生才算？报告说
「零字段滞后 0-1 根」。0 根意味着 confirm 当天就得破，1 根给一天缓冲。

➡️ 推荐 1 根，并把它做成 app 参数进 configs/params/，走 tune-gates 定阈值。

---

❓ **Q4** - **eval 口径**：这个闸的效果用什么判？

➡️ 按项目纪律：median(forward_return) + 首次穿越率，对照 bo_only 基线，不用 win_rate。
这题我几乎确定，列出来是为了不默默假设。
```

你的回答可以就是：

```
1 a。2 where。3 先 1 根，但 0 也要能配、别写死。4 对，但基线要同窗同池的 bo_only，
不是全宇宙。
```

注意 Q3 和 Q4 的回答里你都**推了它一把**（0 也要能配；基线口径收紧），这就是「别当点头机」。等子代理把 outcome 的取值报回来，下一轮才会出现「复用 outcome 枚举还是新加字段」这种题：依赖待查事实的问题就是这样被推到后一轮的，它不该拿来问你，你也不必替它查。

### 3.3 会话中你会看到什么落盘

术语一定下来它就写。比如上面 Q1 定了「破位」，`CONTEXT.md` 会出现（如果文件不存在就此时创建）：

```md
**破位 / breakdown**:
tb 段 confirm 之后，收盘价跌破该 tb 段最低价。是 tb 的一元属性，不是 tb 与其他
事件的关系。
_Avoid_: 跌破、击穿、破位下行
```

一个可能过三道门槛的决定（难回头、事后奇怪、真权衡）会被**提议**成 ADR。下面这条借的是你以前在 revert 毒药闸研究里定过的「TR 归一排序强但当硬闸弱，硬闸用 pct」，只是拿来演示格式，破位闸这场会话未必会产出它：

```md
# 硬闸用绝对百分比，不用 TR 归一

TR 归一在排序类信号上区分度更强，但作为硬闸时阈值跨股不稳、命中数抖动大；
硬闸一律用绝对 pct（如单日跌幅 ≥ 20%），排序/打分时才用 TR 归一。
两者曾在 tb-v1 revert 研究里对照过，pct 版精确复现了预测的三个数字。
```

大多数会话**一条 ADR 也不产**，这是正常的。

### 3.4 会话结束

前沿空了它会停下来问你「理解一致了吗」。你确认之后，**不要 clear**，直接进第 4 步。

### 3.5 中途的三个自救动作

| 症状 | 动作 |
|---|---|
| 一口气倒出十几个问题、没有 ➡️ 推荐、不提 CONTEXT.md | 问它「你加载了 grilling 和 domain-modeling 吗」。没加载就让它现在加载 |
| 问题越问越多、开始绕圈 | 「范围太大了，先把这件事拆成几块，我们只谈第一块」 |
| 某个问题谈不出来（要看到东西才能答） | 停访谈，`/prototype` 做个一次性的看一眼，回来一句话答 |

## 第 4 步 · 同一会话接主链

### 4.1 `/to-spec`

```
/to-spec
```

它**不再问你问题**，只综合刚才谈的。唯一会停下来确认的是**测试接缝（seam）**：在哪个公共边界上测这个功能，越高越好，现有接缝优先，理想数量是一个。对本项目典型的回答是「在 `run()` / `analyze()` 出口按 match 集合测，不测 detector 内部」。

产出 `.scratch/tb-breakdown-gate/spec.md`，固定七节：Problem Statement / Solution / User Stories（很长的编号列表）/ Implementation Decisions / Testing Decisions / Out of Scope / Further Notes。**不写具体文件路径和代码片段**（会很快过时），唯一例外是原型产出的、比散文更精确的片段（状态机、schema）。

**必做的一件事**：拿你自己在访谈里的回答逐条对照 spec。官方承认精确答案（数值默认、否定性要求、顺序保证）会在这一步被软化。

### 4.2 `/to-tickets`

```
/to-tickets
```

先过一条判据：**整个改动一个上下文窗口装得下，就不用切票，直接 `/implement`**。上游把过度拆分列为这个 skill 被报告最多的摩擦。下面把破位闸切成三张只是为了演示格式，这个规模的改动按上游判据多半该直接 `/implement`。

切票时，它把 spec 切成「示踪弹」票：每张是垂直切片（穿透 detector → dag_spec → eval → 测试，单独可验证），**大小以一个新的上下文窗口装下为准**，每张写明被哪些票阻塞。切完先把列表给你看，问三件事：粒度对不对、阻塞边对不对、要不要合并或再拆。你点头后才写文件：

```
.scratch/tb-breakdown-gate/issues/01-tb-outcome-breakdown-flag.md
.scratch/tb-breakdown-gate/issues/02-dag-spec-where-clause.md     (Blocked by: 01)
.scratch/tb-breakdown-gate/issues/03-param-and-tune-gates-entry.md (Blocked by: 02)
```

每张票的模板：

```md
# 02: dag_spec 加破位 where 子句

**What to build:** bottom_burst 的 tb node 增加一条 where 子句，读 outcome=='break'
时拒绝该 tb；扫描结果里 W 组 21 例全部被过滤、G 组保留率不低于研究报告数字。

**Blocked by:** 01

**Status:** ready-for-agent

- [ ] 扫描 2025 窗，W 组命中数为 0
- [ ] 全量回归 uv run pytest tests/ -q 绿
```

一个对本项目特别相关的规则：**大范围机械重构**（改一个共享字段名、全仓改类型）不切垂直切片，走「扩张-迁移-收缩」：先并排加新形式、分批迁调用点（每批一张票）、最后删旧形式。你之前的 `class_id` 消除、`instance_id` 重构就是这种形状。

### 4.3 `/implement`（每票一个新会话）

到这里是一个**阶段边界**。按作者的规则：访谈 + spec + 切票在同一窗口完成，之后**每张票开一个新会话**：

```
/clear
/implement .scratch/tb-breakdown-gate/issues/01-tb-outcome-breakdown-flag.md
```

`implement` 本身只有五句话：按 spec/票实现；尽量走 `/tdd`（只在事先商定的接缝上测）；常跑类型检查和单文件测试，最后跑全量；完了 `/code-review`；提交到当前分支。

本项目要额外注意的两点（skill 不管，得你在 `CLAUDE.md` 里管）：
- 你的「Implementer 用 sonnet / Reviewer 用 opus」约定，`implement` 不认识，它在主会话直接干。要保留这个约定，就在 `CLAUDE.md` 里写明「`/implement` 时把实现派给 sonnet 子代理」，或者接受主会话实现。
- 提交信息、`uv run pytest` 命令、「注释中文」这些规范照旧从 `CLAUDE.md` 读。

还有一条上游确认的行为：`implement` **没有收尾动作**，提交完就结束，不会改票的 `Status:`、不会勾验收框，票的状态要你自己改。阻塞链上尤其要记得：下一张票能不能开始，是按前面的票有没有关掉判的，没人关票就没有票会解锁。

### 4.4 `/code-review`

`implement` 末尾会自己调，但那一次评审通常**看不到你的改动**：`code-review` 只读 `git diff <固定点>...HEAD`，不含暂存区和工作区，而 `implement` 是先评审后提交。上游记为双方都未修的已知 bug。可靠做法是提交之后自己再跑一次：

```
/code-review master
```

给一个固定点（分支名、commit、tag），它先确认 ref 能解析、diff 非空，再派**两个并行子代理**：一个审 Standards（仓库自己写下的规范可以判硬违规；12 条 Fowler 坏味道一律只作判断题；两者冲突时仓库规范优先），一个审 Spec（缺了什么、多做了什么、看着实现了但像是错的）。两份报告并排给你，**不合并不重排**，结尾各报一行「几条发现 + 各轴最严重的一条」。

## 第 5 步 · 冷启动：给现有仓库建 `CONTEXT.md`

这是本项目最该先做的一件事，因为 path2 已经有一套成熟的私有术语（where / edge / qualify / satisfies / 流源 / 复合事件 / 点事件 / span / diagnose / trace ……），散在 `.claude/docs/glossary.md` 里。

官方给的入口：

```
/grill-with-docs help me scaffold my existing repo with a CONTEXT.md.
现有术语在 .claude/docs/glossary.md，第 1 节「用语纪律」是最重要的部分，
其余各节混了实现细节，只取其中「概念是什么」的部分。
```

预期：它会读代码和 glossary，然后**问你很多问题**（有人报告 50+），每个问题本质上是「代码里这两个词是一回事吗」「这个词你要保留还是弃用」。你是那个说「哪个词才是对的」的人。

一份本项目 `CONTEXT.md` 大致会长成这样（**示意**，真实内容由会话产出）：

```md
# path2

独立的多级事件表达框架：detector 产事件流，dag 引擎按 node/edge 声明求解匹配，
app 层（bottom_burst）声明走势形态。

## Language

### 事件与流

**event**:
不可变的多级事件，带 start_idx / end_idx，容器字段一律 tuple。

**点事件 / point event**:
start_idx == end_idx 的事件。口头亦称 spot。
_Avoid_: 单点事件、瞬时事件

**span 事件**:
start_idx < end_idx 的事件，语义上是一段区间。
_Avoid_: 区间事件、段事件

**复合事件 / composite**:
detector 把子结构聚合成的一个宽事件，携带 members；在图里是一等事件。
_Avoid_: 嵌套事件、容器事件

**流源**:
只为产流给别人消费、自己无边的孤立 node。
_Avoid_: 源节点、上游节点

### 约束与判定

**where**:
单个 event 够不够格当某 node 的一元条件，不看拓扑。
_Avoid_: 定语（只作释义）、过滤器、条件

**edge**:
node 间的二元关系，与 where 正交。
_Avoid_: 拓扑（只指整体）、约束

**qualify**:
动词：event 过某 node 的 where。
_Avoid_: 满足、通过

**satisfies**:
动词：两个 event 的边关系成立。
_Avoid_: qualify（那是一元的）、匹配

### 调试视图

**diagnose**:
per-node 的健康检查视图，同时含 where 与拓扑；只指面板，不指条件。

**trace**:
per-完整匹配的判定记录视图。
```

注意它**没有** class_id 的现值列表、没有 `_solve.py:152` 这种行号、没有「五类校验」这种实现清单。那些留在 `.claude/docs/glossary.md` 和 `modules/*.md` 里（怎么分工见 `03` 文档）。也没有「待定歧义」这类小节：「pk 不是 event」这种已经拍板的决定归 ADR，术语表只放定下来的词。

第一次建完之后，`CONTEXT.md` 就靠每次 `/grill-with-docs` 会话增量维护，外加偶尔一次瘦身：

```
/grill-with-docs make my CONTEXT.md more concise and remove any implementation details from it
```

## 第 9 步 · 什么时候用、什么时候别用

| 场景 | 用不用 grill-with-docs | 理由 |
|---|---|---|
| 调一个闸的阈值（只改数、不改结构） | **不用**。走本项目的 `tune-gates` skill | 没有新词、没有新决定，访谈没东西可谈 |
| 加一个新 detector 或改 dag_spec 结构（如上面的破位闸） | **用**，一个会话能谈完 | 有新术语、有 where-vs-边这类真决定 |

## 第 10 步 · 大活：`/wayfinder`

本项目最典型的大活（多流引擎、bo 串成一等事件这种）一个会话谈不完，路线也看不清，这就是 `/wayfinder` 的用武之地。它和 `/grill-with-docs` 是同一套访谈，区别在于把工程画成一张「决策地图」，一票一个决定，每个会话只解一票，直到路线清楚。**它只产决定，不产交付物**：图清了之后照样要回到 `/to-spec` → `/to-tickets`。

前提：它读 `docs/agents/issue-tracker.md` 里的 **Wayfinding operations** 一节决定地图和票放哪。第 2 步选了本地 markdown 就已经有了：地图在 `.scratch/<effort>/map.md`，票在 `.scratch/<effort>/issues/NN-<slug>.md`。

### 10.1 画图（一个会话）

```
/wayfinder 我想把 path2 的 bo 串重构成一等 detector event，替掉 Kleene 特例。
目的地是一份可以直接交给 /to-spec 的设计定论，不是代码。
```

它按固定顺序做六件事：

1. **先定目的地**：用 grilling + domain-modeling 跟你谈清「这张图走到头是什么」（一份 spec、一个决定、还是一次原地改动）。目的地定了范围才定。
2. **广度优先再谈一轮**：不深挖任何一条线，只把整个空间里的开放决定和现在就能走的第一步摸出来。**如果这一轮发现没有雾**（路线其实已经清楚、一个会话装得下），它会停下来告诉你不需要地图，这是正常出口。
3. **建 `map.md`**：五节，Destination（目的地）/ Notes（这张图要用的 skill、你的固定偏好）/ Decisions so far（已定决定的索引，一票一行）/ Not yet specified（看得见但还说不清的「雾」）/ Out of scope（明确划出去的）。
4. **建现在能说清的票**，每张一个问题、带 `Type:`（`research` 查资料 / `prototype` 做个东西看 / `grilling` 谈 / `task` 先干件杂活才能决定），再第二遍连 `Blocked by`。
5. **把 research 票派给子代理并行跑**，结果落在临时分支上、票里留指针。
6. 停。画图是一个会话的活，不解任何票。

### 10.2 走图（每会话一票）

```
/wayfinder .scratch/bo-as-event/map.md
```

不指定票就由它挑前沿里的第一张（`Blocked by` 全部 `resolved` 且没人 `claimed`）。流程：先把票标 `Status: claimed` → 解它（默认还是 grilling + domain-modeling，术语照样进 `CONTEXT.md`）→ 答案写进票的 `## Answer`、标 `resolved`、在 `map.md` 的 Decisions so far 加一行指针 → 新冒出来的问题建票、雾里说得清的部分毕业成票、发现超出目的地的直接关掉记进 Out of scope。**一个会话只解一票**（research 票除外）。

### 10.3 两条上游反馈

- 它是整套里最重、最密的流程，触发条件要窄：真的一个会话装不下、路线真的有雾。拿它去做一个范围清楚的功能是常见错误。
- 最尖锐的未解决投诉是**地图太啰嗦、造成决策疲劳**。前沿虽然允许并行解票，但上游建议一次一张更稳。

## 排错清单

| 现象 | 最可能的原因 | 做法 |
|---|---|---|
| 没问就开始写代码 | 模型/effort 太低，把「访谈到理解一致」压成了两句 | `CLAUDE.md` 加「未经我确认不得实施」；换更强模型 |
| 跑完 `CONTEXT.md` 没出现 | 没有新术语（正常）；或 domain-modeling 没加载；或在别的编排层里跑了 | 问它加载了什么；看工作目录 |
| `CONTEXT.md` 越来越像 spec | 模型把「写进去」理解成「什么都写」 | 瘦身命令，见第 5 步末 |
| `/ask-matt` 说某 skill 没装 | `disable-model-invocation` 让它在列表里不可见 | 直接敲斜杠 |
| `/to-spec` 漏了我明确说过的数值 | 已知的软化问题 | 拿自己的回答逐条对照，手动补 |
| `/to-tickets` 写了一个大文件而不是一票一文件 | 模型把票合并了。「一票一文件」写死在 skill 正文里，不是模板问题（v1.1 曾有过单文件 `tickets.md`，已当 bug 修掉） | 让它按 skill 模板拆开重发；顺便确认 `docs/agents/issue-tracker.md` 里写的是 `issues/<NN>-<slug>.md` |

## 一页总结

- 装插件、跑一次 `/setup-matt-pocock-skills`（选本地 markdown，它会先推 GitHub，要主动改）、`CLAUDE.md` 加一句给 superpowers 让路，配置就完了。
- 主链五步：`/grill-with-docs` 访谈 → 同一会话 `/to-spec` → `/to-tickets`（整个改动一个窗口装得下就跳过）→ 每票新会话 `/implement` → 提交后再跑一次 `/code-review`。
- 首次真跑必撞的三件事：`implement` 末尾那次评审看不到未提交的 diff；票不会自动关，`Status:` 自己改；访谈里事实归它查、决定归你拍，别当点头机。
- 冷启动先做 `CONTEXT.md`（以 glossary 第 1 节为种子，术语表且只是术语表），再回填几条 ADR（三道门槛同时过才够格）。
- 只改数走 `tune-gates`，验证特征走 `feature-study`，一个会话装不下的大活走 `/wayfinder`，其余才是 `/grill-with-docs`。
