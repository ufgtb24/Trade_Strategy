## 拍板点 1：回踩确认要不要变成"独立事件"？（⚠️ 唯一会改变结果的）

### 这在决定什么

现在的代码里，"回踩确认"是挂在**整个突破簇**头上的一个布尔值——具体看的是簇里**最后一个**突破点之后有没有回踩。

新架构想把"回踩"**升级成一个独立的事件**。好处很直接：面板上它能画成一个**独立的节点**、能高亮、能跟突破点连一条线（不再只是个看不见的布尔标志）。

升级有个副作用：detector 会对簇里**每一个**突破点都去算一次"它后面有没有回踩"，于是结果里会**多出**一些"中间突破点的回踩事件"。

**但这不影响命不命中**——pattern 是否命中只看"最后一个突破点 → 回踩"这一条边，跟现在一模一样。变的只是 `events` 列表里多了些东西。

### 两个选项

- **甲（推荐）：允许这些中间回踩事件存在。**
  - 好处：面板能显示"簇内每一次回踩"，信息更丰富；回踩第一次成为能画出来的一等公民。
  - 代价：这是整个重构里**唯一**一处结果和现状不同的地方（命中集合一致，但事件列表更长）。

- **乙：强行只留"最后一个突破点"那一次回踩，让结果和现状逐字节一致。**
  - 好处：结果完全没变，验收最省心。
  - 代价：为了"看起来没变"给 detector 加一道自我设限，不自然，也丢了"面板显示中间回踩"的信息。

### 我的推荐

**甲。** 你既然要面板拓扑信息丰富，这是净增益；而且它不碰命中逻辑，风险低。

### 你什么时候该选乙

如果你有**下游代码或测试严格假设"回踩事件只有一个"**，那选乙避免踩坑。否则没理由选乙。

## 拍板点 2：要不要现在就做"匹配策略"可调开关？

### 这在决定什么

当一段数据里有**好几种**都满足条件的事件组合时，引擎得有个规矩决定"挑哪个、挑几个"。比如一个下跌段后面跟着好几个可能的突破簇，是只认最早凑齐的那一组，还是把所有可能组合都列出来？

新架构默认用一个固定规矩（"遇到下一个就接着往后找"，跟现在代码行为一致）。问题：**要不要把这个规矩做成一个开关**，让将来写 pattern 的人能选别的策略（"严格相邻""列出所有组合"等）？

### 两个选项

- **甲（推荐）：暂时不做开关，固定用默认。** 当前走势根本用不到别的策略；加开关 = 给引擎平添分支、为"还不存在的需求"买单。
- **乙：现在就做开关，给未来留口。** 代价：引擎多一套分支逻辑，提前投入。

### 我的推荐

**甲。** 需要时再加是零损失的——加开关本身不需要推翻任何已有设计。

### 你什么时候该选乙

如果你**心里已经有**一个近期就要做、且需要"列出所有组合 / 严格相邻"这种非默认策略的 pattern。否则选甲。

## 拍板点 3："连续 N 个"的重复结构，要不要现在就做全功能？

### 这在决定什么

"突破簇 = 连续好几个突破点"这种"重复一串"的结构，学名叫 **Kleene 闭包**。它有几种花样：

- **"至少 N 个"**（我们的突破簇正是这种：至少 MIN_BOS 个）→ ✅ 新架构支持，且数学上保证不出错。
- **"恰好 N 个""最多 N 个""不要贪心、要枚举各种长度的子集"** → ❌ 新架构暂不支持。

不支持的那几种，要么需要**指数级枚举**（很慢），要么得换一套更重的引擎机制。新架构只把**我们当前真正用到的那种**做到严格正确。

### 两个选项

- **甲（推荐）：只做"至少 N 个 + 贪心取最长"。** 遇到其他花样，引擎**直接报错**（明确拒绝），**绝不偷偷用贪心给你算个错答案**。
- **乙：现在就做全功能 Kleene。** 代价：引擎要么背上指数级枚举、要么引入更复杂的机制，为"还没出现的需求"投入很大。

### 我的推荐

**甲。** 关键是"明确报错"比"静默出错"安全得多——你永远不会拿到一个悄悄算错的结果。需要别的花样时再建。

### 你什么时候该选乙

如果你近期就要写"恰好 N 个突破""最多 N 个"这类 pattern。否则选甲（报错会挡着你，不会坑你）。

## 拍板点 4：几种"部分交叠"的关系边，要不要现在就做？

### 这在决定什么

两个时间区间的关系，除了"A 完全包含 B"（我们的"横盘段包含突破点"就是这种 → ✅ 新架构已做成一等公民），还有这些花样：

- "A 和 B 前半截交叠""后半截交叠""两者完全相等"——这些**部分交叠**关系，**当前走势一个都没用到**。

### 两个选项

- **甲（推荐）：现在不做这几种部分交叠的边。** 架构里留了个扩展位——将来真要用，**加一个小类、十几行代码、不动引擎核心**就行。
- **乙：现在就把"部分交叠""相等"全补齐。** 代价：为没人用的功能写代码 + 测试（镀金）。

### 我的推荐
  
**甲。** 扩展成本极低（加个子类即可），没必要提前做。

### 你什么时候该选乙

如果你近期有 pattern 需要"两个区间部分交叠"这种关系。否则选甲。
