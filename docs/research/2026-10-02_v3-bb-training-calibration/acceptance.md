# v3 独立验收

验收日期：2026-10-02。本文所有项目内路径相对 repo root。

这次独立检查了技能说明、配置和真实执行链，并用完全合成的价格与信号做了计算复算及串联演练。核心结果支持：它能在机会数量达到下限后按同一个方向成绩搜索和入选，也确实会给出暂用、随后恢复原参数的状态。这个结论不表示真实市场上有改善，更不表示已经具备自动确认改善的能力。

结论：**当前未发现剩余阻断。** 验收曾发现行情整体过旧仍可能被当作正常最终结果的问题；实现者补齐保护后，我用同一合成反例独立复验，现已拒绝过期文件，且完整数据流程仍通过。当前不能自动确认改善的限制已经如实写进技能，与用户允许暂用的请求相容。

## 重要发现及修复复验：拒绝整体滞后的数据

**状态：实质缺陷已修复，并通过独立反例复验。**

初次验收时，`run_check` 只比较当前自然日期与预定 `label_end`，随后立即记录该阶段消费；逐日评价对实际可读取文件裁切并生成其已有标签，没有行情更新状态校验。窗口又以实际可评价日期建日历，因此整体缺失的尾部不会作为空时段保留下来。

独立复现使用八只完全合成股票、真实 `DailyEvaluator`、真实标签、真实固定 bo、真实 Optuna 和真实临时账本：

1. 预定最终买点范围为 `2019-02-01` 至 `2019-06-03`，允许未来尾部至 `2019-06-10`，观察后续 2 根。
2. 全部合成文件只保留到 `2019-03-15`；运行时间已经晚于全部预定日期。
3. `run_check(..., 'final')` 成功保存 `provisional`，且一次使用记录已经消费。
4. 候选实际仅覆盖 29 个可评价日期、116 个股票日；报告 `active_window_fraction=1.0`、`recent_days=29`、`unavailable_count=8`。这些覆盖数字反映的是自动缩短后的可评价池，不能证明预定四个月已得到完整检查。

这里不是指出“每只股票必须每天有数据”。停牌、上市前、退市后和个别非法价格需要有预先固定的处理。初次验收发现的实质问题是：整个数据供应明显落后时，修复前的自动入口也会把剩余早期数据视为正常最终结果。

实现者随后修复：`run.evaluator` 从冻结交易日历计算该阶段 `label_end` 及之前的最后交易日，作为 `required_price_end` 传入评价器；评价器在许可区间内裁切后、该股标签计算前，逐股检查实际末日达到这个要求。训练、最后检查和复核使用同一入口。系统时钟只表示已到预定时点，不能代替行情末日检查。

我重新创建相同定义的合成 fixture，并实际重跑生产链路，结果如下：

| 独立复验 | 实际结果 |
|---|---|
| 完整行情的最终检查 | `provisional`，旧/新可评价股票日仍为 696 / 348 |
| 完整行情的预定复核 | `rollback` |
| 同一个整体滞后反例 | 报错 `S0 行情尚未到齐：最新日 2019-03-15，要求至少到 2019-06-10` |
| 滞后反例的最终结果文件 | 未生成 `final.json` |
| 滞后反例的使用记录 | final 已消费记录保留，没有恢复成“未见” |

因此该发现已经关闭。`SKILL.md` 与配置文档也已说明过期文件失败、保留使用记录、不缩短检查区间。仍需如实说明更窄的边界：末日到齐不等于所有中间日期或价格都无缺陷；逐个买点仍会因完整未来不足或坏价而被排除。当前要求每股达到预定末日，停牌、退市等例外不能在看过成绩后通过临时删股规避；数据未到齐的失败也不能再声称该范围未被使用。

## 已通过的独立核对

### 配置说明与实际 API

直接提取 `references/configuration.md` 第一段 JSON 示例，调用真实 `run.normalize_config`，使用当前 `bottom_burst.load_params()/Params/build_pattern`。示例正常接受：完整原参数含 `bo/burst/tb/edges`，固定简单突破参数规范化为完整 `bo` 段；例子显式 H40，与省略时 H20 的说明没有混淆。仅生成交易日历，没有读取价格。

自动接口真实提供 `search/validate/review/status/abandon`；声明参数由完整现役快照覆盖生成。代码会拒绝旧 `recent_start`、旧 `repeats/block_days` 等非现行字段，不会静默沿用不同方法。

### 方向计算与普通对照

80 组固定随机种子的合成日表，含不均匀股票覆盖、缺股票日期、不同波动档及重复波动尺度。验收脚本逐个完整时段循环，逐条买点找到同日同档普通股票集合，从定义重新求均值和近期权重，再与真实 `WindowPlan` 比较。

- 方向主分与普通对照最大绝对误差均不超过 `5.551115123125783e-17`。
- 独立慢算法使用每个非空时段一份方向均值，未再按时段股票日数量加权。
- 这是实现与已声明公式的一致性证明，不能证明该公式在市场上更有效。

### 搜索、入选及状态流转

串联演练仅替换 app 信号产生器和输入价格，保留真实 `DailyEvaluator`、真实收盘标签、固定 `bo_only` 检测、Optuna、`assess/comparison`、采用函数和账本。

合成因果信号只有两个参数选项：保留所有当日信号，或根据当日及上一日收盘信息只保留上涨信号。8 只股票一半持续上行、一半持续下行，使应选结果可直接判断。4 次尝试后：

| 检查 | 实际结果 |
|---|---|
| 训练候选方向主分改善 | 约 1.0（正常浮点误差） |
| 最终检查旧/新可评价股票日 | 696 / 348 |
| 最终状态 | `provisional` |
| 预定复核状态 | `rollback` |
| 再读已完成最终结果 | 返回原保存结果 |
| 写正式参数 | 没有发生 |

搜索的 `assess` 和最终训练 `comparison` 共用相同方向主分及约束。只加供给下限，不给更多机会额外加主分；空间和回撤未显式配置时不会偷偷成为资格要求。只有合格且比原参数方向主分实际提高的唯一候选会标为值得最终检查。

代码中的可行性优先选择与最后“必须比原参数改善”没有被混为两件互相冲突的承诺：原参数不合格时可以暂存分数较低但合格的候选；若它仍不比原参数提高，最终不会进入最后检查。原参数没有可比成绩时也不会凭空认定改善。

### 样本范围与实际责任

正式流程在创建评价器前登记阶段，账本暴露区间含 `history_start` 至 `label_end`，阶段之间不能重叠。检测输入止于买点结束，标签输入止于允许尾部；这与当前代码一致。旧版账本与同谱系 app 的人工核对、历史查看记录、因果性核查仍属于明确保留给执行者的责任，不能说已由脚本自动完成。

pickle 会读取整个文件后裁切，文档没有误称为文件字节层的隔离。候选更改首部回看需求时，真实 `eval_meta` 会参与样本排除；事件本身确认也没有被误写成整组条件当时已知的保证。

## 自动确认应如何交代

当前 `comparison` 固定返回 `evidence_sufficient=False`，改善上下界为空；`adoption` 中虽然有 `confirmed` 分支，正常正式链路不能到达。复核也不能生成新的确认依据，因此正常暂用到期后只会撤回；这不是只在坏结果时才可能发生的例外。

适合交付给用户的陈述是：**“如果最后检查观察上改善且达到最低要求，可以按预定日期暂用。当前版本尚不能自动确认改善；按现有规则，到预定复核仍缺少确认依据就恢复原参数。”** 不能说“先暂用，等样本多了程序自然会确认”。技能正文及 method/runbook 已清楚披露此限制，且用户请求允许暂用，所以该限制本身不阻断请求。

正式参数写入、原字节备份、写后加载与构建核对、应用记录、复核触发都仍需 agent 按 runbook 执行；CLI 的 `live_params_written=False` 与此一致。没有建立定时任务时，不能承诺自动监控或到期自行运行。
