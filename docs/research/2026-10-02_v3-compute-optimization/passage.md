# close 首次穿越计算：精确方案与实测

日期：2026-10-02。本文项目内路径均相对 repo root。原始问题见本目录 `原始问题.md`；逐次原始数字见 `passage_results.json`。

## 结论先行

5000 只股票、每只 504 个可评价买点日，共 252 万个结果，不代表首次穿越数值核心需要很长时间。在本机单线程、已完成首次编译、价格和目标线已在内存的条件下，简单的编译循环“按日期向后看，碰到一条线就停止”在快、中命中情景需要约 0.014～0.041 秒。即使 120 天里几乎都不碰线，也仅约 0.186 秒。数据读取、波动计算、构造表格、pattern 检测和搜索不在这些数字里。

建议默认采用这种简单早停计算；不因区间树理论复杂度更优就默认引入它。长观察期且绝大多数买点不碰线时，先用滚动最高、最低收盘价排除必无触线窗口，再对剩余买点早停，会更快：慢命中、120 日情景约 0.047 秒，含滚动极值准备。是否值得增加这一分支，应由整条流程的实际瓶颈决定。

滑动窗口矩阵仍是无需编译的合理备选，分批处理可控制内存。在本次输入上它比仿现有风格的逐股索引矩阵更快，但都不如已编译早停。以上只证明合成完好数据上的计算正确性和成本，不证明新 `close` 口径更能预测市场。

## 1. 比较的定义与接口

新设计初定使用收盘价判断穿越。旧 `path2/eval.py:355` 的 `daily_first_passage` 使用后续 high/low；本文没有修改它，也不声称两种价格口径标签相同。

给定正数收盘价 C、买点日 t 已知的正数波动尺度 M：

- 上线为 `C[t] * (1 + k*M[t])`，下线为 `C[t] / (1 + k*M[t])`，与现有目标线算式及运算顺序一致。
- M 由调用层一次计算并冻结。现有定义是含 t 当日在内的 20 个交易日 `TR/close` 中位数；买点在 t 收盘时作出，因此它不是未来数据。
- 从 `t+1` 起看到 `t+H`，包含末日。收盘价等于上线或下线也算触及。
- 只评价 `t+H < T`、观察期完整的起点。尾部不足 H 日不是“未触线”。
- 输出最早触线方向 `-1/0/1 = 下/未触线/上`，以及相对下一交易日的最早位置 `0..H-1`；位置 H 表示未触线。
- 因上线严格高于下线，同一个收盘价不可能同时触两线。本接口不输出最早触及另一条线的较晚日期；当前方向统计不需要它。将来若需要两条线各自的触及时刻，早停条件必须重新设计。

内核接收连续 float64 价格数组、已经生成的上下线；输出 int8 状态，可选 int16 位置。股票长短不一时应按各自有效长度计算，不能用零填充制造未来价格。本次全量计时用等长合成数组，尚未计量异长股票批次的组织成本。

## 2. 候选实现

### A. 仿现有风格的逐股矩阵

每只股票构造 `起点数×H` 的未来下标，分别把未来收盘价与上下线比较，两边各补一个恒真末列，取每行第一次触线位置，然后比较上下位置。这个版本刻意保持现有 high/low 实现的组织风格，但两边价格都换成 close，保证与其余候选讨论的是同一个新定义。它不是对现有函数的直接性能测量，不含 DataFrame 包装。

### B. 每批 32 只股票的滑动视图矩阵

用共享底层价格的滑动视图取得未来窗口；一次计算是否超出上下线，取最早位置，再读取该位置价格确定方向。视图不复制整块浮点价格，但比较产生布尔临时数组，仍需 O(S×D×H) 次比较。批量 32 只是实验值，不是拟要求用户决定的正式参数。

### C. 编译顺序早停

单线程 Numba，无 fastmath、无 parallel：依次查看后续 close，首次碰到任一条线即结束该买点。所做比较约为 `S×D×实际检查天数`，最坏仍 O(S×D×H)。命中较早时不做后续无用比较；不产生二维未来价格或布尔矩阵。

### D. 区间最高、最低值树

每股建立二叉区间树，节点保存该区间 close 的最高、最低值。查询 `[t+1,t+H+1)` 时，先排除区间外节点；若节点最高值低于上线且最低值高于下线，整段跳过；否则先检查左半段，直到找到最早超出目标线的叶子。一棵树同时判断两条线，避免两次独立查询。

建树 O(S×T)，查询约 O(S×D×log T)。理论更少的比较不等于本机更快：分支、树遍历及内存访问有额外成本。树可跨不同 H 复用，本表为单个固定 H 比较，需计入一次构建。

### E. 滚动极值筛选后早停

用两个单调队列精确计算各 `[t+1,t+H]` 窗口的最大、最小 close。若整个窗口都在上下线之间，直接记未触线；其余买点用 C 的早停循环。极值准备约 O(S×(D+H))，但每个 H 需重新准备。这个办法保留了整段跳过的收益，不需通用区间树；不是用事后极值替代首次发生顺序。

## 3. 正确性核对

首先用独立 Python 朴素三层循环作为参考，检查全部候选的最早位置和方向逐项相等：

- 14 组随机情景，共 1435 个买点日；长度 2、5、23、71，H 取 1、2、4、10、20，跳过不可能的组合。每个买点独立生成不同幅度的上下线。
- 6 个手工边界：刚好等于上线、刚好等于下线、始终在线内、第一天触线、最后一天触线、观察期后一天才触线、先下后上。部分条件由同一用例覆盖。
- 完整窗口端点使用 `D=min(40,T-H)`，因此包含最后一个恰好有 H 日未来价格的有效起点，绝不把额外未来一天算入。
- 随后在九个完整规模情景中，将其余实现的全部 252 万个状态和位置逐项与已通过朴素参考的早停实现比较；零差异。补测滚动筛选实现同样全量核对。
- 滚动最高、最低值在每个大情景另选 10 只股票、全部 504 起点，与 NumPy 直接取对应未来窗口的 max/min 核对；零差异。

这是相同 close 定义下的精确结果一致，不是收益统计接近，也未把 close 与旧 high/low 标签混为一谈。

## 4. 环境、输入与计时方法

环境：Intel Core i7-14700KF、Linux x86_64、Python 3.12.12、NumPy 2.2.6、Numba 0.61.2；Numba、OMP、OpenBLAS、MKL 均设置单线程。未固定 CPU 核，14700KF 有不同类型的核心，小幅差异不视为确定排名。

全部性能进程通过 `flock /tmp/v3-compute-optimization-bench.lock` 串行，避免团队同时跑计时。每种情景每个方法重复 3 次，各重复轮换方法先后，原始最小值、中位数、最大值保存在 JSON。每次计算均生成输出，不从缓存读取上次结果。输入生成、上下线生成、首次编译、树构建、查询单独计时；核对过程不纳入方法耗时。

规模：`S=5000,D=504,T=624,H∈{20,60,120}`。**504 是有完整未来窗口的可评价起点数，不是总价格行数**；合成输入另含最长 120 日所需的未来价格。本次从 t=0 起评价，波动 M 是已备好的外部输入；真实流程还须有计算 M 的前置历史。如果两年训练数据末尾没有完整的 H 日标签，实际可评价起点应相应减少，不应越过训练边界补标签。

随机种子 `2026100201 + 情景编号(0,1,2)`，生成公式：

```
rng = np.random.default_rng(seed)
increments = rng.normal(mu, sigma, size=(5000, 624))
close = 100 * exp(cumsum(increments, axis=1))
M = 0.012  # 此次只隔离内核成本，不估算真实波动
k = 4
upper = close[:, :504] * 1.048
lower = close[:, :504] / 1.048
```

情景 0 为持续趋势，`mu=.012,sigma=.004`；情景 1 为随机波动，`mu=0,sigma=.015`；情景 2 为目标线相对很宽、收盘变动较慢，`mu=0,sigma=.001`。第三种不是“低波动一定难触线”的主张：若 M 也随波动同比缩小，触线速度未必改变。它是专为观察几乎没有命中时的算法边界而构造的完好正价序列。

输入价格生成一次约 0.036～0.042 秒，上下线准备约 0.005～0.007 秒；不计入下表内核耗时。未读取真实行情、未检测 pattern 或 bo、未构造 5000 个 DataFrame、未计算波动 M、未写结果磁盘缓存、未运行 Optuna。这些数字不能直接当成整个 v3 启动时间或总搜索加速倍数。

## 6. 内存和采用建议

本实验价格输入约 24.96 MB，上下线约 40.32 MB，252 万状态占 2.52 MB，可选位置占 5.04 MB。单独内核不需要同时物化 `5000×504×120` 的浮点矩阵。

区间树额外保存最高、最低两个数组，本次合计 163.84 MB；滚动筛选需要 40.32 MB 极值数组。可以逐股/小批处理进一步降低峰值，但那是另一种调用组织，本文没有计时。基准进程峰值 RSS 约 395.5 MiB，包含 Python/Numba 与各方法公用驻留树，不能把它归为早停方法单独的内存需求。

建议顺序：

1. 新 close 标签由统一入口一次生成，普通买入、bo、pattern 命中共用，缓存键包含数据版本、窗口 H、k、波动定义和穿越口径。
2. 默认先用编译早停；如果项目希望暂不依赖编译运行库，可用分批视图矩阵作为简明备选。当前环境已装 Numba，但本研究不决定依赖安装与分发方式。
3. 保留简单的朴素参考用于后续实现核对，尤其相等边界、完整尾窗、同股同日结果。
4. 只有真实完整流程剖析显示首穿仍占主要时间，且长 H 大量未触线，才考虑滚动极值筛选。若还需要反复改变很多 H 或不规则日期区间，可重新评估区间树，不根据本次单 H 表一概淘汰。
5. 不为 252 万这个数字直接缩小对照股票池；数值内核在此规模已经很便宜。先检查滚动统计、表格包装、逐行访问、序列化和跨候选重复工作。

## 7. 风险、弃用方案与最易误读处

- 未使用全池巨型三维浮点矩阵，内存代价没有必要；也未将矩阵分批说成降低渐进复杂度。
- 没有默认推荐树：在本实验快、中命中情景，简单早停明显更快；树的优势来自能够跳过大段完全不命中区间。
- 没有因慢情景胜出而推荐所有情况都增加滚动筛选：它在快、中情景反而增加时间和额外内存。
- 当前输出只需要第一种穿越，不需要把后面的另一种穿越也找全，才允许立即早停；未来评价定义改变时必须重审这一点。
- 本轮只用合成完好数据，不能据此声称真实市场通常有 4 日或 14 日命中，也不能据此选择波动阈值。
- 性能收益主要来自省去不必要比较、编译循环及内存组织，不改变统计定义，也不增加独立证据。
- 三次短计时的可重复性不错，但 CPU 调度、数据组织、标签支持长度与安装环境仍可能影响实际启动耗时；性能门槛应在正式集成后再看。
- 只研究计算，未产生符合登记标准的真实市场副产品。

## 8. 复现实验与清理

临时脚本为 `/tmp/v3_compute_passage.py` 与 `/tmp/v3_compute_passage_extra.py`，实验结束按要求删除。保留本说明、输入公式、参数、边界用例说明、算法步骤及 JSON 的全部逐次计时。重建时先暖机并核对小样本，再按 3 情景×3 H，循环轮换 A/B/C/D（及补测 E 的准备/查询/总调用）各 3 次；所有计时命令必须持有团队锁。树大小是大于等于 T 的最小 2 的幂，叶子外最大值填负无穷、最小值填正无穷；区间查询左子树优先。滚动双队列在 j 进入时淘汰下标 `<=j-H`，插入 j，j≥H 后写入起点 `j-H` 的极值。

已完成团队交叉核对：rolling 组确认当前日 M、未来 `[t+1,t+H]`、完整窗口及首次编译单列口径一致；对照组确认当前三态汇总只需最早方向，不需要两条线各自的首触日期，股票/日期关联仍应保留。双方共同确认滚动 high 最大值不能替代 close 极值，预筛选成本必须计入，几个不同输入、不同定义的模块秒数不能相加冒充完整 close 流水线实测。
