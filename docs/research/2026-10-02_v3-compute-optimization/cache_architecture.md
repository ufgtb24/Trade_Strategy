# v3 计算优化：缓存与每轮工作量审查

日期：2026-10-02。本文为研究建议，未修改正式代码。项目内路径相对 repo root。

## 1. 结论与证据范围

可以共享的是“某只股票某天买入后怎样”，每轮必须更新的是“这组参数选中了哪些股票日”。这两部分应分开存储。固定的普通买入对照和固定 BO 对照也能共享前者，但匹配到候选的普通买入对照，权重仍须随候选变化。

本审查依据现有代码与存储字节数推算，没有测进程峰值内存，没有读取实际行情。数值核与评分汇总耗时另见本目录的实验报告，不能把它们误当完整搜索耗时。

## 2. 已有复用与仍在重复的工作

现有 `.claude/skills/tune-gates-v3/scripts/daily.py` 已经在 `_prepare` 中一次生成股票日标签；每轮参数试验不是从头计算全部未来表现。因此，“把 252 万条计算从每轮移到启动”不是本次新发现的优化，代码已有这一层复用。

仍可减少的工作包括：

- `daily.py:_prepare` 对每条记录切出未来 DataFrame，重复验证同一批未来值、求极值、格式化日期和构建元组。完整输入可在入口按其约定检查一次，数值运算与列构表分开做。
- `DailyEvaluator.baseline` 每次读取复制整张表；`evaluate` 为每组不同参数缓存完整结果表，再次读取也复制。参数多而重复少时，缓存会随搜索增长。
- `scoring.py:assess` 每轮对固定基线和原参数重复调用 `summary`、`_rows`、`assert_baseline`、`_indices_for`。这些操作包含全表复制、类型检查、字符串/日期处理与键集合构建。
- `_matched_baseline` 虽已缓存分组，仍每轮重新计算整张基线的指纹，并对全体基线行展开权重；空间的加权中位数另需保留分布计算。
- 新参数产生哪些买点仍由检测决定。`evaluate` 对不同参数重新检测全池，这部分没有被本次标签缓存优化消除。

这些结论是代码审查事实。本轮没有对旧 `assess` 的完整 pandas 路径做计时，不给它编造倍数。

## 3. 建议的最小数据分层

| 数据 | 构建时机 | 后续用途 |
|---|---|---|
| 股票日身份、买入日波动、方向状态、上涨空间 | 行情与评价口径固定后一次 | 所有参数与两种对照共享 |
| 普通对照按日期、波动档的状态数量 | 股票日标签与分档固定后一次 | 每轮按候选分布重配 |
| 固定 BO 选中的股票日身份 | BO 定义与数据固定后一次 | 从共享标签读取，按日期汇总 |
| 所有候选共用的随机窗口起止 | 一轮搜索开始时一次 | 避免不同参数恰好抽到不同难度的时段 |
| 当前候选选中的股票日身份 | 每组参数检测后 | 从共享标签取得状态，并形成日期统计 |
| 当前候选对应的普通对照权重和窗口成绩 | 每组参数评分时 | 只处理候选数量及小型分组统计 |

标签采用不可变共享数组；候选优先存整数行号，避免复制一整套日期字符串和表现列。参数结果缓存按总字节设置上限或采用最近使用淘汰，不假设每次浮点提议都会命中旧缓存。不得把浮点参数随意取整以制造缓存命中，否则改变搜索对象。

如果多轮搜索最终会覆盖大部分股票日，而且优化后的全量准备已很快，优先一次性批量准备；不必先引入逐股票、逐日期的按需加载状态机。仅在实际授权池远大于使用范围、读盘或内存成为瓶颈时，再比较分批/按需方案。当前实验支持先简化准备流程，未测实际磁盘读入，不能据此断言所有环境都应全量读盘。

## 4. 校验与缓存失效不能消失

“一次校验”依赖数据已经冻结：在进入搜索时检查并规范化输入，建立整数身份映射、数据版本和不可变快照；试验只允许引用该快照。外部可变 DataFrame 仍在每轮任意修改，就不能只删除原来的指纹检查。

标签缓存键至少表达以下内容：行情内容/版本、股票池与允许日期范围、复权与交易日约定、买入价格口径、波动计算口径、前瞻长度、上下线定义、close 或 high/low 模式，以及实现/缓存格式版本。具体不必每轮重新散列所有价格；应在加载/变更时生成版本，之后引用该版本。

BO 缓存另含固定 BO 参数、检测实现版本和必要历史缓冲。参数检测缓存另含完整候选参数与 pattern/检测实现版本。固定评价口径与结构参数必须分开：结构参数只改变买点集合时可复用标签；若未来允许连评价期限或上下线一起变化，就必须重建对应标签，不能继续引用旧结果。

缓存不扩大数据使用权限。两年表示被授权训练的日期范围；若需要向后 H 天才能定义标签，则只有未来路径也被允许使用的买入日才合格。不能为了凑齐 504 个起点读入预留验证期。合成实验补充的未来价格仅用于测定同一规模计算量。

## 5. 存储量推算

5000 × 504 = 2,520,000 个股票日。下表是数组有效载荷，不是进程实际内存，原始数字见 `cache_payload_sizes.json`。

| 内容 | 约占 MiB |
|---|---:|
| 每股票日一个方向状态，uint8 | 2.40 |
| 方向状态 + 上涨空间 float64 + 波动 float64 | 40.86 |
| 上述三项再加股票、日期各 uint16 | 50.47 |
| 某候选若选中全部股票日，仅存 uint32 行号 | 9.61 |
| 固定 BO 的 bool 选择掩码 | 2.40 |
| 504 日 × 5 档 × 3 状态的 int64 数量 | 0.058 |

uint16 身份仅适用于当前合成维度的演示，正式实现应按实际范围选整数宽度。40.86 MiB 未包括价格、历史缓冲、日期/股票字典、分档编码、索引、临时数组、Python 对象及复制。不能据此称整个系统只需 41 MiB。

合成数据所有股票共享交易日网格。真实完整数据也可能上市时间、交易日历不同；稠密数组隐式行列身份不能替代原来按各股票交易行定义前瞻的约定。必须保留有效身份与日期映射，不通过强行对齐改变 H 的意义。

## 6. 压缩到什么程度仍然够用

方向次数在组内权重相同的条件下可以先相加再重配；最终比例应由合计后的分子/分母计算，不能无条件平均各日比例。若未来改为按股票重抽、逐股票权重或其他匹配规则，就需要保留对应维度或回到明细，不能拿日期分组表完成原本依赖股票身份的运算。

同样，这张小表足以复算当前范围内的中心方向比例，不等于保留了所有估计误差需要的信息。股票日明细与身份仍应保留，用来检查股票/日期集中程度，以及后续确定的可靠性计算。

上涨空间的精确中位数不能靠“每天/每档的中位数再取中位数”替代。需要时仍从共享标签选择该窗口的原始数值；若它成为瓶颈，再研究保序计数或精确选择结构。本次方向计数提速不涵盖这一步。

## 7. 后续实施的验收边界

1. 原 high/low 语义的纯性能改造应逐值核对原结果；新 close 语义只能与独立 close 公式对照，不能声称与旧标签相等。
2. 先测从加载开始的完整准备，再测固定参数的一轮检测与评分；将读盘、检测、标签准备、评分和输出分开计时。
3. 只有真实完整调用链的测量才能报告“完整搜索快了多少”。当前合成研究足以定优化优先级，不足以替代该验收。
