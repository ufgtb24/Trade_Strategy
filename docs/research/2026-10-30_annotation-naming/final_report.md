## 1. 直接回答

### 1.1 这五样东西是什么

用户放三角并收进一组框，是在下一个判断：「在 pattern P 的逻辑下，这一天（只凭当天及以前看得到的）该买 / 像 P 但不该买」，那组框是判断的依据。app 的一次 match 是另一个作者对同一类问题给的回答：「app 认为在这一天（买点）P 成立」，依据是各 node 绑定的事件。所以用户列的五项其实是三个概念：

| 用户说的 | 是什么 | 规范词 | 界面 | 数据键 |
|---|---|---|---|---|
| 标注的 buy 三角 | 正向判断所在的那一天 | 正例的样例日（新） | 实心 ▲ | `examples[].date`，`judgment: "pos"` |
| 标注的 no_buy 三角 | 反向判断所在的那一天 | 像但不买的样例日 | 空心 △ | `examples[].date`，`judgment: "neg"` |
| 标注的正例（三角 + 框） | 用户的正向判断连同依据 | 正例 | `pos` | `examples[]` 一项 |
| 标注的反例（三角 + 框） | 用户的反向判断连同依据 | 像但不买（Q3；别名反例） | `neg` | `examples[]` 一项 |
| app match 出的那一次 | app 给的结果连同依据 | match（`path2/GLOSSARY.md:95`） | bracket | path2 的 `matches[]` |

正例和像但不买合称**样例**（新）。三角不是独立的东西：数据里只有一条记录（样例），三角是这条记录的 `date` 加正反判断画出来的样子。

### 1.2「买点」包含 no_buy，别扭在哪

现行「买点」在标注里装了三件事（inv 2.1）：①用户的三角连同成员框（buy、no_buy 同一个数组、同一种对象，只差 label，inv 1.1）；②三角那一天（「app 的买点落在买点前后 3 天内」里的后一个）；③app 一次 match 里算收益的 K 线（`path2/GLOSSARY.md:118`、`eval_meta` 的「买点 node」；原型里 app 的回踩起点也叫买点，mock:274、mock:766）。①②拿「买点」叫都名不副实：①里有不买、而且是一组框不是一个点；②对像但不买也不是买。③叫买点是准的：app 真在那里买。所以标注侧整个退出这个词，app 侧留着（Q1）。

### 1.3 app match 出的不叫 pattern

pattern 是那种形态，match 是它在某只股票某段 K 线上被 app 认出的一次。用户口头「app match 出的 pattern」应说 match。

### 1.4 buy / no_buy 要不要挂到 pattern 下面

要，作为这个 pattern 的正例和像但不买。决定性的理由：正反判断本身就是「在 P 看来」的判断——正例 = P 的 app 应该在这天 match；像但不买 = 不该 match，而这天又像 P。离开 P，判断没有对象；同一天对 P1 该 match、对 P2 不该，并不矛盾。由此推出的另外三条（任一条也都要求绑定）：成员框随 pattern 变（同一天对两个 pattern，依据的框不同）；对照要用所属 pattern 的 app；按特征计数、偏离都按 pattern 算。

- **挂的是用户心里的那个形态**（用户起名、配一句定义），不是 app，也不是 app 的某一版：判断说的是用户的逻辑，app 换版本不改它。原型里 pattern 名经 `PAPP` 对到当前实现它的 app，可以还没有 app（inv 1.2）。
- **不绑 pattern 的**：特征、特征名、定义、框、框上的属性——所有 pattern 共用的素材（方向文档第 8 节「事件层」）。
- **未归类**是判断对象还没指定的过渡态，不是一个 pattern。正例挂在这里有意义（对象是一个还没起名的 pattern，攒够了再归组）；像但不买的「像」必须有对象，挂在这里用不起来，只算没填完。

这一点 2026-10-23 已定（方向文档第 8 节「事件不属于任何 pattern，买点和角色属于某个 pattern」）；本轮从第一性原理重推，结论相同，只换词。

## 2. 维度梳理

### 2.1 两个作者，逐层成对（组织原则）

标注侧和 app 侧逐层成对、各用各的词、互不借用。「买点」的毛病，根子就是标注侧借了 app 侧的词。

| 层 | 用户的（标注） | app 的（跑出来） | 对照时比出的结论（谁给） |
|---|---|---|---|
| 形态 | pattern：用户起名 + 定义 | app：会话写，实现这个 pattern | 由 mapping 接起来（会话写） |
| 词 | 特征 / 特征名 | node、where | mapping 一行 |
| 一段 | 框 | 事件 | 框：qualified / detected / missing（app） |
| 一段的性质 | 属性 true / false / null（用户） | where 过没过 | 逐条 checks |
| 段套段 | 框套框（属于） | 复合事件与它的子事件（如 burst 的成员 bo，`path2/GLOSSARY.md:63`） | — |
| 两段之间 | 成员框的先后 | 边 | connected / disconnected / not_qualified（app） |
| 一次判断 | **样例** = 样例日 + 成员框 + 正反判断 | **match** = 买点 + 各 node 绑定的事件 | 对照结果：有没有对应它的 match、买点和样例日同不同天（app；名字见 Q4） |
| 那一天 | **样例日**（一根 K 线） | **买点**（一根或几根：评估按买点 node 事件的跨度逐根算，`path2/core.py:117-119`；原型只取回踩起点一根，mock:274，inv 2.1 末条） | 比远近 |
| 跨度 | 样例的 bracket（虚线，由样例日和成员框派生，不存，inv 1.1） | match 的 bracket（带圈号） | — |

两处不对称，命名必须保住：
- **用户的判断有正反两种，app 只有正的。** app 只报它会买的地方，没有「反 match」。像但不买在 app 侧对应的是「这里不该有 match」。
- **没标的日子是「不知道」，不是「反」。** 用户没看过、没判断过，其中可能有用户会买的。像但不买只是反向判断里用户专门挑出的一小撮——像 P、最容易让 app 犯错的那几天，说明不了 app 在全部「不该买」的日子上错多少。

「成员」两侧意思不同：app 侧的成员是复合事件的子事件（代码子事件槽 `members`，inv 2.8），对应用户侧的「框套框」；用户侧的成员框是样例收进的框，对应 app 侧「match 绑定的事件」。所以用户侧一律说「成员框」。

### 2.2 流程里每一步拿它们做什么、因此必须分开什么

| 步 | 谁 | 拿什么做什么 | 因此必须分开的 |
|---|---|---|---|
| 标注 | 用户 | 选一天下正反判断、画框、收成员框、挂 pattern | 框 vs 样例；样例日 vs 框的起止 |
| 归组 | 用户 | 把未归类的样例挂到 pattern，起名、写定义 | pattern vs 未归类 |
| 写 app | 会话，与用户讨论 | 从正例的成员框归纳必须有的特征；从像但不买的成员框找必须没有的（票 12） | 正例 vs 像但不买（按特征计数时分母只数正例，inv 1.1） |
| 对照 | 会话与用户 | 每个样例 app 有没有对应的 match、买在哪天；每个框 app 认没认出；相邻两段连没连上 | 用户的判断 vs app 的结果；样例日 vs 买点；正反判断 vs 对照结果 |
| 盲看 | 用户 | 对 app 抽出的一天判「在 P 下是不是我的意思」（票 08） | 盲看结论 vs 样例（同类判断、抽样不同）；没标的日子 vs 像但不买 |
| 调参、评估 | 会话 | 在买点上算前瞻收益；报调参后哪些正例不再 match | 买点 vs 样例日；评估里的 label（结果）vs 正反判断（用户当天的认定） |

由此必须分开的几组：
- **样例 vs match**：作者不同，对照就是拿两者比。
- **样例日 vs 买点**：对照时要说「买点离样例日几天」。
- **正例 vs 像但不买**：一个归纳必须有、一个找必须没有；计数分母只数正例。
- **像但不买 vs 没标的日子 vs 盲看判「不是」的那天**：第二种是不知道。第三种和样例是同一类判断——对象同样是（那一天, P），同样只按当天以前看得到的下（票 08 规定后续走势先藏）；哪一版 app 把这一天抽出来只是出处，app 改版不让它作废。但不能并进样例：盲看的日子全是 app match 过的，并进来会凭空抬高「正例 match」「像但不买 match」的比例；它没有成员框；「不是」也没说清是不像还是像但不买。
- **四种判断 / 结果**：正反判断（用户，对自己挑的那天）、对照结果（app 对用户的样例给的，不叫判断）、盲看结论（用户，对 app 抽出的那天）、评估里的 label（不是谁的判断，是后来的走势；任何一天都能算，app 的买点、样例日都行）。最危险的是第一和第四种：整条标注工作流就是要把「用户当天认定」和「后来涨没涨」分开，而「正例的 label 中位数」这种话就是在样例日上算 label。
- **成员框 vs match 绑定的事件 vs 复合事件的成员**：见 2.1 末段。
- **用户的 pattern（形态）vs 声明（node 加边）vs app（声明 + where + 参数，有版本）**：见 Q2。

合计标注侧要的新名字：样例、样例日、正例、像但不买（或反例）、成员框、未归类、正反判断这个字段。app 侧不需要新词。

### 2.3 数据模型要不要改

1. **样例要不要绑 pattern**：要（1.4）。
2. **三角和成员框要不要拆成两个东西**：不拆。它们是同一个判断的两部分（判断那一天、判断的依据），流程里没有哪一步要单独引用其中一个；拆开要多一层「哪个三角配哪组框」的关联，表达力不增加。三角在数据里就是样例的 `date`。
3. **正反判断和归属要不要拆开**：不拆，判断离开 pattern 没有对象。
4. **正例和像但不买共有「像 P」**：两者都认定「这天有 P 的样子」，差在买不买。所以像但不买的成员框也是真实的特征实例——引出第 6 节第 2 条。

### 2.4 逐项维度表

| 东西 | 谁产出 | 粒度 | 带判断？谁给 | 属于 pattern？ | 流程里谁拿来做什么 | 存在哪 |
|---|---|---|---|---|---|---|
| 特征（特征名 + 定义） | 用户 | 一个词 | 无 | 否，跨图跨 pattern | 用户给框起名；会话写进 mapping | 标注文件 `features[]` |
| 框 | 用户 | 一段 | 属性三态是用户对这段的判断 | 否（inv 1.3） | 对照时查 app 认没认出 | `charts[].boxes[]` |
| 样例（正例 / 像但不买） | 用户 | 一天 + 一组框 | 正反判断，用户，只看样例日及以前 | 是：一个 pattern 或未归类 | 写 app 时归纳；对照；调参后报丢失 | `charts[].examples[]` |
| 样例日 | 用户 | 一根 K 线 | 承载正反判断 | 随样例 | 对照时和买点比远近；看图时之后的走势先藏 | `examples[].date` |
| 成员关系 | 默认推断 + 用户点进点出（inv 1.5） | 样例↔框，多对多（inv 1.4） | — | 随样例 | 写 app 时读；对照时按它配对 | `examples[].members` |
| pattern | 用户 | 名字 + 一句定义 | — | — | 收样例；由 app 实现 | 标注文件 `patterns[]` |
| mapping | 会话 | 每个特征一行 | 级（会话定，用户可 ⚑） | 每个 pattern 一份 | 把用户的词接到 app | 随 app 进 git |

| 事件 | app 的 detector | 一点或一段 | detected / qualified / matched（app） | 否 | 对照时和框配对 | 扫描结果 |

## 3. 命名方案

### 3.1 挑词：候选与会不会读错

**用户的判断连同依据（三角 + 框）**
| 候选 | 会怎么读错 | 结论 |
|---|---|---|
| 买点 | 像但不买不是买；一组框不是一个点；和 app 那根 K 线同名，而对照恰恰要比这两者 | 不用 |
| 实例、instance | 本项目 instance 已指单个事件（`instance_id`，`path2/core.py:59-64`；用户触发 diagnose-event 时说「诊断 SYM 的 INSTANCE_ID」就是它），前端还把 app 侧的买点叫实例（`path2_web_ui/src/render/chart.ts:1566`） | 不用 |
| 标注 | 太宽：框、文件、整个活动都叫标注 | 不用 |
| 案例、判例 | 案例偏「案例分析」；判例偏法律 | 不用 |
| **样例** | 正例、像但不买都是「为 P 举的例」，和正例同根。残留：「失败样例」（`path2_web/diagnose.py`）、旧盲看「命中样例」（`chart_workflow/contrast.py:115`）是普通汉语用法，词条注一句 | **用** |

**那一天**
| 候选 | 会怎么读错 | 结论 |
|---|---|---|
| 买点 | 同上 | 不用 |
| 判定日、标注日 | 读成做标注的那天（日历日） | 不用 |
| 决策日 | 读成用户整体的买卖决定；而判断相对 pattern，同一天可以对 P1 买、对 P2 不买 | 不用 |
| 当天 | 相对说法，要有参照；留在「只按当天看得到的判」这句规则里用 | 不作名字 |
| **样例日**（别名三角） | 合成词，读不歪；「三角」须注明只指用户的 ▲ / △，不是 bracket 上标 app 买点的 ▼ | **用** |

**正反判断这个字段与取值**
| 候选 | 会怎么读错 | 结论 |
|---|---|---|
| 字段 `label` | 评估里 label 是结果（`label_horizon`、`path2/eval.py` 的「label 前瞻窗」、tune-gates-v3 先上 +1 / 先下 −1 的方向标签，用户口头「label 中位数」，inv 2.3）。同一主视图里两个 label，一个是用户当天的认定、一个是后来的走势，正是这条工作流要分开的两件事 | 不用 |
| 取值 `buy` / `no_buy` | 光秃秃的「买 / 不买」读成用户整体的买卖决定，而判断相对 pattern。（中文「像但不买」里也有「不买」，但「像」字把判断钉在了 P 上；`pos` 读作「P 的正例」同样钉在 P 上；`buy` / `no_buy` 两个都没钉。） | 不用 |
| 取值 **`pos` / `neg`** | 读作「对 P 的 app 是正例 / 反例」，正好是判断的意思（该不该 match）。配 `label` 会像方向标签 ±1，所以字段必须换名。交易语境里 `pos` 偶尔读作持仓（position），和 `neg` 并排时不成问题 | **用** |
| 字段 **`judgment`** | 说明是用户下的认定，和样例表的 `app` 列对得上。名字待验证，实现时可换，但不得用 label、outcome、target 这类评估词 | **用** |

**正向的**：正例（`pos`）。唯一的读错可能是「后来涨了的 match」，词条写明说的是当天的认定。

**反向的**：Q3。

**依据**
| 候选 | 会怎么读错 | 结论 |
|---|---|---|
| 成员（单说） | app 侧「成员」是复合事件的子事件，对应用户侧的框套框，层级不同 | 不单说 |
| 买入理由 | 像但不买的依据里有「为什么不买」 | 不用 |
| 依据框 | 说出了作用；但用户自己的图景是「一堆框构成的集合」 | 可用，次选 |
| **成员框** | 合乎用户「集合」的图景；带「框」字就和 app 侧的成员 bo 分开 | **用**；界面、数据键 `members` 不变 |

**未归类**：讨论说「未归类」；界面固定文字 `unsorted`、数据 `pattern: null`（现在是字面值 `'未归类'`，inv 2.12）。不用 `unassigned`：同一侧栏已有 `unclaimed`（框没被收进样例），两个「不归属」的词挨着会串。

**一句话**：框和样例上的一句话说「注释」，界面 `note`；不进词表（字段的中文说法，不是领域概念）。

**「断言」不进词表**：推导里把样例说成用户的「断言」，但程序员会读成 assert（必须成立的校验）。词表、界面、方向题一律说「判断」；app 对样例给的结论叫「对照结果」，「判断」只留给用户这一侧。

### 3.2 总表（按四道方向题的推荐）

| 概念 | 中文规范词 | 界面固定文字 | 数据键 |
|---|---|---|---|

### 3.4 边角

1. **未归类的样例**：正例可以挂着等归组；像但不买挂着只算没填完，界面引导当场挂过去（显示 `pattern?`）、不拦（mock:1246-1248）。
2. **同一个框是两个样例的成员框**：允许，同一 pattern 不同天（界面按日期标 a / b）或不同 pattern（inv 1.4）。成员框是框相对某个样例的角色，不是框的种类。
3. **画了没收的框**：相对某个样例说的（样例日之前、离它的 bracket 不远、同名特征在这个 pattern 的样例里用过、不是同 pattern 别的样例的成员框，contract:96-101）。沿用「画了没收」。
4. **不属于任何样例的框**：就是框，共用素材；当前 pattern 的样例没用到它的特征名时不参与对照。不另起名。
5. **同一天两个样例**：不同 pattern 各一个，正反可以相反；同一 pattern 同一天只能有一个（再点即选中已有的，contract:72）。
6. **app 有 match、附近没有样例**：就是一个 match。训练段对照里不被判任何东西——没标的日子是不知道，不是像但不买。它忠不忠实归盲看判「是 / 不是」；盲看结论不并进样例（2.2）。
7. **有 match、但买点和样例日错开**：现行规则下，正例要样例日前后 3 天内有 app 的买点、或样例日落在那次 match 的回踩事件里才算 match；像但不买是前后 1 天（inv 2.10，mock:241-242，天数待验证）。用户在突破那天放正例、app 在回踩起点买、两者隔 3 天以上时（burst 到回踩允许隔 1～20 根），match 的 bracket 盖住了三角，签却是 `no_match`。这是现行名字必然碰上的情形，见 Q4。
8. **成员框伸到样例日之后**：原型里候选框只要求起点不晚于样例日，终点不限，样例的 bracket 右端取成员框最晚的终点（mock:342-351、mock:387-390）；标注模式下样例日之后的 K 线又看得见。从样例日前画到样例日后的框，作为依据时只能算它在样例日及以前的那一段，否则依据里混进后见之明，会话归纳必须有的特征时会把它当成当天可见的。词条先这样写；工具里要不要裁或提示，见第 6 节。
9. **match 里算收益的那根 K 线**：买点（app 侧）。
10. **像但不买的成员框与注释**：成员框里可以有「不买的理由」那段（如派发），会话定级时它是必须没有的来源（票 12）；注释写样例日当天就看得见的理由。
11. **偏离**：只对正例说（正例的成员框和 mapping 对不上）；像但不买照样挂差签，不计入偏离（mock:1377）。
12. **正反改过**：会话题目 `seen` 一类指「上一轮这个样例从 pos 改成 neg，或反过来」（contract:165）。

## 4. 方向题（推荐的放第一）

**Q1 app 一侧还叫不叫「买点」？**
在决定：标注侧不用「买点」之后，app 一次 match 里买的那根 K 线（评估在这里算收益，app 用买点 node 声明它）叫什么。
- **(a) 留，只给 app 一侧用（推荐）**：标注侧退出后它只剩一个意思，而且这个意思是准的——app 真在那里买。用户嫌它「是业务词、不贴合标注」，说的是拿它去叫一个标注产物；app 那次 match 里买的那根 K 线本来就是业务上的东西。
- (b) 两侧都退役，app 侧另起（如「出手日」）：不消除任何会读错的地方（标注侧退出后已无同词），只换来名字整齐。
- (c) 两侧都留、靠定语分（「标注买点」「app 买点」）：标注侧的名不副实还在——像但不买仍被叫成买点、一组框仍被叫成点。
- 改动代价（排最后）：(a) app 侧零改动；(b) 要动项目 skill 约 649 处 / 66 个文件（tune-gates 438、feature-study 129、tune-gates-v3 68）、path2 代码约 59 处 / 7 个文件、path2_apps 5 处（都在 `eval_meta` 说明）、path2_web 约 35 处、CLAUDE.md 1 处（:74）、词表 6 处（`path2/GLOSSARY.md:25`、`:57`、`:104`、`:108`、`:115`、`:118`）、记忆 45 处 / 15 个文件、`docs/explain/` 5 个文件，其中 tune-gates-v3 的 `SKILL.md:14` 按行号引用词表 :118（inv 6.3）。

**Q2 用户的 pattern 和框架里的 pattern 是不是同一个词？**
在决定：样例挂靠的那个 pattern——用户起名、写定义、可能还没有 app 的那个——和框架词表里的 pattern（`path2/GLOSSARY.md:73`「一组 node 加一组边的声明」）用不用同一个词。现在其实有三样东西：用户的形态（名字 + 定义，收着样例）；某个 app 对它的声明（node 加边）；app 本身（声明 + where + 参数，有版本）。另外 path2_web 的「锚 pattern、active pattern」实际选的是 app（`path2_web/GLOSSARY.md:20`，inv 2.13）。
- **(a) pattern = 形态本身；声明说成「pattern 的声明」或拓扑，属于实现它的 app（推荐）**：形态和它的声明是同一个东西的两个阶段，对照就是在比这两者；每句话里动词就分得开——只有 app 能认出、能 match，只有用户能定义、能收样例。词表 :73 改写（见第 6 节），path2_web 词表 :20 注明锚 pattern、active pattern 选的是 app（要不要改名另议）；方向文档第 8 节「当前 pattern 与 active pattern 同义」改成「当前 pattern 有 app 时，对应主视图里实现它的那个 app」（标注的当前 pattern 可以还没有 app，inv 5.3）。代价：一个 pattern 可以先后或同时由几个 app、几个版本实现，各有各的声明，是一对多，「这个 pattern 有几个 node」要读成「它现在那个 app 的声明有几个 node」；「改 pattern」会两义——改用户的那句定义还是改 app 的拓扑——说时要带宾语。
- (b) 用户侧另起一个词（如「形态」）：两义彻底分开。代价：要记两个词指同一个东西的两个阶段；用户一直叫它 pattern；「形态」和退役中的「形态卡 / 形态词库」同根。

**Q3 判断为 neg 的样例叫「像但不买」还是「反例」？**
在决定：讨论、文档、技能正文里统一写哪个。界面和数据照用户说的用 `pos` / `neg`，不受影响；两个词都进词头，用户怎么说都行，这道题只定 AI 写下来的是哪个。
- **(a)「像但不买」，「反例」作别名（推荐）**：这个词自己带着两层限定——像 P、当天就判得出不买——而且缩不短，没有哪个更短的说法会丢掉限定。以后写循环技能、评估、盲看的会话即使没读词表，也不会做这三件事：「反例太少，从没标的日子里抽一批补上」（没标的是不知道，不是反）；把盲看的「不是」并进来（没说清是不像还是像但不买，抽样也不同）；把「这些日子里 app match 了几个」当成 app 的误报率（它们是挑出来最难的几天）。代价：正、反两个词不对称；带「买」字——但「像」字把这个「不买」钉在了 P 上，读不成用户整体的买卖决定，也不是拿业务词去叫一个标注产物，和「买点」的毛病不同。
- (b)「反例」，靠词条收窄：和正例对称，是用户提的工程说法。代价：限定全押在词条上，不读词表的读者（后台 agent、skill 正文）会按通用意思读成「所有不是正例的日子」，上面三件事在通用意思下都顺理成章。折中的「贴边反例」用起来会被缩成「反例」，限定照样丢，不单列。
- 注：用户原问题里自己提的是「正例 / 反例」与 pos / neg；本题推荐 (a) 与用户的提法不同，理由只是上面的读错风险。

**Q4 对照结果（app 对样例给的结论）叫什么、分几种？**
在决定：对照时每个样例旁边那枚 app 的签。它现在实际算的是「样例日附近有没有 app 的买点」，名字却叫 match / no_match（有没有 match）。名不副实的后果见 3.4 第 7 条：app 认出了这段走势、只是在回踩那天买，match 的 bracket 盖住了三角，签却写 `no_match`。这一格里混着两种要分头修的情况——app 根本没认出（改 detector 或 where），和认出了但买在别的天（改买点 node 或边，或者是用户的三角放在突破日、pattern 本来在回踩买）。正反判断在对照里管三件事：计数分母、容差、朱红（inv 7）；每条路都写明这三处怎么落。
- **(a) 拆成两问、显示三种，正例和像但不买一视同仁（推荐）**：签只说 app 做了什么。先问「app 有没有对应这个样例的 match」——判法是 match 的跨度和样例的 bracket 交叠（交叠到什么程度算，待验证）——这一问用 match / no_match，名字从此名副其实；再问「对应的那次 match 买点在不在样例日附近」。三种签：`no_match`（没认出）、`shifted`（认出了、买点错开）、`match`（认出了、买在这天附近）。分母不变（按特征计数只数正例）；容差仍按正反分（正例前后 3 天或落在回踩事件里，像但不买前后 1 天，天数待验证）；颜色按判断定：

  | 签 | 正例 | 像但不买 |
  |---|---|---|
  | `match` | 对得上 | 朱红：app 在用户说不买的那天买了 |
  | `shifted` | 显示出来，默认用朱红以外的另一种标记（待验证）：认出了、买的时机不同 | 显示出来，默认不标朱红（待验证）：app 认出了这个贴边形态、隔几天照样买——不买的理由（如回踩前出了派发）常对整段走势成立，app 换一天买仍等于买进了这个贴边形态，多半是同一个错 |
  | `no_match` | 朱红：app 没认出 | 对得上 |

  好处：3.4 第 7 条的边角消失；同一种 app 行为在正例、像但不买上同一个名字；汇总页、盲看、调参都能分清「没认出」和「买的时机不同」。代价：多一条「哪次 match 对应这个样例」的判定规则，界面多一种状态。
  子选项 (a′) 像但不买不拆、仍只按前后 1 天判：界面少一种情况。代价：像但不买上「认出了、隔两三天照样买」被判成对得上，正好把 app 的错藏起来。不推荐。
- (b) 只问一件事、按实际算的东西起名：「这天附近 app 买不买」，标识符换成「买」这一族的词（实现时定，待验证；不回收 `buy` / `no_buy`——旧原型和研究文档里它们指用户的判断，回收会让新旧文档同词反义）。分母不变；容差按正反分，同现行；朱红同现行（正例没买、像但不买买了）。代价：名字准了，但「没认出」和「买点错开」仍混在一格，汇总页要逐个点开才知道该修哪一头；像但不买上隔几天照样买的错同样看不见。
- (c) 保持 match / no_match，词条里加一句「no_match 不等于 app 没认出这段走势」。分母、容差、朱红都同现行。代价：签和图上看到的互相矛盾，每次靠悬停解释；一个名字要靠「不等于」压住字面意思，就是会被读错。

## 6. 词表条目草案（只是草案，不写入 GLOSSARY）

放在 `path2/GLOSSARY.md`「看图标注」下，取代票 01 第 7 节原计划的「正例 / 像但不买」一条。按四道方向题的推荐写；Q3 选 (b) 时「像但不买」与「反例」在词头互换、正文同改。

**样例 / example**：
用户在一张图上、相对某个 pattern 下的一次判断连同它的依据：一个样例日、一个正反判断（正例或像但不买）、所属 pattern，以及作为依据的成员框。正反判断是「在这个 pattern 的逻辑下、只凭样例日及以前看得到的」认定，不是后来涨没涨，也不是评估里的 label。每个样例只属于一个 pattern（或暂挂未归类）；同一天对两个 pattern 下判断就是两个样例。在 app 一侧和它成对的是 match。诊断里的「失败样例」是普通汉语用法，不是这个意思。
_Avoid_: 买点 —— 会误读：买点是 app 一侧的词（:118），而且像但不买不是买、一组框不是一个点；实例、instance —— 会和事件身份 instance_id 混；样本 —— 那是 app 一侧和评估里的词。

**正例 / pos**：
正反判断为 pos 的样例：这个 pattern 的 app 应该在样例日 match——这天有它的样子，按它的逻辑当时会买。说的是当天的认定，不是后来涨了。
_Avoid_: buy —— 会被读成用户整体的买卖决定，而判断是相对 pattern 的。

**像但不买 / 反例 / neg**：
正反判断为 neg 的样例：用户专门挑的、像这个 pattern 但样例日当天就看得出不该买的那一天，app 不该在这里 match；理由写在注释里或画成成员框、属性。没标的日子是不知道，不是像但不买；盲看里判「不是」的那天也不并进来（同类判断，但抽样不同、没有成员框）。按特征计数时分母只数正例；这些日子里 app match 了几个，说明不了 app 的误报率。
_Avoid_: no_buy —— 理由同正例的 buy；负样本 —— 会被读成全部没标的日子。

**样例日 / 三角**：
样例的那一天，图上画成用户的三角（正例实心 ▲、像但不买空心 △；不是 bracket 上标 app 买点的 ▼）。正反判断只按这一天及以前看得到的下；对照时拿 app 的买点和它比远近；看图时它之后的走势先藏。
_Avoid_: 买点 —— 理由同样例；判定日、标注日 —— 会被读成做标注的那天；决策日 —— 会被读成用户整体的买卖决定。

**成员框**：
样例收进的框，即这次判断的依据；像但不买的成员框里还可以有「为什么不买」的那段。作为依据的只是它在样例日及以前的那一段，伸到样例日之后的部分不算。默认按离样例日的远近推断，用户可点进点出。一个框可以是几个样例的成员框；框本身不属于任何 pattern。界面和数据里叫 members。和复合事件的成员（:63「burst 聚合它的成员 bo」）不是一回事，说时不单说「成员」。
_Avoid_: 买入理由 —— 对像但不买不成立。

**未归类**：
样例还没指定 pattern 的状态，攒到一批再归组、起名；不是一个 pattern。正例可以先挂这里；像但不买的「像」要有对象，挂这里只算没填完。界面写 unsorted。

改动已有词条：
- `path2/GLOSSARY.md:95` **match** 加一句（按 Q4(a)）：「对照时说一个样例 match，指 app 有一次 match 对应这个样例（跨度和样例的 bracket 交叠）且买点在样例日附近；对应上了但买点在别的天叫 shifted；没有对应的 match 叫 no_match。」选 (b) 时改写成「这天附近 app 买不买」的说法；选 (c) 时写现行规则并加「no_match 不等于 app 没认出这段走势」。
- `path2/GLOSSARY.md:118` **买点 / 样本 bar** 加一句：「只用于 app 一侧；标注里和它成对的是样例日。」
- `path2/GLOSSARY.md:73` **pattern**（按 Q2(a)）改写为：「一种形态；app 用一组 node 加一组边声明它，引擎照着声明求解。看图标注里，样例挂在 pattern 下，app 改版不改样例归属。」；`path2_web/GLOSSARY.md:20` 锚 pattern、active pattern 注明选的是 app。
- `path2_web/GLOSSARY.md:45` **bracket**：「一次 match 或一个样例的时间跨度在图上的样子；match 的带圈号，样例的画虚线。」
- 「注释」「对照结果」「盲看结论」不新增词条：前一个是字段的中文说法；后两个归票 01 / 票 08 定稿时再议。

## 9. 最容易误读的地方

1. **「样例属于 pattern」的 pattern 是用户的形态，不是 app。** app 改版、换 app，样例归属都不变（1.4）。
2. **像但不买不是「全部不该买的日子」的代表。** 没标的日子是不知道；像但不买上的 match 比例不是误报率（2.1、Q3）。
3. **「正例 / 像但不买」是当天的认定，评估的 label 是后来的走势。** 两者可以在同一天上都有值，「正例的 label 中位数」说的是后者（2.2）。
4. **对照结果现行的 `no_match` 不等于 app 没认出。** 在 Q4 定下之前读旧汇总时，正例 no_match 里混着「买点错开」（3.4 第 7 条）。
5. **方向题都没定。** 第 3、6 节按推荐写；Q3 选 (b) 时全文「像但不买」与「反例」互换，Q4 选 (b) / (c) 时对照结果的名字与 match 词条改写方式见 Q4 与第 6 节。
6. **数字和交叠判法都待验证**：容差（正例 3 天、像但不买 1 天）、「对应」的交叠程度、shifted 的显示样式、`judgment` 与 `not_sample` 的替换名。
