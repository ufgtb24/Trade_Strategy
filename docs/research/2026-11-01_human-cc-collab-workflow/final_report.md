> 日期：2026-11-01。lead 汇总。锚点：同目录 `原始问题.md`（用户原话 + 补充的那对矛盾）。
> 输入：`诊断.md`（auditor：注意力去向的计数与 11 张未关票的事实）、`机制盘点.md`（mechanist：用户工具箱、cc 机制、外部做法）、`方案.md`（designer：定稿方案，经 critic 两轮）、`审查.md`（critic：对 lead 初始假设的攻击与两轮审稿）。

## 1. 问题

用户原问题：开发「看图标注 → path2 pattern」工具（分支 `annotation-path2`，Wayfinder 决策流程，2026-10-20 起）时，自己参与细节太累、推进太慢；交给 cc 代理又怕做出来不是自己要的、review 和学习成本高。要一套覆盖「开发 + review + 使用 + 学习」的人机合作方式，让用户站在使用者位置，同时开发完成时能掌握工具、把控方向。

## 2. 结论

1. **矛盾的隐藏前提不成立。** 前提是「要确认是不是我要的，只能审 cc 的中间产物（票、规格、原型、代码）」。实际上大部分决定的对错用户在使用时就看得见；使用中看不见的只有少数几类（会用掉 2026 年数据的、会让成绩变好看的、对照显示本身），它们由用户说一次原则、确认几个具体情形，cc 落成自动检查，并用一份用户批准过的例子文件守住。两边都不需要用户读文档或代码。
2. **只把「先讨论后造」倒成「先造后看」不够**（critic A2，auditor 计数印证）。〔事实〕约 36.5 小时在场、用户亲手写 458 条，定方向 20 条（4%）；208 条（45%）在看懂、挑错、改名 cc 做的原型；127 条（28%）落在 12 段同一疑问来回问的澄清链里；用户替 cc 补前提、纠误解 21 条，复述求确认 26 条；cc 在聊天里写约 48 万字（每次回复中位数 748 字，用户每次中位数 31 字）；28 个提交约 7.6 万行、74% 在 `docs/research/`，标注工具正式代码 0 行。慢的根子是：方向只能靠读、不能靠用来检验；cc 加概念比用户消化得快；cc 的说法要用户自己翻译、一处看不懂就升级成研究轮；已定前提散在多处、传不下去（地图把「色弱」写成「色盲」，cc 照着做出黑白原型）；辅助工具（web-loop）自己成了项目。只倒顺序，负担会从「审票」挪到「试用」，所以还要改 cc 的默认行为。
3. **用户改主意的时机分层清楚，这是分流的经验依据**（auditor）：方法与范围在讨论里定下后一直没变；交互和概念一看到原型就改；最大的转向发生在用过真东西之后。所以方法论留在讨论里定（这一层已完成），交互和概念交给试用。
4. **方向已经定完。** 10 张 open 票逐张核过，没有一张还要用户定方向（`方案.md` 4.5）。剩下只需用户提供两个事实：哪台机器做什么（票 07）、旧看图工具的旧标注留不留（票 07、10）。
5. **主链从没走过，第一步就走它。** 「新标注格式装不装得下用户的意思」「会话能不能照标注写出 app 并叠回图上」这两个最没把握的假设 12 天里一次都没验过；任何一个不成立，后面的设计都要变。这是 `.claude/rules/plan-execution.md` 认可的唯一拆段理由。

## 3. 推荐流程（方案 A「先做后看」为主干，从 B、C 各取一样；详见 `方案.md` 第 2～3 节）

- **决定分五类**（判据：用的时候看不看得见 × 错了谁付代价）：① 看得见、只花 cc 时间 → cc 定，试用时反馈；② 看得见、花用户的东西（已存标注、学过的词、别的工作里读惯的数）→ 交付说明里事先告知；③ 看不见、撤不回或会变好看 → 原则用户已定，落法用具体情形确认，cc 落成自动检查；④ 看不见、只花 cc 时间 → cc 定、不告知；⑤ 改变工具用途 → 停下问。② 只在新标注格式第一次真实使用之后才存在。「要不要写进交付说明」按改动碰到了什么机械判定，由不参与编写的复核代理列出，不靠 cc 自觉。
- **只在三种情况停下等用户**：改变用途；动用户已存数据；用掉一次 2026 年数据（含建造与自测，cc 不得为测试读真数据）。其余要问的进交付说明末尾，一次最多三个，用 AskUserQuestion、推荐项排第一；阈值、张数给默认值标「待验证」不问；不再开决策票和访谈会话。
- **cc 的五条默认行为**：新词只在防 ②③ 类错时才加；用户说看不懂时先答「能不能删或并」；第一句先给「这是什么、谁产生、在哪一步」并当场答，不升级研究轮、不播报团队进度；动手前对一遍拍板层；辅助工具同样的手工动作重复两三次后才造。
- **交付说明三栏**（后台会话独立 worktree、照项目后台交付约定提交推送报分支名，交付说明写进提交说明）：能做什么 + 可复制的启动命令 + 最多五步试用链接；碰到用户东西的改动（每条一句业务后果）；要用户定的（零到三个）。红线检查全过时不出现。
- **验收看东西不读东西**：看得见的靠试用；试用验收不了的三样（撤不回的、会变好看的、对照显示本身）全交自动检查；成绩明显变好时先跑因果与泄漏检查再报；交付前 cc 自己按试用步骤走一遍截图。
- **掌握压缩到两处**，以悬停提示推给用户：输入是什么意思（正样本 = 按样本日当时会不会买；成员框不晚于样本日）；结论是什么意思（「过了」只是一次独立观察支持、暂用，无优势 pattern 约一半机会会过）。每个要认的词悬停里带一句「防的是什么错」，不等用户问。交互式引导教程先不做，第一次试用后仍难上手再做。
- **红线清单**见 `方案.md` 3.8（13 行，★ 五条要用户用具体情形确认）。保护对象是**用户批准过的例子文件**（★ 情形 + ③ 类已知答案 + 第 0 步的图），不是检查代码，不装钩子；例子文件一改就照改拍板层处理、用白话问用户；建造结束条件要求例子文件与批准时一致。
- **反应分四格**：这次改掉 / 这次不做（只适用于看得见的反应，看不见的不能静默丢——critic 补记）/ 以后都这样（同类第二次出现才算，能做成检查就不写文字；协作规矩保持一页以内）/ 方向变了（在拍板层就地改写，下次交付起生效）。验收标准在交付时冻结；红线检查不能看了结果再改；停止信号是新反应不再出现新种类。

## 4. 落到标注工具上的步骤（`方案.md` 第 4 节）

1. **第 0 步（用户约一小时）**：用户挑一个现有 detector 能表达的 pattern 想法、3～5 张真图；cc 先把用户的意思写成新标注格式画回图上，问「哪里装不下」，再手工翻成 app、结果叠回图上。这几张图连同「这天该买、这天不该」留作已知例子。走不通就停下回到方向层讨论；若做不到「写成新格式画回去」，建造在标注格式处拆一段。
2. **切换（用户半小时到一小时）**：cc 给五样，用户点头或改：一页拍板层（优先改写 `.scratch/annotation-path2/map.md`，并修正其中「色盲」的错误前提）；★ 红线的具体情形（含股票池偏差的权宜办法）；10 张票处置表；建议删的词；两件只有用户知道的事。
3. **造**：一份自包含计划、单个后台会话无人值守跑完主流程；开跑时用 `/goal` 写结束条件（条件写成命令输出：检查全过、自测截图已生成、例子文件一致、验证段读取账本无新增）；最后检查那条路只用替身数据测；每任务派子代理实施 + 子代理审查。不用 Workflow 工具（关会话即停、运行中不能问用户）。
4. **用**：先标 3～5 张跑一次，确认标注够表达，再大量标、盲看；最后检查最后用、每次用户亲自放行。拆旧代码（票 10）在用新工具做完一轮之后。
5. **要改的东西**：一份始终加载的短协作规矩（十几行，开头写明只适用于方向已定、有拍板层的工作，方向未定的 effort 照旧走决策票）；一组红线检查；一份例子文件；拍板层；说明书开头一句分层说明。不新建技能、不改用户级规则、不挪数据目录、不默认用沙箱。

## 5. 限定条件与未证实项

- 计数来自 auditor 一人人工分类（每条只标一类，边界条目可能归到相邻类）；「问懂后被删改」是因果推断，时间先后是查证的。初稿漏了 web-loop worktree 的 3 个会话，已补算，方向不变。
- 选择题 84 次作答 81% 选推荐，但细节题偏离推荐比例（7/29）高于方向题（5/38），且推荐排第一有锚定。所以把细节交给 cc 的理由只能是「错了看得见、改得起」，不能说 cc 在细节上判得准；预期约四处有一处会在试用中被改。
- 「方向题大多同推荐」不等于方向也能交给 cc：没被采纳的 Q5 恰是后果最大的统计口径。
- 〔事实，lead 本机核实〕`/goal` 在本机 Claude Code 2.1.316 中存在（「Set a goal Claude checks before stopping」）；`/btw` 字串存在。
- **`/goal` 是软约束，不是硬卡**（mechanist 收尾提醒，lead 未复核其判定机制）：它的判定者不跑命令、只看对话里打出来的文字，agent 写一句「全部通过」就可能过关。要硬卡须用 command 类 Stop hook 实际跑检查，而定稿刻意不装钩子。所以建造期靠 `/goal` 守的条件（检查全过、例子文件一致、读取账本无新增）都只是软约束；真正的兜底是交付时由不参与编写的复核代理实际跑检查并把结果写进交付说明。实施计划里要把这一步写成必做。
- **数据墙在实施前并不存在**（mechanist 实读）：`scripts/path2/path2_eval_scan.py`、`scripts/path2/scan-top-miss.py`、`path2_web/eval_runner.py` 的默认参数和 tune-gates-v3 的 `scripts/run.py`（写死主目录绝对路径）默认都读完整数据 `datasets/pkls/`，下载脚本也原地改写它。「本工具读数据入口截到 2025-12-31」要作为实施计划里单独的一步来做；它只防不小心、不防存心绕开（`方案.md` 3.10）。
- 〔未证实〕沙箱在用户常用的 bypassPermissions 模式下是否生效、Linux 下对 `datasets` 软链的处理；PreToolUse 钩子返回 `ask` 在 bypassPermissions 下是否弹提示。方案默认不依赖这两者，只在将来决定上沙箱或钩子时用金丝雀实测。
- 注意力估计（3.5）、切换成本（4.6）是推断，第 0 步之后用实际情况更正。
- 外部证据（Anthropic 52 人随机对照：先生成再追问理解的用法得分接近手写组，纯委托最差）测的是边写代码边学库，对「学会用研究工具」只是旁证；每类用法只有 2～7 人，只支持方向，不保证效果。
- mechanist 统计的「约 17 万字符决策材料」是字符数、含原型 HTML，不等于用户实际阅读量；用户阅读量以 auditor 的口径（给用户读的文档约 10.5 万字）为准。
