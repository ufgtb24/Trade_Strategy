## 0. 一段话结论

用户问的是三件事，产出者不同：① **一个买点由哪几个框构成**（只有用户知道）；② **框与框之间什么关系**（位置已经表达，不靠位置的写成属性）；③ **哪些买点算一个 pattern、pattern 由哪些名称组成**（跨图才看得出，程序算、用户一组一下拍板）。推荐：**每个买点存一份成员框清单**（保存时算好的框编号；默认由界面推断，只在放买点那次停留里生效，离开即冻结；推错在买点 edit 栏点名称块改）；**主图 bracket 轨上的虚线就是 pattern 实例的边界**，由成员派生、不可拖，对照时与 app 的实线 match bracket 同轨；**关系不设编辑器**；**侧栏 summary 改为 pattern tab**——一句话定义 + 一条竖排名称链（骨架与对应表合成）+ 按骨架分组的买点（`→ pattern` 下拉兼做归组、合并、拆出）；**现有拓扑面板在标注模式三个时期（无 app、对照、盲看露结构）都不出现**，看图模式照旧，只借它的画法。相比 lead 的候选：少存范围、角色、「自动」标记三样，不新开 tab，关系与拓扑零新增控件。最大风险是默认成员规则（「两段之间隔多远仍算连着」= 20 根，借来的数），第一批真实标注后必须先查。

## 1. 三件事分开

| | 是什么 | 谁知道 / 谁产出 | 推荐做法 |
|---|---|---|---|
| ① 买点的成员 | 这次买入是因为哪几个框 | 只有用户；默认可推断 | 显式存成员清单，默认推断、看得见、推错才改 |
| ② 框之间的关系 | 先后、交叠、包含、「中间没有 X」、「不破前面那个的价」 | 用户看得见、说得出；翻成什么归会话（已定 5） | 不设编辑器：位置表达先后 / 包含；不靠位置的写成后一个框的属性 |
| ③ 买点归哪个 pattern；pattern 由哪些名称组成 | 跨图才看得出 | 程序按骨架分组摆出来，用户拍板；会话只在对话里给语义建议 | pattern tab：groups + `→ pattern` 下拉；elements 竖链 |

**为什么 ① 必须显式**（critic 1.2、flow F1）：只靠时间窗推断（原型 `buyVerdict` 用「买点前 40 根」），三种情形必错——再买一次（第二个买点的窗盖住第一段回踩；项目里有 re-entry 的 bb_v3）、长底座（窗只收半截）、两个 pattern 的买点时间交错。错的代价是骨架错：会话据此加一个不存在的 node 或漏一个。

## 2. 推荐方案

### 2.1 存什么（topo §5.4）

| 记录 | 字段 | 谁写 |
|---|---|---|
| 词 | 编号、措辞、定义 | 用户（已定 2） |
| 框 | 编号、股票、起止日期、名称（词编号）、属性（词编号 → true / false）、instance 注释、let_go、detach（不属于外框，默认否） | 用户 |
| 买点 | 编号、股票、日期、pattern 编号、buy / no_buy、**成员（框编号清单，新增）**、instance 注释 | 用户（成员可以是接受了的默认值） |
| pattern（新增） | 编号、名字（用户起）、定义（一句话） | 用户；「未归类」是保留值 |
| 纠错（⚑） | 编号、指向对应表某一行（用词编号）、一句话 | 用户 |
| 图 | 股票、窗口 | 界面顺手记 |
| 批次头 | 机器名、时间、数据指纹 | 界面 |

- 存储守方向文档第 10 节（每批一个新文件、文件名带机器名、只新增不改旧文件）。所有记录平铺、带全局唯一编号（机器名 + 时间 + 序号），改 = 新记一条同编号记录、删 = 记一条删除记录。原型 json 的 `b1`、`p2` 是会话内自增，跨文件、跨机器会撞，需要改。
- **不存的派生物**：范围（由成员派生）、框套框父子（由起止日期派生）、骨架与 groups（界面现算）、默认成员建议（只存接受后的结果）、对照状态（app 版本 × 标注，换版本即变）、角色（已定 3）、「默认 / 改过」标记。
- **会话的产物**（对应表、「哪个 app 是这个 pattern 的当前实现」）放在 app 旁边、随 app 进 git，不进标注文件。标注里的 pattern 记录不引用 app 编号（app 会换版本，意图不变）；界面上 pattern 显示用户起的名字，有 app 时旁边等宽小字 `app: bb_v1`（topo §5.2：原型顶栏直接列 app 编号，把「用户的 pattern」和「实现它的 app」混成一个，要改）。

### 2.2 主图（ux §3.1，截图 `ux_1_select_instance.png`、`ux_3_compare.png`）

- **bracket 轨**（`path2_web/GLOSSARY.md:45`）在标注模式下常驻：每个买点一条虚线，从最早成员的起点画到买点（成员越过买点时画到最晚成员的终点），右端挂与主图买点同形的三角（实心 buy、空心 no_buy）；时间重叠的上下叠放；非当前 pattern 的整体变淡；没有编号、没有字。不在任何 bracket 下的框 = 只标事件（用户截图里左边孤立的框自然落在外面）。
- **选中 instance**：点 bracket、买点三角或主图买点记号。成员框换粗虚线，其余框透明度约 0.3（待验证），主图在 instance 起点和买点各一条竖虚线。照搬主视图「点 bracket 高亮这次 match 的事件」，只多了「其余变淡」（用户的框只有虚线、没有底色，光加粗不够醒目）。放下买点即自动选中。
- **名称轨上下顺序** = 当前 pattern 各 instance 里**两两比先后**：两个名字同在一个 instance 的成员里时，谁在前的次数多谁排前；从没同时出现过的、或先后互相矛盾的，退回按平均相对位置；不在任何 instance 里的名字排后面。（用户 2026-10-26 定：原先取平均相对位置，骨架长短不一时会排错——「放量突破 → 回踩」的 instance 把放量突破拉到「下跌 → 底部 → 放量突破」里的底部前面。）一个 instance 读起来是一道从左上到右下的台阶，先后不需额外元素。与 pattern tab 的 elements 同序。
- **框套框**：子框左上角外侧常驻一个 `⊂` 记号，不带父名；悬停或选中子框（或父框）时，父子两个框都换成和普通选中一样的粗虚线、并画一条竖线连起来；edit 栏的「父框」一格写出父名。（用户 2026-10-26 定：原先在子框里写 `⊂ 父名`，短框放不下，而且 band 里出现「横盘」二字会被读成这条 band 就是横盘。常驻记号保证推错时平时也看得见「它被算作属于某个框」，是哪个框靠悬停核对。）
- **名称级的从属写在轨标题上**（用户 2026-10-26 提议：属于是 node 之间的关系，不只是框之间的）：子名称的轨紧跟在父名称的轨下面，轨标题写 `缩量 ⊂ 横盘`。来源与 pattern tab 的 elements 相同——当前 pattern 各 instance 里这个名称的框多数挂在哪个名称下；还没有 instance 时，看这张图上这个名称的框是否全挂在同一名称下。框上的 `⊂` 记号仍是逐框的事实：轨标题说「缩量 ⊂ 横盘」而某个缩量框没有记号，就是这一处例外，一眼可见。轨标题**只显示、不做开关**：悬停时把这张图上这一对名称的所有父子框一起描出（同单框悬停的粗虚线）。（用户 2026-10-26 同意：标题是各框统计出来的，给它加开关要么另存一份名称级从属、与框的 detach 两份打架，要么做成批量点掉、点回时抹掉单框例外；所有 `⊂` 都做开关也不取——关掉后记号消失无处点回、框角和成员块旁的小目标会误点成选框或改成员、同一记号点下去改动范围不同。开关只在子框 edit 栏一处。）
- **断开从属**：时间上落在别的框里、但用户的意思是不属于它（如长下跌里恰好有一天无关的放量），在子框 edit 栏「父框」一格点掉 `⊂` 开关即可（存为框的 detach 字段）；点掉后只是不再算子框；它是不是这个买点的成员不受影响（成员只由默认规则和名称块决定，且只加不踢）。改框起止不受影响。
- **对照开着**：app 的 match bracket 用实线（带主视图原有圈号与买点三角）画在同一条轨上；框旁 qualified / detected / missing、买点旁 app:buy / no_buy 照原型。**图上不画两框之间的 link**：mock 实测，首尾相接的两个成员之间连线只有约 3px 横 + 30px 竖，被前一个框右侧的状态签盖住，看不见。
- 统一画法：**虚线 = 用户的，实线 = app 的**；区分全靠线型、粗细、深浅、实心 / 空心，无新颜色（已定 8）。

### 2.3 成员的默认规则（topo §5.1，critic F7 三方终稿 + lead 拍板）

- **推断**：终点落在买点前 G 根以内或跨过买点的框起头，往左把「终点距这串起点不超过 G 根」的框逐个接上（相接、交叠都算），再带上被成员包住的框。**G = 20 根（待验证）**，出处：bb_v1 允许回踩在末根突破之后最多 20 根内开始（`tb.max_span`）。原稿 2 天把「框边界画粗的容差」和「相邻两段之间的空隙」混成一个数；放量突破后先涨几天才回踩、那几天用户多半不框，空隙远大于 2 天，会静默切短（critic T5）。默认偏向多收：多收的在 bracket 下看得见、点一下排掉；少收更常见也更隐蔽。
- **生效范围（六条）**：
  1. 存保存时算好的框编号清单，不存「自动」标记、读时不现算；
  2. 这次停留里**新画或改动的框**贴着那一串就并进，bracket 随之伸长（lead 拍板：用户常先画短再拉长，只判新画的框会让刚拉长的框收不进来）；
  3. 只并进当前 pattern 的买点（只有它们的 bracket 画在图上）；
  4. 只在放这个买点的那次停留里生效，离开这张图即冻结，以后回来补画的框不自动进任何旧买点；
  5. 只加不踢：成员框改短、挪远也不自动移出（自动踢出是静默丢成员）；这次停留里用户点掉过的框不再并回（这份记录只在内存，停留结束即丢）；
  6. 以后改默认规则不改写任何旧买点。
- `repro/default_members.py` 6 种手造情形（只看失败的样子，不代表频率）：空隙 2 天少收 9、多收 0；20 根少收 1、多收 1；「往左收到同一 pattern 的上一个买点为止」少收 2、多收 2（共用前段、各有后段时漏掉共用的横盘与突破，不采纳）。原型种子：TVRD 2025-04-28 收进横盘、缩量、放量突破、回踩；像但不买 2025-05-08 收进同一串（空隙 2 天时收成空）；WHLRP 53 天前的横盘不收。

### 2.4 侧栏 edit tab

- **选中买点**：原有 pattern、label、instance 注释不变；删掉原型里恒为 auto 的 `role` 一行；新增：
  ```
  members  ┃横盘 ⊃ 缩量┃ → [放量突破] → [回踩] → ▲buy
  others   [放量突破] [回踩]
  ```
  `members` 按先后排、实线边；父块和被它包住的子块一起围在一个深色实线框里，块间保留 `⊃`（用户 2026-10-26 定：原先的浅色点线框看不出来）；`others` 是这张图上买点之前开始的非成员框、虚线边。点任何一块 = 进 / 出；悬停一块 = 主图描出对应的框（同名两段靠此区分）。不标「默认 / 改过」、不设 reset（存的就是一份清单，没有可回的默认态）。对照开着时只在块间箭头挂 `ok` / `broken` / `pending`（框状态和 app:buy 主图已有，不重复）。会话推不出角色时（同一买点前两段同名框）在同名块上挂 `role?`，点一块即回答。
- **选中框**：不变（不列「属于哪几个买点」，选中买点时图上看得见，反查少用）。
- **改成员的入口只有这里**：图上点框的意思始终是「选中这个框」，不随当前选中物变化。

### 2.5 侧栏 pattern tab（替代 summary；截图 `ux_4a_pattern_tab.png`、`ux_4b_unsorted.png`）

当前 pattern 由顶栏定。版式（`未归类` 与某个 P 共用）：

```
pattern  横盘突破回踩   app: bb_v1
定义    [横着走一段后放量越过前面好几个峰，回踩不破就买      ]
elements n=4
 [横盘]       in 2/4   TrendSegment:sideways ⚠default_params ⚑  qualified 0/1
   ⊃ [缩量]   in 2/4   unmapped                                    ⚑
   ↓
 [放量突破]   in 4/4   node:burst ⚑  qualified 2/3
     [放量] 3/3  [突破过好几个峰] 2/3  [突破前沉寂够久] 1/1 null 2
   ↓  ok 2  pending 1
 [回踩]       in 4/4   node:tb ⚑     qualified 2/3
groups n=2
 [横盘]→[放量突破]→[回踩]  ×2  buy 1 app:buy 1/1 · no_buy 1 ▌app:buy 1/1▐  [→ pattern ▾]
   ▸ 名称轨缩略图 × 2
 [放量突破]→[回踩]         ×2  buy 2 ▌app:buy 1/2▐                       [→ pattern ▾]
```
（`▌…▐` = 违背预期，朱红底白字：buy 里 app 漏买、no_buy 里 app 误买。）

- **定义**：pattern 想抓什么的一句话（方向文档第 12 节三处离不开语言之一）；会话写 app 前若空着，在对话里问。
- **elements**（= 骨架与对应表合成的一条竖链，不另有表）：本 pattern 全部 instance 的成员里出现过的名字，每个一行；套框缩进带 `⊃`；属性作行下小胶囊，数字为「看过的里面几个 true」，有没看过的挂虚线签 `null n`（取其一自然呈现：底部下 `W形 6/9`、`V形 3/9`）；出现次数前固定 `in`，认出数前固定 `qualified`（两种分数分母不同，各带标识符，不靠图例，critic U13）。认出数不再按「新 / 老标注」拆开（用户 2026-10-26 定：拆分是过度设计——训练集随便看，看着 app 的检测结果去标、去改是用户的自由，迭代 app 时还会刻意这么做；认出数只是训练集上的开发辅助，如实检验靠盲看和留出数据，不靠它。随之删掉「接触过 app」记号和「新标注不足 5 个只写还不知道」）。有 app 时名字行右侧加 resolver（**写代码标识符，运行时从代码读，不设任何「代码 → 中文名」对照表**：app 里的写 node 名 `node:burst`、`node:tb`，取自 app 声明；会话选来认、但没接进 app 的写事件类名加关键字段 `TrendSegment:sideways`、`Platform`；悬停显示该事件类说明的第一行；edit 栏 resolver 一格同一写法。用户 2026-10-26 改：原按 critic U10 写词表规范词、去掉前缀，其中 `走势区段`、`平台段` 是界面里手写的中文对照，代码改名或新增事件时会悄悄过时、也没有东西核对；代码才是现有资产的唯一出处，界面文字规则也要求标识符对得上代码。`node:` 前缀保留，让人一眼看出它在不在 app 里，写法待验证）、认出数、⚑；属性不写 where 标识符（where 照用户的词命名，写出来是重复），只在没进 app 时挂 `unmapped`；相邻顶层元素之间的 `↓` 有 app 时挂 link 计数。⚑ 只挂在翻译上；骨架本身是计数，数不对 = 成员推错，回图上改。没有 app 时 resolver、认出数、⚑ 都不出现。
- **认出数只数 P 的买点的成员框**（flow §5 末）：不在 P 任何买点里的框是事件层样本，用来帮会话选 detector，拿 P 的 where 考它们会把不属于 P 的场景算成「不够格」。这是对票 Answer 第 3 节「汇总页按名称列认出几处」口径的收窄。

  - 下拉只改归属、不切页：挪完留在当前 pattern，挪走的组从这一页消失；看别的 pattern 只用顶栏的 pattern 下拉（用户 2026-10-26 定：原型挪完会顺手切到目标 pattern，归类和切换混在一个操作里）。

### 2.7 拓扑面板（topo §1、§2、§4）

- 现有面板（`path2_web/GLOSSARY.md:50`，`path2_web_ui/src/components/TopologyControl.vue`、`render/topology.ts`）只吃 app 的声明，四个交互（点节点切显隐、双击拉诊断、点边看 miss、悬停看阈值）全是调 app 用的，没有 app 时整个为空。

- **改造复用（只借 `layoutTopology`）不值**：实测（`repro/skeleton_width.ts`）三个词的链宽 404px、五个词 728px，侧栏可用约 360px；层间距下限写死 96px、不能折行。复用的只是画法（先后从左往右 / 从上往下读、包含挂在下面、用户的用虚线）。唯一需要一般图的情形（两样都在第三样之前、彼此先后不定）在一列里叠两个胶囊即可，且少见。

### 2.8 关系不设编辑器（topo §3，flow §1）

| 边（`path2/GLOSSARY.md:86`） | 用户怎么表达 | 显式操作 |
|---|---|---|
| 时序 | 框的先后；间隔是参数，归调参（不从框量） | 无 |
| 包含 | 框套框（默认「属于」）；翻成复合事件子槽、where 读子事件还是包含边由会话定 | 无；推不出时在图上问 |
| 起点包含、交叠 | 多半是边界画粗，按「紧接着」读；多个 instance 都明显交叠才当真关系 | 无 |
| 同段 | 一个框写几个属性 | 无 |
| 否定 | 属性记 false；单张图分不清「恰好没有」和「有它就不买」，靠跨图证据（买点上一直 false、像但不买常为 true）与名字的定义 | 无 |
| 锚 | 成员关系加先后 | 无 |

**硬事实**：path2 的边只比较两个事件的起止下标（`path2/dag/edges.py`：时序比 `dst.start − src.end`，包含 / 起点包含 / 交叠 / 同段比起止，否定比间隔加一个只看 dst 自身的条件），锚只比身份；没有一类边能比较价格或字段。所以「回踩不破突破价」这类不靠位置的关系，落点是**后一个 node 的字段 + where**（后一个事件的 detector 读前一个事件的流算成自己的字段，bb_v1 的回踩即如此），不是边。写成后一个框的属性恰好落在它在代码里的位置。lead 候选「由会话翻成边」更正为「翻成后一个 node 的 where」。

### 2.9 侧栏按来源加底色（用户 2026-10-26 提议并定）

侧栏内容按谁产出分三类，三类对应用户能做的事不同，用底色区分：

| 来源 | 内容 | 用户能做的 | 底色 |
|---|---|---|---|
| `user` | 用户画的、写的，以及界面从它随时算出的（默认成员、`in n/N`、属性计数、groups、缩略图、let_go） | 直接改 | 不加 |
| `session` | 会话的翻译：由谁来认、`unmapped`、`⚠ default_params`、`⚑`、`role?`、只在 app 里有的 `where:` 行 | 用 ⚑ 或在对话里纠正 | 中蓝（冷） |
| `app` | app 跑出的结果：框状态、`qualified k/n`、`⚠ chance_high`、`ok` / `broken` / `pending`、`app:buy`、checks 的 app 列 | 只看、拿来判断 | 浅琥珀（暖） |

- 用户的不加底色：用户的自然语言已按界面文字规则带浅灰底，再叠一层会冲突；只用两种底色，色弱下也更好分。
- session 的蓝必须比用户的浅灰底明显暗一档（用户 2026-10-26 实测：浅蓝 `#dbeafe` 与浅灰 `#e9e9ec` 明度几乎相同，分不开）；现用中蓝 `#93c5fd`。
- 文字一律黑色（用户 2026-10-26 定）：用户的和程序的已靠浅灰底 + 字体（无衬线 / 等宽）区分，字色不再参与；灰字只留给空着或没选上的状态（输入框占位提示、`others` 里没收进成员的块）。
- 同一行按来源排成连续三段（用户 → session → app），⚑ 挪到「由谁来认」旁边，不再跟在 app 结果后面；groups 行、edit 栏同此顺序。
- 侧栏 tab 下一行图例：三个色块加 `user` / `session` / `app`，与主图「虚线 = 用户、实线 = app」同一套说法。主图不加底色。
- **违背预期一律朱红底白字**（`#D55E00`，用户色板里唯一和主视图现用色都分得开的颜色）：app 漏买 / 误买、框没认出或只看到不够格、前后没连上、checks 的 fail，主图状态签同此。**黑底白字只表示选中 / 按下**（当前 tab、选中的按钮、⚑ 标过的 flagged）。（用户 2026-10-26 定：原先违背预期也用黑底白字，和选中混。）
- **侧栏的程序文字都有悬停解释**（用户 2026-10-26 提）：说清这个字段 / 数字 / 状态是什么意思，能带上当前数字和名称的就带（如 `in 2/4` → 「4 个买点里有 2 个的成员中有『横盘』」，groups 的 `app:buy 1/2` → 「这 2 个 buy，app 买了 1 个，漏买 1 个」）；有解释的地方鼠标变成问号。界面上不加说明文字。
- 附带作用：「未归类」或还没跑 app 时，侧栏只剩无底色的部分，哪些格子要等会话、要等 app，看颜色即知。

## 6. 残余风险（接受）

1. **骨架与对应表就在一个主动点开的 tab 里**（critic U3 / F3）：标新图时用户随时能看到「由谁来认」和认出数，印象会往 app 的样子靠。按用户 2026-10-26 的定法这不算风险要压：训练集随便看，看着 app 去标、去改是用户的自由，不设记号、不拆新老；如实检验靠盲看和留出数据。
2. **默认成员是整套分组的地基，用户最可能不看就接受**（critic 3.4，最担心的一点）：多收出孤组、少收出淡色邻框，两种错误都有可见出口，但都在第二步归组时才集中冒出来。V1、V2 是唯一能提前看到它的地方，列为必做。
3. **夹在成员中间的多收框**不改变 bracket 长度，只在选中买点时看得见；若是顶层框会让该买点自成一组（第二步可见），若是子框不进骨架、影响小。
4. **按顶层名称序列完全相同分组会碎**：近义词、可有可无成员会拆出小组，第二步变整理活（V4）。
5. 「没画还是没有」靠会话照硬步骤问；漏问则「可有可无」被悄悄翻进 app（转票 09 作硬步骤）。
6. 小尾巴：elements 属性子行计数（如「放量 3/3」）尚不带标识符，与 U13 同类，实施时顺手统一；缩略图左展范围与「切短未改」检查窗口取同一个数。
7. 同名两段的名称块靠悬停区分；块上加日期会成文字堆，未采纳。

## 7. 最容易被误读的地方

- **bracket 不能拖**，它只是成员的显示；改成员只在买点 edit 栏点名称块。
- **默认推断不是持续状态**：只在放买点那次停留里帮着填清单，之后清单就是用户数据，规则再改也不动它。「改动的框也判」只会加、不会踢。
- **成员 ≠ 框套框**：框套框 = 小框属于大框（子事件或 where 的来源，`path2/GLOSSARY.md:62`）；成员 = 这个框是这次买入的理由之一。子框随父框成为成员。
- **这里的「骨架」是用户一侧的**：成员名称按先后排成的序列，界面现算，不是 app 的 node（`path2/GLOSSARY.md:76`）拓扑；app 只在 resolver 一格出现。
- **「不复用拓扑面板」不是删它**：看图模式一切照旧。**「不设关系编辑器」不是关系不重要**：关系由成员边界 + 框位置 + 后一个框的属性表达，成员清单是唯一新增的用户数据。
- `in n/N`（出现在几个买点里）与 `qualified k/n`（认出几个）分母不同，不能并排比。
