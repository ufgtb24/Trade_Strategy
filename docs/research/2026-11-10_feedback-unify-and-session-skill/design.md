## 0. 一页结论

| 待设计项 | 结论 |
|---|---|
| `picked` 记录的 `answer` | 新记录**不带** `answer` 键。`answer` 从必有键降为可有键：盲看标记仍必有；`picked` 带了就是旧形状 |
| 旧记录的 `answer` / `dag` | 文件里原样留着、读出来原样带着；界面和改版报告**都不显示**；一经新界面保存就改写成新形状（去掉这两个键） |
| issue 一致性 | 只比 `pattern`、`note`、`nodes`（不论顺序）。`answer`、`dag` 不比，各处不同也不算分歧 |
| 保存条件 | 新形状只有一条：`note` 必写。node 可点可不点 |
| 面板 | 一打开就是三行：`issues`（有可挑的才出）、`nodes`、`note`。没有 `answer` 行、没有 `dag` 按钮 |
| 反馈带记号上的字 | 写点出的 node 名（放得下才写）；没点 node 的不写字 |
| 侧栏组头 | 第一行 node（没点写灰色 `none`）与处数，第二行理由 |
| 改版报告 | 一条反馈不再写答案；node 前的说法从「认错的」改成「落在」 |
| 会话新步骤 | 定格之后、改 app 之前：读齐这一轮的输入 → 一份按去向分三段的处理清单 → 只有要用户定的才出选择题 |
| 会话账本 | **不加新结构**：`conditions` 的 `state` 约定几个开头词，`tags` 取值不变 |
| 会话侧新函数 | `path2_web/annotation/revision.py` 加一个只读函数 `round_digest`（这一轮的输入摘要）；`start_round` 允许在还没有 app 时定格 |
| skill | 一个 skill（暂名 `annotation-round`）＝规格 6.10 的循环技能：照标注翻出 app 与处理反馈共用一轮的骨架；不依赖 `authoring-path2-app` |

没有新增的记录键、原因码、界面固定词；删掉的见第 2 节末尾的清单。

真实标注现状（2026-11-10 用 `read_annotations` 只读统计）：反馈只有 1 条——`picked`、`answer = neg`、`target = range`、有 `note`、带 `issue`（`i-pc-1`，只有这一处）、没有 `nodes`、没有 `dag`。其余旧形状（`off_pattern` 配 `nodes`、带 `dag`、没写 `note` 的）眼下不存在，但用户在本次改动落地前随时可能再存，所以一律按「可能存在」兼容。

## 1. 记录形状

### 1.1 两种形状，靠有没有 `answer` 键区分

只说来源是 `picked` 的记录；盲看标记（来源不是 `picked`）的规则一个字不动。

| | 新形状（今后新界面写出的每一条） | 旧形状（已有的、旧页面还可能写出的） |
|---|---|---|
| `answer` | **没有这个键** | 有，取 `neg` / `off_pattern` |
| `note` | 必有、非空 | 照旧规则 |
| `nodes` | 可有；意思统一为「问题落在这一块上」 | 可有 |
| `dag` | **不许有** | 可有（只存 `true`） |
| `issue`、`family_start`、其余键 | 不变 | 不变 |

理由：二分类这条信息不存在了，键就不该在；写一个固定占位值只会让读的人以为它有意义。不改 kind、不改 schema 号、不做迁移。

### 1.2 存储的键与校验（`path2_web/annotation/store.py`）

- `_VALUE_KEYS["feedback"]`：`answer` 从必有键挪到可有键，**放在可有键的第一个**——`_ordered` 按「必有键 + 可有键」的次序出键，这样旧记录重放出来的键序和今天一模一样（现有测试断言了键序）。
- `_feedback_problems` 逐条：

  | # | 条件 | 规则 |
  |---|---|---|
  | V1 | 来源不是 `picked` | `answer` 必有（缺了报 `bad_op`：盲看标记必有 answer）；其余盲看规则原样 |
  | V2 | `picked`、带 `answer` | **现有规则原样**：取值只能 `neg` / `off_pattern`；`neg` 必写 `note`；`off_pattern` 的 `nodes` 与 `dag` 至少一样；带 `dag` 必写 `note` |
  | V3 | `picked`、不带 `answer` | `note` 非空；带了 `dag` 就拒（不带 answer 的反馈不该有 dag） |
  | V4 | 两种形状都查 | 日期、`target`、`family_start`、`nodes` 是不重复的非空字符串数组、`dag` 只能是 `true`、`issue` 非空且只有 `picked` 能带——全部不变 |

  `FEEDBACK_ANSWERS`、`BLIND_ANSWERS` 两个常量留着。
- `_issue_content` 只取 `(pattern, note, 排好序的 nodes)`；`issue_diverged` 的原因码不变，文字改成「各处内容应相同（pattern、note、nodes）」。
- 盲看「创建后不可改、不可删」（`_blind_changes`、`_replay` 里记第一次出现的值）不动。
- 模块说明「状态的形状」「反馈」「保存时的校验」三段跟着改写（`answer?`、两种形状、issue 比哪些键）。

**旧形状永久合规，没有「过渡期后收紧」**：读批次文件时用的校验和保存时是同一个函数（`_parse_batch` → `_op_problems` → `_feedback_problems`），哪天把旧形状判成不合格，含旧记录的批次文件就整个读不出、全部标注都读不到。

为什么旧形状的规则原样保留、而不是统一放宽：旧页面写出的东西今天能过、改完也必须能过，照抄现有判断最不容易出错；新形状另走一条更严的规则，任何「半新半旧」的值两边都过不了，会被整批拒掉——这正是防坏记录的那道闸。

### 1.3 issue

- 一个 issue = `pattern` + `nodes` + `note`。存法不变：内容写在每条反馈里，共享的几处带同一个 `issue` 值；不带的自成一个只有一处的 issue。
- 旧 issue 里各处的 `answer`、`dag`：不属于 issue 内容。今天的校验保证了同一个 issue 的各处这两个键相同；以后各处被逐条改写成新形状时会暂时不齐，不算分歧、不用处理。
- 界面规则照 brief 第 4 条，逐条落法见第 2.2 节。

### 1.4 旧记录：怎么读、怎么显示、编辑后存成什么

| 旧记录 | 读（`read_annotations`） | 界面显示 | 新界面编辑后存成 |
|---|---|---|---|
| `neg` + `note` | 原样，仍带 `answer` | 理由；没有 node | 去掉 `answer` |
| `off_pattern` + `nodes` + `note` | 原样 | node + 理由 | 去掉 `answer` |
| `off_pattern` + `nodes`，没写 `note` | 原样 | 只有 node | 要先补一句 `note` 才能存（`need note`）；不想补就不改它，或删掉 |
| `off_pattern` + `dag`（+ `nodes`）+ `note` | 原样 | 理由（+ node）；`dag` 不显示 | 去掉 `answer`、去掉 `dag` |
| 带 `issue` 的 | 原样 | 照常按 issue 分组、能被挑去复用 | `issue` 值保留 |

- 「不显示 `answer` 与 `dag`」是有意的：用户已定这个标签不作数，只在一部分记录上露出来只会添乱。原值在批次文件里永远都在。
- `dag` 丢掉不丢意思：带 `dag` 的旧记录一定写了 `note`，「不在某一块上」由 note 说。
- **新界面写出的每一条 `picked` 记录都是新形状**，包括 `all`（各处一起改）时顺带改写的别的处，以及「头一回被共享、为了补 `issue` 值而改写的原来那一处」。唯一例外是撤销删除：见第 2.5 节。
- **挑一个旧的、没写 note 的 issue 来复用**：不特判。挑了以后 `note` 是空的，必须先补；一补内容就和原来那处不同，于是照常出 `all` / `only this`——`all` 是原来那处也补上 note 并变成新形状，`only this` 是这一处另立。
- 打开一条旧记录、什么都没改就按 Enter：记录值变了（少了 `answer`），会写一条把它改成新形状的操作。可以接受，不特意拦。

### 1.5 前端的类型与函数（`path2_web_ui/src/annotate/model.ts`、`feedback.ts`、`stores/annotation.ts`）

- `AnnFeedback.answer` 改成可选（`'neg' | 'off_pattern' | 'pos'`，旧形状与盲看标记才有）；`dag?: true` 留着，注明只读旧记录时会遇到。
- `feedbackValue`：`answer` 有才写、`dag` 有才写（原样照抄，供盲看标记与撤销写回用）。
- `FeedbackDraft`、面板状态、redraw 的 carry：去掉 `answer`、`dag`。
- `draftToFeedback`：不写 `answer`、不写 `dag`；`note` 去首尾空白后必有。
- `saveProblems`：去掉 `answer`、`nodes_or_dag` 两个问题码；`note` 的条件改成「去首尾空白后为空」；其余（`nodes`、`range`、`after_train_end`、`point`、`family_start`）不变。
- `IssueContent`、`IssueGroup`：去掉 `answer`、`dag`；`sameContent` 只比 `note`（去首尾空白）与 `nodes`（按集合）。
- `issueChoices(rows, selfId)`：去掉按答案过滤的参数，列出当前 pattern 全部 `picked` 的组（「只有正在改的这一处自己」的那组除外），排序规则不变。
- `saveFeedback` 里改写别的处：从原值里拿掉 `note`、`nodes`、`dag`、`issue`、**`answer`**，再填上这一处的 `note`、`nodes`、`issue`（即别的处也变成新形状）。
- `undoOps`：**不改**（见 2.5）。

## 2. 界面

固定文字一律英文标识符、等宽、黑色；用户写的内容正常字体加浅灰底；解释放悬停（原生 `title`，英文小写短句）。配色不变。

### 2.1 作答面板（`FeedbackPanel.vue`）

一打开就是完整的面板，没有「先点答案再展开」。从上到下：

1. 页头：股票、日期范围、`target`；改已有的一条时多 `redraw`、`delete`。不变。
2. `pos sample inside` 一行（范围里有正样本时）。不变。
3. `issues` 行：当前 pattern 已有的 issue（跨股票，最近用过的在前，多了在框里滚动，高度上限照旧，待验证）。**一打开就列**；没有可挑的就不出这一行。每条：node 小标签、理由（浅灰底，最多两行）、`places n`。放在最上面是因为挑一条会把下面两行填掉。
4. `nodes` 行：node 按钮，可多选，可以一个都不点。取法不变（范围里这些 hit 绑定的 node 及其子 node，按拓扑顺序；记录里有、当前 app 已没有的排最后、虚线框）。没有可点的时写 `none`（灰字，表示空）。**没有 `dag` 按钮。**
5. `note` 行：多行输入框，占位字 `required`。
6. `need` 行、存不进去的原因行、页脚：规则不变。

键盘与焦点：

- **打开时不抢焦点，也不自动把光标放进 `note`**（同一天几个 hit 时 ←/→ 还要用来挑）。
- **点任一 node 按钮（点上或点掉）后把光标放进 `note`**：按钮按下不夺焦点，光标在 `note` 里不妨碍接着多选。挑 issue 不动焦点（挑完按 Enter 就能存）。什么都不点、直接写的人自己点一下输入框——和原来「点一下 `neg`」同样是一次点击。
- Enter 保存、Shift+Enter 换行、Esc 只关面板、点面板外关掉不存、输入法组字中不截：全部不变。

固定文字（改了的和新写的；没列的不变）：

| 位置 | 文字 | 悬停 |
|---|---|---|
| `issues` 键 | `issues` | `issues already written under this pattern, across symbols, latest first; pick one to share it here: its nodes and note fill in` |
| `nodes` 键 | `nodes` | `where the problem sits: nodes the app's buys here are bound to, and their child nodes; pick any number, or none if it is not on any one node or you cannot tell` |
| node 按钮 | node 名 + 对到它的特征名（同 band 表头，不变） | mapping `notes` 里这个 node 的原话（不变）；当前 app 已没有的写 `not in the current app` |
| `note` 键 | `note` | `what is wrong with buying here, in your own words; required` |
| `need` 行的 `note` | `note` | `write a note first` |
| `redraw` | `redraw` | `drag a new range on the chart; the note and nodes come along and replace this feedback's range` |
| `shared by n places` | 不变 | `places using this issue, this one included; the note or nodes here differ from the other places` |
| `all` | `all` | `change every place of this issue to the note and nodes written here` |

node 按钮自己的悬停继续只放用户定义里的原话；「点它是什么意思」只写一处，在 `nodes` 键上。

### 2.2 issue 的规则（`stores/feedback.ts`、`annotate/feedback.ts`）

| 情形 | 行为 |
|---|---|
| 新标一处 | 不连任何 issue；存下来不带 `issue` 值 |
| 从列表里挑一条 | 连过去，`note`、`nodes` 填成它的；那条加黑边。**不再有「答案相同才算连着」这个条件** |
| 再点一次已连着的那条 | 不再共享，内容留着 |
| 打开已有的一处再挑另一条 | 这一处改指过去 |
| 连着的 issue 还有别的处、内容没变 | 直接存，带上它的 `issue` 值（它还没有值时现取一个，同一批里给原来那一处补上） |
| 连着的 issue 还有别的处、`note` 或 `nodes` 改了 | 页脚换成 `shared by n places` + `all` / `only this`；Enter 不存 |
| 只有这一处的 issue 改了 | 直接存，不问 |
| `redraw` | 带着 `note`、`nodes`、连着的 issue 进下一次拖动 |
| 删除 | 只删这一处 |

删掉的函数与状态：`setAnswer`、`toggleDag`、面板状态里的 `answer` / `dag`、「切到 `neg` 清掉 node」「点回原答案补回 node」两段逻辑。

### 2.3 反馈带的记号与悬停（`render/feedbackStrip.ts`）

- 记号上的字：点出的 node 名，逗号连起来（等宽、黑字）；整串放不下时退成「第一个 node 名加 `+n`」（n 是没写出来的个数），再放不下或没点 node 就只画记号（字为空时不要去画一段空文字）。新旧记录同一规则。已知后果：一个 node 名比原来的 `neg` 宽，只占一根 K 线的 `point` 记号多半写不下字，是个没有字的色块，内容靠悬停看。（待验证）
- 悬停的行，依次：`id`、`target`、`range`、`family_start`（一族才有）、`shared: n places`（两处以上才有）、`nodes: a, b`（点了才有）、`note: …`（浅灰底）、`status`、`tag`、`reason`、`pos sample inside`。**没有 `answer` 行；旧记录的 `dag` 不写。**

### 2.4 侧栏 `feedback` 页（`FeedbackPage.vue`）

组头两行（和现在的排法一样，只是拿掉答案与 `dag`；处数固定在第一行右侧，各组对得齐）：

1. node 小标签（`feedback-row-node`）；一个都没点时写灰色 `none`（testid `feedback-row-nodes-none`，悬停 `not on any one node, or not said`）… 右侧 `places n`、`matched k`。
2. 理由（`feedback-row-note`，浅灰底）。旧记录没写理由的没有这一行。

`places n` 的悬停改成 `places sharing this issue (same note and nodes)`。组内每处一行、排序、朱红 / `lost` / 标签、`edit`、`delete`：全部不变。旧记录的 `answer` / `dag` 在组头、悬停里都不留痕。

### 2.5 撤销删除（`stores/annotation.ts` 的 `undoOps`）

**不改代码，也不要改成「只抄 `note`、`nodes`」。** 现在的做法是：写回的反馈所属 issue 眼下还有别的处时，把 `answer`、`note`、`nodes`、`dag` 四个键整个照那一处现在的抄（没有的键就删掉）。这四个键正好是形状规则管的全部键，所以写回的那条和它照抄的那处形状一致——那处合规，写回的就合规，新旧形状都对。没有别的处时照原值写回，原值是当初存进去的合规记录。

反例（为什么不能只抄两个键再去掉 `answer`）：别的处是旧的「`off_pattern` + node、没写 note」时，写回的那条会变成「不带 `answer`、又没有 `note`」，被 V3 整批拒掉，撤销就失败了。

### 2.6 界面上删掉的东西

- 固定文字：`answer` 键、`neg` / `off_pattern` 按钮、`dag` 按钮、侧栏组头的答案与 `dag` 标签、`need` 行里的 `answer` 与 `nodes | dag`。
- testid：`feedback-answer-neg`、`feedback-answer-off_pattern`、`feedback-dag`、`feedback-row-answer`、`feedback-row-dag`。新增一个 `feedback-row-nodes-none`。其余 testid 不变。
- 保存条件的问题码：`answer`、`nodes_or_dag`。

## 3. 开发途中新旧混搭

用户的后端随 `.py` 改动自动重启、前端热更新，四种组合都会短暂出现。结论：**任何组合都不会有坏记录落盘**，最坏是「这一次没存上」。

| 前端 | 后端 | 保存时发生什么 |
|---|---|---|
| 旧 | 旧 | 现状 |
| 旧 | 新 | 旧页面写的都带 `answer`，走 V2，和今天一样能存。旧页面读到新形状的记录：答案位置是空的、打开后没有预选答案；用户点了答案再存，存成旧形状，合规。旧页面对一个新旧混着的 issue 点 `all`：它会给不带 `answer` 的那几处填上自己的内容，若因此出现「不带 `answer` 却带 `dag`」或「不带 `answer` 又没 `note`」，整批被 V3 拒掉，一条也不写 |
| 新 | 旧 | 新页面写的不带 `answer`，旧后端报缺键、整批拒收，面板写 `not saved`。没有坏记录，但用户存不上——用下面的次序避开 |
| 新 | 新 | 目标状态 |

前端自己改到一半（几个文件新旧不齐）时写出什么不可枚举，兜底只靠一条：后端任何时刻都只收「合规的旧形状」或「合规的新形状」，别的整批拒。

**次序（硬要求）**：

1. `fb-backend` 第一步只改 `revision.py` 里读 `fb['answer']` 的两处（新形状没有这个键，直接下标会抛错）与 `store.py` 的校验，跑通存储测试后，给 `fb-polish-ui` 发一句「存储已两种都收」。
2. `fb-polish-ui` 收到这句之前**不改发出去的东西**（保存形状、保存条件、改写别的处）；只读、只显示的改动可以先做。
3. 其余（文档、报告措辞、`round_digest`、测试补全）不分先后。

e2e 预置旧形状记录是经后端的批次接口写进临时目录的，所以旧形状不只要「读得出」，还得一直「存得进」——V2 正是这个。

后端没有别处读 `answer`：反馈状态接口、判法、变化求差都不碰它（已 grep 确认，只有 `revision.py` 两处）。

## 4. 会话一侧：循环技能的一轮

2026-11-10 用户追加的三个决定（经 team-lead 转达），本节照此写：

- 会话流程只做**一个** skill，就是规格 6.10 规划的循环技能：照标注翻出 app、处理反馈，两种输入共用一轮的骨架，定格一轮只做一次，改版报告一轮一份。
- `authoring-path2-app` 将废弃：新 skill 不交接给它、不引用它，改 app 由会话自己做；它里面还有用的技术知识由 `fb-skill` 核过后写成新 skill 自己的 reference。用户在这条线上不审批设计，只答方向题、靠 compare 和反馈验收。
- 用户选了「写进定义」之后，pattern 定义的文字只能由用户自己在页面上改（会话绝不写 `annotations/`）；会话给建议的措辞，app 可以先加上这条条件。

### 4.1 改版报告（`path2_web/annotation/revision.py`）

- 一条反馈的写法（`_fb_label`）：

  `[CRNC 2025-01-07～2025-01-30](链接) （落在 step、new_plat）「理由前 30 个字…」（f-pc-1，issue i-pc-1）`

  去掉答案；node 前由「认错的」改成「落在」；没点 node 就没有这个括号；旧记录的 `dag` 不写；旧记录没写理由的没有「」。
- issue 汇总行（`_issue_lines`）：标题「各 issue 现在：」，**不再只列共享的**——凡是有一处还在买、有一处 `lost`、或这一版有一处状态变了的 issue 都列一行（只有一处的 issue 用那条反馈的编号当名字）：

  `` - `i-pc-1`（落在 step）「理由…」：3 处，还在买 1 处，这一版变了 2 处 ``

  其余 issue 只给个数：「另有 n 个 issue 各处都不买了、这一版没变。」「变了」的口径同 ① 逐条那一段：旧状态 ≠ 新状态，上一轮没有、这一轮新标的那处也算；这一轮删掉的反馈不属于任何 issue，不进汇总行（它在上面逐条列）。
- 其余各节不动。模块说明里「报告的六节」①的描述跟着改。

### 4.2 round 文件放哪、还没有 app 时怎么定格

- **位置**：`outputs/annotation_rounds/<pattern 名>/<YYYY-MM-DD>-<n>.json`（`outputs/` 已被 git 忽略）。不放 scratchpad：scratchpad 按会话隔离，会话断了新会话找不到，「中途断掉接着做」就落空。改版报告出完后存成同名的 `.report.md`。**有 round 文件、没有同名报告 = 这一轮没走完**：新会话接着做，不再定格。`revision.py` 模块说明里「放 scratchpad」的说法跟着改。
- **还没有 app 的第一轮也在开头定格**（定格的意思不变：此后用户再改的标注归下一轮）。现在 `start_round` 靠 mapping 找 app，没有 mapping 就跑不了，所以请 `fb-backend` 加一种情形：没有任何 app 的 mapping 写了这个 pattern 时，`start_round` 照常读标注、写 round 文件（`app_id`、`app_ver` 为 null，`buys` 为空，`prev` 为 null）、打印快照，并提示「建好 app 和 mapping 后把这段写进会话段」。几个 app 写了同一个 pattern 仍然报错。对这种 round 文件调 `revision_report`：现在已经有 mapping 了 → 不报错，出一份「第一版」报告（写明没有旧版可比；用现在的 app 把全部样本的股票跑一遍，逐张给结论，相反的带链接；读不到行情的列出）；仍然没有 mapping → 报错。这样第 7 步两种情形是同一条命令，会话不用临时写脚本去逐张判。
  - 已知边角：没有 mapping 就没有地方记上一轮的定格；第一轮定格后一直没建出 app、又另开一轮时，新一轮的「上一轮」仍为空。照续跑规则（有 round 文件没报告就接着做）正常走不到，不为它加东西，函数说明里写一句。
  - 不采用「建完 app 之后再补一次定格」：那样会把用户在会话做第一版期间改的标注悄悄算进「已读」，而且留下一个没有报告的 round 文件，下一个会话会把它当成没走完的一轮。
- 第一轮的收尾：和别的轮一样——`revision_report` 的输出加会话补的那一段，存成同名 `.report.md`，这一轮才算走完。

### 4.3 新函数 `round_digest`（同文件，只读）

为什么要它：会话每轮都要把「这一轮要看的全部东西」读齐，没有现成入口时每个会话各写各的临时脚本，这正是要消掉的随机性。

```
round_digest(pattern, round_path, link_base=None, *, cfg=None, registry=None) -> str
```

- 固定在定格之后、改 app 之前调。标注取这一轮定格时的（`as_of` = round 文件里新快照的 `seen`）；状态一律用 round 文件里存的买点算（改之前的 app），不重跑 app。返回 Markdown（和 `revision_report` 成一对：会话是照着读的，编号、链接都在行里，比字典少一道转述；只此一个函数，一条命令读齐）。分节与措辞由 `fb-backend` 与 `fb-skill` 对齐，内容必须有：

  | 块 | 内容 |
  |---|---|
  | 定义 | 这个 pattern 的定义原文；它的样本的成员框用到的特征（编号、名字、定义原文）、各自对到的 node（mapping `features`），没对到的单列 |
  | mapping | app 名、`notes`；mapping 自身的问题、会话段的问题（有就原样带出） |
  | 账本 | 会话段现有的 `conditions`、`tags` |
  | 上一轮以来的变化 | `pattern_changes`（上一轮定格的状态 → 这一轮定格的状态）；没有上一轮时为空并注明 |
  | issue | 按 issue 分组（带同一个 `issue` 值的为一组，不带的各自一组，只看 `picked`）。每组：名字、`nodes`、`note` 全文、账本里 `from` 含它任一处编号的条件行；各处：编号、股票、起止、`target`、状态（读不到行情另注）、会话标签、范围里哪几天在买、范围里用户自己的正样本日、落在 compare 的链接、相对上一轮是新标的还是内容改过。有处还在买的组在前，有 `lost` 的其次 |
  | 样本 | 这个 pattern 的**全部**样本，和 app 相反的（正样本没买到、负样本买了）排前；每张：编号、股票、样本日、judgment、note、结论（一致 / 相反 / 没比）、链接，以及它收的成员框（编号、特征名、起止、属性、note）；另给一致、相反、没比的张数。带成员框是因为照标注翻 app、判断一张相反的样本卡在哪，都要看它收了哪些框 |
  | 没比的 | 读不到行情的股票 |

- **旧记录的 `answer`、`dag` 不输出**（连「仅供参考」也不带：用户已定这个标签不作数，带出来就会有人拿它归类）。
- 还没有 app 的 round 文件：照样返回定义、变化、样本清单；mapping、账本、issue、状态各块为空并注明没有 app。
- 不写 mapping、不写标注。

### 4.4 一份处理清单，按去向分三段

位置：读齐输入之后、改 app 之前。两种输入（标注里的样本与特征、反馈的 issue）放进**同一份清单**，按「接下来会发生什么」分三段——用户只需要知道：哪些会话直接改、哪些要自己定、哪些这一轮不动。一轮只改一版 app，所以清单一次给全，题答完再一起动手。

| 段 | 放什么 | 用户要不要选 |
|---|---|---|
| 一、我这一版直接改 | issue：app 认得比用户的定义松（定义里已有这句话，app 没查或查得松）；样本：和 app 相反、毛病是结构性的；还没对到 node 的新特征（打算对到哪个 node，或新加哪一块） | 不用 |
| 二、要你定 | issue：理由成立，但定义里没有这一条；样本：和 app 相反、会话拿不准的；规格 6.14 规定要问的标注改动（改判、定义文字变了、反馈范围里出现了正样本） | **要** |
| 三、这一轮不改 | issue：当天看不出 / 只差门槛 / 量过不值得加；样本：只差门槛的 | 不用，但可以反对 |

- 归到哪一段是会话的判断，skill 不教；skill 只规定每条必须写什么、怎么问、怎么记。
- 一个 issue 可以拆开：能翻成当天条件的部分归一或二，条件挡不掉的那几天归三。
- 归类只看 note、node 和用户的定义。**旧记录里的 `answer`、`dag` 不拿来归类**（`round_digest` 本来也不带）。
- 「量过不值得加」只在确实量过时才能给；量归 `feature-study`，循环里不量。
- 清单里的「代价」只报买点个数一类的事实（挡掉几天、范围内外各多少），不报收益（规格 6.6：训练段成绩只在三种时候给）。

**给用户看的格式**（一条消息；issue 用理由原话指代，样本用「股票 + 日期」指代，不出现内部字段名）

```
这一轮：你标了 N 个 issue（M 处），和 app 相反的样本 K 张，新特征 J 个。

一、我这一版直接改（a 条）
1. 「<理由原话>」——3 处（[CRNC 2025-01-07～01-30](链接) 等），落在 <node 对到的你的特征名>
   - 你的定义：「<定义里的原话>」
   - app 现在：<一句白话，眼下怎么查的>
   - 我打算：<一句白话，改成怎么查>
2. 正样本 [AAPL 2024-03-08](链接) 没买到：<一句白话，卡在哪>；我打算：<……>
3. 新特征「<特征名>」：<打算让 app 的哪一块去认，一句白话>

二、要你定（b 条，下面逐个问）
4. 「<理由原话>」——1 处（链接）
   - 你的定义里现在：<有关的原话；完全没提就写「没有提到」>
   - 写进定义的话：会多查一条「<翻成的当天条件，白话>」，这一类以后都不买

三、这一轮不改（c 条）
5. 「<理由原话>」——2 处（链接）：当天看不出——<一句理由>。不同意就告诉我。
```

**选择题**（只对第二段，用 AskUserQuestion；一轮 3～5 题以内，多了挑最要紧的，其余当「先放着」留到下一轮）

- 问题正文用白话写清三件事：在哪几处说了什么；现在的定义怎么说；选了各会怎样。会话推荐的放第一位、标签末尾加「(推荐)」。
- 「定义里没有这一条」的 issue，选项固定三个：

  | 选项 | 选了会怎样 | 记账 |
  |---|---|---|
  | 写进定义，这种以后不买 | 会话给出建议的措辞，请用户自己贴进页面上的 pattern 定义；这一版 app 先加上这条条件，初始门槛按这句话的字面意思取 | `conditions` 加一行，`state` 以 `unmeasured` 开头并写明出自哪个 issue、用户哪天同意；mapping `notes` 给这条条件写上用户原话 |
  | 不写，这种可以买 | app 不改，这几处继续买 | 各处挂 `accepted`；翻得出候选条件的，`conditions` 记一行，`state` 以 `declined` 开头 |
  | 先放着 | 这一轮不动，下一轮再问 | 各处挂 `unhandled` |

- 用户改完定义后，这次改动落在下一轮的「上一轮以来的变化」里；账本里那行写明了出处，下一轮认得出是它，不再为它出「定义文字变了」那道题。
- 其余题（样本拿不准、改判等）的问法照规格 6.14、6.1 现有的规定，本设计不新增。

### 4.5 账本怎么记（不加新结构）

`mapping.yaml` 会话段仍是 `snapshot` / `conditions` / `tags` 三样，形状校验不动，`SESSION_TAGS` 不动。

- `conditions` 每行 `{where, from, state}`：
  - `where`：改动落在 app 的哪里——`node.where 名`、边，识别器或拓扑层面的改动写 node 名；还没进 app 的候选条件写拟用的名字（这个键本来就不对着 app 查）。
  - `from`：这个 issue 当时各处的编号（由样本推出的写样本编号）。
  - `state`：自由文字，**开头用下面五个词之一，后面可以跟一句理由**：

    | 开头词 | 意思 | 条件在不在 app 里 |
    |---|---|---|
    | `from_definition` | 照用户定义里已有的话改的 | 在 |
    | `unmeasured` | 用户同意新加的条件，还没量 | 在 |
    | `declined` | 用户说不写进定义 | 不在 |
    | `for_tuning` | 条件已有，只差门槛，留给调参 | 在 |
    | `not_worth` | 量过，不值得加 | 不在 |

    `from_definition` 只记出处这个事实；这类条件送最后检查之前要不要也量一遍，本设计不定（最后检查还没实现），列给用户。
  - 连条件都翻不出来的（纯「当天看不出」）不记行，只挂标签，理由留在改版报告里。
- `tags`：改完 app 之后，还在买或 `lost` 的每一处反馈都要有标签，没有的补 `unhandled`；已经不买的处删掉它的标签（`redefined` 除外，它说的是定义、不随 app 变）。（待验证）
- 「哪些 issue 处理过」由这两处推得出：编号出现在某行 `from` 里，或它还红着的各处都有标签。
- 写完用 `read_mappings` 核一遍会话段没写坏。

### 4.6 改版报告之后会话自己补的一段

接在 `revision_report` 的输出后面，一起存进 `.report.md`、一起给用户；给用户时前面先用几句白话讲「改了什么、说明什么、不说明什么」。条目与 4.4 的清单一一对应：

```
## 这一版按清单做了什么
1. 「<理由原话>」：<改了什么，一句白话>。3 处里现在还买 1 处（链接）——<为什么还买 / 下一步>
2. 正样本 AAPL 2024-03-08：现在买到了。
4. 「<理由原话>」：你选了不写进定义，没改。
5. 「<理由原话>」：这一轮没改——当天看不出。
```

- 每条 `lost` 仍要在报告留的那一行里交代是改好了还是认法变了。
- 样本结论被这一版改坏的（原来一致、现在相反）必须点名，并说打算怎么办。
- 「改好了」只按报告里的新旧对照说。

### 4.7 一轮的顺序（skill 照这个写）

0. **认对象，判断新开还是续跑**：pattern 名；`outputs/annotation_rounds/<pattern 名>/` 里有 round 文件、没有同名报告 → 续跑，从没做完的那一步接着做，不再定格。
1. **定格**：`start_round`；有 mapping 时立刻把打印的快照写进会话段（只替换 `snapshot`）。此前不碰 app 的任何文件。
2. **读齐输入**：`round_digest`。
3. **出处理清单**（4.4）。
4. **出题**：只对第二段；没有第二段就不停。
5. **改 mapping 和 app**：第一段全部 + 第二段里用户同意的。会话自己改，写 app 的技术知识读 skill 自带的 reference。要新写或改识别器 → `authoring-path2-detector`；说不清为什么认成这样 → `diagnose-event`；只差门槛 → 不拧。新条件的初始门槛按用户那句话的字面意思取；mapping `notes` 给新条件写上用户原话。
6. **自查**：app 构造通过；mapping 没有问题（含会话段）、用到的特征都有一行或明说还没对上；这一轮涉及的股票都跑得通。
7. **改版报告**：`revision_report` → 填 `lost` 行 → 补 4.6 那一段 → 存 `.report.md` → 给用户。
8. **记账**（4.5）。
9. **交还用户**：刷新页面再看；等他做的事（把建议的那句话贴进定义、过目范围外砍掉的、不该砍的那天用 `point` 放正样本、新毛病继续标反馈）。不提交。

**还没有 app 的第一轮**走同一个骨架，差别只有：

| 步 | 第一轮 |
|---|---|
| 1 | 照常定格（4.2 的无 app 情形）；快照先留在 round 文件里 |
| 2 | `round_digest` 只有定义、样本、变化为空 |
| 3、4 | 清单里只有「照标注怎么翻」的条目和方向题 |
| 5 | 新建 app 和 mapping，把第 1 步的快照写进会话段 |
| 7 | 同一条命令；出的是「第一版」报告（没有旧版可比，逐张给样本结论，4.2） |

## 5. skill

- **名字**（待用户认）：`annotation-round`，放 `.claude/skills/annotation-round/`。名词短语「一轮标注迭代」；round 与代码里的 `start_round`、round 文件同一个词。
- **description 的触发词**由 `fb-skill` 定，只取用户会说的：「看看我的标注」「处理一下反馈」「根据我标的改一版」「我又标了几处」「新一轮」「接着上一轮」「照我的标注做个 app」。不放 `round_digest`、`start_round`、`mapping.yaml`、round 文件这类内部词。
- **管什么**：4.7 的顺序、每步的产出与给用户看的格式（4.4、4.6）、怎么记账（4.5）、禁忌；写 app 的技术知识（声明层契约、参数落地、`eval_meta` 铁律、识别器选型等）放在自己的 reference 里，改 app 那一步才读。
- **不管什么**：一句 note 该翻成什么条件、几个 issue 是不是同一件事、一条该归清单的哪一段——这些是会话的判断。
- **不依赖 `authoring-path2-app`**：不交接、不引用它的任何文件；把它删掉之后新 skill 必须照样完整可用。它的三层逐层确认、交给 plan mode、网页看图确认、入口分诊都不搬。
- **全池的改前基线与回归对拍不进循环**：每轮必出的对照只有改版报告（只看标注过的股票，不带收益）。带收益的成绩一律照规格 6.6 的三种时候给，走 `tune-gates-v3` / `feature-study`，循环里不主动给。改动碰到别的 app 也在用的公共识别器时，回归义务照 `authoring-path2-detector` 自己的规定。
- **规格写了但还没实现的**（定级、⚑、盲看清单与理由归类、页头 `next` / `edited n`、按收益量一条条件的生产工具、最后检查）：只在一处列明「尚未实现，本 skill 不做」，不为它们写流程。
- **交接点**：

  | 遇到 | 转给 |
  |---|---|
  | 要新写或改识别器、给事件加字段 | `authoring-path2-detector` |
  | 要弄清某一处为什么认成这样、为什么这天买了 | `diagnose-event` |
  | 只差门槛 | 本轮不拧，挂 `for_tuning`；用户要调时转 `tune-gates-v3`，调完回来用同一对函数出报告 |
  | 一条条件按收益值不值 | `feature-study` |

### 9.4 独立审读之后的补充（2026-11-10 晚）

来源：一名没有任何背景的只读审读者（不读研究目录）照 skill 的文字走了一遍，指出 12 处；复审时又发现同类的 1 处。都已改进 skill，其中两处同时改了后端与规格。与 9.3 冲突处以本节为准。

- **G1（定格之前分不清有没有 app 的三种情形，都不能当成「还没有 app」）**：
  - app 在磁盘上、但没注册上（导入失败或缺 `eval_meta`），它的 mapping 写的是这个 pattern；
  - 已注册的 app，它的 `mapping.yaml` 读不出 pattern（YAML 写坏，或 `pattern` 那一行丢了——会话每轮手写会话段，写坏一个引号就是这种状态）；
  - 几个 app 的 mapping 写了同一个 pattern（原来就拦）。
  把有 app 的 pattern 当成没有 app 去定格，旧版买点没存下、上一轮的快照也读不到，这一轮再也补不回。两道闸：skill 第 0 步用只读脚本 `scripts/round_state.py` 认出前两种（第一种告诉用户停下、不动手修；第二种先把那个 `mapping.yaml` 修到读得出，只动它）；`path2_web/annotation/revision.py` 的 `start_round` 在走「没有 app」分支之前加了兜底 `_ensure_no_app`，两种都报 `ValueError`、不写 round 文件。
- **G2（红线 1 补半句）**：第 1 步做完之前不改任何 `.py`，哪怕它有毛病。定格前只许修 `mapping.yaml`（会话段写坏、整个文件读不出）；mapping 的其它问题（特征或说明指向不存在的 node / where）不拦定格，留到第 5 步和 app 一起修。
- **G3（第 1 步）**：定格命令报错一律不重试、不换文件名，去向写成表（文件已存在 → 按续跑走；会话段写坏 → 修会话段再定格；几个 app 写同一个 pattern → 告诉用户停下；旧版 app 在某只股票上跑崩 → 不改 app，告诉用户停下）。完成标志改用 `round_state.py <R>` 核对：「快照已写进会话段: True」，且会话段的 `conditions`、`tags` 条数与定格前一样。原来的标志（会话段问题为 None）在没有会话段时是空转的。`start_round` 遇到文件已存在时的报错不再建议换文件名。
- **G4（第 0 步新增一种停下问用户的情形）**：会话段里已经有快照、却找不到任何 round 文件（换过工作目录或清过 `outputs`）时，先问用户上一轮走完了没有；没走完的那一轮对照已经丢了，照新开一轮走，并在清单第一行说明。
