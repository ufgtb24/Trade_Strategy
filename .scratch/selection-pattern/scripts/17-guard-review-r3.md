## 一、会污染判决或卡住正常使用（建议放行前修）

**新发现 1：规则核对分不出好坏规则（A3）**（已实证；复核子任务用合成数据跑了实验 R1、R2、R3）

- **在哪**
  - chart_workflow/rulecheck.py:158：只比「卡说成立」和「规则这一天成立」是否一致。
  - chart_workflow/rulecheck.py:162：只在一个样本都没核对上时拒绝。
  - chart_workflow/ledger.py:277-282：只查核对结果里来源对得上、声明非空。
- **怎么触发**
  - R1：卡上的样本都是用户的正例，卡上要素在这些天全成立。一条永远返回「成立」的规则，照抄卡上的要素声明，就能通过核对。
  - R2：卡上 3 个样本，一个不是交易日，一个早于看图下界，都被跳过；只核对了 1 个，照样通过。
  - R3：不走对照页命令，直接在 Python 里调记账函数，手填一份来源对得上、声明是假内容的核对结果，被收下。账本把这一轮的条件来源记成「你说的 1、事实表 1」。
- **后果**：一条和形态卡无关的规则，只要抄一份声明，就能在账本里记成「来自用户的形态」，而 A3 要守的正是这件事。
- **严重度**：高，直接污染来源记账。R3 属于有意绕开；R1 不需要任何恶意，一条宽松的规则就会碰上。
- **建议修法**
  1. 核对加反例：在样本的同一只股票、买点前后各取若干天，卡上要素判「不成立」的那些天，规则也必须不成立。也可以在样本股的全部训练日上，要求规则信号和「卡上要素全部成立」高度一致。
  2. 设一个最少核对个数（例如 3 个，或样本数的一半，待验证）；跳过的比例过高也拒绝。
  3. 记账时由账本自己重跑一次核对，不信调用方传来的结果。

**新发现 2：别的分支用合并提交合过 wayfinder 之后，wayfinder 下一次记账起，看图工具全部停下（B1 新引入）**（已实证；在真实仓库的共享只读克隆里做的，克隆已删）

- **在哪**：chart_workflow/state.py:443-449。只看「别的分支上有没有改过记账目录、又不在当前分支里的提交」，不看内容。
- **怎么触发**
  - 前提：某个本地或远端分支用合并提交（不是快进）合了 wayfinder。例如在 GitHub 上用 PR 把 wayfinder 合进 master，或者某个 worktree、后台 agent 的分支为了同步代码执行了 `git merge wayfinder`。
  - 之后 wayfinder 只要再提交一次记账文件，那个合并提交就被当成「别的分支上有更新的账」。
  - 实测过程：合并后立刻查，不拦；wayfinder 再记一次账，就拦。master 和自建分支两种情形都复现了。
  - 把那个分支合回 wayfinder 之后，才解除。
  - 快进合并不触发。现在 master 是 wayfinder 的祖先，所以真实仓库眼下不拦。
- **后果**
  - 那个合并提交里的账 wayfinder 全都有，并没有分叉，却一直停着。
  - 提示让用户「先把它们合进当前分支」：为了解锁，要么把那个分支的无关代码合进 wayfinder，要么把分支删掉，远端的也要删。
  - 每做一次 PR 式合并，就得再合回一次。
- **严重度**：中高。不污染判决，但 PR 合并和 agent 分支同步都是日常操作，会反复卡住正常使用。
- **建议修法**：按内容判。对有这类提交的分支，比较它和当前分支在记账目录下的文件：只追加的文件，在那个分支上的内容都是当前分支版本的开头一段；清单文件当前分支都有而且相同。满足这两条就不算分叉，只有那个分支上有当前分支没有的账才停。

**新发现 3：在对照页放大或标注过同一条（同股同日），回到大涨段清单标注时，只记成「在清单里出现过」（A1）**（已实证，合成数据）

- **在哪**：chart_workflow/views.py:287-289。看过记录里只要条目编号和这一条相同，除了往右拖以外一律跳过，不管是哪份清单的记录。
- **怎么触发**
  - 条目编号就是「代码@日期」（chart_workflow/listfile.py:155），各类清单共用同一套编号。
  - 对照页的结果是公开的。规则如果来自用户的形态卡，就会在用户的样本日上触发，所以同一条很可能出现在对照页里。
  - 用户在对照页放大看过 X@d，下一轮大涨段清单里又有 X@d。用户标注时，实测只记成「在清单里出现过」，「仔细看过」一栏为空。
- **后果**：按用户的口径，「在清单里出现过」不算看过。这条标注等于被记成干净的考题，而用户其实放大看过它的结果。
- **严重度**：中。有条件，但条件就在「形态卡 → 规则 → 对照页」这条正路上。
- **建议修法**：跳过「自己这一条的单张图事件」只限同一份清单，或者只限大涨段清单露出结果之前；别的清单里同一条的单张图事件，照常记成「仔细看过」。补一个测试。

**新发现 4：旧大涨段清单按整份清单补记时，对同一条完全不算，对同股的别的条目只算露出结果前那一小段（A1，和第二轮 B11 的补记相关）**（已实证，合成数据）

- **在哪**：chart_workflow/views.py:240-243、287。代码假定大涨段清单的记录都是「结果藏到露出那一刻」，但 r001～r004 是旧界面生成的，当时结果全程可见。
- **怎么触发**
  - 合并时照第二轮的建议，给旧清单补记一条「打开整份清单」（补记、清单类型是大涨段）。
  - 之后在新清单里标注同一条：完全不算。
  - 同股、不同日的条目：只按「决策日后 15 个工作日」截断后算。
  - 逐张补记「看了这张图」，才会记成「仔细看过」（实测）。
  - 另外，这个痕迹是在标注提交那一刻算好存下的；补记晚于标注，已存的标注不会回头更新。
- **后果**：第二轮报的「新一轮 176 条里有 110 条在旧界面下结果可见」，这一批如果补记方式不对，会全部漏记。
- **严重度**：中。可以靠合并时的固定做法规避，但改代码更稳。
- **建议修法**：补记的记录一律不截断、也不跳过同一条；或者补记时给旧清单标上「当时结果可见」，代码据此不截。不管修不修，合并时都要先补记、再开始标注新清单。

## 二、有条件才触发，或者较轻

**新发现 5：调试视图里留下的峰事件，用「峰价 ÷（1 + 相对高度）」能精确算出下界之前某一根的最低价（A4）**（已实证，合成数据；低～中）
- **在哪**：峰事件在 path2/atoms/breakout.py:584-590 生成。相对高度 =（峰价 − 前 20 根最低价）÷ 前 20 根最低价。删减时，留下的事件字段原样保留。
- **怎么触发**：峰在下界之后，所以事件被留下；但它往回看的 20 根盖到了下界之前。12 只合成股做预览，留下 52 个峰事件，其中 2 个按上式算出的数，和下界前某一根的最低价完全相等。
- **后果**：每只股票最多露出下界前一两个最低价。界面上不显示，只在接口返回的数据里。
- **建议修法**：峰的回看窗起点早于下界时，把相对高度置空；补一个测试，要求留下的事件里没有任何派生值能和下界前的价格精确对上。

**新发现 6：直接写日志的凭据谁都能拿，再走一次正常写入就落盘，账本照信（B3、B5）**（已实证，实验 R4；有意绕开）

- **怎么触发**
  1. 拿这个凭据直接写一条「用户说的、不带原话」的要素。
  2. 再走一次正常的决定文件，只给它挂个别名，它就按日志重算写进了盘。

  4. 只有手动跑「重算并逐字比对」才报出来。

**新发现 7：挨着合理范围边缘的阈值照样收（B4）**（已实证，实验 R5）

## 三、主会话点名的五个重点

**（1）调试视图按 _idx 结尾的字段找锚点，会不会漏**
- 复核子任务把 path2/atoms 下全部 12 个事件类型、三个现役 app 逐个过了一遍，三个 app 都没有自定义事件。
- 没有哪个事件把「自己最早那根 bar」放在不以 _idx 结尾的字段里，按现有规则不会漏删。
- 名字不以 _idx 结尾、但指向别的 bar 的字段有两类：距离（距峰根数、距上次突破根数等）和带 bar 序号的编号。它们只露位置，见新发现 9。
- 能反推价格的只有峰事件的相对高度，见新发现 5。
- 留着的其他字段（平台上下沿、参考价等）都没找到能精确对上下界前价格的。
- 以后新加的事件如果把 bar 位置放进别的名字，就会漏；这是命名约定，没有测试守着。

**（2）露出结果的两级记法：估计真的只会偏宽吗，有没有绕开的路**
- 不是只会偏宽：节假日让估计偏窄，最多偏 2 天，影响小，见新发现 8。
- 对照页：同股不同日的条目会记成「仔细看过」；同股同日的同一条只记成「在清单里出现过」，见新发现 3。
- 聊天、补记
  - 聊天贴图、逐张补记「看了这张图」：记成「仔细看过」，实测正确。
  - 旧大涨段清单按整份补记：漏记，见新发现 4。
  - 补记晚于标注不回头更新，也在新发现 4 里。
- 同一秒：同一秒的记录算在露出结果之前，方向是保守的。
- 前端传来的值：服务端不采信，模型里也没有这个字段，查过没问题。

**（3）rulecheck 只有一个能核对的样本时会不会放行；app 路径和手动记账能不能绕开**
- 一个样本也放行，而且挡不住永远成立的规则，见新发现 1。
- app 那条路的信号是真跑 app 算的，但测试只测了「读声明」，建造方自己也承认。
- 手动的 ledger add 命令拿不到核对结果，这条确实挡住了。直接调记账函数、手填一份假核对结果，能收下（新发现 1 的 R3）。

**（4）「别的分支上有更新的账」会不会误拦正常使用**
- 用的是真实仓库的共享只读克隆，实验后已删。
- 不拦的情形
  - 现在的真实仓库。
  - 把 annotation-stage0 合进 wayfinder 之后，在 wayfinder 上提交记账文件。
  - 从别的 worktree 运行：检查用的是主目录当前所在的分支，worktree 自己在哪个分支不影响。
  - 别的分支只改代码、或只改标记文件。
  - 当前分支领先别的分支。
- 正确地拦的情形
  - 另一台机器记了账，推到 origin，本机 fetch 了但还没合进来。
  - 主目录切到了一个没有最新账的分支。
  - 旧分支上提交过记账文件。
- 误拦的情形：别的分支用合并提交合过 wayfinder 之后，wayfinder 下一次记账起一直停，直到把那个分支合回来或删掉。会反复卡住正常使用，见新发现 2。

**（5）还有没有新路，能借要素合并或重算校验把系统推荐洗成用户来源**
- 合并这条路关死了：定义不同就不许并；账本按卡上记下的要素编号和版本取来源，不跟合并走。
- 新路一：直接写日志的凭据公开，再加一次正常写入就落盘，账本照信，见新发现 6。
- 新路二：旧日志里遗留的同义重复，合并方向由会话选，见新发现 12（推测，现在主目录没有操作日志）。
- 反方向（用户来源少算）见新发现 15，不算洗来源。

## 六、结论：不建议放行

**必须修的 3 处（都是局部改动）**
1. **规则核对要分得出好坏规则（新发现 1）**
   - 加反例核对：样本股在买点前后、卡上要素不成立的那些天，规则也必须不成立。
   - 设最少核对样本数，例如 3 个，待验证。
   - 记账时由账本自己重跑核对，不收调用方传来的结果。
2. **「别的分支上有更新的账」按内容判，不按提交判（新发现 2）**：那个分支上的账当前分支全都有（只追加的文件是当前版本的开头一段），就不拦。否则 PR 式合并之后，看图工具会反复停下。
3. **同一条在别的清单里被仔细看过，要照常记成「仔细看过」（新发现 3）**：跳过自己单张图事件，只限同一份清单。

**二选一：改代码，或者合并时按固定做法规避（新发现 4）**
- 改代码：补记的记录不截断、不跳过同一条。
- 不改代码：合并时给旧清单 r001～r004 逐张补记「看了这张图」，不按整份清单补记。
- 无论选哪个，都要先补记、再开始标注新清单。

**建议顺手修，不挡放行**
- 峰事件的相对高度：回看窗跨过下界时置空（新发现 5）。
- 露出前估计改用真实交易日，或者放宽到 20 个工作日（新发现 8）。
- 补新发现 14 的三个测试。
- 正常写入和账本取数前，先重走全部日志的校验（新发现 6）。
- 根数上界按实际窗口算（新发现 7）。
- 角色记成「你定的」也要原话（新发现 11）。

**合并时要做的事（主会话做，请用户确认）**
- 旧账迁移（第二轮 B11）：旧日志里如果有定义不同的合并，现在重算会报错、拒绝覆盖磁盘。
- 旧清单补记，按上面的做法和顺序。
- 主目录现有的 2 个扫描没有副本指纹，打不开，要重扫。

- 调试视图算出 2025 年成绩算不算一次尝试，请在票 16 写明（新发现 10）。
