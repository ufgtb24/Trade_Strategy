# 03 · 与本项目结合：AI 文档结构该不该换、superpowers 怎么退、分几步走

> 本文回答三个问题：① 现在的 `.claude/docs/` 体系要不要被 grill-with-docs 的 `CONTEXT.md` + ADR 替换；② 从 superpowers 切到 mattpocock 主链，每个环节对应什么、哪些没有对应；③ 建议的迁移顺序。
> 结论先行：**不是替换，是嫁接**。`CONTEXT.md` 和 ADR 补的是本项目现在**没有**的两样东西（正式术语表、决策记录），`.claude/docs/` 里的架构摘要在 mattpocock 体系里没有对应物，保留。
> 本文所有项目内路径均相对 repo root。

## 2. 逐项对应：本项目现有物 ↔ mattpocock 体系

| memory 里的 `feedback_*`（怎么和你合作） | `CLAUDE.md` 散文 | 作者「Config is death」：偏好写进 `CLAUDE.md` | 保持在 memory，那是你私人的 |
| 项目 skill（authoring-path2-app 等） | 无对应 | 完全正交 | 保留 |
| `write-user-doc` / `update-ai-context` | 无对应 | 正交 | 保留；`to-spec` 不替代 `write-user-doc`（研究报告仍走后者） |

### 2.1 所以「该不该替换」的答案

**`.claude/docs/` 不该被替换**，理由三条：

1. mattpocock 体系里**没有**「架构意图摘要」这一层。它假设 agent 靠读代码 + 一份纯术语表 + 几条 ADR 就够。对一个几千行、单人维护、有 dag 求解器和剪枝红线的框架，`modules/path2.md` 这种「为什么这么设计」的摘要是有独立价值的，删了 agent 就得每次从代码重推。
2. `CONTEXT.md` 是**术语表且只是术语表**。它装不下 `glossary.md` 第 2 到 9 节的实现细节，而那些细节对本项目的 agent 很有用（比如 c1_off 的五个来源）。硬塞进去就是官方警告的「CONTEXT.md 膨胀成 spec」。
3. `CLAUDE.md` 已经定了「`.claude/docs/` 只反映当前代码状态、与代码冲突以代码为准」。ADR 恰恰是**历史决定**，「为什么当时这么选」，性质不同，放 `docs/adr/` 而不是 `.claude/docs/` 正好各归各位，不冲突。

**该新增的是两样**：根目录 `CONTEXT.md`（从 glossary 第 1 节 + 各节的概念定义抽出来）和 `docs/adr/`（回填历史硬决定）。这两样是本项目现在缺的，也是 grill-with-docs 真正带来的增量。

`docs/README.md` 的分工表要加三行：`CONTEXT.md`（术语表，`/grill-with-docs` 维护）、`docs/adr/`（决策记录，同上）、`.scratch/`（spec 与票，`/to-spec` `/to-tickets` 维护），并把 `docs/superpowers/` 标为历史。

## 4. 一处真实的方法论张力：「单 session 跑完」vs「每票一个新会话」

你在 `.claude/rules/plan-execution.md` 和 memory 里反复定过：**默认不拆 plan，一份 plan 单 session 无监管跑完**，靠 subagent-driven 的 task 级隔离扛上下文，只有「前段结果大分叉迫使后段重写」才拆。

mattpocock 的 `to-tickets` 走另一条路：每张票的大小就是「**一个新的上下文窗口装得下**」，`/implement` 每票 `/clear` 一次，票是自包含的。它的理由是 phase boundary 那棵树：实现阶段不需要访谈阶段的原文，所以 clear 不丢东西。

两者其实在解决同一个问题（上下文会爆），只是隔离的粒度不同：

| | superpowers（你现在） | mattpocock |
|---|---|---|
| 隔离单位 | task，每 task 一个 fresh subagent | ticket，每 ticket 一个 fresh 主会话 |
| 主会话持有什么 | 整份 plan + 每个 task 的薄摘要 | 只有当前这一张票 |
| 跨 task 状态 | 写进文件 + plan 自包含 | 写进票（票之间靠 Blocked by 和 spec 联系） |
| 人的介入点 | 计划审完后基本无监管 | 每票开一个会话（可以脚本化，但作者的默认是人来开） |
| 每 task 双审 | 有（spec 审 + quality 审） | 无，只有末尾一次 code-review |

对本项目的建议：**不必二选一**。`to-tickets` 切出来的票本来就是「一个上下文窗口装得下」的粒度，正好等于你现在 plan 里的一个 task 或几个 task 的合集。你可以：

- 让 `/to-tickets` 切票（获得它「垂直切片、不写代码、声明阻塞」的好处）；
- 然后在**一个**主会话里，把票当 task 清单，按阻塞顺序把每张票派给 fresh subagent 做（保留你 subagent-driven + 双审 + 单 session 无监管的习惯）。

两个硬约束要先知道：① `/implement` 带 `disable-model-invocation: true`，**子代理调不到它**。上游原话是别的 skill 也调不了它，文档里凡是说「然后每票 /implement」都是说给人听的。所以子代理的 prompt 里要直接写 implement 的那五步（读票 → 在约定接缝上 TDD → 常跑类型检查与单文件测试 → 最后全量 → 提交），不要让它去敲斜杠命令。② 上游明说**没有**批量派发和子代理扇出，同一个 checkout 里并行跑几张票会撞坏 git 状态；按阻塞序串行跑，或者每张票一个 worktree。

这需要在 `CLAUDE.md` 写一段自定义的「本项目 implement 约定」，替代 mattpocock 五句话的 `/implement`。skill 是 markdown，作者鼓励这么做。

## 5. superpowers 插件的去留

现在 `enabledPlugins` 里 superpowers 是开的，它的 SessionStart hook 每次注入「1% 规则」和「创造性工作前必须 brainstorming」。两套并存的问题只有一个：**触发冲突**。你敲 `/grill-with-docs`，它可能先要跑 brainstorming。

三个档位，按激进程度：

| 档位 | 做法 | 适合 |
|---|---|---|
| **共存**（试用期） | `CLAUDE.md` 加一句：「显式调用 mattpocock skill 时不触发 superpowers 的 brainstorming / writing-plans / executing-plans」。`using-superpowers` 自己写明用户指令优先 | 前两三个功能，跑通主链、看效果 |
| **禁用**（决定切换后） | `/plugin` 里把 superpowers 关掉，或 `settings.json` 的 `enabledPlugins` 置 false；插件仍在缓存，随时能开回来 | 主链已经跑顺 |
| **卸载** | `claude plugins uninstall superpowers` | 确定不回头 |

禁用前要把 superpowers 里**没有 mattpocock 对应物、但你在用的**四条纪律迁进 `CLAUDE.md`，每条一两句话就够：

1. 完成前先跑验证、拿到输出再说「做完了」（verification-before-completion）；
2. 收到评审意见先技术核实、不表演性同意（receiving-code-review）；
3. 每 task 的 Implementer 用 sonnet、Reviewer 用 opus（你自己的约定）；
4. 派子代理时的工具调用纪律片段（已在 `.claude/rules/tool-call-discipline.md`，不用动）。

`ralph-loop` 和 mattpocock 不冲突，按 memory 里「只在 cycle 超大 / 高重复时用」照旧。

## 6. `CLAUDE.md`「使用 superpowers」节的改写方向

那一节现在八条，按主题并成六组看去留：

| 现有条目 | 处理 |
|---|---|
| brainstorm 提问带倾向、推荐置首标「(推荐)」 | grilling 每题自带 ➡️ 推荐，**天然满足**，可删或改成「grilling 的推荐答案请附一句理由」 |
| 永远附子代理选项（fork / general-purpose 裁定） | **与 grilling「决定归用户」冲突**。要保留就明确写成用户指令：「grilling 中我可以指定某题派 fork 子代理从第一性原理分析后再由我拍板；子代理只出论证不出决定」。这样不违背原则（最终仍是你拍板） |
| 自动模式（不中断问我，倾向强就直接采用，不确定就派子代理定） | **与 grilling 冲突最大**。grilling 的产出质量绑定在你的回答上，自动模式等于让 agent 自问自答。建议**只在 `/implement` 阶段保留自动模式**，访谈阶段不用；或者明确写「自动模式下 grilling 仍必须等我答，只有实现阶段的疑问才自决」 |
| subagent 模型选择（Implementer sonnet / Reviewer opus） | 保留，改写为「`/implement` 时…」 |
| 计划自包含 + 路径相对 repo root | `to-tickets` 不写路径，前半条自动满足；「spec 顶部声明路径相对 repo root」这句保留给 `.scratch/*/spec.md` |
| executing-plans 默认 subagent-driven、plan 尽量不拆 | 改写成 §4 的「票由 to-tickets 切，实施在单会话按阻塞序派 fresh subagent」 |

改完这一节的标题就不该再叫「使用 superpowers」了，直接改成「## 使用 mattpocock 主链」，§5 里要保住的四条纪律也并进这一节。

## 7. 建议的迁移顺序（每步可独立停下，不动现有东西）

| 阶段 | 做什么 | 产出 | 风险 |
|---|---|---|---|
| **0 · 装 + 配** | `claude plugins install mattpocock-skills`；`/setup-matt-pocock-skills`（本地 markdown tracker、单上下文）；`CLAUDE.md` 加共存那一句 | `docs/agents/*.md`、`CLAUDE.md` 的 `## Agent skills` 块 | 零。不动任何现有文件 |
| **1 · 建术语表** | `/grill-with-docs help me scaffold my existing repo with a CONTEXT.md`，以 glossary 第 1 节为种子，几十题起步，有人报告 50+ | 根目录 `CONTEXT.md` | 低。产出要你逐条审，官方警告「未审阅的 agent 术语表比没有更糟」 |
| **2 · 回填 ADR** | 一次会话，把 5 到 8 条历史硬决定按三道门槛过一遍。先定一条口径：ADR 收「为什么这么选」，memory 收跨会话的工作状态与进度指针；两者重叠时以 ADR 为准，memory 只留一行指针 | `docs/adr/0001..000N` | 低 |
| **3 · 跑通一条真主链** | 挑一个一个会话能谈完的真需求（比如 tb 破位闸、或 pk 应用层的 spec），走 grill → to-spec → to-tickets → implement → code-review 全程 | `.scratch/<feature>/` 一整套 + 代码 | 中。这一步暴露 §4 的张力，据此定 `CLAUDE.md` 的 implement 约定 |
| **4 · 改 `CLAUDE.md`** | 按 §6 改写「使用 superpowers」节；补 §5 的四条纪律；`docs/README.md` 加三行 | | 低 |
| **5 · superpowers 退场** | 禁用插件；观察两三个功能；确认无缺再卸载 | | 可逆 |
| 持续 | 每次 `/grill-with-docs` 增量维护 `CONTEXT.md`；每季度一次瘦身；`glossary.md` 第 1 节退役（指向 `CONTEXT.md`）；`update-ai-context` 继续管 `modules/*.md` | | |

阶段 1 和 2 可以合并成一个会话，但官方经验是冷启动术语表本身就要 50 题，合并会撞「范围太大」的坑，分开更稳。
