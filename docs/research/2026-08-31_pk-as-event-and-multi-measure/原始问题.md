## 拆解（不改变原意，仅供分工）

**Q1 · pk 出 stream 成为 event**
- 合理性：第一性原理下，pk 是不是一个「事件」？把 detector 内部状态提升为一等 Event 是否语义正当？
- 可行性：对 path2 协议（Event/Detector/dag）、显示层（marker 统一）、dag_spec 下游消费（where/edges/match）的影响。
- 用户明确要求：**同时考虑显示和 dag_spec 的下游消费场景**（不能只从 UI 角度论证）。
- 用户明确放宽：**不用考虑开发成本**（但仍受项目「第一性原理 + 奥卡姆剃刀，反对过度设计」纪律约束——放宽的是工程量，不是设计洁癖）。

**Q2 · 多 pk_measure 并行**
- 现状：`pk_measure`（代码字段名 `peak_measure`）high/close 二选一，`breakout_measure` 亦然。
- 用户直觉：二选一总有取舍，high_pk 和 close_pk 可能都能发挥作用，同时支持可让「信号更多、检测更敏锐」。
- 需回答：是否成立？若成立，方案是什么（两套 peak 集合并存？如何避免重复计数 / distinct_pk 语义污染 / burst 与 tb 下游语义？）
