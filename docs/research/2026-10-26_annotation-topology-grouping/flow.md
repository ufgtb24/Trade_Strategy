# flow：拓扑关系与 pattern 分组，沿整个工作流走一遍

本文中所有项目内路径均相对 repo root。队员 flow 的分稿，回答 `原始问题.md`：标注时「框之间的关系」和「哪些框、哪些买点凑成一个 pattern」怎么显示、怎么操作，从整个工作流看合不合理、有没有冗余。用词以 `path2/GLOSSARY.md`、`path2_web/GLOSSARY.md` 为准；已定的 1～10 条（lead 的任务说明）不推翻。

本轮只做设计推理，唯一的计算是在原型种子标注上跑默认成员规则（`repro/default_members.py`，坐标抄自原型，不读行情）；没有量任何特征与后续涨跌的关系，没有副产品要登记 `docs/feature_candidates.md`。

## 0. 结论

- 用户问的其实是三件事，产出者各不相同：**① 一个买点由哪几个框构成**（只有用户知道，要显式记，但默认可以推断）；**② 框和框之间什么关系**（位置已经说了，不靠位置的写成属性，不设编辑器）；**③ 哪些买点算一个 pattern**（程序按骨架分组摆出来，用户一组一下拍板）。
- **买点存「成员框」，范围只是派生显示**：从最早成员的起点画到买点日，在 bracket 轨（`path2_web/GLOSSARY.md:45`）的位置画虚线，对照时与 app 的 match bracket 同轨。不在任何买点成员里的框就是「只标事件」——截图里左边那个孤立的框自然落在范围外。默认成员按「贴着买点的那串框，加套在里面的框」推断，推错时在买点的 edit 面板里点名称块进出。存的是每次保存时算好的框编号清单（可复现，以后改默认规则不会改写旧买点）。默认规则只在「放买点的那次停留」里生效、只并进当前 pattern 的买点：这次停留里新画或改动的框，只要贴着那串就并进去；只加不踢（改短、改远一个成员不会被移出）；点掉过的不再并回（这份记录只放内存，停留结束就丢）——先点买点、再补框解释照样顺；离开这张图就冻结，以后回来补画的框不会悄悄进旧买点。
- **骨架由程序算，不用会话归纳**：骨架 = 一个买点的顶层成员的名称按起点排成的序列（子框和属性不进骨架，它们将来是那个 node 的 where 或子事件）。确定性、实时。会话只在对话里给语义建议（近义词、哪两组只差一样东西）。
- **侧栏不加 tab**：summary 改成 pattern tab，两种状态共用一套版式。当前 pattern 是「未归类」时，它列「按骨架分的组」，每组一个「→ pattern」下拉——这就是第二步「你决定哪些算一个 pattern」的全部操作；当前 pattern 是某个 P 时，它列 P 的一句话定义、元素表（= 原来的对应表按骨架先后排，多一列「出现在几个买点里」），下面同样是按骨架分组的买点，同样的下拉用来把归错的拆出去。
- **拓扑面板（`path2_web/GLOSSARY.md:50`）只留在看图模式**。标注一侧的「拓扑」就是元素表这一张按先后排的名称列表；app 的结构和它之间靠元素表里的 resolver 一格接上，不在标注模式里另画一张 DAG。
- **按用户追加的「少用文字、多用界面元素本身」**：成员、骨架、分组都用名称块（chip）和箭头表达，分组列表里每个买点是一张只画框的小缩略图——那段时间的名称轨缩小版，每个名字一行、行首是它的名称块（成员实线、近处的非成员淡色、买点实心 / 空心），不画 K 线、不写字串；「这组和已有 P 一样」不写标签，改成下拉预选 P。第 4.3 节按这条重筛过。
- 和 lead 候选方案的差别（第 5 节）：存成员而不存范围、不拖边界；骨架程序算而非会话归纳、骨架上不挂 ⚑；不新开 pattern tab 而是把 summary 改成它；归组和拆组用同一个控件。

## 1. 先分清三件事

| | 是什么 | 谁知道 | 现在原型里的状态 |
|---|---|---|---|
| ① 买点的成员 | 这次买入是因为哪几个框 | 只有用户 | 没有记；对照时按「买点前 40 根以内的框」猜（原型 `buyVerdict`） |
| ② 框之间的关系 | 先后、交叠、包含、「中间没有 X」「不破前面那个的价」 | 用户看得见、说得出；翻成哪类边（`path2/GLOSSARY.md:86`）或 where（`path2/GLOSSARY.md:79`）是会话的事（已定 5） | 先后、交叠、包含就在图上；其余可以写成框的属性 |
| ③ 买点归哪个 pattern | 哪些买点算同一个形态 | 用户定，但「哪些长得一样」要跨图才看得出 | 买点有 pattern 字段，可挂「未归类」；没有任何地方帮用户看出哪些该归一起 |

②为什么不需要编辑器：path2 的六类边加锚，我逐条对过用户在标注里能表达什么——

| 边 | 用户在标注里怎么表达 |
|---|---|
| 时序 | 两个框在图上的先后；间隔天数是参数，归调参 |
| 包含、起点包含、交叠 | 两个框在图上的相对位置；框套框另有「属于」的意思（票 Answer 第 2 节），哪种由会话按跨图证据定 |
| 同段 | 两个名字其实框的是同一段：要么一个框写两个属性，要么两个同起止的框 |
| 否定 | 图上画不出「没有」，写成后一个框的属性记 false，或写在名字的定义里；单张图上的 false 分不清「恰好没有」和「有它就不买」，靠跨图证据和那句定义定（topo 第 3 节） |
| 锚 | 「这个回踩是那次突破的回踩」——成员关系加先后就说清了 |

不靠位置的关系（「回踩不破突破价」）落点不是边：path2 的六类边只比较两个事件的起止位置，锚只比身份，没有一类边能比较两个事件的价格或字段（topo 第 3 节，`path2/dag/edges.py`）。它在 path2 里只能是后一个 node 的 where——让后一个事件的 detector 读前一个事件的流、算成自己的字段（bb_v1 的回踩就是读突破串、相对那根 bo 算回撤）。所以写成后一个框的属性，恰好落在它在代码里的位置。

现役 app 全部只用了一条时序边加锚（topo 第 1.4 节；bb_v1 见 `path2_apps/bb_v1/dag_spec.py`），bb_v1 的拓扑里还有挂在 burst 下的 bo 和不参与求解的 pk——app 的拓扑本来就不是用户骨架的照抄，这也是标注一侧不该直接摆 app 拓扑的原因之一。

步骤沿上一轮研究的工作流（`docs/research/2026-10-25_annotation-display-workflow/final_report.md` 第 3 节）。「显示在哪」里，主图 = K 线和副图（标注模式下副图是用户的名称轨），侧栏 = edit / vocab / pattern / json 四个 tab。

| 步 | 这一步要的分组 / 拓扑信息 | 谁产出 | 显示在哪 | 用户要做什么 |
|---|---|---|---|---|
| 1 自由标注，买点先挂未归类 | 框；框套框的父子；每个买点的成员；买点所属 pattern | 用户画框、点买点；程序推断父子和默认成员 | 主图：框、⊂ 父名、买点、派生范围；选中买点时成员实线加粗、非成员变淡。edit 面板：成员名称块 | 画框、点买点。成员推错时点名称块（多数买点零操作） |

| 3 会话写第一版 app | P 的元素表（名称、先后、出现次数、子框、属性）、P 的定义、词的定义；同一买点前有两段同名框时的角色；某个名称只出现在部分买点里时，是「没有」还是「没画」 | 会话写 app 和对应表；推不出的角色在图上问（票 Answer 第 2 节）；「没画还是没有」按名称问一次，不逐张问（topo 第 5.3 节） | pattern tab 元素表多出 resolver 一格 | 只在会话推不出角色、或问到「没画还是没有」时回答 |

| 5 没认出的分流 | 结构性的：哪个成员没认出、哪个买点 link broken、哪组骨架和主骨架不同 | 会话 | 交付单（对话） | 无 |
| 6 看交付单拍板 | 要加删 node、换骨架时：是哪几个买点、哪一组 | 会话写，引用元素表的行和分组 | 对话；pattern tab 里对应的组 | 方向判断；归错的那组用「→ pattern」挪走 |
| 7 改 app | 同 3 | 会话 | 元素表 resolver 更新，旧的认出数标过期 | 无 |

| 9 盲看，第二步露结构 | app 的每个 node 在用户词里叫什么 | 程序用元素表的 resolver 反查 | 露结构时 band（`path2_web/GLOSSARY.md:39`）的名字写用户的词，node 名作灰色等宽小字（建议，票 08 定） | 判是 / 不是；「是，但认错了」点在认错的那条 band 上 |
| 10 调参 | 无，结构不动 | — | — | — |
| 11 调参后回头查 | 每个买点在调参前后 app:buy 有没有翻 | 程序 | pattern tab 分组列表每行的状态 | 定接受还是限范围重调（已定 6） |
| 12 最后检查 | 无 | — | — | — |

几处说明：

- **第 4 步受益最大**：有了显式成员，link 的三态（ok / broken / pending）只在这个买点自己的成员上算，不再靠「前 40 根」去猜。原型那条窗在「再买一次」（同一结构上第二个买点）时会把第一段回踩算进第二个买点，项目里本来就有 re-entry 的 app（bb_v3）。
- **第 9 步复用元素表**：盲看露结构时，用户要判断的是「app 认的这段是不是我说的横盘」，band 上写用户自己的词，用户就不用把 node 名在脑子里翻回去。只有 node 级的对应能这样标；对应到 where 的词（比如「横盘」被翻成突破串上的一条 where）不占 band，在那条 band 的 where 列里出现。
- **第 10、12 步不碰分组和拓扑**：调参只改参数取值，结构不动；最后检查只判输赢。

## 3. 第二步：你决定哪些算一个 pattern

### 3.1 骨架怎么算

一个买点的骨架 = 它的**顶层成员**的名称，按起点先后排成的序列。

- 套在成员里的框（子框）不进骨架：「底部」里套没套两个低点、是 W 形还是 V 形，都算同一个骨架。这正是方向文档第 8 节「骨架相同合成一个，差别放进那个 node 的 where」要的效果，也和已定 10（取其一用 where 的「或」）对上。
- 属性不进骨架，理由同上。
- 买点日本身不进骨架。买在突破当天还是回踩之后，通常已经由「有没有回踩框」区分开了。
- 成员为空的买点自成一组「无成员」。

这是确定性的计算，不需要会话：同一份标注永远得到同样的分组，用户改了成员，所在的组当场变。会话的价值在语义上——「横盘」和「平台」是不是一回事、「只差有没有回踩」的两组是不是该合——这些在对话里作为建议说，不进界面。

### 3.2 怎么摆、怎么一次决定

当前 pattern 选「未归类」时，pattern tab 是一列组，按买点个数从多到少排。按用户追加的「少用文字、多用界面元素本身」，每组只由界面元素构成（版式由 ux 定）：

- **组头** = 骨架的名称块链：用户的词做成块、块间箭头，子框不出现（它不进签名）；后面一个小计数和「→ pattern」下拉。不写「横盘 → 放量突破 → 回踩」这种字串。
- **展开后每个买点** = 一张小缩略图：这个买点附近那段时间的名称轨缩小版——每个出现的名字一行，行首是那个名字的小名称块（块本身就是标签），行序同主图名称轨，框画在自己那行；成员实线、非成员淡色、买点实心（buy）/ 空心（no_buy）；不画 K 线。股票代码和日期只在悬停里。点缩略图跳到那张图并选中那个买点——用户凭图、不凭字串做决定。每行带名称块是为了让淡色框认得出是什么（critic F10）；不能拿组头当图例，因为假小组缺的那个名字恰好不在组头里。
- 缩略图顺带让**默认成员切短**的假小组一眼可见（critic F9）：放量突破之后先涨几天才回踩、那几天没框，默认规则只收进回踩，于是出现一个只有「回踩」的小组；它的缩略图里，「放量突破」「横盘」两行在成员左边紧挨着画着淡色框，用户一眼就知道是成员收少了，点进去在名称块上补。
- 只有一个买点的组收成一个「+n」，点开才列。
- 这组骨架和已有 pattern P 最常见的骨架完全一样时，不加文字标签，而是让这组的「→ pattern」下拉预选 P，点一下确认。
- 下拉里是已有 pattern 加「+ new」。选了就生效，组从未归类里消失；同一个 pattern 选给两组就是合并。新建 pattern 时，pattern tab 头部的「定义」一格是空的，会话写 app 前若还空着会在对话里问（方向文档第 12 节：pattern 想抓什么的一句话决定骨架往哪个方向搭）。
- 「一次决定」的意思：一屏看完全部组，每组至多一下，不用逐个买点改。组一般只有几个，单个的收起来。

### 3.3 决定后买点怎么归进去

选「→ P」= 把这组每个买点的 pattern 字段改成 P。存储照方向文档第 10 节「只新增不改旧文件」，记成新一批文件里的「买点 X 归 P」，后记的覆盖先记的。这个字段也仍可在买点的 edit 面板里一个个改——那是同一个字段的单个入口，留给例外。

标注文件只由界面写：归组在界面上点，会话不代写。会话的建议在对话里，用户照着点。这样标注文件里的每一条都是用户自己做的，出处干净。会话的产物（对应表、哪个 app 实现哪个 pattern）放在 app 旁边，不进标注文件（topo 第 5.4 节）。

pattern 用用户起的名字，有 app 时旁边灰字标 `app: bb_v1`；原型顶栏直接列 app 编号，把「用户的 pattern」和「实现它的 app」（同一走势可以有几个平级版本，`path2/GLOSSARY.md:36`）当成了一个东西（topo 第 5.2 节）。标注里的 pattern 记录不引用 app 编号：app 会换版本，意图不变。

### 3.4 一个买点能不能同时属于两个 pattern

不能，同一天要算两个 pattern 就挂两个买点（方向文档第 8 节已定）。理由：买点上的 label（buy / no_buy）是相对某个 pattern 说的（「像但不买」必须说清像哪个），成员也可能不同（A 只要横盘和突破，B 还要前面的大跌）。操作不需要新控件：顶栏切到 B，在同一根 K 线上再点一次，就多一个属于 B 的买点，它的默认成员重新推断。框可以同时是好几个买点的成员——框本来就不属于任何 pattern。

### 3.5 骨架变了怎么办

不需要专门的机制。骨架从来不由用户编辑、也不单独存，它永远是 P 下所有买点成员的现算结果，于是：

- **新买点多了一样东西**（大跌 → 横盘 → 放量突破 → 回踩）：元素表多一行「大跌 1/11」；分组列表里多一个 1 个买点的小组。会话下一轮看：大多是不进 app 的一笔（元素表里那一行 resolver 写「没进 app」）；要加成必须有的 node，就是「加删 node」，按已定流程进拍板单。
- **新买点少了一样东西**（没有回踩）：同样自成小组。要么用户漏框了（回图上补），要么买点位置其实不同、是另一个 pattern（用这一组的「→ pattern」挪走）。
- **当前 pattern 忘了切、买点归错了**：只要骨架和 P 的其他买点不同，就在 P 里自成小组，看得见、一下挪走。骨架恰好完全相同时不报：按方向文档第 8 节，骨架相同本来就合成一个；用户心里的区别（比如所处的大环境不同）只能靠对照或盲看暴露。

所以 P 的 pattern tab 里，「主骨架」就是最大的那组，「偏离」就是其余的小组，不另设标记。P 下只有一种骨架时不出分组列表——那时它和元素表的先后完全重复；一旦出现第二种就出现，因为这时要被看见的恰恰是小组（忘切 pattern 归错的、默认切短的、骨架偏离的），藏在「点元素表的数」后面就没人点，组上的「→ pattern」拆组控件也需要一个常驻落点（critic F6）。

## 4. 冗余检查与最小元素集合

### 4.1 lead 点名的三处

| 疑似冗余 | 结论 |
|---|---|
| 买点成员既在主图又在面板 | 只在 edit 面板里**改**（名称块），主图只**显示**（派生范围、加粗 / 变淡）。名称块是控件，必须显示自己的开关状态，这不算第二份信息。框的面板里不列「属于哪几个买点」——选中买点时图上就看得见，反过来查很少用 |
| 骨架既在 pattern 视图又在对应表 | 合成一张：元素表 = 对应表按骨架先后排、多一列「出现在几个买点里」。还没 app 时只有这一列 |
| 拓扑既在用户骨架又在 app 拓扑 | 不在同一模式里同时出现：标注模式只有元素表（用户的词），看图模式只有拓扑面板（node）。两者靠元素表的 resolver 一格接上。不合成一张，因为 app 的拓扑里有用户骨架里没有的东西（bb_v1 的 bo、pk），用户骨架里也有不进 app 的东西（「没进 app」的名称） |

### 4.2 另外查到的

- **骨架上的 ⚑ 和对应表的「这一行不对」**：两处纠同一个错。只留对应表那一处，挂在翻译上；骨架是用户自己标注的计数，不会「错」——数不对说明成员推错了，回图上改成员。
- **原 summary 里的「link=broken」清单**：并进分组列表，每行带 link 状态，不另列。
- **词的定义在 edit 和 vocab 两个 tab 里都能改**（原型现状，不属于本题，顺手记下）：同一个字段两个编辑入口。ux 定为两处都留：改的是同一个字段，不会不一致；edit 那处是名字第一次用时写定义，vocab 那处是回头统一整理措辞（改措辞也在那）。
- **属性的 true / false / null 计数**：vocab 里按词跨 pattern 计，和 pattern tab 里按 pattern 计是两张表报同一类数。挪进 pattern tab 的属性子行（取其一在这里按分支拆开，正是票 Answer 第 3 节要的「W 形 6、V 形 3」），vocab 只留词、定义和用了几次（topo 第 0 节）。

| 候选方案 | 意见 |
|---|---|
| 每个买点带一个 instance 范围，画在 bracket 轨，用户虚线、app 实线 | **保留画法，改存法**：存成员，范围是派生的。理由（critic U1、U2）：再买一次时第一段回踩夹在买点 2 的范围中间，拖左边界排不掉；存范围又存成员会打架——用户把横盘往左拉长 10 天、一半出了范围，算不算成员 |
| 放买点时左边界默认延到相连的框起点，不对就拖 | 默认规则保留（贴着买点的那串框 + 套在里面的框），纠错改为点名称块 |

| 关系不另设编辑器；不靠位置的写成后一个框的属性，由会话翻成边 | 前半保留，六类边加锚逐条核过（第 1 节）；后半改为「翻成后一个 node 的 where」——边比较不了价格和字段（topo 第 3 节） |
| 加一个 pattern tab：定义、骨架（会话归纳，带出现次数，⚑ 可标错）、instance 列表 | **合进 summary**：summary 改名 pattern tab；骨架由程序算、并成元素表的一列；⚑ 只挂在翻译上；instance 列表按骨架分组，同一个下拉兼做归组和拆组 |
| 理由：哪几个框构成买入理由只有用户知道；先后看位置就够；pattern 由哪些名称组成要跨图才看得出 | 同意前两条。第三条成立，但「跨图看出」只是计数，程序做就够；会话该做的是翻译 |

## 7. 和队友对齐的记录

- **critic U1、U2（范围管不住中间的框；范围和成员两份存储打架）**：接受，改为存成员、范围派生、纠错用名称块。
- **critic F1（显式分组是否必要）**：必要。按步骤谁读成员：第 2 步归组、第 3 步写 app（骨架、同名两段时的角色）、第 4 步 link、第 6 步拍板单要指出哪几个买点、第 11 步按买点报丢了哪几个。读错的后果都归到骨架错——会话加一个不存在的 node 或漏一个，要一轮盲看才暴露。
- **critic F2（骨架、对应表、词表三张按名称排的表；两处纠错）**：同意合并，见 4.2。
- **critic F3、U3（骨架常驻会锚定新标注；看过骨架算不算接触过 app）**：不算接触。已定 1 防的机制是「看着 app 的事件在同一张图的同一位置下框」，是位置性的；骨架是用户自己过去标注的计数，不含这张图上的任何位置。用户记住「我的 pattern 有缩量」再去新图找缩量，就是方向文档第 8 节「先定目标」阶段本来接受的代价，和用户自己的记忆是同一件事，拿掉表也拿不掉记忆。真正的残余是同一张表里 resolver 一格暴露了 app 的翻译（比如「缩量 → 没进 app」），可能改变用户以后标不标缩量，记为残余风险（第 8 节）。缓解只做一条：标注时侧栏默认停在 edit（选中框或买点就自动切过去，原型已如此），pattern tab 只在用户点开时出现。
- **critic F4（关系类属性被「点名字带上以前的说明」带到不该去的框）**：成立但危害低。被带到「被指的那个框不在成员里」的买点上时，会话翻译时就看到这条说明无从判断，当噪声丢掉，不会翻成错的结构；坏处只是那张图上留了一条不真的说明。不为它单做机制——要做就得让界面按会话的翻译决定带不带属性，等于 app 的翻译反过来影响标注默认值。并进票 01 第 6 节第 3 条一起验，多数一项。
- **critic F5（当前 pattern 忘切）**：见 3.5。不做「每换一张图重置当前 pattern」，因为先定目标阶段每张图都要多切一次。
- **critic F6（买点列表是否与左栏、与「点对应表的数」重复）**：只有一份，见 E7。第 2 步归组是它的主场；第 4 步由元素表的行筛进来；第 6 步会话按组引用；第 11 步看每行 app:buy 有没有翻。

## 8. 不放心的地方

1. **默认成员规则只在 4 个种子买点上跑过**，真实标注里用户框的松紧、买点放在回踩里还是回踩后，都会影响「贴着」的判定。规则错的方向如果是漏收，骨架会碎成很多小组，用户在第二步会看到一堆莫名其妙的组。
2. **按骨架完全相同分组可能太碎**：近义词、该套的框画成顶层、某张图漏框，都会多出组。我赌的是用户的词表可复用、组数不会多到看不过来，没有数据。
3. **resolver 一格暴露 app 的翻译**，会不会让用户以后有选择地标某些名字，记不下来、也量不出。
4. **默认切短可能常见**（critic F9）：用户只框「有特征的那几段」、中间的上涨不框，是很自然的标法，空隙可能远超几天。topo 已把空隙放到 20 根，代价是更容易把孤立的框收进来；缩略图和第 6 节那一行能把它暴露出来，但如果多数买点都被切短，第二步会先变成「一组组补成员」，而不是「一组组定 pattern」。
5. **标注文件只由界面写**：用户在对话里说「1 和 3 合成一个」，会话只能请用户去点，多一步。我认为出处干净值这一步，用户可能不这么看。

## 9. 最容易被误读的地方

- 这里的「骨架」是**用户一侧**的：成员名称按先后排成的序列，来自标注本身，不是 app 的 node 拓扑。app 的结构只出现在元素表的 resolver 一格。
- 「范围」**不存、不能拖**，它只是成员的显示；改成员用名称块。
