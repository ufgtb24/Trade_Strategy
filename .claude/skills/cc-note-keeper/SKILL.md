# Claude Code 笔记管家（本项目版）

帮用户把关于 Claude Code 的知识沉淀到 `/home/yu/PycharmProjects/Trade_Strategy/docs/cc_notes` 的 markdown 笔记中。维护一个根索引（INDEX.md），按一个清晰的分类维度组织所有笔记，并在每次写入时给出**一步式**的位置推荐。

笔记目的：**帮用户高效解决问题**，不是学习知识。可粘贴的自动化流程/操作步骤是最有价值的内容——用户大多数时候只想"无脑做完"。原理一笔带过、一语中的，仅作为出问题排查时的定向查阅，平时不展开。

> 笔记内容本身是跨项目通用的 Claude Code 配置经验，与 trading 业务无关；落在本项目的 `docs/cc_notes` 是为了纳入版本控制和坚果云同步。

## 仓库结构

```
/home/yu/PycharmProjects/Trade_Strategy/docs/cc_notes/
├── INDEX.md              ← 根索引，记录分类维度和文件映射
├── <topic-a>.md          ← 笔记，frontmatter 含 scope 描述
├── <topic-a>-setup.sh    ← 可选：脚本太大不便嵌入正文时拆出（默认不拆，见下）
├── <topic-b>.md
└── ...
```

### 脚本拆分规则

**默认拆为独立 `.sh` 文件**（与 .md 同目录），仅「≤5 行的短命令列表」才嵌入正文。理由：复制粘贴长 bash 块易踩 shell 续行 / 视觉换行陷阱（典型坑：长 URL 被切成下一行变独立命令），`bash xxx.sh` 一键运行明显更顺。

**拆 .sh 的触发器**（满足任一即拆）：

| 触发器 | 原因 |
|---|---|
| 含 `sudo` | sudo 密码 prompt 在独立脚本里更可靠 |
| 含 `set -e` / `if` / `while` / 函数 | 复制粘贴控制流容易选漏行 |
| 含长 URL 单独占行 | 防终端视觉换行被切碎 |
| 多步前置检查 / 失败回滚 | 独立文件可 `bash -x` 调试 |
| 行数 > 10 | 复制粘贴风险随长度上升 |

**仅嵌入正文的情况**：脚本是 ≤5 行的独立短命令列表，用户大概率只挑一两条跑，不需要"一键执行"。

**拆 .sh 时的细则**：

- 命名 `<topic>-<step>.sh`（如 `chat-sync-setup-edge-bridge.sh`），跟相关笔记同前缀便于识别归属
- 文件头加 `#!/bin/bash` + `set -e` + 一两行注释说明用途和幂等性
- 笔记正文保留**调用方式** + **一句话作用 + 一句话前置要求**，**不嵌完整脚本**（要么嵌入要么外置，别两份共存导致漂移）
- 调用方式**必须用 cwd 无关的写法**：`bash "$(git rev-parse --show-toplevel)/docs/cc_notes/<script>.sh"`。理由：PyCharm 等 IDE 点击 markdown 代码块运行时 cwd 是 .md 文件所在目录（不是项目根），相对路径 `bash docs/cc_notes/xxx.sh` 会报 "No such file"
- `INDEX.md` **不索引 .sh 文件**——索引颗粒度始终是「主题笔记」；脚本归属由笔记正文引用承担
- 即使拆出 .sh，**也属于 cc_notes 范畴**（CC 配套工具非项目业务代码，不该外移到 `scripts/`）

### INDEX.md 格式

```markdown
---
dimension: <分类维度名>
updated: YYYY-MM-DD
---

# Claude Code 笔记索引

## 分类维度
<一句话说明按什么分、为什么选它>

## 分类与笔记

### <分类 A>
- [filename.md](filename.md) — <该笔记 scope 一行摘要>

### <分类 B>
- [other.md](other.md) — <…>
```

### 笔记文件 frontmatter

```yaml
---
title: <一句话标题>
scope: <这个文件专门记录什么。明确边界，便于今后判断新内容是否归属这里>
category: <在 INDEX.md 中所属的分类名>
---
```

## 三个使用场景

### 场景 1 · 初始化（目录或 INDEX.md 不存在时）

1. 若 `docs/cc_notes/` 目录不存在，先 `mkdir -p` 建好。
2. 先了解用户**当前想记的内容 + 未来可能记的方向**（至少 2-3 个例子）。
3. 提 **2-3 个候选分类维度**，每个维度说明：
   - 维度名（如「按文件位置」「按配置主题」「按问题类型」）
   - 初步类别列表（基于用户描述的内容样本）
   - 该维度的优点 + 潜在风险（哪类内容可能放不进 / 颗粒度问题）
4. 选维度时把住三道关：
   - 类别**互斥**：同一条内容不能合理地归两类
   - 颗粒度**均衡**：不要出现囊括一切的大类 + 边缘小类
   - 类别**4-8 个**为宜
5. 等用户选定后，创建 INDEX.md（写入维度名和空的类别框架），然后进入场景 2。

### 场景 2 · 写入新内容（主要场景）

触发：用户描述了一段想记下来的 Claude Code 知识。

1. **读** `INDEX.md` + 各笔记的 frontmatter（**不必读笔记正文**，scope 已足够判断归属）。
2. **一次性推荐**（关键：不要分步问），按下方模板给出：
   - 选定的**分类**及理由
   - **目标文件**：现有 `xxx.md` **或** 新建 `yyy.md`
   - 如新建：建议的**文件名**和 **scope 描述**
   - 简短的**判断理由**（为什么选它 / 为什么要新建）
3. 用户确认或修正后：
   - **新建**：写 frontmatter → 正文 → 更新 INDEX.md 加入条目
   - **追加**：定位到现有笔记的合适小节（按 `## 小节` 组织），加入新条目
4. 写完后**简报**用户：写到了哪个文件、加了什么小节。

### 场景 3 · 调整分类维度（重操作，谨慎）

触发：用户明确说要换维度 / 整理；或场景 2 中频繁出现「现有维度装不下」的内容。

1. **先提醒**这是重操作，会改 INDEX.md 和多个笔记的 `category` 字段。
2. 读 INDEX.md + 所有笔记的 frontmatter。
3. 基于现有笔记内容分布，提 2-3 个新维度候选，并**预演**每个新维度下旧笔记的归属（让用户看到迁移效果）。
4. 用户选定后：改写 INDEX.md，逐个更新笔记 frontmatter 的 `category` 字段。
5. 文件名通常**不必改**，正文不动，只动 frontmatter 和索引。

## 推荐模板（场景 2 核心，复制改填）

```
建议这样记录：

  分类：<分类名>
  目标：<新建 xxx.md  /  追加到 yyy.md 的「## 小节」>
  scope（仅新建时）：<一行描述>
  理由：<为什么属于这个分类 + 为什么选这个目标，1-2 句>

确认请回复 ok，或者告诉我要怎么改。
```

## 写作风格（笔记正文）

**核心原则：操作优先于原理。** 用户绝大多数时候只关心"怎么做、能不能复制粘贴一键完成"。原理只在用户主动追问/出问题排查时才需要——平时一笔带过、一语中的。

### 结构上的体现

笔记从上到下按"用户实际查阅顺序"组织：

1. **顶部：可粘贴的自动化流程**（含完整 bash 块、明确标注 `[自动]` / `[手动]` 步骤；多步流程用编号小节）
2. **中部：字段/配置最小说明**（怎么配 + 一句话作用 + 一句话生效条件）
3. **底部：踩坑/原理/为什么**（独立 `## 踩坑：<现象>` 段或 `## 原理` 段，给排查时定向跳）

### 细则

- 标题用 `## <字段名>` 或 `## 一键安装：<目标>` 或 `## 踩坑：<现象>`
- 代码块放**完整可执行**的最小片段，用户直接粘到 terminal 就能跑
- 不写过渡句、不抄官方文档原话
- 复杂行为加一行「踩坑提示」就够，不展开原理
- 避免讲解式语气（"你可以..."、"这样能..."），用祈使句/陈述句

### 操作指南的行文规范

操作指南是笔记最高频被消费的部分，必须**条理清晰、步骤分明、简洁明了**。

- **顶部 1-2 句话概述总流程**：标明步骤数 + `[自动]`/`[手动]` 比例。
  例：「4 步：[自动] 装 bridge → [手动] 浏览器装 extension → [自动] patch → [手动] 重启 shell」
- **每步独立小节**，标题格式 `### Step N（自动/手动）：<一句话动作>`
- **自动步骤**：紧跟可粘贴 bash 块或 `bash xxx.sh` 调用，**先放命令、再用 1 行说明它做了什么**，必要时附一句话前置/后果。不解释为什么。
- **手动步骤**：用 `1. 2. 3.` 列出**具体动作**（点哪里 / 输什么 / 看什么界面），不解释原因
- **步骤间禁用过渡句**（"接下来"、"然后"、"完成后"……），步骤之间靠标题分隔即可
- **步骤里不夹原理**——原理放底部 `## 原理` 或 `## 踩坑：<现象>` 段，操作指南只回答"怎么做"

### 好示例（操作优先）

## 关键决策表

| 情境 | 处理 |
|------|------|
| 目录或 INDEX.md 不存在 | 走场景 1，不要擅自建笔记 |
| 用户给了待记录内容 | 先读 INDEX.md，再一次性出推荐 |
| 内容同时贴合两个分类 | 说明歧义、让用户裁决，不要默默选一个 |
| 找不到匹配分类 | 推荐放最接近的分类 + 提醒「若此类越来越多，考虑场景 3 调维度」 |
| 新内容只有 1-2 句 | 优先追加到相关已有笔记，避免碎片化 |
| 用户说"重新整理" | 走场景 3，先提醒是重操作并等确认 |

## 常见错误

- ❌ 初始化时凭空猜维度直接写 INDEX.md（必须先和用户对齐）
- ❌ 把一条知识写成 200 字散文（笔记是查阅资料，不是博客）
- ❌ 把推荐拆成多步问（分类一步、文件一步、scope 一步……应一次给完整方案）
- ❌ 跳过读 INDEX.md 就开始建议
- ❌ 调维度时连带重写笔记正文（只动 frontmatter `category` 和 INDEX.md）
- ❌ 用 `Other` / `Misc` / `杂项` 当兜底分类（这是维度选错的信号）
- ❌ 推荐时只说结论不给理由（用户无法判断你是否选对）
- ❌ 把原理/为什么放在笔记顶部、操作步骤压在底部（违反"操作优先"原则）
- ❌ 笔记里只指向外部脚本路径而不内嵌可粘贴片段（新机器拿不到外部脚本时就废了）
- ❌ 拆出独立 `.sh` 后又把完整脚本嵌回笔记正文（要么嵌入要么外置，别让两份内容并存漂移）
- ❌ 把 CC 配套脚本搬出 `cc_notes/` 到 `scripts/` 或别处（这不是项目业务代码，应留在 cc_notes 范畴内）
