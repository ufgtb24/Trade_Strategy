# critic：对抗审查记录（拓扑关系与 pattern 分组）

本文中所有项目内路径均相对 repo root。审查基准是 `原始问题.md`：标注时怎样显示和操作「框之间的关系」和「哪些框凑成一个 pattern」，覆盖主图和侧栏；能不能复用现有拓扑面板（`path2_web/GLOSSARY.md:50`）。用词以 `path2/GLOSSARY.md`、`path2_web/GLOSSARY.md` 为准。

## 0. 防谁、停在哪

**防的五类错**（每条质疑必须给出具体失败场景，给不出的不提）：

1. 冗余：同一条信息要在两处编辑，或两处显示同一件事、在两处纠错。
2. 心智负担：用户得记住或理解程序结构（node、where、边的种类、实例编号）才能操作。
3. 违反已定 1～10：尤其是把 app 的结构或现成事件带进标注、让用户想 node / where / 边。
4. 对工作流无效：某个界面元素在七步里的任何一步都没人读、没人点。
5. 色弱与文字风格：靠色相区分；业务内容和程序固定内容混排。
6. 文字代替界面元素（用户追加要求「尽量不要使用大量文字，尽量用软件的 UI 元素本身」）：凡是要读一段文字才明白的地方都算质疑点；反方向同样防——图形太隐晦，用户看不出它代表什么（判法：不看图例、不悬停，第一次看到能不能说出它是什么）。

**不防的**：口味之争（按钮放左还是放右）、实施细节（数据结构字段名）、已定 1～10 本身（除非新证据表明它和本题直接冲突，届时单独写出交给 lead）。

**停止线**：每位队友的主张逐条对过这五类、每条质疑拿到一次回应并判了状态即停；同一条最多追两轮，两轮后仍分歧就记成「未解决」交 lead，不再追。

## 1. 独立分析（未看队友初稿前写下）

### 1.1 用户在问的其实是两件事

用户原话里混着两层：

- **一个买点由哪几个框构成**（实例层的分组）：截图里左边孤立的框和右边挨着的四个框，用户知道前者不是这次买入的理由、后者是，界面上却没有任何东西记下这件事。
- **哪些买点算同一个 pattern、这个 pattern 由哪些名称组成**（pattern 层）：买点归哪个 pattern 已经有「当前 pattern」与买点的 pattern 字段（票 Answer 第 1 节）；「由哪些名称组成」是跨图才看得出的东西。

关系（先后、包含、交叠、「中间没有 X」、「不破前面那个的价」）挂在实例层上：它是同一个买点里两个框之间的事。

### 1.2 显式分组到底要不要

先问谁读这份信息、读错了会怎样：

- **会话写 app**：要知道每个买点由哪几个框构成，才能归纳骨架。现在原型是按「买点前 40 根以内的框」推断（`.scratch/annotation-path2/prototypes/01-annotation/index.html` 的 `buyVerdict`）。
- **对照**：两框之间的 link 和买点的 pending，都要先知道哪些框是同一次的。

只靠时间窗推断，确定会错的场景有三种：

- **再买一次（同一结构上第二个买点）**：横盘 → 放量突破 → 回踩 → 买点 1 → 回踩 → 买点 2。买点 2 的时间窗把第一段回踩也收进来，会话归纳出「这个 pattern 前面有两段回踩」。项目里本来就有 re-entry 的 app（bb_v3），这不是假想。票 Answer 第 2 节「同一买点前两段同名的框才在图上问」正是这个场景，说明推断在这里本来就要问人。
- **长底座**：横盘 80 根，时间窗只收到右半截；或缩量套在横盘里却落在窗外。
- **两个 pattern 的买点在时间上交错**：一次标注可以有多个 pattern，A 的成员框落在 B 的时间窗里。

推断错的代价不是显示难看，而是**骨架错**：会话据此加一个不存在的 node，或漏一个，之后要在盲看里花一轮才暴露。而「哪几个框是这次买入的理由」只有用户知道，这和用户原话一致。所以：**要显式的成员关系；但默认值可以推断，用户只在推错时改。** 关键是推断结果必须看得见——用户原话抱怨的正是「没有 pattern 的边界」，看不见的推断用户不会去改。

### 1.3 lead 候选方案里我预判的薄弱处

**范围框管不住中间的框。** 「买点带一个范围，范围里的框 = 成员，左边界默认延到相连的框，不对就拖」：拖边界只能把最左边的框排出去，排不出夹在中间的框。上面「再买一次」的第一段回踩正夹在买点 2 的范围中间。再者，范围的左边界本来就由「最早的成员」决定，存一个范围又存一组成员，两者会打架：用户把横盘往左拉长 10 天，横盘一半出了范围，它还算不算成员？用户得再去拖一次范围（同一件事改两处）。倾向：**存成员，不存范围；范围是成员的派生显示**（最早成员起点到买点）。纠错用「在买点的编辑栏里勾掉 / 勾上某个框」，或在图上点框切换，不用拖边界。

**「关系写成后一个框的属性」会被「点名字带上以前的说明」放大。** 「不破突破价」写在回踩上之后，每个新回踩框都会默认带上它，包括另一个 pattern 里前面根本没有突破的回踩。那张图上的这条说明要么用户手动勾掉（多一步），要么默认留着为 true（会话收到一条自相矛盾的说明）。这类说明指向另一个框，带不带应看那个框在不在同一个买点里。属于票 Answer 第 6 节第 3 条「一点全带上让人懒得核对」的加重版。

**骨架常驻在侧栏，会在标新图时锚定用户，并和「新标注」打架。** 骨架是会话从已有实例归纳的，app 正是照它写的。标新图时侧栏摆着「横盘 9/10、缩量 3/10」，用户会去新图里找缩量，新标注于是长得像骨架、也就像 app，新标注的认出率虚高。这和已定 1 的理由（看着 app 的东西标、再拿去考 app 是自证）是同一个机制，只是隔了一层。若把「看过骨架」也记成「接触过 app」，骨架常驻就会把所有新标注变成老标注，新标注组攒不起来（票 Answer 第 1 节最后一条要防的正是这个）。倾向：骨架不在标注时常驻，放在每轮的汇总页里。

**骨架、对应表、词表是三张按名称排的表。** 词表（vocab）按名称列使用次数；骨架按名称列在本 pattern 里出现次数；汇总页的对应表按名称列 app 由谁来认、认出几处。后两张同一 pattern、同一行键，骨架上的 ⚑ 和对应表的「这一行不对」是在两处纠同一个错（例：「缩量不该是必须有的」两处都能点）。倾向：骨架并进对应表，多一列「出现在几个买点里」；还没有 app 时对应表只有这一列。

### 1.4 拓扑面板能不能复用

现有拓扑面板画的是 app 的 DAG：节点是 node 名，边标签常驻显示边的种类和规则（`path2_web/serialize.py` 的 `_edge_rule`，如 `before · gap∈[0,20]`），悬停节点显示 where 门槛数字，点节点切显隐，双击拉诊断，点边标签看 miss 明细。

- **在标注模式（含对照开着）里原样摆出来不行**：节点名是 app 的 node（违反已定 1、5），边标签常驻显示门槛天数、悬停显示 where 门槛（违反票 Answer 第 1 节「对照开着时不出实测值和门槛」）。失败场景：用户对照时看到 `gap∈[0,20]`，下一张图就把回踩框画在突破后 20 天以内。
- **拿它画用户的骨架（节点换成用户的词）**：交互全部要换——显隐切换勉强可留，诊断、miss 明细都不适用，边标签的种类词（before / contains）是程序概念，要么让用户读边种类（心智负担、违反 5），要么换成人话，那时复用的只剩布局函数。而用户的 pattern 多半是一条直链加一层套框，一行文字「横盘 ⊃ 缩量 → 放量突破 → 回踩 → buy」就能讲完，画 DAG 只在有并列分支时才有增益。
- **拿它做编辑器（在面板上连箭头定关系）不行**：先后在图上的位置里已经有了，面板再定一次就是两处来源。失败场景：面板上连了「横盘 → 突破」，第 3 张图上突破却套在横盘里，会话不知道听谁的。而且连箭头就是在定边，正是已定 5 说用户不必做的事。

倾向：看图模式下拓扑面板照旧；标注模式下不出现。实例的结构在买点的编辑栏里用一行文字派生显示（就是这张图上的成员与先后、套框），pattern 层的结构只在汇总页的对应表里。

### 1.5 我自己倾向的最简方案（供被挑战）

- 存：买点多一个「成员框」列表（框的编号），默认由界面推断，用户可改。不存范围、不存关系。
- 主图：选中买点时，派生范围画在 bracket 轨上（虚线），成员框加粗、非成员框变淡；不选时只画派生范围不加粗。靠线型和粗细，不靠颜色。
- 侧栏买点编辑栏：一行派生的结构文字（成员按先后排，套框用 ⊃），每个成员前一个勾，勾掉即移出；图上同一时段的非成员框列在后面、可勾上。
  - 自查（按第 0 节第 6 条）：这一行若是纯文字串，就是用文字转述图上已有的东西，和主图重复。改成一排可点的名称块（chip，名字是用户的词、按先后排、套框缩一级），块本身就是开关，点一下进 / 出成员，主图同步加粗 / 变淡；不另写说明句。
- 关系：不另设编辑器。不靠位置的关系写成框的说明；「点名字带上以前的说明」对这类说明的副作用交给实施时验证（见 1.3）。
- pattern 层：不加 pattern tab。pattern 的一句话定义和骨架放进汇总页顶部与对应表的一列；标注时看不到骨架。

## 2.5 交最终报告的待验证项

**V1 突破到回踩之间的空隙有多长（T5 / F9 的量级）**。本机是 pc，没有截到 2025-12-31 的副本（pc 的 `datasets/pkls` 含 2026 年数据且复权有错，绝不能读），所以没跑；lead 确认改记成待验证项，不在 pc 上找替代数据。

- 在哪跑：upc，只读 `datasets/pkls_until_20251231`，训练段 2021-10-08～2025-12-31，bb_v1 默认参数，全部 match。
- 量什么：每个 match 里，从 burst 的末根 bo 到其后收盘最高那根（在末根 bo 与 tb 起点之间取）隔几根——用户多半框「放量突破」到末根 bo 附近、从高点开始框「回踩」，中间那段涨的通常不框，这就是两框之间的空隙。顺带报末根 bo 到 tb 起点隔几根。这只是代理：用户的框可能把那段涨一起框进突破，所以它给的是空隙的上限量级，不是用户框的实测。
- 判据（量之前定）：空隙超过 2 根的 match 占一半以上，就判「空隙 ≤ 2 天算连着」在主线 pattern 上会系统性切短。
- 判成切短时怎么办：改默认规则，不改方向（存成员、点名称块纠错都不变）。候选：往左一直收到同一 pattern 的上一个买点或图的左边，再由用户点掉；或把容差放宽到空隙的上四分位附近。选哪个由第一批真实标注定（见下一条）。
- 不论量出多少，第一批真实标注都要查「切短了但用户没改」：对每个买点，找图上紧挨着 bracket 左边、名字又在这个 pattern 的常见骨架里的非成员框，列给会话核对。只数「用户改过成员的买点」数不到这一类。

## 3. 总体判断

### 3.1 三份分稿收敛到的方案

- **存**：每个买点一份成员框清单（保存时算好的框编号）；不存范围、不存角色、不存「自动」标记；骨架、套框、对照状态都现算不存（topo.md §5.4）。
- **主图**：bracket 轨上的虚线范围由成员派生（最早成员起点到买点），对照时和 app 的实线 bracket 同轨；选中买点时成员粗虚线、非成员变淡，放下买点即自动选中。
- **改成员**：edit 栏的成员名称块与 others 名称块，点一下进 / 出；悬停名称块在图上描框；默认往左收「相邻两段隔不超过 20 根」的那串（待验证，往多收偏）；那次停留里新画或改动的框贴着就并进、只加不踢、离开即冻结（lead 拍板）。
- **关系**：不设编辑器。先后、包含看位置；不靠位置的写成后一个框的属性。path2 的边本来只比起止下标和身份（`path2/dag/edges.py`），这类关系在代码里也落在后一个 node 的字段 + where 上。
- **拓扑面板**：标注模式三个时期都不出现，看图模式照旧。原样复用会漏门槛数字；只借布局函数不值，且实测放不进侧栏。
- **pattern 层**：summary 改名 pattern tab，不新增 tab。上半是骨架与对应表合成的一张（每个名字一行，出现在几个买点里、由谁来认、认出几个、⚑）；下半是按顶层成员分组的买点（组头名称块链，→ pattern 下拉兼做归组与拆组，展开为名称轨缩略条）；未归类时它就是「决定哪些算一个 pattern」的界面。
- **对照**：每个框的状态只在主图；侧栏只留图上画不出的块间 link。

### 3.2 我的判断

推荐方案成立，并且比 lead 的候选更简：少存了范围、角色、自动标记三样东西，少开了一个 tab，关系与拓扑零新增控件。按第 0 节六条防线逐条看：

1. **冗余**：成员只有一处来源（清单），范围只是显示；骨架和对应表合成一张；买点列表只有一份，对应表点数是筛它；⚑ 只有一处。已无「同一信息两处编辑」。
2. **心智负担**：用户不碰 node / where / 边。对应表「由谁来认」一格已改成词表规范词（U10）；两种分数各带 `in` / `new` / `old` 标识符，不再靠图例句（U13）。
3. **已定 1～10**：标注模式不出现 app 拓扑与门槛；角色不手填（只在推不出时挂 `role?`）；当前 pattern 与买点归属照旧。没有发现需要推翻的已定项。
4. **对工作流有效**：每个元素都对到了具体步骤（flow.md §4.3 最小元素集合逐个写了「删了会怎样」）；被判为死元素的（role auto、train_score、auto / edited / reset、edit 栏骨架文字、对照连线）都已删掉。
5. **色弱**：全部靠深浅、线型、粗细、实心 / 空心三角，没有新颜色。
6. **文字 vs 界面元素**：骨架、成员、分组都改成名称块；缩略条用名称块当行首而不是图例；buy / no_buy 的 app 判定错的那格反白（U12）。pattern tab 仍是程序文字最密的地方，但每个数都有固定标识符，没有说明句。

### 3.3 残余风险（接受、写进最终报告）

1. **骨架与对应表就在主动点开的 tab 里**（U3 / F3）：标新图时用户随时能看到「由谁来认」和认出数，印象会往 app 的样子靠；「接触过 app」记不下这件事。只靠「选中框 / 买点自动切回 edit」压低，与票 Answer 第 6 节第 5 条同一类，接受不验证。
2. **默认成员规则的量级未知**（T5 / F9，待验证项 V1）：20 根是借来的数。往多收偏之后，夹在成员中间的多收框不改变 bracket 长度；它若是顶层框，会让这个买点在 groups 里自成一组，第二步看得见；它若是套在别的框里的小框，不进骨架，影响小。少收由「首次归组时一次过缩略条」兜底。
3. **按顶层名称序列完全相同分组会碎**：近义词、可有可无的成员都会拆出小组，第二步变成整理活；靠会话在对话里建议合并（flow.md §6 第 4 行的验证）。
4. **小尾巴**：pattern tab 属性子行的计数（如「放量 3/3」）还不带标识符，和 U13 同类，影响小，实施时顺手统一。缩略条只画「附近」的框：它的左边界应不窄于 topo 查「切短了但用户没改」用的窗口（40 根，待验证），否则 ux_2a 那种离得更远的横盘在缩略条里看不到，假小组在第二步不显形；两个数实施时取同一个。

### 3.4 最担心的一点

默认成员是整套分组的地基，而用户最可能的行为是「不看就接受默认」。方案对两个方向的错误都有可见的出口（多收出孤组、少收出淡色邻框），但这些出口都在第二步归组时才集中出现，不在标注的那一刻；如果第一批标注里默认错得多，第二步会从「一组一下」变成逐个返工。V1 和首次归组时的「切短了但用户没改」计数是唯一能提前看到这件事的地方，最终报告里要把它们列为第一批标注后的必做检查，而不是可选项。
