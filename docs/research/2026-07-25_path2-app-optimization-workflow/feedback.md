> 本文件记录研究交付后由用户提出的反馈。两类：
> **§0 定案性反馈**——推翻或收窄第一轮设计的决定，**第二轮设计的直接输入**；

## §0 · 定案性反馈：尺子的作用域（2026-07-26）

### 用户裁定

> pattern 的职责是**确定这只股票未来存在上涨的驱动力**。能不能真赚到钱很大程度取决于交易策略，**那不是 pattern 的责任**。
> 尺子 = `docs/research/pattern_config_scoring_standard.md` + 先涨后跌 / 先小跌后大涨的走势判据。
> 接受先按这个标准跑，**跑出来不理想再迭代**。

### 这条推翻了什么，以及它为什么是对的

**被推翻**：2026-07-26 讨论中我提议的「直接按止损止盈规则算期望收益」，以及把可执行性、波动率归一化并进判定链。

**这不是取舍分歧，是设计错误**：尺子一旦含止损止盈参数，它评的就不是 pattern，而是「**pattern + 某组交易参数**」的联合体。同一个 pattern 配不同止损值得分不同 ⟹ 分数下降时**无法判断该改 pattern 还是改交易规则** ⟹ 两层耦合在一把尺子里，**两边都失去独立迭代能力**。这比"考虑得太多"严重，它让优化循环失去方向。

**我引入它的动机本身也是错的**：当时的理由是"止损会自动为高波动付账，顺手解决波动率之争"。但用户早已表态**波动率暴露是他接受的风险偏好，不是缺陷**——⟹ **我把用户的风险偏好当成了需要修复的东西**，为了摆平一个统计争论而引入了一个业务上的耦合。本末倒置。

### 第二轮尺子的作用域划分

**移出判定链**（三样）：

| 项 | 去向 |
|---|---|
| 止损止盈期望值 | **完全移出**（交易层） |
| 可执行性（滑点 / 容量 / 价格分布） | 降级为**定案后的一道过滤**——pattern 选完看一眼命中集的价格与成交额，买不动就是买不动。**不进 score** |
| 波动率归一化 | 降级为**披露项**——报"命中集波动率是全宇宙几倍"，**不参与打分**（实测它不提 lift、只让分数变诚实；而用户接受这个敞口） |

**保留**（三样，全部与交易策略无关）：

| 项 | 为什么它不算"考虑太多" |
|---|---|
| **因果可容许闸** | **正确性问题不是复杂度问题**。买点锚点的 bar 不得早于该事件物化的 bar——纯粹是"这个信号当时是否已知"，与怎么交易毫无关系。A.3 的实例：同一结构改动，锚"事件成立那天"得 0.075、锚"事件开始那天"得 0.436（=回到过去买），后者三道硬门全过且极其显著；**而现成的 `eval_skeleton` 默认取的就是错的那个** |
| **平凡对照** | 几分钟的事，防止整套东西在复读市场平移 |
| **顺序闸** | 用户第 1 条判据的落地。**必须非对称**：先跌 `a%` 还是先涨 `b%`，`a < b`。对称版（±5%）测的是一个不会被使用的规则。`a/b` 由用户一次性声明——**那是风险偏好，不是搜出来的参数** |

### 第二轮尺子的完整形式

```
score = w · (median_maxhigh_配置 − median_maxhigh_基线)      ← 沿用现有标准，不动
w = n/(n+200)；硬门 n ≥ 200 且 q25 ≥ 0                      ← 沿用
排序用 median_confirm（买点窗第一天）                         ← 沿用
基线 = bo_only                                              ← 沿用

+ 顺序闸：非对称首次穿越比例 > 基线                           ← 新增（用户第 1 条）
+ 因果闸：买点锚点 bar ≥ 事件物化 bar                         ← 新增（机械可检）

披露（报数、不判定）：命中集波动率倍数 · 价格与成交额分布
```

**每一项都只依赖「信号发出的时刻」与「之后的价格路径」，不含任何持仓决策参数。**

### 两件不能省

- **基线继续用 `bo_only`**：它把"突破本身"的贡献扣掉，剩下的才是筛选条件的增量。实测 `bo_only` 自己在这套口径下就有 +72% 的原始抬升 ⟹ **若 pattern 相对它的增量很小，说明那些筛选没产生价值**。
- **记账（append-only）**：用户明确"不理想再迭代"——每一轮迭代都在消耗尺子的统计效力。至少记：本轮查询次数、所用窗口。很轻，但没有它，之后所有"这个提升是真的吗"都无法回答。

### 同一轮里被用户推翻的其它两条

- **「覆盖面够多 ⟹ 有泛化能力」不成立**（本条是我方论点，用户第 3 条判据）：同期买点非独立观测（一个月普涨的 100 个买点只是 1 次市场环境）；过拟合来自自由度而非样本量；**且本项目的样本量本身就是调参的产物**（`stop_confirm_bars` 2→0 使买点 41→423、`min_relative_height` 定在 0.2 恰为分数极值）⟹ 用它当泛化证据是循环的。
- **判据体系缺校准物**（未解决）：整套判据只在一个**已知不合格**的对象（bbb）上试过 ⟹ 只验证了"能否认出次品"，**完全没验证"会不会误杀良品"**。补法是拿公认有效且无可调参数的规则当参照（**52 周新高突破**——bbb 的已知有效近亲；12-1 横截面动量）。**用户判定不必展开，记录在此供第二轮决定是否采纳。**

## §1 · 因果闸的落地机制（2026-07-26）

### 用户提出的引擎层面标准化

**原问题**：现在每个 detector 要自己声明"我在哪一根 bar 上物化"，知识分散在消费者侧（burst 用 end、tb 用 start，恰好相反），容易出错。应该在引擎层面统一解决。

**提议**：在 `start_idx` / `end_idx` 之外增加一个 **`confirm_idx`**，表示"事件被确认成立的 bar"——只读 ≤ 这一根的数据就足以判定本事件成立。买点锚点须 ≥ `confirm_idx`。

### 两个可做的改动

#### ① 加 `confirm_idx`（支持，低风险）

**收益**：因果闸从"查 per-detector 的物化点声明表"塌成一行 `buy_bar >= ev.confirm_idx`，知识从消费者侧集中到 detector 侧。

**引擎能验证什么**：只能验证 `start_idx ≤ confirm_idx ≤ end_idx`（区间不变式）。引擎无法验证"只读 ≤ confirm_idx 就足够判定成立"——这是 detector 内部的事，引擎不知道它读了什么。**所以这是把约定挪到更容易守住的地方，不是机械保证。**

**关键设计决定（2026-07-26 用户异议后修正）**：`confirm_idx` **必填、无默认值**，每个 Event 子类都必须显式声明。

> 初稿写的是"默认值取 end_idx，只有 tb 需显式声明"。用户质疑：既然 confirm_idx 是引擎协议的一部分，为什么只有 ThrowbackEvent 显式声明？
> **质疑成立**：默认值（哪怕是保守的 end_idx）会把"哪些 event 该用 end_idx"这个判断藏回基类里——这跟要治的病（知识分散在消费者侧）是同一种病，只是藏深了一层。必填 + 显式声明，才能逼每个 detector 作者回答"我的事件在哪根上算成立"。

**核实过的各子类取值**（没有一个等于"碰巧的默认值"）：

| 子类 | confirm_idx | 理由 |
|---|---|---|
| `BOEvent` | `start_idx`（点事件） | 单根 bar，那根就确认 |
| `Distribution` | `start_idx`（点事件） | 同上 |
| `BurstEvent` | `end_idx` | 前缀物化：每实例在最后成员 bo（= end_idx）那根 emit。一串 N>min_bos 个 bo 产生多个实例，各自 end_idx 不同，各自 confirm_idx = 各自 end_idx |
| `TrendSegment` | `end_idx` | regime 切换才确认完整区段 |
| `Platform` | `end_idx` | 价格走出平台才确认 |
| `ThrowbackEvent` | `start_idx` | start_idx 本就是确认点 |

**实现**（改动面小，零 DIFF 验收）：
- `path2/core.py Event` 基类加 `confirm_idx: int = field(kw_only=True)`（必填，kw_only 避开字段顺序约束）
- `__post_init__` 加 `assert self.start_idx <= self.confirm_idx <= self.end_idx`
- 每个 Event 子类的构造点显式传 `confirm_idx=...`（取值见上表）
- 因果闸接上：买点锚点字段 `bar >= ev.confirm_idx`（必填，无 None 分支）

**全程 match 逐字不变。**

#### ② tb 的 `start_idx` 改回几何起点、消掉 `anchor_field`（不成立）

**动机**：tb 的 `start_idx` 当前是语义重载（= 确认点），如果有了 `confirm_idx` 承担确认职责，`start_idx` 可以解放出来指回触发它的 bo。那样就不用 `anchor_bo_id` 这个字符串字段 + 专门的边机制了。

**三层反对理由**：

1. **把身份约束换成了位置约束**。现在 `_anchor_ok` 比的是 `event_id`（结构等同）；改成 `gap==0` 后比的是位置。两者只在"一根 bar 最多一个 bo"前提下等价——这是偶然等价。
2. **tb 的身份定义会变，不是 match-preserving 的重构**。源码写明：同窗多 bo → 同 span 同 id，去重。如果 `start_idx` 改成 bo 的位置，合并的事件会因为 `start_idx` 不同而裂成多个独立事件，去重不再发生 → 命中数虚增。要保持等价，去重键必须同步改成 `confirm_idx`。
3. **`anchor_field` 存在的根本原因**：burst 的 `last_bo` 和 tb 锚定的 bo **是同一个 event 对象**，DAG 边只能表达关系、不能表达同一性。`anchor_field` 比的是 `event_id`，这是结构等价方式。改成 `gap==0` 等于把"同一"降级编码成"位置巧合"，前提一破就静默错配。且项目正在往多同 bar 同类事件的方向走（`assign_auto_source_tags`）。

**求解器耦合**：`anchor_field` 不只影响 `satisfies`，还进了求解器——`_solve.py:88` 把 anchor 边的 src 节点单独加进前沿签名源。动它要连 INV-C 剪枝正确性一起验，而那块的 bug 上次是靠多候选 fuzz 才抓出来的。

**结论**：两件事应分开。加 `confirm_idx` 是低风险纯增，可以随时做；改 tb 的语义是另一件事，应作为独立提案单独论证，不应作为加字段的副产品。

### 另一条路：tb 用 child 表达"被某个 bo 触发"（全栈重构，非增量）

项目已有 nested event 机制（`child_slots` / `Child(node,key)` 端点选择器）。

tb 可以把触发它的 bo 声明成自己的 child —— `anchor_bo_id` 字符串升级成真正的对象引用，`where` 能直接读那个 bo 的字段，而不只是拿到一个 id。

**好处**：tb 能直接读 bo 的字段、几何起点被干净表达；在 `visible.ts` 一处反而简化（bo 走 child_refs 自然进可见集，anchor_field 弱引用反查路径可删）。

**代价（被严重低估过，此处修正）**：`anchor_bo_id` / `anchor_field` 是一条**贯穿全栈七层的机制**，不是局部字段。改它牵动：
- **引擎核心**：`edges.py` `_anchor_ok`（同一性复核）、`_solve.py` 前沿签名第 5 源（anchor 边专用，改它须重跑 fuzz）、`spec.py` `_validate_anchor`
- **序列化 / 诊断**：`serialize.py` topology.edges schema、`diagnose.py` 诊断通道③（整个为 anchor 复核设计）
- **前端**：`render/visible.ts` 的 `matchedIds`（主图可见集算法）、`stores/view.ts` 的 `findBoBar`（tooltip/marker 定位用 anchor_bo_id 反查）、`types.ts` `TopoEdge`
- **测试**：十几个测试文件
- **skill / 研究脚本**：`label-study/extract_skeleton.py`、`2026-07-20_label-study-tb-pullback-vol-shrink/extract_vol_shrink.py`

⟹ **净影响是"换掉一条全栈机制"，不是"加一层"。** 成本量级远高于 `confirm_idx`（后者只动基类 + 6 个构造点 + 评估层一行）。**两者必须分开**：`confirm_idx` 是局部改动可先做；child 方案是全栈重构，应作为独立提案单独评估。

## 疑问 1 · 波动率的测量窗口，可能测的是突破本身

**提出时间**：2026-07-26 ｜ **状态**：✅ **已闭合**（2026-07-26 补测，见文末「补测结果」） ｜ **影响范围**：g 项（波动率暴露体检）整路，**不影响 c 项**

> **结论速览**：**主体是混杂，疑问不足以推翻 g 项，但确实改了它的正确做法。**
> 命中集在突破发生之前就已经比全宇宙躁动 **1.83–2.13 倍**（`bo_only` 则是 1.5 倍且完全不随滞后变化）。**这个定性答案对滞后档的选择稳健**——所有 L≥40 的读数都远高于 1。
> 突破本身只贡献了超额的约 **29–46%**，其余是这些股票的先在属性。
> ⟹ **A.1 最锋利那条（`bo_only` 的 +72% 控制后归零）不受影响，反而被加强。**
> ⟹ 但 g 项的匹配口径**应当改用滞后波动率**，否则会连中介一起控制掉，系统性低估 pattern 的残差。

### 用户原话

> 波动率的衡量是在启动大涨之后，还是 tb 到来之前？如果是启动大涨之后则是不可避免的，**你不能要求一只股票又大涨又不波动**。

### 为什么这个疑问要紧

它问的是一个因果推断上的分岔，而两条分岔通向相反的结论：

| 如果波动率是…… | 它的身份 | 控制它是…… | g 项的结论 |
|---|---|---|---|
| 突破**之前就存在**的属性 | **混杂因素** | 正确——你选中的只是本来就躁动的股票 | 成立 |
| 突破**造成**的结果 | **中介变量** | **过度控制**——把策略的效应本身控制没了 | 塌掉 |

**这不是措辞之争。** A.1 里那条最锋利的结论——"bo_only 原本 +72% 的 lift，控制波动率与月份之后完全归零"——**完全建立在"波动率是混杂而非中介"这个前提上**。前提若不成立，那句话就该改写成"控制掉了策略赖以生存的东西之后，策略没有剩余效应"，而那是一句几乎没有信息量的话。

### 现状核实（2026-07-26 现场读代码与文档）

**主口径 `rv63` = 买点前 63 个交易日的对数收益标准差，只用 ≤t 的数据**（定义见 `07_operational_spec.md:715`）。

⟹ **63 天的窗口把突破那一段包含进去了。** bo 与 burst 发生在买点前几天到几十天内，所以主口径上用户的质疑**成立**，测量确实有部分自我度量成分。

研究组预见到了这一点并做过滞后检验，`final_report.md` A.1 的原文是：

> 且**不是自我度量**（换成滞后 40/80/120 交易日的波动率，偏斜基本不变）

**但这条检验的具体数字没有被记录下来。** 只有"基本不变"四个字，没有数值表；执行这项测量的角色没有独立中间文档，产出直接并进了附录。**⟹ 目前既无法核实，也无法重跑。**

> 按报告自己 §附录 B.2 那条纪律——**转述数字必须连同证据等级一起转述**——"基本不变"本身就是一个成色已被压缩掉的表述。**这条缺口是那条纪律在本报告自己身上的又一次复现。**

### 需要补什么

**滞后波动率倍数表**，落数、进版本控制。

```
rv63_lag_L(t) = 用 [t − 63 − L, t − L] 这段窗口算的 rv63
L ∈ {40, 80, 120}（至少三档，见下方 ⚠）
指标 = median(rv63_lag_L | 命中集) / median(rv63_lag_L | 全宇宙同期)
对照 = 主口径的 2.46x
```

**⚠ 一个决定检验有没有效力的技术要点**：**`L` 必须大于 pattern 自身的完整时间跨度**（从最早的 bo 到买点那根）。若 pattern 跨度是 60 根 bar，那么 `L=40` 的滞后窗口 `[t−103, t−40]` **仍然覆盖着突破的一部分**，检验会自带污染而不报错。

⟹ **补测前先量一下命中集的实际跨度分布**（`buy_idx − 最早 bo 的 start_idx`），取 `L > p95`。原研究选 40/80/120 时**有没有做这个核对，无从得知**——这也是数字丢失的连带损失。

**成本**：低。复用 g 项现成的面板逻辑（`stage0_probe.py` 的 `rv63` 面板部分），只改窗口偏移；面板首次构建约 3 分钟，之后秒级。

### 判读规则（先写死，免得看到结果再定）

| 滞后口径下的波动率倍数 | 判读 | 后续动作 |
|---|---|---|
| 仍显著 > 1（接近 2.46x） | **混杂** | g 项成立，A.1 结论逐字不动 |
| 回落到 ≈ 1 | **中介** | g 项那一路作废，A.1 需重写；"分数在奖励波动率"降级为"分数在奖励涨幅，而涨幅必然伴随波动" |
| 居中（如 1.5x） | 部分混杂、部分中介 | 需要更细的分解，本表不够用；届时另行设计 |

### ⚠ 影响范围的边界：不要扩大解释

**即使这条疑问最终成立（波动率是中介），也只推翻 g 项那一路，不触及 c 项（首次穿越）。**

c 项不做任何波动率控制，它直接比较"先涨 /(先涨+先跌)"与随机日的差。实测 `pk4` 在 8 个（年 × 阈值）单元里 **7 个低于随机日**，2024 全部四档 t = −3.0 ~ −4.0，且在同根命中比例最低的 15% 档（`pk4` 仅 3.5%）结论依然成立。

⟹ **"这个 pattern 在方向上没有优势"这条结论有独立支撑，不依赖疑问 1 的答案。**

## 待补测 2 · b 项口径一致性：`max_high_20` vs `max_high_40`

**确定时间**：2026-07-26 ｜ **状态**：⬜ 未执行 ｜ **来源**：用户声明持有期语义后导出的替代口径

### 它替代了什么

b 项初版用"20 日持有到期"当替代口径，得到秩相关 −0.186，被当成"目标函数在度量另一个维度"的证据。**该结论已撤回**（见 `final_report.md` A.1 的用户异议）——持有到期换掉的是持有期语义，不是度量维度，对一个"pattern 找入场 + 独立卖出程序兑现、允许回撤到买入价以下"的策略，两个口径本就不该一致。

**替代口径改为**：

```
口径 A = max_high_20  = max(high[t+1 : t+20])  / close[t] − 1
口径 B = max_high_40  = max(high[t+1 : t+40])  / close[t] − 1
```

同为 max-high 语义，**只换窗口长度**，与声明的持有期语义兼容。

### 它问的是什么

**不再是"度量维度是否一致"，而是"这个信号的优势对时间窗口有多敏感"。**

这个问题直接对应那个尚未开发的卖出程序有多大择时容错空间：

- 秩相关高 ⟹ 优势不依赖精确择时，什么时候卖差别不大，卖出程序好写
- 秩相关低 ⟹ 优势是短促的，必须卡在特定窗口内兑现，容错很小
- 秩相关为负 ⟹ **这才是原 b 项想抓、但抓错对象的那个真警报**：候选的排名会随窗口长度反转，说明"哪个候选更好"这句话本身没有定义

### ⚠ 一个会让判读整个失效的结构性事实（必须先处理）

**40 日窗口包含 20 日窗口**，所以 `max_high_40 ≥ max_high_20` 恒成立，两个指标共享前 20 天的全部数据。

⟹ **秩相关的零假设基线远高于 0，甚至可能高于 0.8。** 直接拿"相关系数 0.7 算高吗"来判读是错的——0.7 在这种嵌套结构下可能已经**低得反常**。

**必须先估基线**，做法就是 a 项平凡对照的复用：

```
用全宇宙随机日买点跑同样两个口径，算它们的 Spearman ⟹ ρ_null
真正的判据 = ρ_候选排行榜  与  ρ_null  的差，不是 ρ 的绝对值
```

**没有 `ρ_null` 就不要读这个检验的结果。**

### 判读规则（先写死）

| `ρ_候选` 相对 `ρ_null` | 判读 | 后续动作 |
|---|---|---|
| 接近或高于 | 优势对窗口不敏感 | b 项 PASS，卖出程序择时压力小 |
| 显著低于 | 优势是短促的 | b 项 WARN，**卖出程序必须窗内择时**，把这条写进它的设计约束 |
| 显著为负 | 排名随窗口反转 | b 项 FAIL，"哪个候选更好"无定义，回去修目标函数 |

### 需要什么才能跑

- **多候选**。秩相关需要一个候选排行榜，不是两个配置。原研究的 contender 集合 `K=23` 可复用其构造规则（单旋钮邻域 + 去 where 子句 + 节点子集拓扑），**但那批脚本已随 `temp_code/` 清理删除**（`05_opt_methodology.md` §8 局限第 7 条），只留复现要点，须照要点重写。
- **`label_horizon=40` 的一次重跑**。`repro/opt2_collect.py` 写死 `H=20` 且只有 2 个配置，不能直接用。

### ⚠ 两个实施注意

1. **40 日口径把尾部缓冲从 20 天推到 40 天**，会进一步吃掉终局 holdout（`final_report.md` §7 实测已只剩约 3.5 个月、`n≈120` 过不了硬门）。⟹ **本项只在搜索窗上跑，不占用终局窗。**
2. **两个口径必须在同一批买点上算**（公共随机数），否则窗口差异会和抽样差异混在一起。

### ③ 判读

**按 feedback 事先写死的规则**：倍数"仍显著 >1 但未保持在 2.46 附近" ⟹ 落在**居中档**，需要分解。

**分解 —— 给区间，不给点估计**（初稿只取了 L≥160 一个读数，见 ④ 的更正）：

| 用哪段窗口当"突破前的波动率" | 2025 倍数 | 混杂占超额的比例 |
|---|---|---|
| **L=40**（买点前 2–5 个月，即 pattern 要求的横盘期内） | 1.83 | **54%** |
| **L≥160**（买点前 8–10 个月，横盘期之前） | 2.10 | **71%** |

⟹ **结论对 L 的选择是稳健的**：**所有** L≥40 的读数都在 1.83–2.13 之间，全部远高于 1。无论取哪一档，答案都是同一个——**这些股票在突破发生之前就已经明显比全宇宙躁动**。

⟹ **用户的疑问部分成立：确实有 29–46% 是"大涨必然波动"。但主体（54–71%）是先在的属性，不是突破造出来的。**

### ④ 一个非单调，以及它的机理（内部一致性检验）

`pk4` 的曲线是 **U 形**：L=40 最低（1.83），随 L 增大回升并在 L≥160 稳定（≈2.1）。

机理：**pattern 的结构里有横盘要求**（`burst.first_drought_min = 20`，即 burst 之前须有 ≥20 根无突破的干旱期；加上"底部启动"的整体语义）。所以 L=40 那一档测的是**命中集在横盘期内**的波动率，L≥160 测的是**横盘期之前**的波动率。**两个都是真实读数，回答的是不同的问题。**

**内部一致性**：`bo_only` **没有**任何横盘/干旱要求，它的曲线**完全平坦**（1.49–1.54）。
⟹ **U 形只出现在有横盘要求的那个配置上，平坦只出现在没有的那个上。** 这不是噪声，是结构的指纹。

> **⚠ 初稿在这里犯了一次措辞上的倾向性错误，原地保留当教训（2026-07-26 用户指出，成立）。**
> 初稿写的是"波动率被**人为压低**""测到的是 pattern **自己造出来的**平静期""L≥160 才是**不受结构影响的常态**"，并据此只取 L≥160 一个读数做分解。
> **三处措辞都把 pattern 的正确行为写成了人工制品。** 横盘期不是 pattern 制造的假象——**它是真实的市场结构（机构建仓吸筹阶段），也正是这个 pattern 有意要捕捉的特征之一**。命中集在启动前确实经历过一段相对平静期，**这是形态特征被正确捕捉的量化证据，不是需要被排除的污染**。
> **而且那次措辞恰好服务了一个对我有利的选择**：只取 L≥160，混杂占比 71%；若取 L=40 则是 54%。**我在一个有自由度的地方挑了让原结论更好看的那个读数，并用贬义词给这个选择做了包装。**
> ⟹ **更正**：两个读数并列（见 ③），并强调**结论不依赖这个选择**——所有档位都给出同一个定性答案。**这个表述既中立，也比原来更强。**
> 同型前科：[[feedback_argument_discipline]] 记录的"把契约正确行为污名化为脏数据"。**同一类错误，第二次。**

**⟹ 滞后档的选取规则（中立表述）**：**报告整条滞后曲线，不要只挑一个点。** `L` 要大于 pattern 跨度（必要条件，否则窗口仍含突破段）；此外**不同 L 对应 pattern 语义里的不同阶段**（本 app：L≈40 落在横盘期，L≥160 在横盘期之前），**它们各自有独立的解读价值**——曲线形状本身就是 pattern 时间结构的读数。判断混杂/中介时看**整条曲线是否一致地高于 1**，而不是取某一档的值。
