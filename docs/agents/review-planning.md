# Review planning for implementation tickets

Read and apply this document whenever implementation tickets or `Blocked by`
prerequisites are added, by any route: a breakdown (`to-tickets` or an equivalent
workflow), a decision answer that proposes tickets, a follow-up to a closed
ticket, a user question's resolution, or a scope adjustment. Draft the tickets and
their prerequisites first, then apply this document before they are presented for
review: finding a build-on point (Step 2) follows the prerequisites. This document
settles where the user reviews results, so that the acceptance criteria carry the
review and executors never decide it.
[implementation-tickets.md](implementation-tickets.md) governs everything else
about the tickets.

Every ticket already gets checkable acceptance criteria, tests and an independent
code review (implementation-tickets.md). This document adds only human review, and
only where a wrong result would otherwise be built on.

The user decides direction, not parameters (see User questions there): this
document asks the user only where a wrong choice of review would be expensive, and
fills in the rest from a recommendation the user can still change.

## When the source already says

If the spec, a decision or an approved validation item already specifies how a
result is reviewed, copy it into the ticket and skip the steps below for it. Do
not ask again.

Project rules that force a review regardless of planning still apply. Account for
them in the plan instead of planning a second review of the same thing.

## Step 1: what only the user can judge

Put everything checkable into acceptance criteria: tests, metrics against an
approved reference, invariants, comparisons with recorded outputs. What is left is
what only the user can judge: whether it is what the user wants, looks real, reads
well, feels right. If nothing is left, the ticket needs no human review.

## Step 2: is anything built on it?

A result's **build-on point** is the first later step whose result would have to
be redone, not merely rerun, if this result turned out wrong, and that happens
before the user would otherwise see this result:

- an expensive or irreversible run: a long job, an output generated only once
  (such as a fixed validation set), a release;
- a judgment made from this result's behaviour: a decision, a tuned parameter or
  calibrated threshold, a reference other work is accepted against;
- substantial human effort on it, such as labelling or manual repair.

The step may lie inside the ticket itself (its own long job) or in a successor.
Code that uses the result only through an interface is not a build-on point:
fixing the result behind the same interface leaves that code valid.

Find it by walking downstream from the ticket: the tickets that list it in
`Blocked by`, then theirs, and so on, until the first step that would have to be
redone. A ticket that would only rerun on a corrected result is passed through,
not stopped at. Look beyond the drafted breakdown too: already published tickets,
and work outside tickets that the spec or decisions say will consume the result,
such as jobs the user runs or a release.

Keep the term `build-on point` untranslated in tickets, breakdowns, questions and
other prose in the project's language, so every session uses the same word.

If a later review already shows this result before its build-on point, the review
belongs there; record that instead of planning another one.

- Something only the user can judge, and a build-on point exists: plan a **human
  review gate** (see Where and when the review sits).
- Something only the user can judge, but no build-on point: plan no review and
  record the skipped part on the ticket (see Writing it into the ticket).

Whether a long job follows never calls for a review by itself: what the result
contains and what is built on it decide. A typical case is data generated by one
ticket and consumed by a formal training run. The training run is the data's
build-on point, so the gate goes in the data ticket, which can still change the
data, not before the training run, which cannot.

## Where and when the review sits

1. **Where**: in the ticket that can still change the result, normally the one
   that produces it. Only when that ticket is already closed does the gate go into
   the ticket that depends on the result, immediately before its build-on step.
2. **When**: no earlier than the first output sufficient to judge (a trial run, a
   small batch, a prototype) and no later than the first build-on step. Within that
   window take the earliest point, so a failed review wastes least. If a full
   generation is itself a long job, review a trial batch before the full run and
   let machine checks compare the full output with the trial; if it is cheap,
   review the full output before the ticket is done.
3. **Which version**: the version that will be built on. A gate at the end of a
   ticket comes after the machine checks, the independent code review and its
   fixes, and any regeneration they require; merging and completion come after the
   gate. Record the reviewed version (a commit or an artifact hash) in the
   question's answer and under `evidence/<NN>/`. A material change to the reviewed
   result before its build-on step voids the review: review again.

## Adding tickets or prerequisites later

Walking downstream from a new ticket misses the reverse case: the new ticket can be
the build-on point of an older result whose user-only part was skipped. So when a
ticket or a `Blocked by` edge is added after the original breakdown, or the spec or
a decision newly declares work outside tickets that consumes a result, also walk
upstream from the new consumer along `Blocked by`, passing through tickets that
would only rerun.

For each upstream ticket carrying a `未安排人审：` line, ask whether a step of the
new consumer is that result's build-on point. If it is, add a human review gate: in
the upstream ticket when it has not started (then check Make sure a gate holds);
otherwise in the new consumer's ticket, immediately before its build-on step.
Present the added gates in the same round as the new tickets or prerequisites.

## Make sure a gate holds

A human review gate placed in an upstream ticket, before it is done, holds the
build-on point back only through prerequisites: the ticket containing the build-on
point waits because it lists the upstream ticket, directly or through others, in
`Blocked by`. Check that it does. If it does not, add the missing prerequisite when
it reflects a real technical dependency; otherwise move the gate into that ticket,
just before its build-on step, as the second case of rule 1 in Where and when the
review sits.

## The recommendation

Write one for every human review gate, choosing the method from the ticket's
content rather than from a fixed list:

- **What the review covers**: what the acceptance criteria check, what is left for
  the user, in one or two sentences.
- **Method**: how the user judges the remainder, for example inspecting rendered
  samples, trying the interface, reading output excerpts, listening, or comparing
  with real or reference cases side by side.
- **Timing**: the gate's position under Where and when the review sits, and the
  build-on point it protects.
- **Samples**: picked by machine, not at random: the most suspicious by the
  metrics (extremes, values near thresholds, failures), two or three typical
  ones, at least one per category, within a size the user can review in one
  sitting. Each sample is labelled so the user can point at it.
- **Outcome handling**: what a pass confirms: the result only. A pass never
  approves launching a long job; that approval is a separate question about the
  machine's time. On failure, fix within the ticket and review again, or return to
  the decision process if the fix changes an interface or an approved decision.
- **Alternatives**: one or two other methods or timings with their cost, such as
  merging into a later gate, or planning no gate and recording the part as
  unreviewed.

## Asking the user

Ask in the round where the proposed tickets are reviewed, not in a separate round.
Use the interactive question tool (AskUserQuestion in Claude Code): the
recommended option first, labelled as recommended, then at most two alternatives
and a "decide later" option; free-form answers go through the tool's own "Other".
It takes at most four questions per call, so split larger rounds into several
calls, keeping gates that share a build-on point together.

- **Human review gates: one question per gate.** The header names the ticket. The
  question states what only the user can judge, the build-on point the review
  protects, and the recommended method and timing. The recommended option's
  description gives method, timing and cost; alternatives include planning no gate
  (recording the part as unreviewed, with what that risks) or merging into a later
  gate. Gates that share a build-on point go in the same call, and the question
  says whether one review can cover them.
- **Every other ticket: one question for the whole round.** The breakdown first
  lists every other ticket on one line each: the ticket and either "no human
  review" or its `未安排人审：` line with the reason. One question in the last call
  then confirms them: "apply as listed" (recommended), or "change some" with ticket
  numbers and changes written in "Other", most often adding a gate. If the
  breakdown itself is approved through the question tool, fold this into that
  question instead of asking separately.

## Writing it into the ticket

Executors stop only where the acceptance criteria name a human review gate, so
write it there, in the project's prose language, with these exact prefixes. They
are the only classification: do not add numbered levels.

- Ordinary acceptance criteria carry no prefix.
- `人审闸（停在 X 之前）：` names a human review gate. X is the step it precedes.
  Then state what is shown and how, how samples are picked, what a pass confirms
  (the result only, never a launch) and what happens on failure. The executor
  stops before X and asks through a question.
- `未安排人审：<the part only the user can judge>；原因：<why there is no build-on
  point, such as consumers using it only through an interface, or no consumer>`
  records a skipped review. The executor does not stop for it; later additions
  (Adding tickets or prerequisites later) and execution (implementation-tickets.md)
  read it.
- Record in Comments where the review came from: copied from the source, chosen by
  the user at breakdown, or written from the recommendation.

Reviews that only become apparent during execution follow implementation-tickets.md
(User questions): an executor about to perform a build-on step on a result whose
user-only part was never reviewed stops and asks. Anything else goes into the
completion record's limitations.
