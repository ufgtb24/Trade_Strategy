# 处理清单与出题

第 3、4 步读。归到哪一段是你的判断；这里规定每条必须交代什么、怎么问。

## 一份清单，按去向分三段

两种输入——反馈的 issue、标注里的样本与特征——放进**同一份清单**，按「接下来会发生什么」分三段。一轮只改一版 app，所以清单一次给全，题答完再一起动手。

| 段 | 放什么 | 用户要不要选 |
|---|---|---|
| 一、我这一版直接改 | issue：app 认得比用户的定义松（定义里已有这句话，app 没查或查得松）；样本：和 app 相反、毛病是结构性的；还没对到 node 的新特征（打算对到哪一块，或新加哪一块） | 不用 |
| 二、要你定 | issue：理由成立，但定义里没有这一条；样本：和 app 相反、你拿不准的；上一轮以来的变化里必须问的（见下） | **要** |
| 三、这一轮不改 | issue：当天看不出 / 只差门槛 / 量过不值得加；样本：只差门槛的 | 不用，可以反对 |

归类的依据只有：note、点出的 node、用户的定义、图上 app 实际认出的东西（`look.py` 的输出）。点出的 node 说问题落在哪一块；一个都没点时由 note 判断是不是整体或拓扑上的问题。

- **一个 issue 可以拆开**：能翻成当天看得到的条件的部分归一或二；这条件挡不掉的那几天归三（当天看不出）。
- **你判断是同一件事的几个 issue 并成一条**，写明并了哪几个。
- **账本里已有记录的 issue**（摘要在该 issue 下列出）沿用上次的结论，不重新争论；有新标的处、或内容改过才重看。
- **「只是后来跌了」**（样子对、当天也看不出毛病）归三，理由写「当天看不出」。
- **「量过不值得加」只在确实量过时才能写**；量归 `feature-study`，这里不量。
- **代价只报买点个数一类的事实**（会多查一条什么、哪几处会受影响、数得出时能挡掉范围里几天），不报收益。改完之后范围内外各砍掉多少，由改版报告给。
- **上一轮以来的变化里必须问的**，并进第二段：
  - 样本改判了、收的框没变：问「改判的理由那天看得见吗」；
  - pattern 定义的文字变了：问是改说法、放宽、收窄，还是换了想法。账本里已有一行写明这句是用户照上一轮建议贴的，就不再问。特征定义的文字改了不会出现在「上一轮以来的变化」里（摘要的定义一节给的总是定格时的原文）；
  - 某条反馈的范围里出现了用户自己的正样本（摘要在那一处标出）：问这一处以哪个为准。
- 用户的定义放宽后不再成立的旧反馈：在第三段说明，记账时挂 `redefined`。

## 一条反馈怎样才算改好

摘要和改版报告里每处反馈的状态，按用户标的方式判（判法只有一份，在 `path2_web/annotation/match.py`）。写「我打算」和报「代价」之前先对一遍，免得承诺一个做不到的结果：

| 用户怎么标的 | 还在买（`matched`，页面上朱红） | 恢复常色（`unmatched`） |
|---|---|---|
| 一天、拖出来的一段 | 范围里还有任何一天在买 | 范围里一天都不买 |
| 一族 | 范围里还有买点，**或**这一族（起点相同的 hit）在别的日子还在买 | 这一族一天都不买了，但起点那个事件还认得出 |

- 一族的反馈另有第三种状态：连起点那个事件都认不出了（摘要和报告里写「起点认不出」）。它可能是改好了，也可能只是认法变了（比如某一段的长度改了，全部起点平移），所以报告里每条都要交代是哪一种。页面上它显示成 `unmatched`（不买了）；你判为「认法变了、毛病还在」并挂了原因标签的，页面上是 `unmatched` 加标签，用户靠这个标签看出还没改好。
- 所以一条只挡掉其中几天的条件，改完这一处仍然是「还在买」：在清单里照实写「能挡掉范围里哪几天，剩下几天挡不掉」，剩下的归第三段。
- 条件读的是事件上现成的字段时，挡得掉哪几天现在就数得出——`look.py` 的表里那一列各天的实测值对着拟用的门槛看；要新字段的，写「改完在报告里给」。

## 给用户看的格式

一条消息，并且**这条消息必须以一个工具调用结尾**：有题就紧跟出题的调用，没有题就紧跟写 `.plan.md` 的调用。会话中途发一条不带调用的消息，这一回合就结束了，后面的步骤都不会发生。「中途消息正文至多一句状态行」的纪律在这里是例外：正文就是清单全文。

标注有冲突、越界，或数据指纹不一致时（第 0 步看到的），在清单最前面加一行如实说明，不单独发消息。

issue 用理由原话指代，样本用「股票 + 日期」指代；链接用摘要里现成的。每条都要有：用户原话（或股票 + 日期）、标在哪几处、有关的定义原话、app 现在怎么认的、你打算怎么办。

没买到的正样本每张一行，都要有一句「卡在哪」：页面上不显示 app 把框认到了哪一步，这一行是用户知道原因的唯一地方。用他的词说（如「阶跃切晚了一天，算出来的涨幅不够」），不出现档位名（detected、qualified、in_hit、missing）、node 名和条件名。

```
这一轮：你标了 N 个 issue（M 处），和 app 相反的样本 K 张，新特征 J 个。

一、我这一版直接改（a 条）
1. 「<理由原话>」——3 处（[CRNC 2025-01-07～01-30](链接) 等），落在 <node 对到的你的特征名>
   - 你的定义：「<定义里的原话>」
   - app 现在：<一句白话，眼下怎么查的>
   - 我打算：<一句白话，改成怎么查>
2. 正样本 [AAPL 2024-03-08](链接) 没买到：<一句白话，卡在哪>；我打算：<……>
3. 新特征「<特征名>」：<打算让 app 的哪一块去认，一句白话>

二、要你定（b 条，下面逐个问）
4. 「<理由原话>」——1 处（链接）
   - 你的定义里现在：<有关的原话；完全没提就写「没有提到」>
   - 写进定义的话：会多查一条「<翻成的当天条件，白话>」，这一类以后都不买

三、这一轮不改（c 条）
5. 「<理由原话>」——2 处（链接）：当天看不出——<一句理由>。不同意就告诉我。
```

某一段为空就写「没有」，不省略段名。

## 出题

只对第二段，用 AskUserQuestion。

- 一轮 3～5 题以内，多了挑最要紧的，其余当「先放着」留到下一轮。一次调用最多 4 题，第 5 题另起一次。
- 题目正文用白话写清三件事：在哪几处说了什么；现在的定义怎么说；选了各会怎样。读一遍就能选，不需要先翻清单。
- 你推荐的选项放第一位，标签末尾加「(推荐)」。
- 不让用户定门槛，不让他在 node 和 where 之间选，不问拓扑和 detector 选型。
- **「定义里没有这一条」的 issue，选项固定三个**：

  | 选项 | 选了会怎样 |
  |---|---|
  | 写进定义，这种以后不买 | 你给出建议的措辞，请用户自己贴进页面上的 pattern 定义；这一版 app 先加上这条条件 |
  | 不写，这种可以买 | app 不改，这几处继续买 |
  | 先放着 | 这一轮不动，下一轮再问 |

- 用户拒绝选择、想先弄清楚时，只把来龙去脉讲清，等他表态再继续；不在解释后面立刻再挂一道题。
- 用户对第一、三段有异议时，照他的意思挪段，不争。

## 存下清单

题答完后，把清单全文连同每题的选择写进本轮的 `.plan.md`；没有题时，写 `.plan.md` 就是清单那条消息结尾的调用，不能跳过；用户选了「写进定义」的，把你建议他贴进定义的那句话也写在那一条下面。
