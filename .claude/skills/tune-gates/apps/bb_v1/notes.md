## 2. 分类实测

| 类别 | 维度 |
|---|---|
| D（5 个，进检测组合笛卡尔积） | `bo.min_relative_height`、`bo.exceed_threshold`、`burst.gap_max`、`tb.stop_confirm_bars`、`tb.big_rise_k` |
| F（2 个，不进检测组合，事后按字段谓词切） | `burst.min_bos`→`burst.count`（`>=`）、`tb.max_day_drop_pct`→`tb.day_drop`（`<`） |

- **检测组合数** = 5 个 D 维 × 4 档 = **1024**；联合空间 442,368 格，真正调用 `engine.analyze()` 的只有 1024 次。
- **选维排除**：`tb.big_rise_k` 与 `tb.atr_window` 共线（都在表达「涨幅相对 ATR 的倍数」），`atr_window` 用机制值不扫；`bo.vol_baseline_period` / `burst.vol_baseline_period` 等口径参数也不进网格。

## 3. 扫描实测（2026-08-25 轮）

```
股票 8325 待扫;进 detector 6720 / 过滤 1605 / 有 match 3985 / 异常 0
检测组合数 1024;累计行 7,831,477(约 1165 行/股)

每股耗时 ms(6720 股):p50 1385.2 / p90 2260.1;每检测组合均摊 1.400ms/股
```

- 数量级核对：p50 1385.2ms / 1024 组合 ≈ 1.353ms/组合，与均摊值自洽。
- **选维结论**：F 维不进检测组合、事后按字段谓词切，是常数级开销；D 维每加一维直接 ×4。同口径对照里把 `min_bos` 从 D 挪到 F，每股耗时从 1688ms 降到 1114ms——能事后切的参数优先放 F 类。

## 5. 识别实测（2026-08-25/27 轮，旧流程）

当时的功效线是每折 100 个买点日（逐行口径），在 12 维之前的 11 轴联合空间上直接找区：

```
联合空间 (4,4,4,4,4,4,3,3,3,2,2) = 442,368 格;可评估 361,629(81.7%)
邻域分为负 361,412 / 361,629 可评估格(≈99.94%);仅 217 格邻域分 >= 0
推荐格:朴素邻域分 0.0705;对半分验证 -0.1319;
```

四条证据合读：朴素分为正，但扣掉挑选偏差后与对半分验证都转负；300 个副本里只有约 21 个重新选中推荐格的 r=1 邻域。判读 = **未观测到稳健区**，与 bb_v1 既有「无底子」先验一致，是预期内的负面结果、不是管线失败。那一轮没算选中稳定性的零基线，不对 0.07 是否「接近随机」作定性。

## 6. 复核记录（2026-08-25/27 轮）

- **first_drought 闸在部分格里结构性恒真**：chain 簇首必是断点，所以 `first_drought > gap_max` 结构性成立；阈值 ≤ `gap_max` 的格里这道闸拦不下任何东西，读数应视同未设该闸（唯一例外是簇首恰为扫描窗首根 bo，那时取 `drought_floor`，是首部缓冲不够、不是闸生效）。现在的联合识别按「紧档计数与相邻松档全等」把这类格自动标为退化格、不可评估，不再靠手写规则打标。
- **可评估面**：逐行口径功效线 100 时 81.7%，敏感性口径 300 时 56.1%——面缩小符合预期，但不能反推「朴素分为正的格数也变少」（实际从 217 变到 504）。
- **推荐格 ≠ 采用**：选中稳定性只有 0.07，是「不采用」的直接依据。

## 8. 坑的具体案例

对应 `reference.md` §6 的通用教训：

1. **验证夹具字面代码不能跑**：纯 Python 语法问题（两侧元组键 dict 用 `dict(a, **b)` 直接炸），无 app 相关数字。
2. **F 维参数误放进 where 档**：`tb.max_day_drop_pct` 是 F 类，放进 `WHERE_LEVELS` 会被 `classify()` 拒绝；它的字段 `tb.day_drop` 是 `<` 语义，掩码判断要按运算符。
3. **比较键写死含孤立 node `bo`**：`bo` 不进求解集，长表没有 `bo.start` / `bo.end` 列，取键直接 `KeyError`；比较键只用 `burst`、`tb`。
4. **夹具缺股票级前置过滤**：直接调引擎没有 `volume_min` 均值前置过滤；1337 只候选先验排除 259 只过滤股，剩 1078 只。
5. **窗口预读的 `len(win)<300` 边界多余**：它漏掉 71 只股票（长表里这 71 只共 9,469 行非空）；放宽到与生产一致的 `len(win)==0` 后 71 只全部跑通、mismatch=0。主验证（1007 只，410,856 次）+ 补跑（71 只，28,968 次）= 1078×408，精确对上。
6. **没有 mismatch 可查——坑在夹具自己**：全程 439,824 次比较 mismatch 恒为 0，排查时间全花在参照侧的 1~5 条上。
7. **全量格级 CSV 体积超限**：442,368 格的全量 CSV 76.5MB；2,654,208 格那轮建表 3~4GB、CSV 490MB。现在全量落 `cells.npz`。
8. **计数单位**：那一轮的功效线 100 卡的是买点日样本数，实测约为 match 数的 2.5~4 倍，方向不保守（同一 tb 段内买点日强相关）。同一回踩还会按不同 burst 前缀在长表里重复出现 1.22~1.44 倍——现在一律按买点事件（这里即回踩）只计一次。跨年份的 tb 段整段记进起点日所在年。
9. **敏感性门槛同时流经对半分验证，等效严格度翻倍**：门槛 300 传给对半分验证等效于对全样本卡 600，让它从 -0.1319 「翻正」到 +0.0199，看起来像证据分歧；单独给对半分验证传减半门槛 150 复算得 -0.1859，方向重归一致。
10. **真实耗时**：全宇宙扫描 ≈ 20 min @8 workers；单进程全量验证 ≈ 2.58h；识别分钟级。排期时验证是瓶颈。
11. **内存被扫描规模放大（2026-09-07 整机 OOM）**：网格从 1024 格扩到 4096 格时每股行数从 1165 涨到 8641（7.4×）；扫描主进程把每股结果攥在 Future 里，扫到第 2580 股时 anon-rss 23.4GB 被杀（整机 31GB）。验证端与识别端当时也会把整张长表（3522 万行 × 396B ≈ 14GB）读进内存。改法见 `reference.md` §6 坑 11；等价性逐元素验过：扫描端新旧代码同一批 91 股 535,023 行逐行逐列相同，识别端整表与分片离散化结果逐元素相同。

## 10. 红线的 bb_v1 实证案例

1. **档位漏上界**：会把「推荐值落在档位右缘」伪装成平台——peak_age 最大值 507 却只测到 180，补测 250/350 后从「疑似尖峰」翻案成平台 [125,250]。定范围时用样本分位铺档就是为了防这个。
2. **档位漏下界**：丢结构性样本——first_drought 漏了 x=0，丢掉 499 个首簇样本。
3. **分年方向**：peak_age 整体交集 [125,250] 漂亮，分年一拆 2024 强升 / 2025 持平 = 单年驱动，外推大概率失效；vol_spike 两年峰值同在 x=15。现在分年与年交互只作旗标，但仍要分年说。
4. **「无增量」先查列分布**：毒药闸「白过滤」实为 day_drop p50=0.006 / p90=0.08，单日跌 20% 的样本不到 1%，0.2 档几乎不删样本——区分「从不触发」和「触发但无增量」。
5. **单闸结论可被组合推翻**：毒药闸全池切档显示「白过滤」，组合审计才发现 first_drought ≥ 20 下的单日暴跌样本首次穿越率 0.33，是真坏样本、该闸有效。
6. **后缓冲（标签前瞻期）**：2026-08 数据到 8-17、前瞻 40 → 有效区间只剩 03~06，43% 的 match 没有标签。现在开局核对从数据覆盖划窗，确认窗后面自动留出标签窗。
7. **前缓冲（首部缓冲样本量）**：首部缓冲 63→250，2026-01 事件 0→10、样本 ×3.3。
8. **首部缓冲是隐式过滤器**：首部缓冲 63 恰好滤掉 01~02 的负底子样本，误把 0.65 当真实外推，完整检测下实为 0.42。训练与验证必须用同一首部缓冲。

| **A+C（已采纳）** | **1.05** | **+2.30 点** | **+3.89 点** |
| A+B+C（B = `stop_confirm_bars` 1→3，未采纳） | 0.97 | +3.09 点 | +4.13 点 |

- A 是全表唯一「松开它、买点变多、两年首次穿越率还都涨」的闸：它删掉的样本比留下的更好，没挣到自己的位置。
- B 未采纳的理由是机制：`stop_confirm_bars` 1→2→3→4 首次穿越率单调上升、买点递减（1983→1822→1349），本质是「多等几天再买」，可能只是趋势跟随。
- 组合回放没有推翻单闸结论，但效应次可加（单闸和 +4.30/+6.22 vs 实际 +3.09/+4.13）。
- **`tb.max_span` 定 20**：20/30/50 三档几乎无差别（买点只多 21 个、两年差值在 ±0.5 点内），10 明显更差（-4.0/-2.2 点、买点 -19%）。
- **引擎侧同口径复核**：60 只股票、任一事件落训练窗 + 按 tb 去重，66 → 71（×1.076），与长表预测的全宇宙 ×1.05 方向一致。第一次复核用全窗且没按 tb 去重得 ×0.92——口径不对，不是反证。
- 按新流程的分辨力看，这两处改动的效应在「只验一个事先写好的改动约 3.5 点」以内：不一定错，但也没被证明是改进，所以放进下一份验证清单。

**尝试次数**：识别运行 1 次；定案环节在同一份数据上做了约 40 次单闸查询 + 9 次组合回放（已回填进账本）。候选池比 265 万格小 5 个数量级、且要求两年方向一致，选择偏差远小于推荐格那个数字，但仍不是无偏的；唯一干净的判据是留出的验证数据。当时数据末端 2026-03-08，训练窗之后留不出标签窗，所以没做验证。

### 11.1 内存改造的 bb_v1 实测数字

| 项 | 改前 | 改后 |
|---|---|---|
| 长表每行内存（读回 pandas） | 396 B | **88 B**（省 4.50×；13.94 GB → 3.10 GB） |
| 长表磁盘（58 片、3522 万行） | 142 MB | 141 MB（parquet 本就列压缩） |
| 扫描收尾台账 | 全量读入 ≈ 14 GB | 元数据 + 逐片 groupby，约 0 |
| 识别端全量产物 | 全量 CSV 490 MB（建表 3~4 GB） | `cells.npz` 99 MB + `cells.csv` 928 KB（前 5000 格） |
| 识别端进程峰值 | 未测 | **3.68 GB**（含分片离散化 1.5 GB + 张量 + bootstrap） |
| 验证端读数据 | 26 列 | **22 列**，535,023 行读入 0.1s；91 股子集峰值 0.47 GB |

**等价性证据（全部实测）**：元数据行数 35,223,590 与已知真值相同；格 × 折分布 min 76 / p50 3636 / max 14330 相同；同一份长表重跑识别，`cells.csv` 前 5000 行与旧全量 CSV 对应行逐字节相同；新窗口一致性验证 111,748 = 91 × 1228 次比较、mismatch=0、91/91 股不漏；58 片列类型转换逐片逐列值比对全部通过。

**本轮踩到的三个坑**：
1. **原地转换只搬 parquet 会漏掉 `run_meta.json`**：它与分片同级、是口径的单一来源，漏了下一步直接失败。
2. **改 `params.yaml` 定案之后，那份长表就不能再重做一致性验证**：底座与分类表记录不一致，可再生性判为否，这是正确判断。验证端的改动要在新窗口上走「新底座 + 新格式 + 新代码」全链路，判据用 mismatch=0 + 股数 / 项数验算。
3. **重建分类表会把底座溯源悄悄接回来**：顺序是「扫描（旧底座）→ 改 `params.yaml` → 重建分类表」时，只比「当前代码 vs 分类表」会报可再生，但那份长表是用 `exceed_threshold=0.003` 扫的。现在 `check_regenerable` 另核长表记录的底座指纹，且底座与源码指纹进了续扫口径（中途变了直接拒绝续写）；两层都用这份真实的坏数据验到过。
