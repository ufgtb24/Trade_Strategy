# 处理清单与出题

第 3、4 步读。归到哪一段是你的判断；这里规定每条必须交代什么、怎么问。

## 一份清单，按去向分三段

两种输入——反馈的 issue、标注里的样本与特征——放进**同一份清单**，按「接下来会发生什么」分三段。一轮只改一版 app，所以清单一次给全，题答完再一起动手。

| 段 | 放什么 | 用户要不要选 |
|---|---|---|
| 一、我这一版直接改 | issue：app 认得比用户的定义松（定义里已有这句话，或账本里有他定过的一行——题里的选择、两轮之间的决定——app 没查或查得松）；账本里的 `pending` 行（两轮之间他定的，待这一轮实施）；样本：和 app 相反、毛病是结构性的；还没对到 node 的新特征（打算对到哪一块，或新加哪一块） | 不用 |
| 二、要你定 | issue：理由成立，但定义和账本里都没有这一条；note 里的关键词 app 里完全没有、词表的意思又对不上标的那几处（writing-app.md 第 3 节）；样本：和 app 相反、你拿不准的；「先怀疑切法」查出的（见下）；上一轮以来的变化里必须问的（见下） | **要** |
| 三、这一轮不改 | issue：当天看不出 / 只差门槛 / 量过不值得加；样本：只差门槛的 | 不用，可以反对 |

归类的依据只有：note、点出的 node、用户的定义与账本里他定过的、图上 app 实际认出的东西（`look.py` 的输出）。点出的 node 说问题落在哪一块；一个都没点时由 note 判断是不是整体或拓扑上的问题。

- **一个 issue 可以拆开**：能翻成当天看得到的条件的部分归一或二；这条件挡不掉的那几天归三（当天看不出）。
- **你判断是同一件事的几个 issue 并成一条**，写明并了哪几个。
- **账本里已有记录的 issue**（摘要在该 issue 下列出）沿用上次的结论，不重新争论；有新标的处、或内容改过才重看。
- **「只是后来跌了」**（样子对、当天也看不出毛病）归三，理由写「当天看不出」。
- **「量过不值得加」只在确实量过时才能写**；量归 `feature-study`，这里不量。
- **代价只报买点个数一类的事实**（会多查一条什么、哪几处会受影响、数得出时能挡掉范围里几天），不报收益。改完之后范围内外各砍掉多少，由改版报告给。
- **上一轮以来的变化里必须问的**，并进第二段：
  - 样本改判了、收的框没变：问「改判的理由那天看得见吗」；
  - pattern 定义的文字变了：问是改说法、放宽、收窄，还是换了想法。账本里已有一行写明这句是两轮之间经他同意写进定义的（「已写进定义」），就不再问。特征定义的文字改了不会出现在「上一轮以来的变化」里（摘要的定义一节给的总是定格时的原文）；
  - 某条反馈的范围里出现了用户自己的正样本（摘要在那一处标出）：问这一处以哪个为准。
- 用户的定义放宽后不再成立的旧反馈：在第三段说明，记账时挂 `redefined`。

## 先怀疑切法

app 把一张图切成哪几段（哪几天算哪一段）是 detector 定的，用户只在 `compare` 里看得到结果。条件改来改去总在同一张图上卡住时，毛病常常不在条件，而在切法：同一批 K 线换个段，条件就不用迁就。只把日期写进清单不够——用户会按你给的说法去读它，所以要作为一道题问。

两个信号，任一个响就照下面三步做：

| 信号 | 在哪一步看 |
|---|---|
| 同一次形状上（同一只股票，共用成员框，或 app 里是同一个候选、同一段），被**不同的**条件或症状卡住 2 次及以上。算一次的：一张和 app 相反的样本（按它卡在哪算，连候选都没有也算一种）；一条新条件挡掉这里的正样本（试了又撤的也算）；一条新条件的门槛只能按这里的正样本定或被它卡住；量过发现一条拟加的条件和这里的正样本分不开、因此放下没加的，也算一种。同一个门槛挡住同一次形状的几张样本只算一次 | 第 2 步看完相反样本时数一次；第 3、4 步量门槛、拟条件时接着数；第 5 步每撞一次正样本再数 |
| 出局核对查出一处累计的量回不来，而让它回不来的是一两根特别的 K 线（一次猛涨、一次冲高），按用户的定义它们本该属于相邻的那一段 | 第 3 步出局核对 |

1. **把切法写成白话。** 用日期说 app 在这几张图上哪几天算哪一段、卡住买点的那几根落在哪一段（「KULR 2024-11：app 只把 11-25 算阶跃，11-29 的 +61% 和 12-02 冲到 14.0 都算在新平台里」）。写进第二段那道题的正文。写出来后看明白与切法无关的（数据错误之类），撤掉这个信号，照常处理。
2. **出一道方向题**（问法见「出题」里的切法题）：这几根按用户的意思该归哪一段。原因相同的几张图并成一题；同一张图上原本要问的下游题并进这一题，不另问。
3. **这一轮不拿这几次形状当考题去改下游条件**：
   - 不为它们放宽或绕开条件（缩窗口、降门槛、加兜底）。
   - 从正样本量门槛时，这几次形状上的读数不参与，按其余正样本定。重定门槛后，被拿掉的形状上原本买得到的正样本不得因此变成买不到；会的话这一处保留原门槛，并在报告里点名。
   - 第二个信号响的那一处回不来的写法，这一轮先保持原样，在报告的 invalidation 一节写明「这条回不来是我暂时保留的，等切法定了再改」——它这时多半正在替切错的段兜底，换成能回来的写法会把切错带来的日子放出来。用户对这道切法题选「先放着」时，下一轮照样再问，不无限期留着。
   - 这样押后的下游冲突里，若有不是切法造成的（换了切法它照样会撞上），在报告里点名，切法定了之后作为正常的题问。

第 5 步才响的不出题（题已经问过）：停在这次形状上不再打补丁，写进报告末尾，下一轮放进第二段。

用户选「现在的切法对」，就照常在下游处理，账本记一行；下一轮同一次形状上又出现新的、不同的较劲时，照样再按这一节走。

## 出局核对

每轮都做，没有 issue、没有相反的样本也做；还没有 app 时只核对你拟写的条件。照 [writing-app.md](writing-app.md) 第 11 节，把 app 里每一条 where（复合的拆开看各半）和 detector 的每一处截断过一遍，挑出回不来的，各自落一个去处，从上往下停在第一行对得上的：

| 这一处 | 去处 |
|---|---|
| 切段时决定有没有这一段（开不开段、收段、段长上限、跳过不够格的段），或数据坏了的截断 | 不归核对：它们定的是有没有这一次，不是这一次往后还能不能回来 |
| 只读已定型的段，用户原话说的是形态本身（这一段要够大、够平） | 不归核对：它定的是这一次算不算这个 pattern。不进清单，也不进 invalidation 一节 |
| 对得上 pattern 定义里用户明说的「这样就算失败」，或账本里他定过的一行（出局核对的选择、两轮之间的决定） | 不进清单，列进改版报告的 invalidation 一节（SKILL.md 第 7 步） |
| 往后最多看多少根的上限，用户没说过 | 不进清单，列进 invalidation 一节，注明「会话定的上限，不同意就告诉我」（上限是参数，不出题） |
| 用户原话说的是形态守没守住、站没站上（读得出「这次失败了」），但没明说算失败 | 第二段，按下面「出题」里出局核对的选项问 |
| 其余：用户原话是逐日的买入理由，或明说暂时不该买（「波动小」「先别买」） | 第一段：改成能回来的写法。「app 现在」一行写清它为什么回不来（「从阶跃后第一天起的振幅，早期晃一次就永远过不了」） |

某一处回不来、要改成能回来之前，先看让它回不来的是什么：如果是一两根按用户定义本该在相邻段里的 K 线，就是「先怀疑切法」的第二个信号——这一处这一轮先保持原样、在 invalidation 一节写明，照那一节走；换窗口解决不了。

**几处管的是同一件事**（读同一个量、只是门槛不同，如一处截断和一条 where 都看跌回多少）：合成一条处理，一起问、一起改。改之前看清谁盖住了谁：被盖住的那一处可能从来不起作用，也可能有它管不到、原本靠另一处兜着的日子；把兜着的那一处改成能回来时，这些日子要另外补上，写进「我打算」。

做完的标志：每一条回不来的写法都落在上表某一行；三类（累计取最大最小或振幅、只读定型段、detector 截断）都查过，第三类读过 detector 的判据；管同一件事的几处已经合并。查出要改、要问的，这一轮就不算「三段都为空」。

## 一条反馈怎样才算改好

摘要和改版报告里每处反馈的状态，按用户标的方式判（判法只有一份，在 `path2_web/annotation/match.py`）。写「我打算」和报「代价」之前先对一遍，免得承诺一个做不到的结果：

| 用户怎么标的 | 还在买（`matched`，页面上朱红） | 恢复常色（`unmatched`） |
|---|---|---|
| 一天、拖出来的一段 | 范围里还有任何一天在买 | 范围里一天都不买 |
| 一族 | 范围里还有买点，**或**这一族（起点相同的 hit）在别的日子还在买 | 这一族一天都不买了，但起点那个事件还认得出 |

- 一族的反馈另有第三种状态：连起点那个事件都认不出了（摘要和报告里写「起点认不出」）。它可能是改好了，也可能只是认法变了（比如某一段的长度改了，全部起点平移），所以报告里每条都要交代是哪一种。页面上它显示成 `unmatched`（不买了）；你判为「认法变了、毛病还在」并挂了原因标签的，页面上是 `unmatched` 加标签，用户靠这个标签看出还没改好。
- 所以一条只挡掉其中几天的条件，改完这一处仍然是「还在买」：在清单里照实写「能挡掉范围里哪几天，剩下几天挡不掉」，剩下的归第三段。
- 条件读的是事件上现成的字段时，挡得掉哪几天现在就数得出——`look.py` 的表里那一列各天的实测值对着拟用的门槛看；要新字段的，写「改完在报告里给」。

## 给用户看的格式

一条消息，并且**这条消息必须以一个工具调用结尾**：有题就紧跟出题的调用，没有题就紧跟写 `.plan.md` 的调用。会话中途发一条不带调用的消息，这一回合就结束了，后面的步骤都不会发生。「中途消息正文至多一句状态行」的纪律在这里是例外：正文就是清单全文。

标注有冲突、越界，或数据指纹不一致时（第 0 步看到的），在清单最前面加一行如实说明，不单独发消息。

issue 用理由原话指代，样本用「股票 + 日期」指代；链接用摘要里现成的。每条都要有：用户原话（或股票 + 日期）、标在哪几处、有关的定义原话、app 现在怎么认的、你打算怎么办。

没买到的正样本每张一行，都要有一句「卡在哪」：页面上不显示 app 把框认到了哪一步，这一行是用户知道原因的唯一地方。用他的词说（如「阶跃切晚了一天，算出来的涨幅不够」），不出现档位名（detected、qualified、in_hit、missing）、node 名和条件名。

```
这一轮：你标了 N 个 issue（M 处），和 app 相反的样本 K 张，新特征 J 个。

一、我这一版直接改（a 条）
1. 「<理由原话>」——3 处（[CRNC 2025-01-07～01-30](链接) 等），落在 <node 对到的你的特征名>
   - 你的定义：「<定义里的原话>」（依据是账本里你定过的，就写「<第几轮 / 哪天>你定的：<内容>」）
   - app 现在：<一句白话，眼下怎么查的>
   - 我打算：<一句白话，改成怎么查>
2. 正样本 [AAPL 2024-03-08](链接) 没买到：<一句白话，卡在哪>；我打算：<……>
3. 新特征「<特征名>」：<打算让 app 的哪一块去认，一句白话>

二、要你定（b 条，下面逐个问）
4. 「<理由原话>」——1 处（链接）
   - 你的定义和你定过的：<定义里有关的原话；账本里定过的写「<第几轮 / 哪天>你定的：<内容>」；都没提就写「没有提到」>
   - 加上这条的话：会多查一条「<翻成的当天条件，白话>」，出现这种情况的那几天不买，好转了同一次照样买

三、这一轮不改（c 条）
5. 「<理由原话>」——2 处（链接）：当天看不出——<一句理由>。不同意就告诉我。
```

某一段为空就写「没有」，不省略段名。

## 出题

只对第二段，用 AskUserQuestion。

- 一轮 3～5 题以内，多了挑最要紧的，其余当「先放着」留到下一轮。一次调用最多 4 题，第 5 题另起一次。
- 题目正文用白话写清三件事：在哪几处说了什么；现在的定义和他定过的怎么说；选了各会怎样。读一遍就能选，不需要先翻清单。
- 你推荐的选项放第一位，标签末尾加「(推荐)」。
- 不让用户定门槛，不让他在 node 和 where 之间选，不问拓扑和 detector 选型。
- **「定义和账本里都没有这一条」的 issue，选项固定三个**：

  | 选项 | 选了会怎样 |
  |---|---|
  | 加上这条：出现这种情况的那几天不买，好转了同一次照样买 | 这一版 app 加上这条条件（写成能回来的），记进账本；不请用户改定义 |
  | 不加，这种可以买 | app 不改，这几处继续买 |
  | 先放着 | 这一轮不动，下一轮再问 |

  这组选项说的都是 setback（`path2/GLOSSARY.md` 的 setback 词条）。出题前对一遍：选项写的「不买到什么时候」和你打算的条件写法一致。用户在回答里说这种就该从此不买的，照出局核对那组的 invalidation 记账。

- **出局核对查出的、拿不准的那一处，选项固定三个**（题目正文写清：这一处现在怎么回不来、在哪几张图上会因此不买、用户定义里有关的原话和他定过的）：

  | 选项 | 选了会怎样 |
  |---|---|
  | invalidation：这次从此不买 | app 保持这种写法，记进账本 |
  | setback：好转了照样买 | app 改成能回来的写法 |
  | 先放着 | 这一轮不动，下一轮再问 |

  前两个选项的结论照 [ledger.md](ledger.md) 记一行，下一轮出局核对不再问。

- **「先怀疑切法」查出的，选项固定三个**（正文写清：app 在这几张图上怎么切的、卡住了哪几天、用户定义里有关的原话和他定过的）：

  | 选项 | 选了会怎样 |
  |---|---|
  | 这几根归到<相邻的那一段>（改切法） | 转 `write-detector` 改认法。它会牵动几乎所有条件，通常单独一轮做；这一轮这几次形状上不加下游补丁 |
  | 现在的切法对 | 照常在下游改条件 |
  | 先放着 | 这一轮不动这几次形状，下一轮再问 |

- 用户拒绝选择、想先弄清楚时，只把来龙去脉讲清，等他表态再继续；不在解释后面立刻再挂一道题。
- 用户对第一、三段有异议时，照他的意思挪段，不争。

## 存下清单

题答完后，把清单全文连同每题的选择写进本轮的 `.plan.md`；没有题时，写 `.plan.md` 就是清单那条消息结尾的调用，不能跳过。出局核对里不进清单、要列进 invalidation 一节的那几处（对上了的、会话定的上限），也一并记在 `.plan.md` 末尾，第 7 步照它写。
