## 3. 用户刚提出、lead 给了候选方案但**用户尚未批准**的（本轮重点检验对象）

用户的疑问见 `原始问题.md`。lead 的候选方案：

- 同一个 pattern 只允许一种顶层骨架（path2 一次 match 要求每个 node 都绑上事件，`path2/GLOSSARY.md:95`，顶层写不出「有时有有时没有」；方向文档第 8 节已定骨架不同就分开）。
- 「可有可无 / 取其一」只发生在次级：复合事件的子事件（如缩量）或属性（where 的「或」/ 凑够 k 条）。顶层名称理应恒为 `in N/N`。
- 顶层的模糊只允许在写 app 之前（未归类、混骨架、角色没起名）；写 app 时定成一个骨架。次级在写完 app 后仍可有「还没放进 app」的名称 / 属性（后来新标的、或会话暂不放、等「放在要用的地方量」验证）。
- 现在 mock 里「app 已建好却有 unmapped、顶层 in 2/4」主要是演示数据的毛病：mock 拿标注之前就写好的旧 app bb_v1 硬配演示标注，横盘、缩量在 bb_v1 里根本没有 node。
- 候选阶段表：1 自由标注（什么都行）→ 2 归组成 pattern（门槛：这个 pattern 的买点同一骨架）→ 3 会话写 app（门槛：顶层没有 unmapped；次级可先不放但要说原因）→ 4 对照与迭代（新买点须符合骨架，不符显示违背预期；新词先「还没放进 app」）→ 5 盲看、调参、最后检查。
- 由此推出的界面改动候选：有 app 的 pattern 里出现第二种骨架的组标红；顶层名称不再显示 `in`；unmapped 只出现在次级、改成「还没放进 app」并悬停说原因，顶层出现就标红；会话写 app 前先查骨架唯一；「翻成可有可无前先问没画还是没有」缩到次级；mock 演示数据换成照标注写的假 app。

## 4. 用户是谁、怎么说话（所有 teammate 必须遵守）

- 用户是**策略方向的决策者，不是参数的决定者**：阈值、尺寸、颜色值这类给默认值标「待验证」，不要拿来问用户。
- 用户讨厌过度设计，倾向一切从简（例：缓存未保存的修改被判过度设计；新 / 老标注拆分被判过度设计）。护栏只拦撤不回的东西。
- 用户色弱：分明暗正常、分色相弱；深浅相近的同冷暖色对会混；浅色底之间、浅色底和浅灰之间要拉开明度。不要退成黑白。
- 界面文字规则（`~/.claude/rules/ui-text-style.md`）：业务内容自然语言、程序固定内容等宽标识符、可用英文对上代码；不写口语化说明句，解释放悬停；文字全黑。用户追加要求：尽量不用大量文字，尽量用 UI 元素本身表达。
- 对用户讲话用白话、不打比方；`GLOSSARY.md` 定过的词照用并带 `文件:行号`（`path2/GLOSSARY.md`、`path2_web/GLOSSARY.md`，先 grep 再只读那一段）。
- 不碰 2026 年起的数据；这台机器（pc）没有 `datasets/pkls_until_20251231`，**禁止读 `datasets/pkls`**（含 2026 数据）。只用 mock 自带的 `repro/data.js`。
