- 作者：mechanist（agent team「人机协作开发流程」）；日期 2026-11-01；锚点：同目录 `原始问题.md`
- 范围：用户手里已有的工具箱、cc 自身机制、外部做法，按「意图采集 / 自主实施 / 验收 / 汇报 / 学习」五环归类，最后列缺口。**只盘点，不出方案**，方案归 designer。

## 0 先说结论

1. **用户的工具箱偏科。** 意图采集和「看得见的验收」投入很重：Wayfinder 每张决策票至少要用户点两次头（先定方向，再签字），web-loop 自动评审界面，path2 app / detector 的设计流程逐层确认。相比之下，学习环只有「用户点名才触发」的白话翻译（write-user-doc）。「看不见的正确性」（数据泄漏、基线错）的检查只存在于调参和特征研究的流程里，没有接进标注工具的开发流程。【实+推】
2. **cc 已经有让「自主实施 + 自动验收」形成闭环的原生零件。** `/goal` 可以设成「条件不满足就不停」，Stop hook 能拦住提前收工，后台会话关掉终端也继续跑，`/verify` 会把应用跑起来看结果，`/code-review` 用没看过对话的新上下文来审。汇报环有回来时的自动摘要、推送到手机、Artifact 页面。**真正缺的不是机制，是三件事**：验收条件由谁写、写在哪里、agent 能不能改它。【文+推】
3. **外部的共识是：能放手多少，取决于不看代码能不能判断对错。** Anthropic 自己的数据团队只在低语境的可视化工具上做到不读代码；StrongDM 把验收场景放在代码库外面，当作 agent 看不见的留出集；Shapiro 的五级划分里，从「人当产品经理」再往上走一级，靠的是检查能力而不是模型能力。对本工具来说，界面层可以放手，评估核心需要 agent 看不见、也改不了的检查。【外+推】
4. **重型的规格驱动开发会把用户的痛点放大。** Böckeler 实测 Kiro 把一个小 bug 写成了 4 个用户故事、16 条验收标准，Spec Kit 产出大量重复的 markdown，她的原话是「我宁可 review 代码也不想看这些 markdown」。更对症的做法是「推右 + 简报」：检查点尽量往后推，到时一次问完，问的时候只给决策简报、不给草稿。这套说法在用户已装的 Matt Pocock 插件源码里有现成的词（loop-me），parallel-tickets 的提问方式也已经接近它。【外+实】
5. **学习环有实证可依。** Anthropic 2026-01 的随机对照实验显示：完全交给 AI 的用法，测验得分最低（<40%）；「先让 AI 生成、再追问去理解」和「概念性提问」这两类用法，得分（65%+）和手写组相当。外部已成型的做法是让 agent 成批产出讲解，比如走读文档、交互式讲解页，代替用户一条一条地问。cc 这边有可用的零件：Explanatory 输出风格、`/btw` 侧问、Artifact 页面（页面里能直接向 Claude 提问，还能记录测验结果），以及已装但没用过的 `/teach`。【外★+文+实】

## 1 五环各指什么

| 环 | 指什么 | 用户在这一环的理想角色 |
|---|---|---|
| 意图采集 | 把用户脑子里的宏观意图变成 agent 每次都能读到的持久形式 | 说方向、给例子，不定参数 |
| 自主实施 | agent 在无人值守下写代码、跑实验、修错 | 不在场 |
| 验收 | 不靠用户读代码，判断做出来的东西对不对、是不是要的 | 只判断「只有我能判断的」部分 |
| 汇报 | 把结果、证据、待决事项以最省注意力的形式交给用户 | 读一份简报就能做决定 |
| 学习 | 开发完时用户能掌握工具：会用、知道它为什么可信、能把控下一步方向 | 不一条条提问也能懂 |

### 2.2 Matt Pocock 插件里和五环相关、但还没用上的件【实】

插件清单 `.claude-plugin/plugin.json` 注册了 27 个 skill。以下几个都是 `disable-model-invocation: true`，只能由用户敲命令调用：

- **`/teach`（学习）**：在一个工作目录里维护几样东西：`MISSION.md`（为什么要学）、一课一个 HTML 的 `lessons/`、`reference/` 速查页、`learning-records/`（记录用户已经学会了什么，用来判断下一课该讲什么）。它的方法包括：区分「当下想得起来」和「长期记得住」，靠回忆练习、间隔、交错来巩固，测验要有即时反馈。**限制**：它是为「学一个外部话题」设计的，要求先找高可信的外部资料，不拿模型自己的知识当依据；要拿来「学自己做的工具」，需要改造【推】。
- **`/wait-what`（汇报）**：「上一条没看懂，重讲」。要求用简化技术英语，并使用 GLOSSARY 的词。
- **`/to-questionnaire`（意图采集）**：把一个自己答不了的决策写成问卷，让别人异步填写。
- **`/retro`（实施环的长期改进）**：回顾一次会话，提出环境层面的改进，比如自动检查、导航指针、规范该放哪。它有一条原则：机械性的规范做成确定性的检查，不写进说明文档。
- **`/handoff`**：把当前对话压缩成交接文档。
- **只在源码里、没注册、不能调用的**：`in-progress/loop-me`、`in-progress/chief-of-staff`。可以借鉴思路：
  - loop-me 的词汇：**Push right**，检查点尽量往后推，「在请人之前把能做的都做完，只问一次，问得晚，材料齐」。**Brief**，检查点给的是决策简报，包括产出了什么、为什么、链到原件，绝不给原始输出；「用户读的是简报，不是草稿」。
  - chief-of-staff 的思路：一个长会话当总负责人，所有活派给子代理；每次干活都同时想「怎么改环境，让下一次更顺」。

### 2.3 从工具箱里能直接看出的事实

- **Wayfinder 决策流的注意力是按票数计的。** 规则要求每张票认领后先定方向，答案出来再签字，所以至少两次用户交互【实，decision-tickets.md「Ticket framing」「Sign-off」两节】。annotation-path2 现有 15 张决策票（5 resolved、1 claimed、9 open）【实】。2026-10-20 以来，`.scratch/annotation-path2/` 下的决策材料约 17 万字符：票 4.8 万、研究 4.6 万、原型 4.2 万（含 HTML）、说明书 3.6 万、地图 0.3 万【实，wc -m】。这些材料多数要用户读过才能签字【推】。诊断是 auditor 的事，这里只给成本结构。
- **superpowers 插件装了，但没启用。** `~/.claude/settings.json` 的 `enabledPlugins` 里只有 playwright、mattpocock-skills、qa-nav【实】。所以记忆里「默认执行器 = superpowers subagent-driven」那一套，本会话调不到；目前能用的执行器是 Matt Pocock 的 `/implement`、`/implement-spec`（用户调用），以及 parallel-tickets。
- **用户的推送链路已经打开。** settings 里 `agentPushNotifEnabled`、`inputNeededNotifEnabled`、`remoteControlAtStartup` 都为 true，另有自定义的 Notification hook（ghostty-notify）。项目当前的输出风格是 `Concise`（`.claude/settings.local.json`）【实】。
- **项目 CLAUDE.md 有一处失效指针。** 「评估纪律」一节指向 `.claude/skills/eval-discipline/SKILL.md`，但这个 skill 已经解散，目录不存在【实】。不属于本研究的范围，记在这里，交给 lead 处理。

## 3 cc 自身的机制（按五环）

除非另行标注，均为【文】，即子代理逐页读过官方文档；页面都在 `https://code.claude.com/docs/en/<页名>`。

### 3.1 意图采集

| 机制 | 能做什么 | 限制 / 注意 | 来源 |
|---|---|---|---|
| 「访谈我直到你能写出规格」 | 官方最佳实践的原话是「Interview me until you could write the spec, then write it to SPEC.md」，然后开一个新会话照 SPEC.md 去实现 | 问题会多，这正是用户的痛点；也问不出用户自己不知道该关心的东西（比如泄漏）【推】 | best-practices |

| Artifact 页面上的 `db` / `comments` | 页面可以让用户勾选、填写、评论，数据由 Claude 读回（ArtifactData 工具），评论可以发给 Claude | 只有页面本身，没有自建后端；能力要在发布时声明【实，本会话 artifact-capabilities 能力清单】 | artifacts |

### 3.3 验收

| 机制 | 能做什么 | 限制 / 注意 | 来源 |
|---|---|---|---|
| `/goal`、Stop hook | 见上表：把「验收条件」变成不满足就不准收工 | 条件写不出客观判据，就只能交给模型判断 | goal、hooks |

### 3.6 文档冲突与未证实项

- **Artifact 有没有后端。** 子代理读官方页面后写的是「单页、没有后端」。本会话的能力清单则有 db、sample、comments 等平台能力。两者并不矛盾：页面自己不带后端，平台提供存储和问答。置信度高。
- **自动记忆整理（autoDream）。** 用户 settings 里有 `autoDreamEnabled: true`，但官方 memory 页面没写它，行为**未证实**，不要依赖。
- **Workflow 的 args 是字符串还是对象。** 旧实测是字符串，2026-10-29 实测已改为对象。保留兼容写法即可【实，记忆】。
- **官方最佳实践页的内容变了。** 页面上已经没有 explore-plan-code-commit、先写测试、通过提问上手代码库这几条，只剩一个「先写失败测试再修」的示例提示。
- **SessionStart hook 支持哪些类型。** 有一份摘要说只支持 command 和 mcp_tool，原文没能确认。

## 4 外部做法

每条写清它解决什么问题、在本场景会在哪里失效。「本场景」指：单人自用、研究型工具、有一部分正确性用户看不见（数据泄漏、基线口径），而且用户最终要掌握这个工具。

### 4.1 意图怎么从脑子里出来

| 做法 | 解决什么 | 本场景会在哪失效 | 来源 / 置信度 |
|---|---|---|---|
| 一次问一题的访谈 → 规格 → 新会话实施（Harper Reed；cc 最佳实践） | 把没写下来的意图逼出来，留下「做完长什么样」 | 问题数量正是痛点；问不出用户自己不知道该关心的事（泄漏）【推】。Harper 自己也提醒，人会被 AI 带着跑到自己掌控不了的地方 | harper.blog/2025/02/16/my-llm-codegen-workflow-atm/【外】 |
| 重型规格驱动开发（GitHub Spec Kit、Kiro、Tessl） | 编码前强制把意图写成规格 | Böckeler 实测：小 bug 被写成 4 个故事、16 条验收标准；markdown 冗长重复，「宁可 review 代码」；agent 仍会无视或过度执行规格，给人「虚假的控制感」。研究型工具的需求是在使用中长出来的，前置冻结不合适【推】 | martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html（2025-10-15）【外】；Thoughtworks Radar 评级「Assess」【二】 |
| 推右 + 简报（Matt Pocock loop-me 词汇） | 检查点尽量往后推，一次问完；只给决策简报 | 往后推意味着前面要有可靠的自动检查兜底，否则错误会走得更远【推】 | 用户已装插件源码 `in-progress/loop-me`【实】 |
| 用样例表达意图（金标准样例、批准过的固定用例） | 冻结已认可的行为，防止回归 | 一个带泄漏的 pattern 也可能命中所有样例，所以样例证明不了没有泄漏【外·Böckeler「行为约束是房间里的大象」+推】。**本工具的独特之处是：用户的标注本身就是现成的意图样例**【推】 | martinfowler.com/articles/harness-engineering.html（2026-04-02）【外】 |

### 4.2 不读代码也能判断对错

| 做法 | 解决什么 | 本场景会在哪失效 | 来源 / 置信度 |
|---|---|---|---|
| 给 agent 一个能跑出「过 / 不过」的检查，并要它附证据（cc 最佳实践） | 没有检查时，「人就成了测试套件」 | agent 既写检查又写代码时，两边会有同一个盲点；泄漏检查必须出自懂泄漏怎么发生的人或流程【推】 | code.claude.com/docs/en/best-practices【文】 |
| **agent 看不见的留出场景**（StrongDM「软件工厂」） | 场景存放在代码库外，像模型训练的留出集；由模型给运行打分；agent 没法对着它过拟合 | 每个工程师每天约 1000 美元的 token 成本；由模型当裁判不适合判泄漏【推】。**能借的是「agent 看不见也改不了的检查」这一点** | factory.strongdm.ai（2026-02-06）；simonwillison.net/2026/Feb/7/software-factory/【外】 |
| Anthropic 量化研究指南：agent 碰不到的留出集，每次试验都记账、按试验次数调整统计量，信号由研究员挑 | 防止「试了很多次，挑最好的那次」 | 和项目里 tune-gates 的「没碰过的数据 + 样本使用账本」是同一个思路【实+推】 | claude.com/resources/guides/the-ai-investment-firm/front-office-quantitative-research【外】 |
| 泄漏金丝雀（scikit-learn 官方示例：在随机数据上先选特征再切分，准确率 0.76，应为约 0.5） | 抓出「看起来对、而且比真实更好看」的泄漏 | 一种金丝雀盖不住所有泄漏类型（幸存者偏差、事后修订的数据、多次试验挑最好）；需要懂行的人设计一次【推】 | scikit-learn.org/stable/common_pitfalls.html【外】；agent 时代的泄漏扫描工具只有 README【二】 |
| 把规格句子变成性质测试（Kiro） | 「对任意 t，改动 t 之后的数据，t 时刻的信号不变」这样的句子可以自动生成随机测试 | 性质本身必须写对；随机测试不是穷举 | kiro.dev/blog/property-based-testing/（2025-11-17）【外】 |
| 测试由人掌控的「增强编程」（Kent Beck） | 人维护一张「必须为真」的测试清单，决定下一条测哪个；警惕 agent 删测试、改测试作弊 | 写成代码的测试，对当使用者的人来说也是 review 成本；**能移植的是「人掌控清单、清单用白话写」**【推】 | newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes（2025-06-25）【外】 |
| agent 自己做手工测试并录证据（Willison 的 Showboat：`exec` 记录实际输出，防止 agent 写「预期会发生什么」） | 抓出「测试通过，但一跑就崩、少了界面元素」 | 只能证明看得见的行为，正好就是「界面上看着对」的陷阱 | simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/【外】 |
| 约束工程（Böckeler 的 harness engineering）：事前引导 + 事后检查，各分确定性的和靠判断的两类 | 系统化地减少需要人看的东西；「不是要消灭人的输入，而是把它引到最重要的地方」 | 是思考框架，不是配方；她也承认「功能正确性」的检查还没解决 | martinfowler.com/articles/harness-engineering.html【外】 |

### 4.3 用看结果的方式验收

| 做法 | 解决什么 | 本场景会在哪失效 | 来源 / 置信度 |
|---|---|---|---|
| Anthropic 数据团队：「当老虎机用」，先存档、放手跑 30 分钟、不行就重来；做出 5000 行的可视化应用而不读代码 | 在「错了代价低、一眼看得出」的部分获得吞吐量 | 他们明确说之所以能这样，是因为可视化应用「低语境」。评估核心是高语境，所以这条支持**按可见性分区放手**，不支持全盘放手【推】 | claude.com/blog/how-anthropic-teams-use-claude-code（2025-07-24）【外】 |

### 4.4 最终能掌握工具（认知债）

| 做法 | 解决什么 | 本场景会在哪失效 | 来源 / 置信度 |
|---|---|---|---|
| 认知债 / 理解债（Storey；Osmani） | 给「代码能跑，但没人知道它为什么这样」起了名字；Storey 的建议是每个 AI 改动至少有一个人完全理解，并记下「为什么」；Osmani 的话是「测试是必要的，但不充分」 | 只指出了风险，没给出流程 | margaretstorey.com/blog/2026/02/09/cognitive-debt/；addyosmani.com/blog/comprehension-debt/【外】 |
| **Anthropic 随机对照实验** ★ | 学一个新库：AI 组测验 50%，手写组 67%（p=0.01），差距最大的是调试题。纯委托、逐步依赖、让 AI 反复调试这几类用法得分 <40%；「先生成再理解」「代码加讲解混合」「概念性提问」这几类 ≥65% | 每类只有 2～7 人，测的是刚做完任务时的理解，对象是学库而不是掌握工具。**能用的结论是：让 agent 生成之后追问理解，不必自己手写**【推】 | anthropic.com/research/AI-assistance-coding-skills（2026-01-29）；arXiv 2601.20245【外，已复核】 |
| 批量讲解：线性走读、交互式讲解（Willison） | 由一个新 agent 规划并写走读文档，代码片段用 sed/grep 摘出来而不是重打（防止编造代码）；再把走读做成动画讲解页。原话「当我们不再清楚 agent 写的代码怎么工作时，就背上了认知债」 | 讲清的是代码结构，不判断领域逻辑对不对。「为什么我们相信没有泄漏」必须单独要【推】 | simonwillison.net/guides/agentic-engineering-patterns/linear-walkthroughs/ 与 …/interactive-explanations/（2026-02 起）【外，已复核】 |

## 5 缺口：五环 × 已有 × 缺什么

「缺什么」一律说的是能力，不是方案。除非标【实】，「缺什么」一列都是【推】。

| 环 | 用户已有 | cc 原生可直接用 | 缺什么 |
|---|---|---|---|
| **意图采集** | Wayfinder 地图与决策票、grilling / brainstorming、假装做完的说明书 `manual.md`、界面原型 | plan mode、访谈写规格、AskUserQuestion、rules / 记忆、Artifact 页面收集勾选和评论 | ① **一个短的、agent 每次都会读的宏观意图载体**，用户只改方向。地图的两句目的地接近它，但现在每张票还要再定一次方向【实】。② **成批提问的通道**：决策阶段是逐票逐题问；实施阶段 parallel-tickets 已能成批问【实】。③ **把用户的标注样例当成意图的正式载体**：标注就是「我要的长什么样」，现在还没接到验收里 |
| **自主实施** | parallel-tickets、human-ticket、`/implement`、worktree-prep、`plan-execution.md`（单会话无监管） | 后台会话、`/goal`、Stop hook、子代理 + worktree、auto mode、Workflow（方向定了之后的长跑） | ① 默认执行器缺位：superpowers 没启用【实】。② 长跑依赖窗口常开：parallel-tickets 明说关窗口全停【实】；后台会话可以解决关终端的问题，但重启机器照样停【文】 |
| **验收** | web-loop（看得见的部分）、tune-gates-v3 / feature-study（基线、没碰过的数据、账本）、review-planning（只有用户能判断的才设人审） | `/goal` 条件、Stop / PreToolUse hook、`/verify`、`/code-review`、第二会话审查、Playwright | ① **看不见的正确性没有进开发流程的自动验收**：泄漏金丝雀、随机数据对照、未来数据扰动这类检查，现在只活在调参和特征研究的 skill 里。② **「agent 改不了」的保护**：验收件可以被同一个 agent 改掉，没有 hook 守着。③ **用户可判断部分的演示载体**：web-loop 的截图给评审 agent 看，用户看到的是文字结论【实】。④ **验收条件写成「对话里可见的证据」**：这是 `/goal` 的硬要求【文】 |
| **汇报** | parallel-tickets 汇报格式 + 推送、write-user-doc、白话汇报规则（`~/.claude/CLAUDE.md`） | 自动摘要、`/recap`、PushNotification、Artifact、`/insights` | ① **统一的决策简报格式**，跨所有长任务通用：做了什么、证据（命令 + 输出 / 截图）、只需要你定的几件事、不定的后果。现在只有 parallel-tickets 有自己的一套【实】。② **证据随报告附上**，而不是只给结论：最佳实践的硬要求【文】 |
| **学习** | write-user-doc（被动）、GLOSSARY、domain-note-keeper（显式触发）、`manual.md` 可兼作教程底稿 | Explanatory 风格、`/btw`、Artifact（`sample` 问答、`db` 测验记录、评论）、`/teach`（已装未用）、`/wait-what` | ① **里程碑自动触发的成批讲解**：走读 +「为什么可信」说明，而不是等用户一条条问。② **在真工具上走一遍任务的引导教程**，用户最初提的「交互式引导教程」。③ **掌握程度的回路**：测验或复述，加一份学习记录（用户已经懂了什么），避免重复讲、也知道哪里还没懂。④ **讲「为什么可信」而不只讲「怎么工作」**：外部做法普遍只讲代码结构 |

## 6 给 designer 的可用零件组合（候选，全部是【推】）

只说明零件之间怎么接，取舍留给方案。

1. **验收闭环。** 用户用白话写一份「必须为真」清单，附上标注样例，作为验收件。
   - 每完成一项实施，agent 跑检查脚本，输出 PASS 并附证据。
   - `/goal` 或 Stop hook 要求「检查全过、且证据已贴出」才准收工。注意 `/goal` 的裁判不自己跑命令，只看对话里打出来的东西，单靠它挡不住 agent 写一句「PASS」就收工；硬约束要 command 类 Stop hook 真跑检查（见 7.2）。
   - PreToolUse hook 拦截 agent 对验收件的写入，所以改验收件只能走「向用户提问」这条路。
   - 整个过程跑在后台会话里，结束时推一条简报到手机。
2. **看不见的正确性。** 一次性建一套金丝雀，作为固定验收件：随机标签、打乱日期、截断未来数据、未来数据扰动之后信号不变。用户只批准每个金丝雀「在防什么」的一句白话，不看实现。沿用 tune-gates-v3 的「没碰过的数据 + 账本」，不另起炉灶。
3. **用户能判断的部分只看演示。** web-loop 已经有截图配方和自测；缺的是把最终截图和关键交互做成一页 Artifact 交给用户，用户在页面上评论，评论回流到会话。
4. **学习按里程碑成批进行。** 每到一个里程碑，由一个新子代理产出两样东西：走读文档，和「为什么我们相信它没有泄漏」的说明。做成 Artifact 教程页：页面里可以直接问 Claude（`sample`），带小测验（`db` 记录答题）。教程底稿用 `manual.md`，学习记录借 `/teach` 的格式。
5. **意图采集推右。** 决策阶段也按 parallel-tickets 的方式攒问题，一次问至多 4 个方向题，每题带推荐；参数一律由 agent 推导，标「待验证」。可以照搬 tune-gates-v3 的「禁止词 → 人话」译法表的写法。

## 7 补充：回答 designer 的追问

按 lead 要求，凡是需要改 settings、权限或钩子配置的本机实测都没有做。下面标「未证实，需金丝雀实测」的条目，意思是方案若要依赖它，先用一份假数据做一次真跑：故意去读或改受保护的东西，确认真的被拦住，再算数。

### 7.1 会话侧数据墙：防 cc 临时写的分析脚本读到完整行情

- **现状【实】。**
  - 应用层已有截断副本 `datasets/pkls_until_20251231`；`path2_web/guard.py` 和 `chart_workflow.loader` 只读这份副本。
  - 一批入口的默认路径仍是完整数据 `datasets/pkls`：`scripts/path2/path2_eval_scan.py`、`scripts/path2/scan-top-miss.py`、`path2_web/eval_runner.py` 的默认参数、`.claude/skills/tune-gates-v3/scripts/run.py`（写死了主目录的绝对路径）。
  - `scripts/data/data_download.py` 原地改写 `datasets/pkls`。
  - 所以「默认数据目录就是截断副本」要成立，得把这些默认值翻过来；下载流程也要改成先写完整数据、再重新生成副本。
- **钩子能看到什么。** PreToolUse 钩子能看到工具调用的参数：Bash 的命令行、Read 的路径；Write / Edit 写脚本时，脚本正文也在参数里（字段名未证实）。它看不到运行时才拼出来的路径，也看不到被 import 的项目函数里的默认路径，所以钩子只能当提醒，防不住。【推，机制本身为文】
- **漏掉的原生办法：沙箱。**
  - 用法：在 settings 里设 `sandbox.enabled` 和 `sandbox.filesystem.denyRead`。
  - 效果：由操作系统层（Linux 上是 bubblewrap，本机已装 bwrap 0.9.0 和 socat【实】）拦住 Bash 及其子进程的读取，和路径怎么拼无关。
  - 逃生口：`allowUnsandboxedCommands: false` 能关掉，也就是禁止命令申请到沙箱外运行。
  - 内置的 Read 工具不归沙箱管，要另配 permissions 的 deny 规则。官方说 Read 的 deny 规则不管 Bash 子进程；有一份用户报告称新版本也会拦 Bash 参数，未获官方确认。
  - 来源：官方 sandboxing 页（经搜索摘要）、多份第三方指南、GitHub issue #45200。【二】
  - 下面几件**未证实，需金丝雀实测**：bypassPermissions 模式下沙箱是否仍生效；软链（worktree 里的 `datasets` 指向主目录）怎么解析；沙箱起不来时会不会悄悄不设防（第三方说 `failIfUnavailable` 为 false 时会照常跑命令，只给一句警告）；最后检查入口怎么放行（`excludedCommands`，或由用户用 `!` 前缀亲手跑，这条路是否也走沙箱）。
- **designer 的定稿默认不用沙箱、不装钩子**（lead 2026-11-01 通知）。本节只留作备选。

### 7.2 无人值守建造（几千行、单会话）

- **建议形态【推】。** 开一个后台会话（计划批准后 `/bg`，或 `claude --bg`）：
  - 主线程只当调度者。计划里每个任务派一个新上下文的子代理去实施，再派一个子代理对照计划审。
  - 跨任务的状态写进文件。
  - 外面再套一层 `/goal`，条件写「全部验收命令输出 PASS，或 N 轮后停」，防止提前收工。
- **不推荐用 Workflow 工具做这件事。**
  - 它运行中不能问用户，关会话就停【文】。
  - 编排在开跑前写死，适合 web-loop 那种同质循环，不适合实施中会冒出真依赖的异构计划【推】。
  - 实测坑：用 SendMessage 回复它的子代理，会拉起同 id 的副本，两个进程并发改同一个文件【实，记忆 feedback_no_sendmessage_to_workflow_agents】。
- **已知的坑。**
  - 后台会话重启机器即停【文】。
  - 需要权限时会停在「Needs input」【文】；bypass 模式下是否还会停：**未证实**。
  - superpowers 没启用，所以 subagent-driven 那个 skill 调不到【实】。
  - 子代理的 worktree 不会自动带上 `datasets` 软链和 `.venv`：项目没有 `.worktreeinclude`，只有 `.worktree-prep`【实】。子代理 worktree 从哪个基线起：**未证实**（用户设了 `worktree.baseRef: "head"`，它管不管子代理也未证实）。
  - parallel-tickets 的调度窗口一关，所有后台 agent 全停【实】。
  - **`/goal` 的裁判不自己跑命令**，agent 只要在对话里打出「PASS」就可能过关。真要硬约束，得用 command 类 Stop hook 真跑检查。这又回到改钩子配置，按定稿不做。【文+推】

### 7.3 「先做后反应」：反应怎么收敛

- **本项目硬证据【实】。** web-loop 按「问题清空才停」跑 50 轮不收敛；改为对照开跑时冻结的验收标准，3 轮收敛（`.claude/skills/web-loop/SKILL.md` 运转方式一节；记忆 project_web_loop_skill）。
- **外部做法【外，子代理读原文】。**
  - Hamel Husain 的错误分析：先自由记反应，再归类计数、按类修。停止规则是「新样本不再暴露新类别、也不改变已有类别」，不是「没反应了」。只设一位领域专家拍板。（hamel.dev/blog/posts/evals-faq/，页面元数据 2026-09-18；field-guide/，2025-03-24）
  - Shape Up：先定这一轮花多少（胃口），范围可变；不设 backlog，重要的想法会自己回来；超期默认砍掉。（basecamp.com/shapeup 第 3、7、14 章）
  - 标准漂移：「评输出需要标准，评输出又在帮人定标准」。（Shankar 等，arXiv 2404.12272，只读了摘要）
  - 反应变规则时防膨胀：官方建议 CLAUDE.md 只收「纠正过两次」的事，单文件少于 200 行，不能有例外的规则用钩子做；Every 的 compound engineering 要求写进规则后验证下次能被自动抓到；ICLR 2026 的 AGENTS.md 实证显示上下文文件总体不提升成功率、成本多 20% 以上。（code.claude.com/docs/en/best-practices 与 /memory；every.to/guides/compound-engineering；arXiv 2602.11988）
  - 「纠正两次还不对就 /clear 重写提示，别纠正第三次」：官方最佳实践。
  - 「2～3 轮截图迭代」这个说法：原文已下线，**未证实**。
- **对 designer 三分法的建议（这次改 / 以后都这样 / 方向变了）【推】。**
  - 加第四格「这轮不做」，不进待办。
  - 「以后都这样」要第二次出现才升格成规则，升格前先问能不能做成检查。
  - 「方向变了」只在轮边界生效。
  - 守护看不见的正确性的冻结检查，永不按结果改。
  - 收敛信号用「反应不再出现新类别」。
- 没找到有人公开把「先做后反应」和「反应分格」配成一套流程；最接近的是 Matt Pocock 的 prototype skill：一个原型绑定一个问题，结束时只留结论。
