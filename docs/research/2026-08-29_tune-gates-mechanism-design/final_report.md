## 1. 问题一：resume 机制的必要性

### 1.1 判定：原设想的机制【不做】

用户要求必要性当闸。**闸没过。**

决定性的一条是**结构性无消费者**：`region_core.bootstrap()` 的七个入参 `(prep, ref_index, min_count, axes, B, seed, top_n)` 里没有任何一个能携带历史（`critic` 读 `region_core.py:426-506` 复核）。跨轮信息想进入 optimism 只有一个口——把 `argmax` 空间换成两轮网格的并集——而那要求对并集里**每个格都能在当前数据上取到四态计数**，元数据只能给出格的**名字**。二分下来两边都落空：

- 旧格的行**还在长表里** → 直接把 `region_find` 的 `COMBO_LEVELS` 设成两轮并集重跑就够（识别端常量，`reference.md` §4.0 表末行免对拍，分钟级）。跨轮状态是多余的。
- 旧格的行**不在** → 名字补不出计数。

唯一能纯靠元数据写出的替代（按 `ln m` 放大 optimism）被实测否掉：`opt/√(2 ln m)` 从 0.0015 单调涨到 0.0050，缩放律不成立——硬套等于拿编的数字换掉有实测支撑的数字。

### 1.2 代价量级：两个独立实证，方向一致

**(a) 合成模拟**（`repro/two_stage_optimism.py`）。直接模拟「看完结果删维」这个最隐蔽的场景，把删维当成流程的一部分、每个 bootstrap 副本重跑整套两段流程：

| 锁档规则 | 现状报告值 | 正确值 | 低估量 |
|---|---|---|---|
| 锁该维最好档 | +0.0188 | +0.0167 | **−0.0021 ± 0.0024** |
| 锁底座档 | +0.0165 | +0.0160 | **−0.0006 ± 0.0011** |

与 0 不可区分，**符号还是负的**（现状反而略偏保守）。

**(b) 真实长表验证**（`critic` 独立做，补上 (a) 最大的 caveat）。用 `2026-08-25` 那份真实长表（43 分片 / 38MB / 783 万行 / 3985 股），先逐字复现基线 `naive=0.0705 / opt=0.1263±0.0062 / sh=−0.1319`，再逐条塌缩一根轴（候选集 442,368 → 110,592，砍到 ¼）：

| 条件 | 候选格数 | optimism |
|---|---|---|
| 全网格 | 442,368 | 0.1263 ± 0.0062 |
| 单轴塌缩 ×11 | 110,592 ~ 221,184 | **[0.0886, 0.1379]**，最大偏移 0.0376，**3 条反而变大** |
| 多轴塌缩 | 27,648 / 1,728 / **432** | 0.0818 / 0.0909 / **0.0885** |
| **全部 15 条的 optimism 带宽** | | **0.0561** |
| 同一份数据 split-half 换种子的 sd | | **0.0762** |

**核心一句**：候选集从 442,368 压到 432 格——**三个数量级、1024 倍**——optimism 全部变动范围只有 0.056，**小于同一份报告里 split-half 换个随机种子的噪声（sd 0.0762）**。

要校正的那个东西，比报告里另一个并列上报的数字自身的抖动还小。在精度上它是噪声。

> **数字口径（三方各错一次，最终以程序产物为准）**：`critic` 首轮发的是 8 条 → `resume-analyst` 据日志重算成 9 条、把 0.038 改成 0.026 并质疑 → lead 读日志得 11 条 → `critic` 用 `.json` 重算，完整是 **15 条**，`0.0376` 成立。**`resume-analyst` 主动撤回了自己的 0.026。**
>
> **准确归因（`resume-analyst` 实测，不是「谁看漏了」）**：`critic_optimism_vs_gridsize.log` 是**边跑边写的流式文件**。它核对时用的是 `tail -14`——若那一刻文件已写满 11 条 `drop_` 行，该命令会全部拿到；实际只吐出 9 条，说明**文件当时确实只有 9 条**。所以这是**同一份流式日志的两个不同未完成截面**，不是任何一方读漏。
>
> **可复用的教训（本轮最一般的一条方法论收获）**：**报一个数之前，先确认它的口径边界是什么。**
>
> 这轮四个参与者在数字上**各栽一次，形态完全相同——都是把一个「会随调用方式变化的读数」当成了定值**：
>
> | 谁 | 踩的读数 | 真相 |
> |---|---|---|
> | `critic` | 边跑边写的流式 `.log` | 发出去时只跑了 8/15 条 |
> | `resume-analyst` | 同一份 `.log` 的另一个截面（`tail -14` 只吐 9 行） | 文件当时确实只有 9 条 |
> | `resume-analyst` | `du -sh` 一次传多个路径的父目录读数（144M） | `du` 按 inode 去重，父目录只报未计入部分（182 − 38） |
> | `app-lifecycle` | F+G 合计（110.6 MiB）口头挂到单项上 | 长表单项只有 37.6 MiB |
> | lead（我） | 把数字分歧归因为「两人各漏了不同的行」 | 实为同一流式文件的两个未完成截面，无人读漏 |
>
> 推论：**验算一律以程序写出的最终产物（`.json`）为准**，流式 `.log`、`du` 的多路径去重、口头转述的合计值，都不是可直接引用的定值。
>
> **诚实边界**：表末 3 个多轴塌缩条件的 `naive` 已翻负（−0.018 / −0.035），是与全网格**不同的 regime**。它们支撑「optimism 对候选数不敏感」这个一般观察，**不直接为「删一维的代价」背书**——后者由前 11 行与 §1.2(a) 的两段式估计（−0.0021±0.0024）承担。

> 两处诚实边界（请按这个强度读）：(a) 是纯 null 合成数据，其真正的限制不是 R=5，而是 **null 下「删哪根轴」的决策不携带任何真实信息**，是该机制最弱的一档；(b) 是单一 app、单一长表的单次验证。两者方向一致但都不构成「一定为 0」。

### 1.3 那么什么是真该补的

**识别端的运行审计日志** —— `region_find` 每次运行都无条件覆盖 `region_report.md`（`region_find.py:183`），而 `out` 默认落在 gitignore 的目录下。同一份数据上「又看了一遍」这件事不留任何痕迹。

扫描端**早就为同一个覆盖病**加过 `run_stats.jsonl`（注释写明「修复轮 1 Important 1」）——扫描端修了，识别端没修，**而识别端才是选择真正发生的地方**。`apps/bb_v1/notes.md` §6 证明真发生过第二次识别运行（可评估面 81.7% vs 56.1%），那两个数字之所以还在，只因为有人手抄进了 notes。

方案：`apps/<app>/exposure.jsonl`，append-only，每次 `region_find` 追加一行（时间戳 / study 指纹 / 长表目录 / 功效线 / 邻域轴 / `REF_POINT` / 网格形状 / 选中格 / 三口径 / stability / note）。每行 <1KB。

> **⚠ 称呼很重要，请沿用「运行审计日志」，不要叫它 resume 状态。** 前序报告 §3.2 给 resume 状态的授权理由是「丢了它 optimism 就低估、报告就是错的」，而这条理由已被 §1.1/§1.2 拆掉——`exposure.jsonl` 丢了，算出来的数字一个都不会变，变的只是人解读时手上有没有背景。它兑现的是「使后续判断更**知情**」而非「使后续行为**正确**」。挂错标签会把已被拆掉的授权理由带回来。

**为什么必须放 `apps/<app>/` 而不是 `outputs/`**：`RUN_CALIBER` 含 `study_fingerprint`，改 `study.py`（换档位／加维／删维）就强制换 `OUT_DIR`（`write_run_meta` 直接 `SystemExit`），历史会碎在多个目录里——**而改网格恰恰是最该被记住的那次跨轮动作**。

### 1.4 唯一真正无防线的泄漏：外推窗跨轮重复使用

外推窗的无偏性只对**第一个**被拿去验证的候选成立。第一轮把候选 A 拿到 2026 窗、不行；第二轮改网格、拿候选 B 去同一个窗——**从第二次起这个窗自己就变成了搜索空间**，而 bootstrap 只作用于样本内长表、够不着它，红线「别借缓冲差异挑子窗」只管一轮内。

`SKILL.md` 第 7 步已要求「记录尝试次数（防隐性超支）」，但它**指定的落点是研究目录**，而研究目录**按轮切分**——一个跨轮计数器放在按轮切分的目录里必然碎片化。这与反对把 `exposure.jsonl` 放 `outputs/` 是同一条论证。所以这不是「没人照做」的执行问题，**是原设计的落点选错了**。

建议改指 `apps/<app>/notes.md`。但要说清楚：**tune-gates 不执行外推，没有任何脚本能自动写它，这只能是人填的记录纪律，不是机制。** 不愿意每次动手填就直接不做——半途而废的计数比没有更糟，会造成「已经在管」的错觉。

### 1.5 另一件事：`compare_longtable` 断点续跑

字面意义的 resume，与上面无关。确认无 done 集，方案照抄扫描端按股 done 集，但**不能靠产物反推、必须显式落 done 文件**。优先级不高（代价是崩了重跑二十几分钟，且该数字是外推非实测）。

## 2. 问题二：APP 用什么方式传

### 2.1 推荐方案 e（不在原四候选内）

新增 `.claude/skills/tune-gates/current.py`（约 6 行，`APP` / `RUN`），四个入口脚本 `main()` 顶部各写一行 `APP = C.APP`。

关键洞察：**「值存在哪」和「值在哪被读」是两个问题**。原候选 a（改原件一行）与 c（`study_io` 里 `CURRENT_APP`）各丢一半，正是因为把它们当成了同一个问题；分开就都能满足。b（环境变量）是四个里最差的——`export` 一次后静默继承，跑错 app 白烧 20 分钟。**c 被 e 严格支配。**

### 2.2 `critic` 的修正：承重句要改，方案不改

`app-lifecycle` 原写「不需要在规范的字面与初衷之间取舍」。**这句不成立**：方案 e 的 `main()` 里是 `APP = C.APP`，按回车前看见的是「它来自单源」，**看不见这一跑作用在哪个 app 上**。那是可发现性，不是用来枪毙 c 的那个可见性。按其自身定义严格判，「调用点可见」只有 a 满足。

**论证改为**：e 用一跳间接换单源编辑，代价小、收益大。（方案不变——这个交换是划算的。）

`critic` 还指出一处论据误用：把「初衷 ✓」的理由写成「切 app 只改一处」不对——初衷是「不喜欢每次运行手动输入参数」，而方案 a 同样不需要每次敲东西。**初衷在 a 与 e 之间不构成区分**；真实区别是编辑工效（4 处 vs 1 处），那是正当的工程价值，但不是这条规范说的事。

### 2.3 一行成本的加固（建议一并做）

四个脚本动手前打印解析后的身份：

```python
print(f"APP={APP} RUN={RUN} → {out}")
```

**运行时横幅比源码字面量更强**：它显示**实际会用的**值与推导出的路径，源码字面量只显示你以为的值。对 `app_setup MODE=build` 尤其值——它现在是写完才 `print(f"写入 {p}")`，覆盖 git 跟踪的 `classification.json` 之前一声不吭。加了横幅，e 与 a 在「调用点可见」上的差距才真正消失。

### 2.4 两条硬约束（不是偏好，做错会静默出错）

**① run 级常量绝不能进 `study.py`。** `study_io.py:127` 的指纹是 `file_sha256(study_path)`——**整份文件的 sha256**，且 `check_run_matches_classification` 拿它当长表准入校验。把 `TOP_N` 从 20 改成 30，那份 38MB 长表当场读不了、必须重扫。落点必须是 `apps/<app>/` 下的**独立文件**（如 `run.py`）。

> 这背后有个道理值得记：`study.py` 天生只能装「改了就该重扫」的东西，而 `TOP_N` / `NEIGHBOR_AXES` 这类识别端常量改了根本不该重扫——它们本来就不该同居一个文件。

**② `bench_workers.py` 是第五个入口脚本，改动必须同批更新它。** 它用 `re.sub(count=1)` 改写 `multivar_scan` / `compare_longtable` 源码里的 `APP = None` / `OUT_DIR = None` / `LONGTABLE_DIR = None` / `TICKER_REGEX` / `WORKERS` 字面行，**不匹配时静默 no-op**。其中 `TICKER_REGEX` 失配最坏：benchmark 会拿全宇宙 8000+ 只跑 7 档 WORKER 网格，完全静默。建议顺带把它的 `re.sub` 换成 `re.subn` + 断言。

> **一条观察**：`bench_workers.py` 的正则改写，和研究目录里那四份脚本副本，是**同一个成因的两个产物**——都是「参数只能写死在 `main()` 里」逼出来的。前序报告 §5.1 消掉的是其中一个，另一个还在，而且更脆（前者至少是人照着填，后者是正则静默匹配）。

**③ `OUT_DIR` 靠 `APP` 推不全。** 外推窗与主窗口径不同、必然是第二份长表，而 `write_run_meta` 口径不同时直接拒写。需要第二个坐标（`current.py` 里的 `RUN`，默认 `"main"`）。

## 3. 问题三：一次性删除某 app 的耦合物

### 3.1 只走精确匹配，绝不 glob

假树对照实测（`repro/substring_safety_test.py`）：glob 法**误伤 6 项、同时漏掉 3 项**。

- **漏**：本 repo 里真实存在的 `2026-08-20_tune-bb-v1` 用连字符命名，`*bb_v1*` 直接漏掉；
- **误伤**：最重的一项是把整个 `2026-08-25_multivar-bb_v1` 研究目录连报告一起删。

改用精确路径（`apps/<app>/`、`outputs/tune_gates/<app>/`）+ `run_meta.json` 的 `app` 字段**精确相等**反查：0 误伤 0 漏删。

补充一个数字：全 repo `grep -rIl bb_v1` 命中 **161 个文件**，绝大多数是包名与历史文档。这本身就是「不能 grep-and-delete」最直接的证据。

### 3.2 分级轴是「能不能再生」，不是「进不进 git」

这是 `critic` 抓到的**本轮唯一事实错误**，方向是会导致数据丢失，必须改。

`app_lifecycle` 原把那份 38MB 长表与 74MB `cells.csv` 归「单列确认」，理由「gitignore、可重跑，重跑 20~40min」。实测：

```
长表 run_meta.study_fingerprint : 31cf49ee...0106
当前 apps/bb_v1/study.py sha256 : 31cf49ee...0106   ← 一致
apps/bb_v1/study.py 的 BASE_YAML : "p2.yaml"
path2_apps/bb_v1/p2.yaml         : 不存在（41fd193 删除）
```

指纹一致，但底座 yaml 已被 tb 换代删掉——今天跑 `multivar_scan` 会在 `base_snapshot()` 直接 `FileNotFoundError`。**更彻底：即使恢复 `p2.yaml` 也重跑不出同一份长表**，因为 `throwback_v1.py` 已重写成方案 C，事件本身变了。要复现只能 `git checkout 88ec1c3`。

**它的真实性质**：未进 git、**当前代码无法再生**、且是一份已提交研究报告唯一的底层数据。按双方都同意的不对称（漏删 = 留垃圾，多删 = 数据丢失），它不属于「确认一下就删」。

> **两个体量数各自都对，取决于在论证什么**（`resume-analyst` 的分辨，比「哪个数字对」更根本的一层）：
>
> | 论证的问题 | 该报的数 | 为什么 |
> |---|---|---|
> | 「删维时做并集重分析，需要什么」（§1.1） | **37.6 MiB**（长表） | `cells.csv` 是 `region_find` 的派生输出，重分析时会重新生成，不构成所需资产 |
> | 「用户点一次头会丢掉多少」（本节） | **110.6 MiB**（合计） | 两项都在删除清单里，都会一起消失 |
>
> **而「不可再生」这个性质只属于长表那 37.6 MiB**——`cells.csv` 只要长表还在就能几分钟重跑出来。它的风险是**间接的**：长表一没，它也就再生不出来了。所以删除功能真正要挡住的是长表；`cells.csv` 跟着长表的判定走即可。

> **⚠ 比这更严重的一层（`app-lifecycle` 复核时发现）：指纹链在这里给的是「假绿」。**
> 长表的 `study_fingerprint` 与当前 `study.py` **逐字相同**（`31cf49ee…`），所以 `check_run_matches_classification` 会**放行**——它只校验 `study.py` 这一个文件，**不覆盖 `BASE_YAML` 指向的底座**（`p2.yaml` 已被 `41fd193` 删除），**更不覆盖 detector 源码**（同一 commit 改写 `throwback_v1.py` 589 行）。
> **精确化（`critic` 复审）**：不是 `classification.json` 没算 source 指纹——它**算了**，`MODE=check` 也**会**比它（前序报告开头那句「source: 已变更」正是它报的）。真正缺的是 **`write_run_meta` 没在 `run_meta.json` 里留 source/base 指纹的副本**，所以**从长表侧出发**的核对只能比 study，而 study 恰好是没变的那个。这个更准的表述顺带给出一个更小的修法：给 `run_meta` 补存 source/base 指纹副本即可。
>
> 结论不变：「指纹一致」在这里不等于「可再生」，任何只凭 `study_fingerprint` 的自动判断都会在这里判错。
>
> **由此得到一个更强的检测（`app-lifecycle` 已实现进原型）**：多走一跳读 `classification.json`，用它**记录的文件清单**重算 source 指纹——不需要 import app，因为 `source_fingerprint` 只是按序读那些文件的字节：
>
> ```
> classification 记录的 source hash : 49dc105449f8dd25…
> 按同一文件清单重算                : cbaa9c15a882051d…   ← 抓到了 throwback_v1.py 的重写
> ```
>
> 升级后原型对本例**同时报出两条原因**（源码指纹不符 + 底座 `p2.yaml` 不存在），比只报后者更完整。

> **⚠ 这条与问题一直接相扣，必须放在一起看**：§1.1 判定「不需要跨轮状态」的依据之一是「删维时旧格的行还在长表里，设 `COMBO_LEVELS` 为并集重跑就够」——**那个论证依赖的正是这份长表继续存在**，而它恰好就是删除功能初稿要清掉的那份。更要紧的是，它现在还在盘上**靠的是没人清理，不是制度保证**（`outputs` 与研究目录的 `longtable/` 都在 gitignore 里）。所以「不做跨轮机制」这个结论要成立，前提是这类长表不被顺手删掉。

**改法**：dry-run **实际去验可再生性**——不能只对指纹，要核 `BASE_YAML` 指向的文件是否存在、detector 源码是否还是当初那份。验不过就降到「绝不自动删」，把理由打进输出。**37.6MB 不是「重跑 20 分钟」的问题，是「回不去」的问题。**

**原型实跑结果**（`repro/app_purge_prototype.py`，真实 repo）：加上可再生性检测后，**那 110.6 MiB（长表 37.6 + `cells.csv` 73.0）一个字节都没进「可删」组，全部自动降级**。按修正前的分级实施，用户点一次头就会永久丢掉一份已提交研究报告的全部底层数据。

### 3.3 「`apps/<app>/` 整夹可删」要撤回

`SKILL.md:19` 与 `reference.md:28` 都写着「app 耦合内容全部在 `apps/<app>/`……整夹可删」。实测**两头都不成立**：

- **往外**：耦合还在 `fixtures/` 与五个测试文件里（import 与断言级，不是注释）；
- **往内**：夹里那 3~4 个文件性质不同。`study.py` / `classification.json` 是「这个 app 怎么调」的**配置**，app 没了就没意义；`notes.md` 与 `exposure.jsonl` 记的是「**对这批数据做过什么**」，意义不随 app 消失。

**应改成「夹内分两类」。** `notes.md` 与 `exposure.jsonl` 从「必删」降级为「**点名确认**」，默认保留——误删后果（跨轮记录永久丢失）比误留（目录里多两个文件）严重得多。

> 这个降级由 `critic` 与 `resume-analyst` **各自独立提出**、方向一致，`app-lifecycle` 采纳。

删 `notes.md` 时要报出：通用区仍有 **29 处**指向它（`SKILL.md` 11 + `reference.md` 18），且 `region_find.py:36` 那个「仅在一个 app 上校准过」的默认功效线 100，其校准记录就在这份 notes 里——**bb_v1 是目前唯一的 app**。

### 3.4 `fixtures/` 绝不碰

它里面确实是 bb_v1 的活代码，但**它扮演的角色是「一份具体的被测输入」，不是「app」**。`classify()` / `build_classification()` 必须拿真实 dag_spec 才能测（探针要真探、指纹要真算），挑中 bb_v1 是**选材，不是耦合**。

而且它与 `apps/bb_v1/` 是解耦的——`test_study_io.py:20` 用的是 `fixtures/study_bb_v1.py` 而非 `apps/bb_v1/study.py`，所以**删 `apps/bb_v1/` 对自测零影响**，两难其实没在删除这条路径上发生。真两难在别处：退役 `path2_apps/bb_v1` 这个包本身，那属 path2 侧的独立工单。

### 3.5 其余安全设计

- **不做自动备份**（复制 110.6 MiB 只是制造新垃圾），改成删 git 内容前检查 `git status --porcelain apps/<app>` 是否干净——**未提交的改动是整个操作里唯一真不可逆的东西**。
- **delete 分支必须在 `load_study` / `import_app` 之前短路**。`app_setup.py:23-27` 无条件先跑那两行，而删除场景里 app 很可能已经坏了。**这条有现成实证，不是假想**：`apps/bb_v1` **此刻就是坏的**——`base_snapshot()` 抛 `FileNotFoundError`（`p2.yaml` 已删），今天跑 `app_setup MODE=check` 连三行报告都打不出来。删除功能若不短路，就会在最需要它的时候用不了。
- **归属不明的长表只报不删**：`smoke/longtable/` 有 parquet 但没有 `run_meta.json`，内容反查够不着。
- **`current.py` 要进清单**（`critic` 问题 D）：方案 e 新建的这个文件里存着 app 名，删除时该一并处理。
- **跨 worktree 作用域**：只作用于当前 worktree，不去别的 worktree 找。
- 并入 `app_setup` 作第三个 MODE。
- **一词修复（`critic`）**：`notes.md` 默认保留会引入「目录还在、`study.py` 没了」这个新状态，而入口协议的判据写的是「`apps/X/` 存在？」——会绕两跳且第一跳报错指错方向。判据改成「**`apps/X/study.py` 存在？**」——具体位置 `SKILL.md:22` 与 `reference.md:31` 各一处。
- **一条建议升格为设计原则**：可再生性检测「报『不可再生』一定对，报『可再生』只是没发现问题」。误差全推到「多留垃圾」一侧，正是安全检查该有的形状；写成原则后，「抓不住 detector 源码被改」就从弱点变成**已吸收的边界**。

## 5. 本轮之外发现的两个问题（都建议单列处理）

### 5.1 【新发现·重要】`split-half` 的种子噪声远大于本轮讨论的一切

`critic` 在测噪声地板时捞到的，与本轮三个问题都无关，但**比它们都更值得处理**。

固定全网格、只换 `split_half` 的种子（0→19）：

```
seed= 0 -0.1319    seed= 4 -0.2456    seed=16 -0.3083
seed= 2 -0.0346    seed= 9 -0.1388    seed=18 -0.0748
...
split_half over 18 seeds: mean=-0.1659  sd=0.0762  min=-0.3083  max=-0.0346  range=0.2737
（20 个种子里 2 个返回 NaN）
```

而 `region_find.py:38` 把 `SEED` 硬编码为 0、只做一次对半分，报告里写成 `split-half = −0.1319（下界）`——**四位小数、无不确定度**。同一行的 optimism 却是带 ±SE 的，红线还专门要求看 `|optimism|` 相对 `optimism_se`。

**换个种子，同一份数据的「下界」可以从 −0.03 变成 −0.31。** 红线「split-half 当下界」在这个抖动下不是一个稳定的界。

量级对照（本轮所有数字放在一起看）：

| 量 | 数值 |
|---|---|
| **split-half 种子噪声 sd** | **0.0762**（极差 0.274） |
| 候选集变动 **1024×** 对 optimism 的全部带宽 | 0.056 |
| 候选集砍 4×（单轴塌缩）对 optimism 的最大偏移 | 0.038 |
| optimism 自身的 MC SE | 0.0062 |
| 跨轮删维偏差（本轮主问题） | 0.0021 |

**大家担心的跨轮暴露，比报告里一个没人注意的抖动小 36 倍。**

修法现成：多种子取均值 + 报 SE，与 optimism 对称。**不要把它塞进 resume 方案里**——会把一个真问题绑到一个已判「不做」的机制上。

**它有分量**，因为 `reference.md` §4.0 明写工具**故意**不进源码指纹、正确性就靠这套测试兜底——**这个兜底现在是失效的**，而 `SKILL.md:106` 还写着「必须看到 passed」。

`41fd193` 删了 `p2.yaml`，而 `apps/bb_v1/study.py:5` 与 `fixtures/study_bb_v1.py:5` 至今指着它。这一行同时造成**三处红**：

## 6. 附带结论：要不要把「单参数」与「多参数」拆成两个 skill —— **不拆**

> 本节起因于本轮研究之后的一个追问：单参数调参（找平台）与多参数调参（稳健区）「工作流完全不同、从起点就分叉、没有复用的功能」，是否该拆成两个 skill。结论是不拆，但这个直觉指向了一个真问题（§6.4）。

### 6.1 事实核查：前提被推翻了一半

**「从起点就分叉」不成立**——真正分叉的只有第 4-5 步：

| 步骤 | 归属 |
|---|---|
| 1 声明（训练窗 / 指标契约 / 功效线） | **共享** |
| 2 分层宽进（按可否事后切档给参数分两类） | **共享** |
| 3 单特征质检（AUC 粗筛） | **共享** |
| 4 前半：事后切档 · 后半：多维稳健区 | **← 分叉点** |
| 5 逐闸判定（`plateau.py`） | 单参数专属 |
| 6 人复核拍板 | **共享** |
| 7 回放校验 + 台账 | **共享** |

**「没有复用的功能」在代码层面成立**：`plateau.py` 只 import 标准库与 matplotlib，**零内部依赖**；反过来也没有任何脚本 import 它（`grep plateau` 命中的全是 `test_region_core.py` 里的变量名与测试名，是「平台」这个概念、不是模块引用）。

但 **skill 的复用单位是判据与流程，不是 import 图**。按代码耦合划 skill 边界，等于按 import 关系切文档。

### 6.2 不拆的四条理由

1. **共享的是判据，而判据刚合并过一次。** 指标契约（FP 字典序优先、`win_rate` 废弃）、带对照才下结论、算术效应归因、台账、整节红线——都是两条路都要守的横切纪律。拆成两份必然「改一处忘另一处」。而且有前科：**评估纪律原本是独立 skill `eval-discipline`，2026-08-20 才内联进来、原 skill 解散**；按路径拆开等于把那次合并撤销一半。
2. **分流器本身是共享步骤。** 第 2 步「按可否事后切档分两类」的**结果**才决定走哪条路（能事后切 → plateau；必须真扫 → region），且它在多维路径里已工具化为探针分类（`multivar_core.classify` 的 W/F/D/E）。拆开后这步放 A 则 B 反向依赖 A、放 B 则 A 用不到探针却要读 B、各放一份就是复制。**分流决策不能住在被分流出去的分支里。**
3. **`plateau.py` 至今零实战。** SKILL.md「首轮使用注意」自陈「本轮跑的是 multivar 链路，`plateau.py` 全程未调用」，其 1SE/tol 与 `REL_TOL 0.05` **仍待首轮实战校准**。给一条从未在真实数据上跑通的路径单独立 skill，是给它还没挣到的地位。
4. **触发上没有收益。** 现行 `description` 已明写两条入口，两批用户口径词都在（「跑阈值扫描 / 画平台图 / 拍板参数取值」与「同时调好几个参数 / 找不敏感的稳健区域 / 嫌一个格子一个格子扫太慢」）。拆开只多一份要同步维护的 `description`。

### 6.3 方法论上两条路是同一件事

多维稳健区的核心判据是「取 r=1 邻域最小分最高的格」——**这在一维上就是 plateau 的平台判定**。单参数是多参数的退化情形（1 维网格），不是另一个问题。

硬证据：`test_region_core.py` 的测试名就叫 `test_rank_cells_zero_neighbor_spike_loses_to_plateau_center` 与 `test_plateau_recovered_end_to_end`——**多维那套的测试，验的正是「找平台」**。拆开会把一个统一的方法论割成两半。

### 6.4 真问题：第 4 步里塞了一整条流水线

`SKILL.md:44` 是**一个步骤的正文**，却用加粗引出「必须真扫参数的调参（多维稳健区 v2）」，再展开 ①探针分类 ②扫描出长表 ③`region_find` ④人复核 ⑤外推窗 五个子步骤，中间还夹着对拍作用域、格数≠检测组合数、OAT 降级等大段内容。

**七步骨架是为单参数路径设计的，多参数路径被硬塞进了第 4 步。** 「像两个 skill」的感觉来源在此——不是边界画错了，是**文档结构没跟上功能扩展**。

### 6.5 建议：重组结构，不拆 skill

```
判据与纪律（原 1 / 6 / 7 步 + 红线）      ← 横切，只写一遍
分流器（原第 2 步 + 「入口粒度」节合并）   ← 决定走哪条路
├── 路径 A：事后切档 → plateau（原 4 前半 + 5）
└── 路径 B：多维稳健区（原 4 后半，展开为平级五步）
```

两条路各自完整可读、互不打扰，共享部分只有一份。**这条与 §2 / §3 的改动无冲突，可独立实施。**

### 6.6 何时才真该拆（前瞻判据，免得日后反复纠结）

- **当 plateau 路径实战后长出自己的一套判据，且与 region 路径的判据冲突时**——那时共享段会开始打架，拆才有收益；
- **或共享部分萎缩到只剩评估纪律**——那说明该拆的是**纪律**（重新独立成 skill），而不是两条路径。

现在两条都不满足：判据共享且一致，共享部分占 5/7 步。
