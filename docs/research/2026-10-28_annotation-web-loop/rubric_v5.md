## 使命与两条原则（用户定，一切取舍以此为准）

标注工具的使命：用户通过看图标注直接得到 path2 pattern。流程：找图 → 标注 → 会话写 app → 拿 app 对标注 → 盲看 → 调参 → 最后检查。

1. **标注功能能高效、高质量地完成这个使命**：标得快、标得准，标出来的东西能直接变成 pattern，pattern 能直接对回标注。
2. **用户友好、心智负担低**：用户要知道的概念、要记的规则、要认的词越少越好；看一眼就读对。

## 0. 判法总则

1. **must / nice**：违反第 2 节任一硬条款、违反 GOAL 子项、真实 bug 或回归 = must；其余改进建议 = nice。
2. **【方向题】**：凡是会推翻第 4 节「已定规矩」的，或者要在两条都说得通的路之间选一条的，**一律记 nice，标题以【方向题】开头**，正文写清：选项（至少两个）、各自代价、推荐哪个及理由。**implementer 不做【方向题】**；reviewer 也不得因为「没做某个【方向题】」记 must。第 7 节列出已知的方向题，不要重复提。
3. **只判截到的证据**：需要别的状态才能看到的，写「需加 state」，不自己开浏览器。
4. 指出缺陷，不设计替代方案（【方向题】除外，它本来就要写选项）。

## 1. 项目特化（填 principles.md 的占位）

## 2. 硬条款（全部 lens 通用，违反 = must）

| # | 条款 | 怎么判 |
|---|---|---|
| H1 | **配色规范逐条成立**（`color_spec_draft.md` 第 1 节）：底色只说「这一段判断是谁下的」，**按段上色**——用户和界面从用户标注直接数出来的不加底；会话 `#93c5fd`；app `#F2C25C`；朱红 `#D55E00` 只盖「和用户的 label / 判断对不上」的那一段，并取代琥珀。明文特例只有两条：band 和档位签用档位色（node 本色 / 深灰 / 浅灰），instances 表列头按这一列的值是谁的判断上色 | 任一段底色和来源不符；朱红盖到对得上的段上；新出现第三条特例 |
| H2 | **规则不随阶段或页面变**：同一元素在不同页面、不同 mode、有没有 app 时，算法和意思一致；buy、no_buy 的差签同一种算法（D5） | 例：同一个计数在两页分母不同；同一个按钮在两页做不同的事 |
| H3 | **同一个词只有一个意思**（全界面，含悬停）。`detected`、`qualified`、`matched` 一律按 `path2_web/GLOSSARY.md` 第 28 行的绝对定义（依次收窄：被检测出来 / 通过所在 node 的全部 where / 进了某一次 match）；主图和选中框时的档位签只标最深一档，写 `qualified_only` / `detected_only`；app 的判断写 `match` / `no_match`；不出现「够格」「认出」这类自造的替代说法 | 同词两义；悬停和签对同一个词的解释不同 |
| H4 | **没有任务对应的元素**：截图里每个列、签、按钮、计数、颜色都要能对到第 3 节的某个任务 | 对不上 = must（razor 主判） |
| H5 | **新手第一眼读错**：几周没碰、不看悬停的用户第一眼会读错、读不出，或会因此点错下一步 | newbie 主判，正确含义以本文件第 3、4 节与配色规范为准 |
| H6 | **界面文字规则**（`~/.claude/rules/ui-text-style.md`）：程序固定内容（字段名、状态、按钮、标签页、表头）用等宽标识符；用户 / 会话的业务内容用正常字体，不在输入框里的加浅灰底；**字一律黑色**，灰字只给空着、没选上、用不了；**说明放悬停**，界面上不写说明句、口语问句，不重复已显示的内容；字段名用名词、状态用枚举或布尔 | 任一处违反 |
| H7 | **悬停说明**：一句短话说清「这个东西是什么」，一般 15 字内、最多约 30 字、至多两小句；用用户的词（标注、对应表、app、match、会话、label，特征名用「」）；不写算法细节、设计理由、开发历史（原先 / r2 / critic / U 编号）、括号补充、后续流程叙述。用户亲自定的样板：列头 `must / must_not` =「标注 和 对应表 是否一致」；`−回踩` =「标注缺少「回踩」」；`in k/N` =「N 个 buy 里 k 个有「横盘」框；点一下列出这几个」 | 任一条悬停超长、含上述应删内容，或同一概念两处说法不同 |
| H8 | **色弱**：用户靠冷暖和深浅分颜色，不靠色相。要分开的两种颜色要么冷暖相反（暖：红、橘、黄、绿；冷：蓝），要么深浅明显拉开；同是暖色的红-绿、绿-橘分不清；着色区域要和底色拉开深浅（浅灰底上的天蓝、浅黄、奶油色看不出）；不要深到压掉明暗；叠在色块上的标记同样按冷暖或深浅拉开。不得退成黑白 | 新出现只靠色相区分的一对；着色和底色深浅相近 |

| H10 | **已定规矩不得违反**（第 4 节）；要推翻只能记【方向题】 | 改动与第 4 节冲突 |
| H11 | **心智负担不得变多**：razor 每轮对照本轮 diff 与截图，逐项列出新增和删去的「概念 / 要记的规则 / 屏上固定词」（数法见第 5 节）。净增且没有对应任务、或可以用已有的词表达 = must | razor 主判 |
| H12 | console error / pageerror 为零；smoke 全绿 | func 主判 |
| H13 | **高频操作不得变慢**：第 3.2 节每项的点击数不得多于基线列 | func / razor |

## 5. 数法（H11，razor 每轮按同一把尺数）

- **概念**：用户要知道「它是什么」才能读对的东西；同一含义多处出现算一个。
- **规则**：用户要记住才能读对或用对的条件句（「X 时 Y」）；屏上直接写着的不算；悬停写着、但不悬停就会读错的算。
- **固定词**：屏上出现的不同程序固定词（表头、签、按钮、符号、状态值）；用户内容不算；同词算一次。
- 本次不设全量基线：razor 每轮只数**本轮相对上一轮的增删**，逐项写出「新增了哪几项、删了哪几项」，净增要逐项说明对应哪个任务、为什么不能用已有的词。
