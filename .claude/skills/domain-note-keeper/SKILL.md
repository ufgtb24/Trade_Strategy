# 领域方法论笔记管家

帮用户把**方法论概念**沉淀到 `docs/domain_notes/`（repo root 相对路径）的 markdown 笔记中。维护根索引 INDEX.md，按一个分类维度组织主题文件，概念以 `## 小节` 形式聚合在主题文件内。

笔记目的：**让概念解释可复用、口径一致**。每条概念是一个标准化的解释条目（本质→算法→数值解读→适用→局限），写一次、每次引用同一版本——避免同一概念在不同会话里被重新组织成不同口径。

与相邻笔记体系的分工：

| 体系 | 内容 | 入口 |
|---|---|---|
| **本 skill**（domain_notes） | 方法论概念：统计概念、评估指标与口径、归一化方法、数学工具 | `docs/domain_notes/` |
| cc_notes | Claude Code 配置/操作经验 | `docs/cc_notes/`（cc-note-keeper skill） |
| 评估纪律（已内联） | 评估的**试验纪律**（怎么做评估：对照、口径自检、小样本计数） | tune-gates / feature-study 各步骤内联（原独立 skill eval-discipline 已于 2026-08-20 解散） |
| `.claude/docs/` | 当前代码状态的结构性描述（AI 上下文） | update-ai-context skill |

与评估纪律的分界：同一指标（如 first passage）的**概念解释**（是什么/怎么算/怎么读）归本笔记，**怎么用它做评估的流程纪律**（对照基线、口径自检）已内联 tune-gates / feature-study 各步骤，不在本笔记。

**不收录**：市场形态/交易直觉观察（如「跳空高开+阴线+放量=利好」）、项目操作步骤、代码结构说明。用户若要记这些，说明放错了本子，提醒改走对应体系。

**技术指标类概念（ATR/TR/RSI 等）的边界**：指标的定义与计算口径（怎么算、口径差异、量纲性质、适用条件）算方法论概念，**收**；指标的行情信号解读（某读数意味着什么市场状态）算经验假设，**不收**。判定一句话：回答「怎么算、什么性质」收，回答「意味着什么行情」不收。

## 仓库结构

```
docs/domain_notes/
├── INDEX.md              ← 根索引：分类维度 + 主题文件映射
├── <topic-a>.md          ← 主题文件，内含多个 ## 概念小节
└── <topic-b>.md
```

颗粒度约定：**一个主题文件聚合一类概念的多个 `## 小节`**，不为一词一条建独立文件。概念多了优先在主题文件内加小节；主题文件超过 ~10 个概念小节时，在场景 2 的推荐中向用户提出**拆分**（新建主题文件 + 把相关概念小节迁移过去 + 双方 frontmatter/scope 重写 + 更新 INDEX），经确认后执行——拆分是内容重组，与场景 4 只动分类标签的维度调整是两回事。

### INDEX.md 格式

```markdown
---
dimension: <分类维度名>
updated: YYYY-MM-DD
---

# 领域方法论笔记索引

## 分类维度
<一句话说明按什么分、为什么选它>

## 分类与笔记

### <分类 A>
- [topic-a.md](topic-a.md) — <该主题文件 scope 一行摘要>

### <分类 B>
- [topic-b.md](topic-b.md) — <…>
```

`updated` 字段在**每次改动 INDEX.md 时**刷新为当天日期。

### 主题文件 frontmatter

```yaml
---
title: <一句话标题>
scope: <这个文件专门记录什么概念类别。明确边界，便于判断新概念是否归属这里>
category: <INDEX.md 中所属的分类名>
---
```

## 概念条目模板（写入时的正文格式）

每个概念一个 `## 小节`，**先人话后形式**（直观读法优先，教科书定义其次），总长 300-600 字：

```markdown
## <概念名>（<符号/英文名>）

**一句话本质**：<等价直观读法优先；教科书定义放括号内提一句>

**怎么算**：<算法步骤，具体到可手工复算；必要时给一个小数字例子或公式>

**数值怎么读**：<关键档位的经验含义，如 0.5/0.7/1.0 各代表什么>

**何时用 / 为何用它**：<相对替代品的优势，如"不依赖阈值/量纲无关">

**局限**：<它看不到什么、什么时候会误导>

（可选）**与 <X> 的辨析**：<相邻概念的分工，如 AUC 管排序、ρ 管共线性>
```

细则：

- 不打比方，用语言把机制本身讲清（用户偏好；仅当用户自述「完全不懂」才用比喻）
- 「怎么算」要落到具体步骤（例：AUC = 穷举坏×好配对数「坏>好」的比例），不给只含公式没有语义的式子
- 「局限」必写——概念被误用的地方比定义更值得沉淀
- 记录来源研究语境（如「在 2026-08-18 tb revert 研究中用于筛选特征」）有助于日后判断适用性，但不展开研究本身
- **记「两个概念的关系」**（如 MWU 与 AUC）：默认记入其中主概念条目的「辨析」小节；仅当两个概念各自都值得独立成条时才双侧建条 + 交叉引用，避免为陪衬概念硬造薄条目

## 四个使用场景

### 场景 1 · 初始化（目录或 INDEX.md 不存在时）

1. **一次性**向用户问两件事（一轮完成，不拆两次）：① 当前想记的概念；② 未来可能记的方向（至少 2-3 个例子）——维度要能装下它们，否则之后又得重排。
2. 提 **2-3 个候选分类维度**，每个说明：维度名、初步类别列表（基于用户答的样本）、优点与风险（哪类概念可能放不进）。**给出自己的倾向性推荐并说明理由**（首位标注），由用户最终拍板。
3. 选维度把住三道关：类别**互斥**、颗粒度**均衡**、类别 **4-8 个**为宜。
4. 用户选定后再动手：`mkdir -p docs/domain_notes/` → 创建 INDEX.md → 进入场景 2 写入首批概念。（目录创建放在维度选定之后——用户中途放弃时不留空目录。）

### 场景 2 · 写入新概念（主要场景）

触发：用户描述了一个想记下来的方法论概念。

1. **读** INDEX.md + 各主题文件的 frontmatter（不必读正文，scope 足够判断归属）。
2. **一次性推荐**（不分步问），按模板给出：选定的**分类**及理由；**目标文件**（现有或新建）；如新建给文件名和 scope；概念归入该文件的哪个位置。
3. 用户确认或修正后：新建文件写 frontmatter → 按条目模板写概念小节 → 更新 INDEX.md。
4. 写完后**简报**：写到了哪个文件、加了什么小节。

推荐模板：

```
建议这样记录：

  分类：<分类名>
  目标：<新建 xxx.md  /  追加到 yyy.md 的「## <概念名>」小节>
  scope（仅新建时）：<一行描述>
  理由：<为什么属于这个分类 + 为什么选这个目标，1-2 句>

确认请回复 ok，或者告诉我要怎么改。
```

### 场景 3 · 手动查阅（仅显式触发）

触发：用户明确说「查一下笔记」「看看有没有能做 xxx 的数学工具」「笔记里 AUC 是怎么记的」等。

1. 读 INDEX.md → 定位候选主题文件 → 读相关概念小节。
2. 基于笔记内容回答，**注明出处**（哪个文件哪个小节）。
3. 笔记里没有就明说「没有」，不硬凑近似概念充数。
4. 查阅后若用户未要求记录新概念，**不主动追问**「要不要把刚才讲的沉淀进笔记」。

### 场景 4 · 调整分类维度（重操作，谨慎）

触发：用户明确说要换维度 / 重新整理；或场景 2 中频繁出现「现有维度装不下」的内容。

1. **先提醒**这是重操作，会改 INDEX.md 和多个主题文件的 `category` 字段，等用户确认。
2. 读 INDEX.md + 所有主题文件 frontmatter。
3. 提 2-3 个新维度候选，**预演**每个新维度下现有文件的归属（让用户看到迁移效果）。
4. 用户选定后：改写 INDEX.md，逐个更新主题文件 frontmatter 的 `category`。文件名与概念正文**不动**。

## 查阅的边界（探索性保护）

**概念问答不自动查笔记**：用户问「X 是啥/怎么算」时正常直接解释，不先去查笔记本——已定论的设计决策（2026-08-19），理由：

1. 选型/求解场景下，默认优先查笔记会锚定在已知概念上，阻止吸收新工具——检索只能找到「知道自己不知道」的，真正的新方法在词汇空间里离问题很远；
2. 笔记本是探索的**输出**（发现好概念→沉淀），不该前置成输入的替代；
3. 收敛（查笔记）还是发散（探索新方法）的开关留在用户手里。

即使在显式查阅命中的情况下，笔记内容也只作为**参考信息**呈现，不替代对当前问题的独立思考——命中 ≠ 决策。

## 关键决策表

| 情境 | 处理 |
|------|------|
| 目录或 INDEX.md 不存在 | 走场景 1，不要擅自建笔记 |
| 用户给了待记录概念 | 先读 INDEX.md，再一次性出推荐 |
| 内容同时贴合两个分类 | 说明歧义、让用户裁决，不要默默选一个 |
| 找不到匹配分类 | 推荐放最接近的分类 + 提醒「若此类越来越多，考虑场景 4 调维度」 |
| 新概念只有一两句、撑不满模板 | 先按模板问清要点再写；实在单薄就并入相邻概念作「辨析」小节 |
| 用户说「重新整理」 | 走场景 4（维度调整）：只动 frontmatter `category` 和 INDEX.md，不动概念正文 |
| 用户主动要求拆分某个主题文件 | 按颗粒度约定中的拆分流程执行（场景 2 同款确认式：新建+迁移+scope 重写+更新 INDEX，经用户确认） |
| 用户问「X 是啥」 | **不触发本 skill**（保护探索性），直接解释 |
| 用户要记形态观察/CC 操作 | 不收，改指 cc_notes 或研究文档体系 |

## 常见错误

- ❌ 概念问答时自动去查/自动建议沉淀（违反「仅显式触发」定论）
- ❌ 把概念写成散文或博客（条目是标准化解释，按模板五要素）
- ❌ 定义先行、直观读法压后（应先人话后形式）
- ❌ 一概念一文件地碎片化（聚合在主题文件内）
- ❌ 初始化时凭空猜维度直接写 INDEX.md（必须先和用户对齐）
- ❌ 推荐拆成多步问（分类一步、文件一步、scope 一步……一次给完整方案）
- ❌ 用 `Other`/`Misc`/`杂项` 当兜底分类（维度选错的信号）
- ❌ 收录形态观察/项目操作步骤（超出方法论概念边界）
- ❌ 条目缺「局限」小节（误用场景比定义更值得沉淀）
