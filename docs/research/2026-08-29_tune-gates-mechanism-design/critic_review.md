### 1.2 【C·中】§2.2 的论据 (b) 不成立

resume-analyst 的自辩 (b)：「`SKILL.md` 第 7 步已经要求记录尝试次数，我补的是**落点**不是新机制」。

第 7 步原文：

> 整轮落 `docs/research/<日期>_tune-<内容>/`，记录尝试次数（防隐性超支）。

**落点是指定了的——研究目录。** 悬空的是执行（没人照做），不是设计。所以「补落点」不准确；实际动作是把指定位置从研究目录**搬到** `notes.md`。

但这个搬迁有一条 resume-analyst 没写、却比 (b) 强得多的理由，**而且是它自己在别处已经用过的**：研究目录**按轮切分**，一个**跨轮**计数器放在按轮切分的目录里必然碎片化——这与它反对把 `exposure.jsonl` 放 `outputs/`（改 study 强制换 OUT_DIR → 历史碎在多个目录）是**同一条论证**。第 7 步把跨轮计数指向按轮目录，是原设计的缺陷，不是执行问题。

**裁定**：结论（该有个跨轮落点）可以救，论据必须换。已要求改。

### 1.3 【E·低】「resume」这个标签会带回被拆掉的授权理由

resume-analyst 已明写消费者是人，这点干净。但 `exposure.jsonl` 仍挂在「resume 必要性」这个框下，而前序报告 §3.2 给 resume 状态的授权理由是「**丢了它 optimism 就低估，报告就是错的**」——这条理由已被 §1.1/§1.3 拆掉。

按 §3.2 的定义（跨中断保持、**使后续行为正确**），`exposure.jsonl` 兑现的是「使后续判断更知情」而非「正确」：丢了它，算出来的数字一个都不变。

**裁定**：实质判断无误，但需在 §2.1 开头显式切割——「这不是 §3.2 所说的那个状态；那个状态没有消费者。这是一个更小的东西：识别端的运行审计日志。」防的是标签替论证干活。

### 1.4 【F·低】删维实验的限制来源写偏了

resume-analyst 点名要我查修正后的规则（「按逐档均值极差最小挑轴」）是否仍有退化。

**不是算术退化**——第一版那个 `argmin` 恒选 0 号轴的 bug 确实修对了。但有一处设计天花板：纯 null 下每档均值都是 0 + 噪声，`argmin` 基本由噪声决定；5 次重复选中 d0/d1/d4/d2/d3 各不相同被读成「决策随数据变化」，**而在 null 下「随数据变化」与「随机」观测不可分**。

这不使实验失效——噪声驱动的选择**正是** winner's curse 的机制本体，所以结果不是 vacuous。但它测的是该机制**最弱的一档**：真实数据里删维决策会被真实结构强烈驱动，那种情形 null 设计够不着。

**裁定**：caveat #2 的措辞（「未观测到可区分于 0 的低估」）本身是对的，但限制的**真实来源**应从「R=5 样本少」改为「null 下第一段决策不携带真实信息」。R=5 是次要的。我的真实数据实验（§3）正好补在这一格。

### 1.5 我认为没有问题的

- §2.3 `compare_longtable` 断点续跑：必要性低但为正，方案照抄扫描端，并正确指出**不能**照抄 done 集的推导方式（对拍端无对应产物，必须显式落文件）。无意见。
- 坚持按 `meta["app"]` 而非 `current.py` 的 `APP` 归档 `exposure.jsonl`：正确，理由（真分歧时按长表归属才不归错档）成立。
- `exposure.jsonl` 放 `apps/<app>/` 不污染 study 指纹——我核过，指纹是 `file_sha256(study_path)`，只哈希 `study.py` 单文件。安全。

## 2. 对 `app_lifecycle.md` 的审查

### 2.1 【A·高】删除分级 2 的「可重跑」对 F/G 实测为假 —— 唯一的事实错误

§3.2 把 F（`docs/research/2026-08-25_multivar-bb_v1/longtable/`，37.6MB）与 G（`cells.csv` 73MB 等）归「单列确认」，理由：「**gitignore、可重跑**；但体积大、重跑 20~40min」。

实测三项：

```
长表 run_meta.study_fingerprint : 31cf49ee34dd95be30cdd0ac022b3a0ad02e9778342c46d644bcfbd38b5e0106
当前 apps/bb_v1/study.py sha256  : 31cf49ee34dd95be30cdd0ac022b3a0ad02e9778342c46d644bcfbd38b5e0106   ← 一致
apps/bb_v1/study.py 的 BASE_YAML : "p2.yaml"
path2_apps/bb_v1/p2.yaml          : 不存在（41fd193 删除，内容并入 params.yaml）
```

study 指纹与 classification 都一致，但底座 yaml 已被 tb 换代删掉。今天跑 `multivar_scan` 会在 `study_io.base_snapshot()` 的 `Params.from_yaml(p2.yaml)` 直接 `FileNotFoundError`——与 skill 自测那 8 个 error 同一根因。

更彻底：即使恢复 `p2.yaml` 也重跑不出同一份长表，因为 `throwback_v1.py` 已重写成方案 C，事件本身就变了。要复现只能 `git checkout 88ec1c3`（run_meta 记录的 head）。

**F/G 的真实性质**：未进 git、**当前代码无法再生**、且是一份已提交研究报告（`2026-08-25_multivar-bb_v1/final_report.md`）唯一的底层数据。按双方都同意的不对称（漏删=留垃圾，多删=数据丢失），它不属于「确认一下就删」。

**要求的改法**：把分级轴从「进不进 git」换成「**能不能再生**」，并让 dry-run **实际去验**——读 `run_meta.study_fingerprint` 对当前 `study.py`，再核 `BASE_YAML` 指向的文件是否存在。验不过就降到「绝不自动删」，把理由打进输出。这比任何体积/耗时提示都有用：37.6MB 不是「重跑 20 分钟」的问题，是**回不去**的问题。

### 2.2 【B·中】§2.2 的承重句不成立

app-lifecycle 把 Y2 的独立价值定义为：

> **调用点可见**。你在按回车之前，能在即将运行的那个文件的开头看见**这一跑到底作用在什么上**。

方案 e 的 `main()` 里是 `APP = C.APP`。按回车前看见的是「它来自单源、去 `current.py` 找」——**看不见作用在哪个 app 上**。表里给 e 的 Y2 打 ✓，注为「看不到字面值，但看得到它来自单源」。那是**可发现性**，不是用来枪毙 c 的那个**可见性**。

按其自身定义严格判：**Y2 只有 a 满足**。e 把它降级成一跳间接（比 c 好，c 连指针都没有），但不是「不取舍」。

**这不是要求换方案**——e 用一跳间接换单源编辑，交换划算。要求改的是论证：「不需要取舍」→「**e 用一跳间接换单源，代价小、收益大**」。理由是这句话是 §2.2 的承重墙而它是错的；一个自定义标准又给自己打 ✓ 的表格是最容易被逐条审穿的形态。

**附带的论据误用**：§2.3 把「初衷 ✓」的理由写成「正常切 app 改一处」。初衷是「**不喜欢每次运行手动输入参数**」——方案 a 同样不需要每次运行敲任何东西，§2.2 表格自己也给 a 的初衷列打了 ✓。**初衷在 a 与 e 之间不构成区分**；真实区别是编辑工效（4 处 vs 1 处），那是正当的工程价值，但不是这条规范说的事。

**我给的建设性替代（成本一行，能真正消掉张力）**：四个脚本动手前打印解析后的身份——

```python
print(f"APP={APP} RUN={RUN} → {out}")
```

Y2 要保护的是「别让这一跑作用在你以为之外的东西上」。运行时横幅比源码字面量**更强**：它显示**实际会用的**值与推导出的路径，源码字面量只显示你以为的值。对 `app_setup MODE=build` 尤其值——它现在是写完才 `print(f"写入 {p}")`，覆盖 git 跟踪的 `classification.json` 之前一声不吭。加了横幅，e 与 a 在 Y2 上的差距才真正消失，那时「不需要取舍」才成立。

### 2.3 【D·低】§3.1 自称穷尽，漏了方案 e 新建的 `current.py`

`current.py` 含 `APP = "bb_v1"`——**通用区、进 git、带 app 名**的新文件，而 §3.1 的 A~M 没有它。删掉 app X 后 `current.py` 仍写着 X，下次跑 `app_setup`/`multivar_scan` 会撞 `SystemExit(f"{study_path} 不存在...")`。

严重性低（失败响亮、改一行即可），但**这张表是整个删除功能的依据**，完备性有要求。建议加一行 N：不删文件，delete 分支完成后把 `APP` 置回 `None` 或提示重置。

顺带：`current.py` 让「切 app」每次都在 skill 通用区产生 git diff。不违反 `SKILL.md:34`（那条只管 6 个文件、且管的是参数名/节点名/数字，不是 app 名），但值得明说，别让后来人以为通用区零 app 名。

### 2.4 app-lifecycle 点名要我判的两条

**§2.5 `RUN`（它标「中等强度、不坚持」）→ 我要求它坚持。** 它漏了一条让 `RUN` 明显划算的性质：**忘记改 `RUN` 的失败模式是响亮的**。做外推窗必然改 `START_DATE`/`END_DATE`，而这两项在 `RUN_CALIBER` 里，撞 `write_run_meta` 就是 `SystemExit`「换口径请换 OUT_DIR」。所以「忘了换 RUN」不可能静默污染长表，最坏是被拦下。零成本 + 失败响亮 + 服务 SKILL.md 必做步骤，没有理由不加。

**§3.2 `notes.md`（它问是不是仪式性补丁）→ 处置对，理由要换，警告要瘦身。**

- 理由「尊重它自己的声明」**弱**：一份笔记对自身可弃性的自我评价不是证据；而通用区 28 行引用（实测 `SKILL.md` 9 行 + `reference.md` 19 行含 `notes.md`）恰恰是**反对**这个自我评价的证据。撑得住的理由只有一条：**它进 git、删了可恢复，而 `git status --porcelain` 干净检查已罩住唯一不可逆的部分（未提交改动）**。
- 警告**不是**仪式性的——「这是最后一个 app」确实可能改变用户的决定。但**逐条列出 28 处引用是仪式性的**（用户对它无法采取行动）。压成一行即可。

### 2.5 我复核后认为做对了的

- `Path('outputs/tune_gates') / ''` → `PosixPath('outputs/tune_gates')`；`/ '/'` → `PosixPath('/')`；`/'..'` resolve 后仍在 repo 内。**三条我都跑了，全部属实**，是全文最实的一段。
- 连字符命名的 `docs/research/2026-08-20_tune-bb-v1` **确实存在**，据此否掉「按名字 glob 找研究目录」——反例是真的。

## 3. 我独立做的实证：optimism 对候选集大小的敏感度（真实数据）

resume-analyst 的 Q3 模拟是**纯 null + 格间独立**的合成数据，它自认这是最大弱点。我用真实长表补了这一格。

**脚本** `repro/critic_optimism_vs_gridsize.py`；**数据** `docs/research/2026-08-25_multivar-bb_v1/longtable/`（7,831,477 行 / 3985 股）；**做法** 配对同 seed（`SEED=0`, `B=300`），逐条塌缩网格轴 = 「这一轮没搜这一维」。

**基线先复现，逐字命中已提交的 `region_report.md`**：`naive=0.0705 / optimism=0.1263±0.0062 / split_half=-0.1319`。

**全部 15 个条件**（数字从 `critic_optimism_vs_gridsize.json` 程序重算，非肉眼读日志）：

| 条件 | 格数 | optimism | split_half |
|---|---:|---:|---:|
| **全网格** | 442368 | **0.1263 ± 0.0062** | −0.1319 |
| 塌缩 tb.day_drop（pred） | 221184 | 0.1186 | −0.1319 |
| 塌缩 burst.peak_age_max（pred） | 221184 | **0.1379** | −0.0757 |
| 塌缩 burst.first_drought（pred） | 147456 | 0.1014 | −0.0690 |
| 塌缩 burst.distinct_pk（pred） | 147456 | 0.1162 | −0.1859 |
| 塌缩 burst.max_bar_vol_ratio（pred） | 147456 | 0.0886 | −0.1319 |
| 塌缩 bo.min_relative_height | 110592 | 0.1008 | −0.1127 |
| 塌缩 bo.exceed_threshold | 110592 | 0.1119 | −0.2139 |
| 塌缩 burst.gap_max | 110592 | **0.1265** | −0.1199 |
| 塌缩 tb.stop_confirm_bars | 110592 | **0.1326** | −0.1965 |
| 塌缩 tb.big_rise_k | 110592 | 0.1024 | −0.1522 |
| 塌缩 burst.count（pred） | 110592 | 0.1144 | −0.2044 |
| 同时塌缩前 2 根 combo 轴 | 27648 | 0.0818 | −0.2849 |
| 同时塌缩前 4 根 combo 轴 | 1728 | 0.0909 | −0.1381 |
| **同时塌缩前 6 根 combo 轴** | **432** | **0.0885** | −0.1269 |

**三个读数**：

1. **单轴塌缩（候选集 ÷4 或 ÷2，11 个条件）**：optimism 落在 [0.0886, 0.1379]，相对全网格 0.1263 的最大偏移 **0.0376**，且**非单调——11 次里有 3 次反而变大**（0.1265 / 0.1326 / 0.1379）。「候选集大小 → optimism」这条关系弱到连方向都不稳定。
2. **跨三个数量级也一样**：把候选集从 442368 一路压到 **432 格（1024×）**，optimism 只从 0.1263 走到 0.0885。**全部 15 个条件的 optimism 都落在 [0.0818, 0.1379] 这个宽 0.056 的带子里。**
3. **同一批条件下 split-half 从 −0.0690 荡到 −0.2849，跨度 0.216**——比 optimism 的整个变动带还宽近 4 倍。而 split-half 是与 optimism **并列上报**的三口径之一。

**结论**：在真实结构数据上，候选集大小改变三个数量级，optimism 的整个变动范围（0.056）**小于** split-half 单是换个随机种子的噪声（sd 0.0762，见 §3.1）。跨轮暴露要校正的量在这个尺度下不可见。这独立支持 resume-analyst 的 Q3 判定（「精度上是噪声」），并覆盖了其 caveat #1 说「没测过」的那一格。

**诚实边界（两条，请按这个强度读）**：

1. 塌缩一根轴同时改变候选数、邻域结构（`neighbor_min` 少一根轴）与可评估面，**不是**干净的「只改候选数」操纵。但它恰好**就是**「第二轮删了一维」的真实形态，对本问题反而比干净操纵更贴切。
2. 表末三个「同时塌缩多轴」的条件已经离开原问题的语境——`naive` 在那里翻负（−0.018 / −0.035），是与全网格不同的 regime。它们支撑的是「optimism 对候选数不敏感」这个更一般的观察，**不**直接是「删一维的代价」；后者由前 11 行与 resume-analyst 的两段式估计（−0.0021±0.0024）承担。

### 3.1 噪声地板的干净测量（同一全网格，只换 split-half 的种子）

上面的跨条件散布混杂了「换条件」与「换随机性」。干净测法：**固定全网格不动，只把 `split_half()` 的 seed 从 0 换到 19**。

```
split_half over 18 seeds: mean=-0.1659  sd=0.0762  min=-0.3083  max=-0.0346  range=0.2737
（20 个种子里 2 个返回 NaN——两个方向的选中格都不可评估）
```

对照三个量级：

| 量 | 大小 |
|---|---|
| **split-half 自身的种子间 sd（同数据同网格）** | **0.0762** |
| 候选集砍 4× 对 optimism 的最大偏移（§3 表） | 0.038 |
| optimism 自身的 bootstrap MC SE（B=300） | 0.0062 |
| resume-analyst 直接测的两段式删维偏差 | 0.0021 ± 0.0024 |

**跨轮暴露要校正的量，比同一份报告里 split-half 的种子噪声小 36 倍。** 问题 Q3 到此不必再争。

### 3.2 【副产品·独立于本轮两个问题】`split_half` 的报告方式有实质缺陷

上面的测量顺带暴露一件与 resume / app 生命周期都无关、但更值得处理的事：

- `region_find.py:38` 把 `SEED` 硬编码为 0，`region_find.py:61` 调 `split_half(..., SEED)` 只做**一次**对半分。
- 报告里写成 `split-half = {sh:.4f}（下界）`——**四位小数、无不确定度**。
- 而同一行的 optimism 是带 `± optimism_se` 上报的，`SKILL.md` 红线还专门要求「判断 optimism 是否与 0 可区分，看 `|optimism|` 相对 `optimism_se` 的量级」。
- 实测这个「下界」在种子上的分布是 **sd 0.0762、跨度 0.2737（−0.3083 ~ −0.0346）**，另有约 10% 的种子直接返回 NaN。

也就是说：三口径里 optimism 有不确定度、split-half 没有，而 **split-half 的抖动比 optimism 的 MC 噪声大一个数量级**。`SKILL.md` 红线「split-half 当下界」在这个抖动幅度下不是一个稳定的界——换个种子，同一份数据的「下界」可以从 −0.03 变成 −0.31。

**这不是本轮两个问题的一部分**，也不该塞进这两个方案里；但按「三口径并报、不折中」的取向，它比跨轮暴露重要得多——修法也现成：对若干个种子取均值并报 SE，与 optimism 对称。建议 lead 作为独立一条列进 `final_report.md` 的后续项。

（口径声明：`B=300`、`MIN_COUNT_PER_FOLD=100`、`FOLDS=["2024","2025"]`、全网格 442368 格，与已提交的 `region_report.md` 同口径；基线三个数字逐字复现。）

## 4.5 第二轮（两位改完后）的复审结果

6 条意见**两位全部采纳并改完**。复审中又出三条，均已送达：

**(2) 默认保留（`DELETE_notes/exposure=False`）是对的，但引入了入口协议的第三种状态。** app-lifecycle 把 `notes.md` / `exposure.jsonl` 的默认落在保守侧（保留），比我原话「删是可接受的」更严谨，我不要求改回。但默认保留会出现「目录在、`study.py` 没了」这个新状态，而 `SKILL.md:21` / `reference.md:30` 的入口协议判据是 **`apps/X/` 存在？**——会走「是」分支 → `MODE=check` → `SystemExit("先跑 build")` → 用户照做 → 才在 build 里报「`study.py` 不存在」。能收敛但要两跳、且第一跳报错指错方向。

> **一词修复**：判据从 `apps/X/` 存在？改成 **`apps/X/study.py` 存在？**（两处文本各一词）。改完后该状态直接走「否」=首次接入，语义正确、一跳到位。这是删除功能引入的新状态，应由该功能收口。

**(3) 「单向可靠」应升格为设计原则。** app-lifecycle 把可再生性检测标注为「报『不可再生』一定对，报『可再生』只是没发现问题」。这不只是局限说明——它正是安全检查该有的形状：误差全部推到「多留垃圾」一侧，与本轮的不对称一致。写成设计原则之后，「抓不住 detector 源码被改」就从弱点变成已被设计吸收的已知边界。

**另：数字口径的一处教训。** resume-analyst 复核我的实验时算出「最大偏移 0.0255」与我的 0.0376 对不上，追下来是它读的日志停在 9 行、而完整是 11 行——缺的两行恰好含全表最小值（`burst.max_bar_vol_ratio` 0.0886）。根因是我第一次发表时用了**跑到一半的日志快照且未标注**。教训：**流式日志随时可能是半截，验算口径一律以程序写出的最终产物（`.json`）为准。** 已要求其改用 0.0376 与「11 次里 3 次变大」。
