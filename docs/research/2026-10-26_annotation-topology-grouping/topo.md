# topo：拓扑面板能不能复用、关系与分组怎么表达、存什么

本文中所有项目内路径均相对 repo root。队员 topo（web_ui 拓扑面板与数据模型）的分稿，回答 `原始问题.md` 里「标注时拓扑关系和 pattern 分组怎么显示、怎么操作，能不能复用现有拓扑面板」中归 topo 的四项。用词以 `path2/GLOSSARY.md`、`path2_web/GLOSSARY.md` 为准。不改任何正式代码、原型和票；唯一的临时代码在 `repro/default_members.py`。

## 0. 结论先说

- **现有拓扑面板（`path2_web/GLOSSARY.md:50`）在标注模式下三个时期都不复用**，看图模式里原样保留。它的四个交互全是调 app 用的，标签是 node 编号和参数串，没有 app 时整个面板是空的；更根本的是，用户的「骨架」和 app 的拓扑不是同一种东西，把后者放进标注模式会同时违反已定 1、4、5。
- **用户要的「定义关系」其实已经由框本身定义了**：先后看位置，属于看框套框。原型真正缺的只有两样：① 一个买点由哪几个框构成（**instance 成员**，只有用户知道）；② 一处能看到「这个 pattern 整体长什么样」的地方（**骨架**，由界面从各 instance 现算）。
- **六类边都不需要用户显式操作**。其中一条硬事实值得写进结论：path2 的边只比较 K 线位置和事件身份，不比较两个事件的价格或字段（`path2/dag/edges.py` 六个子类的判定只读 `start_idx` / `end_idx`，否定边另加一个只看 dst 自身的条件）。所以「回踩不破突破价」这类不靠位置的关系，在 path2 里的落点本来就是**后一个事件的字段 + where**（detector 读前一个事件的流、算好字段，如 bb_v1 的回踩读突破串），而不是边。lead 候选里「写成后一个框的属性」方向对，「由会话翻成边」要改成「翻成后一个 node 的 where（必要时让它的 detector 读前一个的流）」。
- **分组存「每个买点一份显式成员清单」，不存时间范围**；bracket 轨上的虚线范围由成员推出来画。放买点时默认往左收一串框（框与框之间隔不超过 20 根就算连着，待验证），改成员在买点的 edit 栏里点（ux 定）；同一次停留里新画或改动的框贴着那串就并进去、只加不踢、点掉过的不并回，离开这张图就冻结；存的永远是算好的清单。
- **骨架和汇总页是同一样东西**：每个名字一项，没有 app 时只有界面现算的事实，有 app 后同一项加上「由谁来认、认出几个」。建议侧栏 tab 从 edit / vocab / summary / json 改成 edit / vocab / pattern / json。
- **按用户追加的「少用文字、多用界面元素本身」（§4.5）修订**：骨架不画成表，画成一串用户词的胶囊，从左往右箭头连、套框挂在父胶囊下面——借的是现有拓扑面板的**画法**（先后横着读、包含竖着读），不是它的组件，也不是它的布局函数（实测它的最小层间距让三个词的链就宽 404px，放不进约 360px 的侧栏可用宽度，且不能折行）。现有面板里靠文字的四处（边上的种类和规则串、子槽名、悬停阈值、底部操作提示）在骨架里全部由图形本身代替。
- 骨架、套框关系、对照状态、默认成员建议都是派生物，不进标注文件；对应表是会话的产物，跟 app 放在一起，也不进标注文件。

## 1. 现有拓扑面板是什么

### 1.1 吃什么数据

`path2_web/serialize.py` 的 `serialize_pattern(spec)` 把 app 的 pattern 声明投影成：

- `topology.nodes[]`：`node_id`、`solve`（参不参与求解）、`where_rules`（where 的静态阈值树，没有实测值）、`render_grid`、`materialize_keys`（detector 构造参数名）、`produced_by` / `child_slot`（子结构 node 的物化来源）、`parent_refs`（被哪些父的哪个子槽引用）。
- `topology.edges[]`：`src`、`dst`、`kind`（边类名）、`rule`（人读的规则串，如 `before · gap∈[1,20]`、`contains`、`forbid · gap∈[0,5]`）、`anchor_field`。
- `event_styles`：每个 node 的颜色；app 没显式声明的按 node 首次出现顺序从兜底色板取。

也就是说，它**只吃 app 的声明**，不吃任何事件或标注。前端 `TopologyControl.vue` 顶部 `v-if="effectivePattern"`：没有 app 就什么都不画。

### 1.2 画什么、怎么布局

`path2_web_ui/src/render/topology.ts` 的 `layoutTopology`，走势无关：

- 边（六类，`path2/GLOSSARY.md:86`）按最长路径从左往右分层，画成灰色曲线 + 箭头，标签两行：小灰字边类（去掉 Edge 后缀），深色规则串。
- 父子关系（`parent_refs`）竖直挂在父节点下方，浅色虚线 + 子槽名；挂不上时退回水平虚线。
- 节点是圆角按钮，底色 = node 颜色（`render/colors.ts` 的 `deriveNodeColors`：同色的多个 node 按明度散开），子结构 node 虚线边框，被隐藏的 node 透明度 0.32。

### 1.3 交互

| 操作 | 效果 | 在标注模式里的处境 |
|---|---|---|
| 单击节点 | 切这个 node 的事件在 K 线上显隐（`view.toggleNode`） | 标注模式不画系统事件，没东西可切 |
| 双击节点 | 在诊断侧栏展开这个 node 的漏斗（`view.toggleExpandedNode`） | 诊断全是实测值和门槛，违反「对照不给数字」 |
| 点边标签 | 拉这条边在当前窗口的 miss_reasons 和失败配对（`getNodesDiagnose`，scope=nodes） | 同上 |
| 悬停节点 | tooltip 列 where 的阈值（`field op threshold`） | 同上 |

面板放在 `ChartArea.vue` 第一行，开关在 `stores/panels.ts`（存 localStorage），和诊断侧栏、滑杆一样是全局开关。

### 1.4 现役 app 实际用到了多少

全部现役 app（`bb_v1`、`bottom_burst`、`try_conplex_where`；`bo_only` 无边）**只用到时序边一类，每个 app 一条**：「burst 的最后一根 bo → tb」，带身份锚定（`path2/GLOSSARY.md:89`）。包含、起点包含、交叠、同段、否定五类在引擎里有、在 app 里一次都没出现。bb_v1 的面板就是：bo（虚线挂在 burst 的 members 下）、pk（孤立、不参与求解）、burst → tb，一条边。

## 2. 用户的「骨架」和 app 的拓扑是不是一种东西

不是。两者之间隔着一张对应表，而且是多对多。

| | 用户的骨架 | app 的拓扑 |
|---|---|---|
| 单位 | 用户的名字（框） | node |
| 先后 | 框的位置，定性 | 时序边 + 间隔区间（参数） |
| 属于 | 框套框 | 复合事件的子槽（`path2/GLOSSARY.md:62`），或 where 读子事件，偶尔是包含边 |
| 可有可无 | 有的 instance 画了、有的没画 | **拓扑里不存在**：match 要求每个参与求解的 node 都绑定一个事件（`path2/GLOSSARY.md:95`），可有可无只能落在 where 的「或」或复合事件的空子槽 |
| 取其一 | 同名框上有的写 W 形、有的写 V 形 | **拓扑里不存在**：where 的「或」 |
| 不靠位置的关系 | 写在后一个框上的属性 | 后一个 node 的字段 + where（边表达不了，见 §3） |

拿原型种子（`.scratch/annotation-path2/prototypes/01-annotation/index.html` 的 `seed()`）对 bb_v1 看：用户的骨架是「横盘（套着缩量）→ 放量突破 → 回踩 → 买点」，四个名字；bb_v1 的拓扑是 bo、pk、burst → tb。用户的「横盘」「缩量」在 bb_v1 里没有 node（原型示意的对应表把「横盘」接到不在 bb_v1 里的走势区段，或接到 burst 的「突破前沉寂够久」那条 where）；app 的 bo、pk 用户从来没画过；用户的「放量」「突破过好几个峰」「回踩里没有大跌」是 burst 和 tb 上的 where，拓扑图上根本不出现（只在悬停 tooltip 里以阈值形式出现）。

所以把 app 的拓扑放进标注模式：

- **违反已定 1**：标注时只画 K 线和用户自己的东西。拓扑面板画的是 app 的结构。
- **违反已定 5**：用户看到 bo / pk / burst / tb 和「before · gap∈[1,20]」，就被拉着按 node 和边去想；而它和用户自己画的东西对不上（多出 bo、pk，少了横盘），用户会自然地想去「改」它，这正是已定 5 要挡住的。
- **违反已定 4**：边标签和悬停里全是数字。
- 还没有 app 的时期它是空的，帮不上「我怎么定义关系」这个最初的问题。

## 3. 六类边逐类判断

前提：用户的框是随手画的，相邻两个框的边界常互相蹭一两天。所以从框的位置读关系时必须带容差（下面统一用对照里的同一个容差，默认 2 天，待验证），否则「画得粗」会被读成「交叠」。

| 边 | 用户会不会自然表达 | 能不能从框直接推 | 要不要用户显式操作 |
|---|---|---|---|
| 时序（A 在 B 之前，间隔在某个范围内） | 会，按时间顺序画框就是在表达 | 先后能推。间隔的范围是参数，不从框量（地图已划掉「从框过的例子定参数默认值」）；用户在意时会说「紧接着」「突破后第一次回踩」，写成后一个框的属性或名字的定义，会话翻成间隔上限或「第一次」 | 不要 |
| 包含（A 整段包住 B） | 会，就是框套框（已定：默认算「属于」） | 能推。翻成复合事件的子槽、where 读子事件，还是包含边（两个独立 detector 的事件恰好一个落在另一个里），是会话的翻译选择，用户不用分 | 不要；只交叠不包含、或推不出时在图上问（已定） |
| 起点包含（B 从 A 里面开始，可以伸出去） | 不会有意表达；它是为保持迁移前后 match 不变引进的工程写法 | 和交叠一样读作「B 从 A 里开始」。几天以内的伸出按画得粗处理，读成「紧接着」 | 不要 |
| 交叠（B 从 A 中间开始、比 A 结束得晚） | 很少有意表达；多半是边界画得粗 | 同上；只有多个 instance 都明显交叠一大截，才值得会话当成真关系 | 不要 |
| 同段（A、B 占完全相同的一段） | 不会画两个一模一样的框；用户的说法是「一个框写几个属性」 | 能推：一个框带多个属性，会话可能翻成两个 node + 同段边，也可能翻成一个 node 的几条 where | 不要 |
| 否定（A 之后某段时间里不许出现 B） | 会说「没有 X」 | 属性记成 false（三态里的「看过、没有」）。但单张图上的 false 分不清「恰好没有」和「有它就不买」；跨图看：买点上的框一直 false、像但不买上常为 true，就是禁止的证据；最终由名字第一次出现时那句定义说清意图（与已定 2「取其一 / 两个 pattern / 都是加分」同一个口子） | 不要 |

不靠位置的关系（「回踩不破突破价」「放量在横盘后半段」）：path2 的六类边全部只比较两个事件的起止下标（`path2/dag/edges.py`：时序比 `dst.start − src.end`，包含 / 起点包含 / 交叠 / 同段比起止，否定比间隔再加一个只看 dst 自身的条件），锚定只比身份。没有一类边能比较两个事件的价格或字段。所以这类关系在 path2 里只能写成「后一个事件的 detector 读前一个事件的流，把关系算成自己的字段，where 去判」——bb_v1 的回踩就是读突破串、相对那根 bo 算回撤。写成后一个框的属性，正好落在它在代码里的位置。它引用的「前一个框」在同一个 instance 里通常唯一；不唯一（instance 里有两个突破）时，就是已定 3 里「推不出才在图上问」的那种情况。

**小结**：关系不需要任何编辑器。关系之所以显得「没有地方定义」，是因为原型里缺了 instance 边界——没有它，会话不知道哪几个框之间的位置关系算数。

## 4. 三个时期分别怎么办

### 4.1 还没有 app（只有标注）

- 拓扑面板：不显示（本来也是空的）。标注模式下顶栏的拓扑面板开关隐藏。
- 主图：bracket 轨（`path2_web/GLOSSARY.md:45`）上给当前 pattern 的每个买点画一条**虚线** bracket，从最早的成员框起点到买点，带圈号；像但不买换一种线型或带 `no_buy` 字样（不加颜色）。选中买点或 bracket 时高亮它的成员框——照主视图点 bracket 高亮这次 match 的事件那套（`view.focusMatch` → `highlightedEventIds`；主视图是给组员加深色描边和阴影，**不淡化非组员**，淡化其余是标注模式新加的，因为用户的框只有虚线、没有底色，光加粗不够醒目）。不在任何 bracket 里的框就是「只标事件」，不加额外标记。
- 侧栏 pattern tab：pattern 名字、定义（用户的一句话）、骨架（界面现算，见 §5.3；画成胶囊链，见 §4.5）、instance 列表（哪张图、哪天、buy / no_buy、点了跳过去）。「未归类」的 pattern tab 把 instance 按骨架签名分组（签名只取顶层成员的名字序列，如「横盘 → 放量突破 → 回踩」；套在里面的小框不进签名——那是一个 node 内部的差别，按方向文档第 8 节进 where，算进签名会让同一个 pattern 按「套没套缩量」碎成两组；小框的出现次数在骨架胶囊下面看得到。此条采纳 flow），整组「归入某 pattern / 新建 pattern」——这就是方向文档第 8 节「骨架相同的排在一起，由用户决定哪些算同一个 pattern」的界面落点。

### 4.2 有了 app、在对照

- 拓扑面板：仍不显示。它能给的（node 编号、边规则、阈值、miss_reasons）在对照里全属于不该给的东西。
- 主图：app 的 match bracket 用**实线**画在同一条 bracket 轨上，和用户的虚线 bracket 叠着（与已定 4「同轨叠画」一致；只比状态，不标起止差）。框旁是 qualified / detected / missing 徽标。link 状态不在主图上画连线：ux 在 mock 里实测，框首尾相接时连线只剩约 3px 横 + 30px 竖，被框右侧的状态签盖住，看不见；改为挂在买点 edit 栏成员块之间的箭头上和 pattern tab 骨架相邻两项之间（仍满足上一轮报告 2.2 节「毛病在边上时字样挂在关系上，不冤枉某个框」）。
- 侧栏 pattern tab：同一串骨架胶囊，每个胶囊下加「由谁来认」（等宽灰字标识符，如 `node:burst`、`atom:trend[sideways]`）和「认出几个」的徽标（新老分开）；两个胶囊之间的箭头带 link 状态（实线 = 都连上，断开的线 + 数 = 有没连上的）；⚑ 只挂在「由谁来认」上（会话的翻译可能错），骨架本身不挂——骨架是从框推出来的，不对就回图上改框（单一来源，critic T3；ux 定）。原 summary tab 的内容全部在这里，summary tab 去掉。

### 4.3 盲看露结构

- 拓扑面板：不需要。用户在这一步要判断的是「app 抓的这几段，是不是我说的那几样东西」，要的是**用自己的话标出来的段**，不是 app 的结构图。
- 做法：露结构时把这次 match 的事件画在各自的 band 上，band 标签用对应表里用户的名字（`放量突破`，必要时后面灰字 `burst`），取其一的 node 标出走的是哪一支（「底部：W 形」）；可选在卡片顶上用用户的词写一行骨架，标出这次各段对上的是哪个。
- **否定类条件怎么露**（critic T7）：若「前面没有派发」被翻成一个派发 node 加否定边，这次 match 里那条 band 本来就没有事件（否定边的 dst 不进 match）。不能只给一条空 band，否则读不出「要求没有、确实没有」还是「app 没认出」。画法：在这条 band 上把查过的那段窗口画成一块带斜线的空心区域（意思是「这段查过、要求没有」），窗口里 app 看到了但不够格的派发照 detected 档画成浅灰；band 标签前加一个划掉的记号。这样用户一眼分得出三种情形：斜线区里空着（app 查过、确实没有）、斜线区里有浅灰块（app 看到了、判为不够格）、斜线区里空着但 K 线上明显有派发（app 漏认——正是盲看要抓的，用户点「不是」或「是，但认错了」）。match 存在就意味着否定已经满足，所以露结构时不会出现「否定没过」。若这条否定被翻成后一个 node 的 where（如「回踩里没有大跌」），它就是胶囊下的一个属性小签，同样用划掉的记号。
- 想看 app 真实结构的，切回看图模式看原样的拓扑面板（看图模式本来就会让这张图记「接触过 app」）。

### 4.4 复用方案的三档

| 方案 | 做什么 | 量级 | 判断 |
|---|---|---|---|
| 原样复用 | 标注模式也挂 `TopologyControl` | 几乎零代码 | 不行：违反已定 1、4、5，且无 app 时为空 |
| 改造后复用 | 新写一个组件，只借 `layoutTopology` 布局函数（它走势无关，喂合成的节点 / 边 / 父子引用就能画），节点标用户的词、去掉显隐 / 诊断 / 阈值、加出现次数和取其一徽标 | 组件约 150～250 行 + 骨架转合成拓扑约 50～80 行 + 测试 | 能做，但不值：用户的骨架几乎总是一条时间链加几处套框，排好序、缩进表示套框的列表就能完整表达；图多占地方、多一套视觉语法，出现次数和取其一还得另外标在节点上。只有骨架里出现大量「互相不分先后的并列分支」时图才有优势，用户在一条时间轴上画框，这种情况很少 |
| 不复用组件、借画法 | pattern tab 里一串胶囊（§4.5），用普通的可折行横排 + 父下挂子，不用布局函数 | 胶囊链组件约 60～100 行 + 骨架计算约 80 行（与「未归类」的按骨架分组共用） | **推荐**（§4.5 修订后；原稿写的是一张表） |

「改造后复用」那一档还有一个实测的障碍：用现有布局函数原样画用户骨架（节点名换成用户的词、边只有先后、没有规则文本、套框挂在父下），`repro/skeleton_width.ts` 量得「横盘（缩量）→ 放量突破 → 回踩」宽 404px，加一个买点 538px，五个词的链 728px。侧栏 380px、扣内边距约 360px，三个词就放不下。原因是层间距下限写死 96px（为边标签留的位置，骨架没有边标签也照留），而且分层布局不能折行。要用它就得把层间距改成参数；就算改到 28px，五个词仍约 430px。

可选、可后置：看图模式的拓扑面板节点旁加一行用户的词（从对应表读，如 `burst · 放量突破`），约 20 行；只是数据、不写走势分支，不破前端「类型无关渲染器」红线。不是标注工作流的必需品。

### 4.5 少用文字、多用界面元素（用户 2026-10-26 追加）

**现有拓扑面板里，图形本身表达了什么、靠文字的是哪些**：

| 信息 | 现有面板怎么表达 | 骨架里怎么表达 |
|---|---|---|
| 有哪些东西 | 节点（图形）+ node 编号（文字） | 胶囊 + 用户的词（词是业务内容，本来就该是字） |
| 先后 | 箭头方向（图形） | 同，从左往右的箭头 |
| 属于 | 父下挂子的竖虚线（图形）+ 子槽名（文字，如 `members`） | 子胶囊挂在父胶囊下面，或画在父胶囊里面（和图上的框套框一致），去掉子槽名 |
| 边是哪一类、什么参数 | **只靠文字**：每条边常驻两行标签（种类 + `before · gap∈[1,20]`），图形上六类边长得一样 | 用户的骨架里只有「先后」一种，箭头本身就是；参数不给用户 |
| where | **只靠文字**：悬停 tooltip 列 `field op threshold` | 属性做成挂在胶囊下的小签，签上一个数（用了几次）；取其一自然是并排的几个签（`W形 6`、`V形 3`） |
| 显隐 | 透明度（图形） | 不需要 |
| 怎么操作 | **只靠文字**：底部一行提示 | 去掉；可点的东西靠光标和悬停反馈 |
| 对照状态 | 无（在诊断侧栏，全是数） | 胶囊上一个小徽标（qualified / detected / missing 的计数，或一条按深浅分三段的小条，不靠色相）；箭头用实线 / 断开的线表示 link ok / broken |

**落到三处**：

- **pattern tab 的骨架**：一串胶囊。侧栏窄，ux 改成竖排（每行一个名字，从上到下是先后，相邻两行之间的 ↓ 挂 link 计数），套在里面的名字缩进挂在父下；有 app 时同一行右侧加等宽灰字标识符（`node:burst`）和认出数——骨架和对应表因此合成同一条竖链。出现次数是胶囊角上的一个数（`7/10`）；同一 instance 里同名两个是 `×2`。点胶囊 → 在当前图上高亮这个名字的框。主图名字轨的上下顺序和这条竖链同序（当前 pattern 各 instance 里成员的平均先后），一个 instance 在副图上读起来是一道从左上到右下的台阶（ux）。
- **变体行**（「未归类」的按骨架分组、pattern 内部的变体）：每行是同一个胶囊链组件的缩小版 + `×6`，整行一个「归入」操作。合并后的骨架和变体行不重复：前者每个名字只出现一次、对照状态挂在这里；后者保留「各 instance 长得不一样在哪」（ux 指出合并会把变体抹平，这正是变体行存在的理由）。
- **主图**：bracket 本身就是「pattern 边界」，不用字说明；选中买点 → 成员框加粗描边，其余框变淡；框的状态用徽标；link 不在主图上画（见 §4.2）。

**全篇统一的一条画法**：虚线 = 用户的，实线 = app 的——图上的框、bracket 都已经这么分，骨架胶囊是用户的，跟着用虚线框。这样用户不用读字就分得清哪个是自己画的。

**什么时候真需要一张一般的图（DAG）**：只有两个元素都在第三个之前、但彼此先后在各 instance 里不固定时。例：「W 形底」和「地量」都在「放量突破」之前，有的图先 W 形底、有的先地量。变体行会把它拆成两行（A→B→C ×3、B→A→C ×2）；合并骨架可以把 A、B 竖着叠在同一列再接 C。这仍然不需要分层布局算法，一列里叠两个胶囊就够。而且实际中少见：同时出现的特征，用户多半会套框（地量套在底部里）或写成属性，而不是画成两个并列的框。

## 5. 分组与 pattern 级信息：存什么、存哪、谁写

### 5.1 成员：显式清单，不存范围

lead 候选是「每个买点带一个 instance 范围，范围里的框 = 成员」。显示上我同意（bracket 就是用户要的「pattern 边界」），存法上建议改成**每个买点存一份成员框编号清单**，bracket 由成员推出来画。理由是范围在三种常见情况下会错，而且没法纠：

1. **同一张图两个相邻买点**：横盘 → 突破 → 回踩 1 → 买点 1 → 回踩 2 → 买点 2。买点 2 的范围要盖住横盘和突破，就一定盖住回踩 1，回踩 1 被算成买点 2 的成员，instance 里出现两个回踩，又得问角色。清单里点掉回踩 1 即可。
2. **范围里夹着无关的框**：用户顺手标了一个只当事件素材的框，恰好落在某个 instance 的跨度里。
3. **后画的框悄悄加入**：存范围的话，成员是读的时候按日期现判的。几天后在这段里补画一个框（哪怕是在标别的 pattern、那条 bracket 根本没画出来），它就自动成了旧买点的成员，而且没有任何时刻让用户看到这件事。下面「同一次停留里新画或改动的框按规则并进去、只加不踢」和这个不同：只对这次停留里放下的买点生效，离开这张图就冻结，结果存成清单，用户当场看得见、点得掉。

只新增的存储本来就要求框有跨文件、跨机器的稳定编号（改一个框 = 新记一条同编号的记录），清单引用它不增加新负担。

**操作**（交互细节以 ux 为准）。改成员的入口只放在买点 edit 栏的成员块（members / others 两排，点一下进出，悬停时在图上描出那个框），不做「选中买点后在图上点框切换」——图上点框的意思始终是「选中这个框去改名字和属性」，同一下点击不随当前选中了什么而变（ux 的理由，采纳）。

- 放买点时默认往左收一串框：终点落在买点前 G 根以内或跨过买点的框起头，往左把「终点距这串的起点不超过 G 根」的框一个个接上（相接、交叠都算），再把套在成员里的小框带上。**G 默认 20 根**（待验证），取自 bb_v1 允许回踩在末根突破之后最多 20 根内开始（`tb.max_span`）。原稿用的是 2 天，那是把「框边界画粗的容差」和「pattern 相邻两段之间的空隙」混成了一个数——后者在突破之后先涨几天才回踩、中间那几天用户不框时远大于 2 天（critic T5）。
- 默认规则收错有两个方向，代价不一样：**少收比多收更常见也更隐蔽**——多收时 bracket 伸到明显无关的框上，一眼看得出；少收时 bracket 看起来照样合理，要等骨架上某个名字的出现次数掉下来才暴露。所以默认往多收那边偏，再加一道显示上的保险：买点放下时自动选中，成员加粗、非成员变淡，紧挨着 bracket 的一个淡框就是「可能漏收」的样子。
- `repro/default_members.py` 在 6 种手造情形上比了三种规则（只为看失败的样子，不代表各情形多常见）：2 天少收 9 个框、多收 0；20 根少收 1、多收 1；critic 提的「往左收到同一 pattern 的上一个买点为止」少收 2、多收 2。20 根的那次少收是「下跌之后隔 25 根才进底部」；那次多收是「两次回踩各买一次」时第二个买点把第一次回踩也收了进来——这次多收看得见，而且有时正是用户要的（「突破后第二次回踩」，critic 指出）。「到上一个买点为止」在同一种情形里反而把共用的横盘和突破漏掉（少收、隐蔽），在「左边孤立框没有买点」时把它收进来，所以没有采纳。用户截图那张（原型种子 s0）三种规则都对。
- **新画的框何时自动并进**（与 flow、critic 三方口径一致，critic F7）：
  1. 存保存时算好的框编号清单；
  2. 新画或改动的框按默认规则判，贴着某个买点那串就并进去、范围随之伸长（用户常先画短再拉长，只判新画的框会让刚拉长的框收不进来——lead 拍板的理由）；
  3. 只并进当前 pattern 的买点（只有它们的 bracket 画在图上）；
  4. 只在放这个买点的那次停留里——离开这张图，这个买点的成员就冻结，以后回来补画的框不再自动并进任何旧买点，要加就到买点的 edit 栏里点；
  5. **只加不踢、点掉过的不并回**：把一个成员框改短、改远，它不再贴着那串时也不会被自动移出（自动踢出是静默丢成员，critic F10）；用户在这次停留里点掉过的框，之后再改它也不会被并回（这份「点掉过」只在内存里记，停留结束就丢，不存）；
  6. 改默认规则不改写任何旧买点（因为存的是清单，见下条）。
  这同时解决两头：用户先点买点、再补框解释为什么时，不用每个框手点（flow 的理由）；几天后回来补画的事件框不会悄悄进旧买点（反例 3）。
- **存的永远是算好的框编号清单，不存「自动」标记、不在读的时候按规则现算**（critic F7）。默认规则待验证、一定会改；若存的是「自动」，规则一改，所有没动过的买点的成员和骨架都会被静默改写。
- 删掉一个成员框时，清单里的编号按「已删」忽略。

**一个框属于多个 instance**：自然支持，它出现在几个买点的清单里，主图上被几条 bracket 盖住。**一个买点属于多个 pattern**：不支持，也不需要——方向文档第 8 节已定「两个 pattern 落在同一天，就是同一天挂两个买点，各算各的」，各自带自己的成员清单。框本身不属于任何 pattern（已定），pattern 是经由买点挂上去的。

### 5.2 原型里要改的一处混淆

原型顶栏的 pattern 下拉直接列 app 编号（`bb_v1`）和「未归类」，把「用户的 pattern」（意图，用用户自己起的名字）和「实现它的 app」（同一走势可以有好几个平级版本，`path2/GLOSSARY.md:36`）当成了一个东西。应该是：pattern 用用户起的名字；有 app 时旁边灰字标 `app: bb_v1`。标注文件里的 pattern 记录不引用 app 编号——app 会换版本，意图不变。

### 5.3 骨架：界面现算，不存

骨架完全由已存的东西决定（成员清单 + 框的起止 + 名字 + 属性），而且算法是确定的，不需要会话：

- 对当前 pattern 里每个 buy 的 instance，取它的成员框。
- 每个名字一行：出现在几个 instance 里（n / N）；通常排第几（成员按起点排序后的中位次序）；通常套在谁里面；各属性 true / false / null 各几个（取其一在这里自然呈现，如「W 形 6 · V 形 3」）。同一 instance 里同名两个的，标「×2」。
- 像但不买的 instance 列在下面，带它们的 instance 注释。

界面现算的好处：用户边标边看到这个 pattern 由哪些名字组成，不用等会话跑一遍。建议只写一份实现（放在后端、界面和会话的循环工具都调它），避免两边算得不一样。

**骨架行上有一处和属性 null 同类的含糊**：某个名字只出现在 7 / 10 个 instance 里，可能是「可有可无」，也可能是「另外 3 张懒得画」。框的缺席分不清这两种（属性有 null / false 之分，框没有）。这件事归会话解释、不归界面判，而且要写成循环技能里的硬步骤（票「串起「图 → 代码」循环的技能」，`.scratch/annotation-path2/issues/09-loop-skill.md`）：会话把任何名字翻成「可有可无」之前，必须先在这一行上问一次，一个名字问一次、不逐张问。缺席其实有三种，问之前先机械地分出第三种：
  1. 画了、但没算进这个买点（默认规则少收了，或用户点掉了）——会话先查那张图上买点左边有没有同名、却不在成员里的框，有就直接把这几处摆出来（图上那个框照非成员淡显），用户点一下收进来或确认不算；
  2. 没画、其实有；
  3. 没有。
  只有剩下分不出 2 和 3 的才问用户。答「没画」的，等于这几张图上这个名字的框要补（会话列出来请用户补框）；答「没有」的才进「可有可无」的证据。
  落点（与 flow 对齐）：循环第 3 步「会话分流」，进拍板单，配缺这个名字的那几个买点的缩略条，一个名字问一次；写第一版 app 时同理。

### 5.4 存什么、谁写

存储守方向文档第 10 节：每批一个新文件、文件名带机器名、只新增不改旧文件；记数据指纹；框按日期存、不存系统事件编号。建议所有记录平铺、带全局唯一编号（机器名 + 时间 + 序号），改 = 新记一条同编号的记录（按批次时间取最新），删 = 记一条删除记录。原型的 json 是按图分组、编号是会话内自增的 `b1`、`p2`，跨文件、跨机器会撞，买点也没有编号可被引用，需要改。

| 记录 | 字段 | 谁写 | 性质 |
|---|---|---|---|
| 词 | 编号、措辞、定义 | 用户 | 用户数据（已定 2） |
| 框 | 编号、股票、起止日期、名字（词编号）、属性（词编号 → true / false）、instance 注释、放过 | 用户 | 用户数据（已定 2） |
| 买点 | 编号、股票、日期、pattern 编号、buy / no_buy、**成员（框编号清单）**、instance 注释 | 用户（成员可以是接受了的默认值） | 用户数据；成员是本稿新增 |
| pattern | 编号、名字、定义 | 用户 | 用户数据；本稿新增。「未归类」是保留值，不需要记录 |
| 纠错 | 编号、指向（对应表里的某一行，即会话对某个词或某对先后的翻译，用词编号指）、一句话 | 用户（⚑） | 用户数据；骨架本身不挂 ⚑，不对就回图上改框 |
| 图 | 股票、窗口、接触过 app | 界面顺手记 | 必须存：它记的是用户的行为，事后算不出来 |
| 批次头 | 机器名、时间、数据指纹 | 界面 | 元数据 |

**不进标注文件的派生物**：

| 东西 | 从哪来 | 为什么不存 |
|---|---|---|
| 框套框（谁属于谁） | 起止日期 | 存了就和日期可能不一致；改一个框的起止就得同时改它 |
| 骨架 | 成员 + 日期 + 名字 + 属性 | 同上，且每加一张图都会变 |
| 默认成员建议 | 位置规则 | 只存用户接受后的结果 |
| 对照状态（qualified / detected / missing、link、app:buy / no_buy） | app 版本 × 标注 | 换 app 版本就变；汇总页「过期」靠重算，不靠存 |
| 角色（框扮演哪个 node） | 会话推断（已定 3「不存角色」） | 用户在图上回答「是哪一个」时，答案落成成员的增减或 instance 注释，不新设角色字段 |

**会话的产物，存在 app 旁边、不进标注文件**：对应表（用户的词 / 两词之间的先后 → node、where、边，或「不进 app」；用词编号作键、抄一份措辞便于读；带 app 版本）和「哪个 app 是这个 pattern 的当前实现」。放在 git 里跟 app 一起走，因为它们随 app 改版而变，是 app「反映了什么意图」的说明；标注目录在 git 外的同步目录里，只放用户的东西。

## 7. 不放心的地方

1. **默认成员规则的 20 根是借来的数**（bb_v1 的回踩预算），没在真实标注上验过。这台机器（pc）没有截到 2025 年底的副本，pc 的完整行情按数据墙不读，所以没有量「突破之后几天才回踩」，也不在 pc 上找替代数据；量级的检查归 critic.md 2.5 节的待验证项 V1（在 upc 上量 bb_v1 全部 match 末根 bo 到其后最高收盘隔几根，超过 2 根的占一半以上即判 2 天会切短；结论只改默认规则，不改「默认往多收偏」的方向）。第一批真实标注出来后分三个数报：
   - **多收几个**：默认收了、用户点掉的。主要是多点几下的成本。
   - **少收几个**：默认没收、用户点进来的。
   - **切短了但用户没改**：这个数从用户的操作里看不出来，要另查——在成员从没被手动改过的买点里，数 bracket 左端往左 40 根以内（待验证）有没有非成员的框，有的占几成；再把这些买点连同那几个淡显的框摆给用户过一遍（一次性，缩略条形式）。这一类和 §5.3「画了但没算进这个买点」是同一种查法，可以合并成一步。
   少收和「没改的切短」多，就加大 G 或换规则；多收多就减小。
2. **「一点全带上」式的懒惰**同样会出现在成员上：用户不看就接受默认成员，会把无关框带进 instance、污染骨架。和票里第 6 节第 3 条同一风险，同一种查法。
3. **「没画」与「没有」分不清**（§5.3）。我给的是「会话在要用时按名字问一次」，代价是会话得记得问；如果会话漏问，「可有可无」会被悄悄翻进 app。
4. 骨架在名字很多时会长，胶囊链要折行；变体行在 instance 很多时会多。我没有量过真实规模。

## 8. 最容易被误读的地方

- 「不复用拓扑面板」不是说要删它或改它：看图模式里它一切照旧。
- 「关系不要编辑器」不是说关系不重要：关系由 instance 边界 + 框的位置 + 后一个框的属性表达；instance 边界（成员清单）是必须新增的那一样。
- 「骨架不存」不是说用户对骨架的纠错不存：⚑ 和它的一句话是用户数据，要存；不存的只是界面能从别的数据算回来的那张表。
- 「属性 false」不等于「否定边」：单张图上它只说「看过、没有」，要不要变成「有它就不买」由跨图证据和那句定义定。

## 11. 对队友问题的回应（2026-10-26）

### critic

- **T1 原样复用会漏数字**：同意。我的方案里标注模式（对照开不开都一样）**不显示**拓扑面板。若硬要显示，要去掉的是：边上常驻的规则串（`_edge_rule` 输出的间隔区间）、节点悬停的 where 阈值、双击诊断、点边拉 miss 明细；还得把 node 编号换成用户的词——去到这一步，它已经不是 app 的拓扑了。
- **T2 改画用户骨架还剩什么可复用**：同意，只剩布局函数和画法；而布局函数实测也不合适（§4.4：三个词就 404px，超出侧栏）。一行讲得完：用户的 pattern 是一条时间链加几处套框，「横盘（缩量）→ 放量突破 → 回踩」一行就讲完；按用户追加的要求，这一行画成胶囊而不是文字（§4.5）。真需要 DAG 的例子：两个元素都在第三个之前、彼此先后在各 instance 里不固定（「W 形底」和「地量」都在「放量突破」前，顺序不定）；即使这样也只需在一列里叠两个胶囊，不需要分层布局，而且少见（同时出现的特征用户多半套框或写属性）。
- **T3 面板做编辑器 = 两处来源**：同意，不做编辑器。唯一来源是图上的框和成员清单，骨架只读、只派生。用户觉得骨架不对时只有两条路：回图上改框 / 改成员，或在骨架上点 ⚑ 写一句话交给会话；不能在骨架上直接拖改。
- **T4 成员存在哪**：和你一致——买点上存成员框编号清单（默认推断、可改），范围不存、只派生（理由见 §5.1 三个反例）。一个框是两个买点的成员：它的编号出现在两份清单里，图上被两条 bracket 盖住。「成员框不属于当前 pattern」这个情形不存在：框本来就不属于任何 pattern（已定），任何框都可以是任何 pattern 的买点的成员；切到别的 pattern 时，这个框只是不在当前 pattern 的 bracket 下，它在框的 edit 面板里列出自己属于哪几个买点。

### flow

- **(1) 能不能不改协议画一份「不是 app 的」结构**：布局函数只读节点的 `node_id`、`parent_refs`（`produced_by` 只影响虚线边框）和边的 `src`、`dst`、`kind`、`rule`（后两样只用来估标签宽度），喂合成数据（`node_id` = 用户的词、`kind` / `rule` 留空）能画，`repro/skeleton_width.ts` 就是这么画的；但组件 `TopologyControl.vue` 直接从 view store 读 app 的声明、颜色、显隐，交互全绑 app，不能直接喂。所以要改的话全在前端，后端序列化不用动（骨架的来源是标注，不是 app 声明）。但我的结论是连布局函数也不用：宽度放不下，且不能折行。
- **(2) 现役 app 用到哪几类边**：只有时序边，每个 app 一条（bb_v1、bottom_burst 都是「burst 的最后一根 bo → tb」，间隔 1～`tb.max_span`（bb_v1 为 20），带身份锚定）；另外五类引擎里有、app 里一次没用过。边上的规则串只有两种内容：边的种类，和间隔的上下限——全是参数级。你的论点我同意，补两点：① 否定不能只靠位置和套框推，要靠属性 false 加名字的定义那句话（单张图上的 false 分不清「恰好没有」和「有它就不买」）；②「写在后一个框上的属性」会话翻成的不是边，而是后一个 node 的字段 + where——path2 的边只比位置和身份，比不了价格。你中间方案里「范围内顶层框 = 成员」我和 critic 都主张改为存成员清单（§5.1）。

### ux

- **a. 抽纯展示组件要动多少、侧栏会不会溢出**：组件和 store 的耦合在六处：从 view store 读 `effectivePattern`、`nodeColors`、`nodeVisible`、`symbol`、`activePatternId`、`effectiveScan`，调 `toggleNode`、`toggleExpandedNode`，调诊断接口、嵌 `PairListCard`。抽成「只吃节点 / 边 / 标签 / 角标」的纯展示组件，大约是把模板和样式（约 120 行）搬出来、加 props 和事件，原组件改成包一层。溢出：会，实测三个词 404px、五个词 728px（侧栏可用约 360px），最小层间距 96px 写死且不折行（§4.4）。所以我建议不抽，直接写一个可折行的胶囊链。
- **b. 主视图 band 顺序**：按 app 声明里 node 的**书写顺序**（`to_topology()` 照 `spec.nodes` 顺序，`deriveTagMap` 按首次出现排，再滤掉钉在主图上的 node），不是按拓扑先后。所以标注模式的名字轨按骨架先后排，和主视图不会有冲突——主视图本来就没有「按先后排」这个约定；对照时 app 事件是叠在用户名字的轨上（按对应表），不是用 app 自己的 band 顺序。
- **c. 主视图点 bracket 后组员怎么显示**：组员加深色描边和阴影（`render/chart.ts` 的高亮层 `group` 一支），**非组员不变淡**。你要的「其余变淡」在主视图里没有现成做法，是新加的；我赞成加，因为用户的框只有虚线、没有底色，光加描边不够醒目。
- **d. 什么时候一张图比变体行好**：只有 §4.5 末那种「两个元素先后不固定、都在第三个之前」；其余情况变体行（每行一串缩小的胶囊）更好，且同意你说的合并会抹平变体。我的建议是两样都要、不重复：合并骨架每个名字一次、挂对照状态；变体行保留差异、挂「归入」操作，两者用同一个胶囊链组件。
- **关于你方案第 1 条「范围里的框 = 成员，不另设成员开关」**：我反对这一处，理由是 §5.1 的三个反例（相邻两个买点时前一个的回踩会被后一个收进去；范围里夹着无关的框；后画的框悄悄加入）。成员开关不必是一个显式按钮：选中买点后点一下框就切换进出，平时看不见这个操作。
- 你的「左端碰到同一 pattern 的上一个买点就停」挡住了反例 1 的一半（回踩 1 不会被收进买点 2），但换来另一半：买点 2 和买点 1 共用的横盘、突破也在上一个买点左边，同样收不进来；要收就得把左端拖过买点 1，回踩 1 又跟着进来。范围存法在「共用前段、各有后段」这种情形下两头都对不了，成员清单可以。
- 你方案第 2 条「会话翻成边」同 flow 的那条更正：翻成后一个 node 的字段 + where。

### 第三轮（F7 三方口径、ux 三处）

- **F7 时间范围**：采纳 flow、critic 的「只在放买点那次停留里生效，离开即冻结」。改动的框：lead 最终拍板为「新画或改动的框贴着就并进、只加不踢、点掉过的不并回」（理由：用户常先画短再拉长；只在本次停留内生效，风险小）。完整六条见 §5.1。critic 给的场景（几天后在突破和回踩之间补一根放量长阴当事件素材，离成员不到 20 根，夹在中间、bracket 长度不变）我找不到反例：回访时新画的框该并进旧买点的常见场景我给不出——回访多半是补事件素材或标别的 pattern，要改旧买点的成员时用户本来就会去点那个买点。
