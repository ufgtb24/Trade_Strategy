# 看图标注接到 path2 pattern 开发：方向讨论记录

本文所有项目内路径均相对 repo root。记录的是 2026-10-20～10-23 用户与会话谈定的方向结论，供之后用 wayfinder 画新地图、或直接写规格时当起点；还没定的事列在末尾。词汇以 `path2/GLOSSARY.md` 为准。

## 1. 为什么转向

- 旧 effort「建一套找优秀选股 pattern 的流程」已停止并归档到 `.scratch-archive/selection-pattern/`（地图开头有停止说明）。它的评估纪律类结论沿用：分辨力、幸存者偏差、股票池口径、同日对照怎么配，见那份地图的 Decisions so far。
- 看图标注证明有用。但用户的说法多是「事件加先后关系」，如「单日放巨量大阳线 → 缩量下跌 → 被支撑」「挖坑 → 出坑（水平 → 下跌 → 涨回）」，旧 effort 的平形态卡（事实表 → 要素 → 形态卡，只有「且」、没有事件间关系）写不进。
- path2 的 node、where、边本来就表达「事件 + 关系」，而且已模块化。所以不再另建一套要素表示，标注直接服务 path2 app 的开发。

## 2. 已定的前提

- **训练段不记账，随便看。** 训练段里看过哪些图、放大过哪张、露出过多少后续走势，一律不记，不再区分看过 / 没看过，也不再把 2024 年留作「没看过的那年」。训练段是 2026 年以前的数据（最早 2021-10-08）；2026-10-24 地图「训练段用多长」已定默认用全部 2021-10-08～2025-12-31，详见那张票。用户原先的考虑是「样本多」和「和现在的市场像」之间的取舍，像又分两面——周期性（几年前是熊市、今年也是熊市）和不可逆的变化（如量化交易占比越来越大）。工具里的训练段做成可配置，各工具读同一个设置。
- **2026 年以后的数据永远不给看。** 读数据只经截到 2025-12-31 的副本（`chart_workflow/loader.py`、`chart_workflow/snapshot.py`）。这是唯一的墙。
- **只有一处记账：在没碰过的数据（2026 年起）上检查。** 每查一次记一次，记查的是哪一版 app。训练段随便看以后，训练段上的成绩分不清多少是凑出来的，app 有没有用只能靠这次检查说明。
- **股票池照旧**，含 2026-10-20 加的 SPAC 壳期排除（`chart_workflow/panel.py` 的 `_after_spac_shell`，配置 `chart_workflow/config.py` 的 `pool.spac_shell`；按名称认壳的规则也补了带编号的壳，见 `chart_workflow/securities.py`）。数据错误登记照旧。这两样管数据干净，和看没看过无关。

## 3. 标注流程（新方向）

1. **找图**：在训练段的大涨段清单里翻，或在 path2_web 里随便看哪只股票。找共同特征时，涨了的和长得像却没涨的都要看；大涨段清单只有涨了的，后一半靠第 5 步补。
2. **标注**：点买点（可以多个），选「正例」或「像但不买」；以事件为单位标出图上的结构（点系统已有的事件，或自己框，见第 8 节）；新概念配一句话。存成普通文件，不记账。
   - 正例的意思是「这一天有我说的那个样子，当时我会买」，不是「后来涨了」。涨没涨由系统按后续走势算，不用用户标。
   - 「像但不买」的理由必须在买点那天以前就看得到。看到跌了才找出来的理由也可以用，但要当新想法拿去第 5、6 步验证，不能直接当结论。
3. **写 app**：会话读备注和图，用 `authoring-path2-app` 技能把说法搭成 node、where 和边；缺的事件用 `authoring-path2-detector` 新写 detector。
4. **拿 app 对标注**：在标过的图上跑 app。正例的买点应该 match，没 match 就用 node 诊断看是哪个 node、哪条边、哪条 where 挡住；「像但不买」那天不应该 match。
5. **盲看 app 抓出来的图**：在整个股票池里随机抓 app 的 match（用户标过的股票不抽；2026-10-23 定，理由：涨的不涨的都会抽到，比例和 app 将来真实遇到的一样，才补得上「长得像却没涨」的那一半），用户逐张点「是我说的形态 / 不是」，「不是」写一句理由。会话把理由翻成要加的 node 或边，回到第 3 步。第 3～5 步是主循环，次数不限。
6. **调参数**：用 tune-gates-v3 在训练段上调，排名看比同日普通买入多出的部分。
7. **最后检查**：定下的那一版在 2026 年起的数据上检查一次，记一次。没过就回去改结构，再查再记。

只有第 7 步判输赢，前面都不判。

第 3～5 步由一个新写的技能串起来（2026-10-23 定）：用户只管在网页上标注、点是 / 不是，然后说一句「看看我的标注」就进循环；技能按顺序调现有的写 app、写 detector、node 诊断、特征验证这些技能。理由：不写的话，每次开工都要用户提醒会话做哪几步，容易漏。

在 pattern 里加一条新特征（如给底部多并一种利好）时，有没有用「放在要用的地方量」（2026-10-23 定）：
- 不单独量。有的特征只在和别的特征配合时才起作用（如「底部放量」单独看可能没用，出现在已企稳的底部里才有用），单独量会误判；反过来，单独量有用的特征，并进去后可能和已有的说同一件事。
- 拿 app 比两遍，一遍带这一条、一遍不带；只因为这一条才多 match 进来的那些图，和同日普通买入对照比。它和其他特征的配合、是否重复，就都算在里面了。
- 多出来的 match 往往不多，这份数据只看得出较大的差别，结论常是「看不出」而不是「没用」。看不出时先留着，标「待验证」，由没碰过的数据统一判（训练段本来随便看、只算参考，先留着的代价不大）。

## 4. 后续走势藏不藏

| 步骤 | 看不看后续走势 | 理由 |
|---|---|---|
| 翻图、找共同特征 | 看 | 要靠结果找方向 |
| 标正例、像但不买 | 看 | 涨没涨由系统算；用户标的是「这一天有那个样子」 |
| 盲看 app 抓出来的图，点是 / 不是 | 先藏，点完再露 | 这一步检查 app 是否忠实于用户的说法；看着结果点，「是」会偏向涨了的，app 会被改成专挑训练段赢家的样子，到第 7 步才暴露，白白用掉一次检查 |

藏只是界面行为，不记「有没有提前拖过去偷看」。

## 7. 一个 node 包容多种特征：path2 现有机制够用

用户的总思路：path2 是「代码 → 图」（app 产出事件、事件画在 K 线上），看图标注是反向的「图 → 代码」；希望训练段的标注能被代码表达，并在没碰过的数据上泛化。形成 pattern 时，某个 node 要能包容多种特征。例：V 字反弹的底部，W 形底、底部持续放量或其他不典型特征都是利好，不要求同时出现。用户希望底部能「多种特征取其一」或「累计加分」衡量强度，而不是为一点出入就另建一个 pattern；不典型的特征单独成 pattern 时 match 太少，并进同一个 node 才能让 match 变多。

结论（2026-10-23 核对代码）：不改框架就能实现。底部和底部特征是父子关系，用复合事件表达；用户明确不用边来做这件事，因为边表达的是两个独立事件之间的关系，不表达「谁属于谁」。

- 核对过的两处机制：事件可以挂多组、不同种的子事件，每组有名字（`path2/core.py` 的 `child_slots` / `child` / `children`）；detector 的输入可以是别的 detector 产出的事件流（`path2/core.py` 的 `Detector` 说明）。
- where 只读事件本身：自己的字段（可以几个字段再算一步），以及复合事件的子事件的字段（`path2/dag/where.py` 的 `child` / `children`）。读不到 K 线、其他 node 上的事件。K 线回看只能在 detector 里做。

| 构想里的部分 | 写法 |
|---|---|
| 底部是父亲，各种特征是孩子 | 写一个「底部」复合事件的 detector，读进各特征的事件流，把同一个底部里出现的挂成子事件 |
| 底部的读数类特征（持续几天、跌多深、平均量倍数，哪怕算法复杂） | 底部事件的字段 |
| 自己会发生的事（有自己的起止或某一天、可能出现 0～n 次、别的 pattern 也可能用），哪怕很简单 | 独立 detector 产出的事件，挂成底部的子事件 |
| 特征之间取其一 | 底部 node 的 where 用「或」（`W.any`） |
| 凑够 k 条、累计加分 | detector 把总分算成字段，where 写「总分 ≥ k」；或 where 里写自定义判断，数几个子事件或几条成立 |
| 子事件之间的先后（如放量在 W 形底第二个低点之后） | 合成 detector 里检查好，或 where 读子事件的字段去比；不是 node 之间的边 |
| 底部和 pattern 里其他事件的先后（如底部之后才突破） | node 之间的边 |

- 要投入的是写 detector：每种特征一个，每种底部概念一个合成的。这是写 app 的常规工作，不是框架缺能力。
- 唯一不顺手的是「凑够 k 条」：用自定义判断写，node 诊断只显示过没过，看不出是哪几条凑起来的。补一个「至少 k 条成立」的组合子能解决（原来数子事件个数的组合子 2026-06 已归档，见 `path2/dag/where.py` 中 `children` 的说明），只影响诊断看得清不清，不影响能不能实现。
- 代价：取并集以后，本身不带信息的特征会把噪声一起带进来，所以每条特征并入时要放在要用的地方量（见第 3 节末）。权重和 k 事先定、每条一样重，不按成绩挑：2026-09-07 给 bb_v1 研究打分制时，权重在噪声范围内调不出差别，四个条件里只有一个真带信息。

## 8. 结构化标注：用 path2 的事件来标

2026-10-23 定：看图标注引入 path2 的事件，标注从「点买点 + 一句话」改成以事件为单位。旧的看图标注只能靠语言，是因为当时没接 path2。

- **用词**：图上标的是事件（点事件或 span 事件），不是 node。node 是 pattern 声明里的位置；「标一个底部」的准确说法是：标出一段事件，说明它应该占住 pattern 里「底部」这个 node。
- **为什么**：语言说得清意思，说不清位置（底部从哪天到哪天、放量指哪几天），会话只能猜，detector 就对着猜的那一段调。画出框就不用猜：
  - detector 级的检验：不只查买点那天有没有 match，还查 detector 产出的事件是不是用户框的那一段，漏了、偏了、短了都看得出，诊断也能对着框查；
  - 事件之间的前后、包含、间隔从框的几何直接读，不用再用文字描述；
  - 攒下来的框可以给 detector 阈值提供默认值（待验证）；
  - 和「至少 k 条」组合子的逐条诊断直接对照：系统说是哪几条凑起来的，用户的框说有哪几条。
- **样子：看系统的事件，改它，补它**。标注图像主视图一样画出已有 detector 产出的事件：
  - 系统抓对了：点一下那个事件，表示「这就是我说的某某」；
  - 抓偏了或漏了：自己拖一个框，挂一个名字，名字可以选已有种类，也可以新写；
  - 新名字配一句话说明它是什么，会话照这句话写 detector，写好后它成为可选的事件种类。
  - 找共同特征时，系统画的事件会把用户往已有种类上带，要能一键关掉，只看干净的 K 线。
- **语言仍然需要**：新概念第一次出现时只能靠一句话说明；名字必须允许自己新写，不能只从列表里挑（旧事实表的教训：现成选项会框住用户看到的东西）。
- **不再预设事实表**：起点是 path2 已有的事件种类（突破、连续突破、走势区段、平台、派发、回踩企稳等），它们只是图上画出来、可以直接点的东西，不是要逐条回答的问卷。会积累下来的有三样：
  1. 用户起的事件种类：名字、一句话、框过的例子；
  2. 为它写的 detector，任何 path2 app 都能当零件用；
  3. 框过的例子，同时是检验 detector 的样本。

  事件身上供 where 读的字段，也是写 detector 时按需要加的，不是一张固定的表。
- **现状（2026-10-23 查）**：标注页和主视图是两个页面（`path2_web_ui/src/components/App.vue` 带 `?wf=` 时整页换成 `WorkflowView`）；标注图 `AnnotChart.vue` 完全不画 path2 的事件和 match。标注里存什么、标注界面和主视图怎么合，要在地图上先定。

### 标注和显示一一对应（2026-10-23 定）

用户的看法：结构化标注 → pattern 代码 → match 到的股票 → web_ui 的显示，是一个「图 → 图」的过程，首尾两张图应该在功能上对应。定为结构化标注的基本方向：**标注就是「用户期望的显示」，web_ui 的显示就是「app 实际的输出」**，两者用同一套画法，才能叠在同一张图上直接比——「拿 app 对标注」这一步就是看两层差在哪。界面上标注可以做成主视图的一个可编辑模式，不另写一套画图代码。对应按意思对，不机械地一比一（界面词见 `path2_web/GLOSSARY.md`）：

| 显示侧（代码 → 图） | 标注侧（图 → 代码） |
|---|---|
| 副图里画出的事件 | 用户点选的系统事件，或自己框出的事件 |
| band：一个 node 一条轨 | 给事件指定它在 pattern 里的角色（如「底部」）；可以先空着 |
| 事件过没过 where（qualified；诊断侧栏逐条列实测值和阈值） | 给事件打勾：它具备哪几条特征 |
| bracket：一次 match 的跨度，以及买点 | 用户点的买点，以及正例 / 像但不买 |

三处不对称：
1. **where 的阈值**：显示侧有具体数，标注侧只标「有没有」。用户判断的是「这个底部有放量」，不是「量是平时的 2.3 倍」；数由 detector 量，要用户填数就成了让用户定参数。用户顺口说「这个跌幅就算深了」可以当阈值提示。
2. **标注侧多出来的**：新的事件种类（显示侧只能画已有 detector 的）、新概念的一句话、正例 / 像但不买（用户的判断，显示侧没有对应）。
3. **显示侧多出来的**：没过 where 的候选（detected 档）和 detector 尝试失败的痕迹，诊断用，不需要标。

另外，显示时 pattern 已写好，每个事件属于哪个 node 是确定的；标注时 pattern 可能还不存在，所以角色允许先空着，写 app 时再对上。

### 一次标注里可以有多个 pattern（2026-10-23 定）

分两层：**事件不属于任何 pattern，买点和角色属于某个 pattern。**
- 事件层（W 形底就是 W 形底）是所有 pattern 共用的素材和检验 detector 的样本，标一次各 pattern 都能用。
- 买点、「这段事件扮演底部」、「像但不买」都是相对某个 pattern 说的（「像但不买」必须说清像哪个），每个买点带一个 pattern 名。

由此：
- 一次标注里不同的图可以标不同的 pattern；本来在标底部反转、中途发现新规律，就给它起新名或挂「未归类」，接着标，不另开一次。
- 一张图上可以有好几个 pattern 的买点；两个 pattern 落在同一天，就是同一天挂两个买点，各算各的。
- 界面上有一个「当前 pattern」，新点的买点默认归它，随时可换，和主视图已有的 active pattern 同义。
- 买点允许先挂「未归类」，攒到一批再归组、起名、建 app。

### 先看特征，还是先定目标 pattern（2026-10-23 定）

两种都要，用在不同阶段：
- **先看特征、后归纳**：还不知道自己信什么时用。眼睛不被框住，新规律能冒出来；坏处是会攒下很多只出现一两次的东西，归组费劲。
- **先定目标 pattern**：有了想法、要做成 app 反复对图时用。每张图标得一致，直接喂给对标注、盲看、改 app 的循环；坏处是容易只看自己要找的。

配合方式：
- 事件层永远自由，看到什么标什么。
- 买点先「未归类」，某一组攒到几张就起名、建 app，转成先定目标，跑循环。
- 先定目标的阶段里看到新东西照样标（起新名或挂「未归类」），不打断当前循环。
- 归组可以让循环技能帮忙：把「未归类」的买点连同上面的事件结构列出来，骨架相同的排在一起，由用户决定哪些算同一个 pattern。

**能不能合并看骨架**：骨架是 pattern 由哪几个 node 组成、它们之间的先后关系。
- 骨架相同（如都是「下跌 → 底部 → 突破」，只是底部有的是 W 形底、有的是持续放量）：合成一个 pattern，差别放进那个 node 的 where（取其一或凑够 k 条，见第 7 节）。
- 骨架不同（如底部反转和突破后回踩）：分开。
- 合并后，新并进来的那一种有没有用，照第 3 节末「放在要用的地方量」。

## 10. 两台机器之间同步数据和标注

用户有两台机器（pc、upc），提议用 Syncthing 同步数据和标注，让两边的数据和标注保证对应。2026-10-23 查到：两台机器已在用 Syncthing 同步 `~/.claude/projects`；完整行情 `datasets/pkls` 约 311M，截到 2025 年底的副本约 265M。会话判断可行、比 git 合适，但要守四条（待地图上的票定具体做法和目录）：

1. **训练数据同步的是截到 2025 年底的那份副本。** 它固定不变，同步一次两台就完全一样；旧 effort 里「副本只在 upc 生成再拷到 pc」、两台对不上的问题一并解决。
2. **完整行情（含 2026 年）每天被下载脚本原地改写，要小心。** 下载只在一台上跑；另一台等同步完成再做没碰过的数据上的检查，否则可能读到半新半旧的数据。也可以不同步完整行情，只在做检查的那台下载。
3. **标注文件不能两台写同一个文件。** Syncthing 不合并，两边同时改同一个文件只会多出冲突副本。所以标注设计成「每批一个新文件、文件名带机器名」，只新增不改旧文件，冲突就不可能发生；同步目录打开 Syncthing 的文件版本保留，防一台误删、另一台跟着删。
4. **标注里记当时用的是哪份数据。** 副本里有带指纹的说明文件（`SNAPSHOT.json`），标注写进这个指纹，数据重做后也知道每条标注对应哪一版。

数据和标注放在 git 之外的同步目录，Syncthing 不碰仓库和 `.git`；worktree 里用软链接指过去，和现在的 `datasets/` 一样。

## 12. 结构化标注是构建 pattern 的唯一入口（2026-10-23 用户定）

- 今后结构化标注是构建 path2 pattern 的唯一方式，一切为结构化标注服务。各项拿不准时，按「怎样让标注直接变成 pattern、让 pattern 直接对回标注」来取舍。
- 语言仍然需要，但位置变了：从单独描述 pattern 的入口，变成挂在图上某个位置的附注。仍离不开语言的三处：新概念第一次出现时的一句话；盲看点「不是」的理由；pattern 想抓什么的一句话（决定往哪个方向搭骨架）。
- 脱离图的语言不能直接改 pattern。例如用户说「底部应该再深一点」，技能要反问「在哪几张图上看到的」，转去标注或指出已有标注。理由：每次改动都有对应的例子，改完马上能查对不对，以后的改动把它改坏也查得出；标注随改动越攒越多，检验 app 的样本越来越全；对着图就不用猜「深多少、指哪种底部」。用户在对话里贴的 K 线截图也先变成工具里的标注。
- 只调参数取值（tune-gates-v3）不受影响，那是在数据上量出来的。
- 受影响的现有技能（地图第 11 张票定具体改法）：

| 技能 | 现在的输入 | 改成 |
|---|---|---|
| 写 app（`authoring-path2-app`） | 自然语言描述或 K 线截图 | 标注（事件、角色、特征勾选、买点）加附注；脱离图的说法转去标注 |
| 写 detector（`authoring-path2-detector`） | 语言描述的事件 | 用户框过的例子当必须标中的样本，附注当说明 |
| 诊断（`diagnose-event`） | 「诊断某只股票的某个事件」 | 加一个入口：从「标注和 app 输出对不上」直接进来 |
| 特征验证（`feature-study`） | 一个特征或直觉 | 加一个入口：由循环技能按特征调用 |

## 15. 择时：为什么判输赢只看选股，择时怎么单独量（2026-10-24 讨论）

用户的问题：最终目标是绝对意义上赚钱，为什么一定要跑同日对照？「大盘好时跟进、不好时不入场」的 pattern 难道不好？一个 pattern 在训练段挑的股票都赚钱、总伴随大盘上涨，而训练段里大盘并非一直涨——每次都踩准，算不算本事？

**一个 pattern 赚的钱拆成三块**：大盘本身的涨跌（谁买都有）；择时（出手的那些天是不是正好赶上普通股票都涨的日子）；选股（同一天里挑的股票是否比别的涨得好）。词表里两把尺子正对应：随机日基线（`path2/GLOSSARY.md` 「随机日基线」）比出来的是选股加择时；同日普通买入对照（「同日普通买入对照」）只剩选股；两者之差就是择时。同日对照比的是同一天、同一池子里随便买一只，不是大盘指数。

**为什么判输赢只用选股**：不是择时不值钱，而是这份数据量不准择时。
- 择时的有效样本太少：训练段四年多，大盘真正的牛熊转换只有几次；一个 pattern 正好多在一两段上涨里出手，绝对收益就好看，和猜对一两次硬币分不开。选股是每个买点和同一天几百只股票比一次，四年有成千上万次独立比较。
- 绝对收益在这份数据上偏高：数据只含至今还在交易的股票，跌到退市的不在里面；同日对照两边都是幸存者，偏差大部分抵消（FC-017 说明最便宜那一成抵消不了）。
- 波动大的股票在绝对收益上会被白算成好；以前的 app 打分实为波动大小的读数，就是这个坑。

**择时不丢，单独量**：
- 每个 pattern 的择时那一块单独算出来给用户看（出手日之后大盘的表现，和随机日之后比），注明样本少、只当参考不当证据。有些 pattern 天然带择时（如底部反转多在大跌之后出现），用户要知道它赚的钱有多少来自这里。
- 「每次都踩准」算不算本事，要过三条：
  1. **数独立的行情段，不数买点**：出手日落在多少段彼此独立的大盘涨跌里、每段都踩准了才算；同一段上涨里的几百个买点同涨同跌，只算一次证据。
  2. **下跌前要闭嘴**：择时有两半——要涨之前出手、要跌之前不出手。很多 pattern（如突破类）是被大盘上涨触发的，大盘已经在涨了它才出现；要看大盘转跌时它是提前安静了，还是照样出手、一起被套。
  3. **和最简单的择时办法比**：例如「大盘在 50 日均线上方才买」。和它差不多，就说明择时本事是大盘自己的趋势，不是这个 pattern 的；这种趋势用几十年的指数历史就量得清，不用靠 pattern 得到。
- 三条都过，就是真本事，而且可能比选股更值钱：可以拿它的出手多少当作「今天要不要入场」的开关，管所有买入。
- 同日对照下这份本事会被打成零（同一天里它挑的票和别的差不多，选股领先就是零），所以择时那一块必须单独报。2026 年起的九个月行情段不多，只能弱确认。

**呈现给用户的固定四样**（2026-10-24 用户同意）：

| 报什么 | 回答的问题 | 用途 |
|---|---|---|
| 比同日普通买入多多少 | 同一天里挑得好不好（选股） | 判输赢 |
| 比随机日多多少 | 随便哪天随便买一只，它好多少（选股加择时） | 参考 |
| 两者之差，附出手日落在几段独立行情 | 择时贡献了多少 | 参考，样本少时明说 |
| 绝对收益 | 实际赚没赚钱 | 参考 |

随机日从同一个股票池里抽，否则择时那一块里混进「池子不同」的差别。随机日和绝对收益只报不判：择时有效样本太少，数据只含幸存股票会使这两个数整体偏好看。tune-gates-v3 已经在算比随机日的差，只是没给用户看。胜过同日对照不等于绝对收益为正：同一天普通股票平均都在跌时，胜过它也可能只是少亏。

**大盘择时作为独立问题**：「今天该不该买任何股票」和「今天买哪只」分开。选股用这份四年的个股数据和同日对照判；择时单独研究，用几十年的指数历史（牛熊转换几十次）；两者叠起来用。这项研究不在本地图的终点之内，要做需另开。

影响到地图上的票：「没碰过的数据上的检查：沿用 tune-gates-v3，跨次计数怎么补」要定报什么、判什么（择时那一块和绝对收益怎么报）；「串起『图 → 代码』循环的技能」交给用户的成绩里要带择时那一块。
